Before writing any Godot-specific code, it's worth having a general way to talk about what an agent actually is, one that will keep applying no matter which specific technique (steering, pathfinding, state machines, learned policies) you use to build one. This lesson lays out that vocabulary: the Situated Agent Model, or SAM.

Part 1. Agent and Environment

SAM starts from a simple split: there is an Agent, and there is an Environment the agent is situated in (hence the name). The agent doesn't have direct access to the environment's true state; it only knows what it observes, and it can only affect the environment through whatever actions it's capable of taking. Everything the agent does happens in a loop: observe, decide, act, and observe again.

Part 2. Four Units Inside the Agent

Inside the agent, that loop breaks down into four units, each with a distinct job:

  • Perceptor: detects observables in the environment and converts them into information the rest of the agent can use. A raycast hitting a wall, a distance check to a target, reading another node's position; all of this is perception.
  • Memory: holds information over time. Perception alone is only ever a snapshot of right now; memory is what lets an agent remember a target's last known position, keep a running count, or track whether some condition was true a moment ago.
  • Decider: takes whatever the Perceptor is reporting right now, together with whatever Memory is holding onto, and decides what to do. This is where the actual "AI" of an AI agent usually lives.
  • Actuator: carries out whatever action the Decider chose, back out into the Environment. This is the only unit that's allowed to actually change anything outside the agent.
The Situated Agent Model: Environment feeds the Perceptor, the Decider draws on Perceptor and Memory, and the Actuator's action feeds back into the Environment.

Part 3. Mapping SAM Onto Code

None of this requires special engine support; it's a way of organizing code you're already writing. In the agents you'll build this semester:

  • Perceptor: a RayCast2D check, a distance_to() call, reading target.global_position.
  • Memory: exported or plain vars that persist between frames (a stored target, a remembered last-known position, a counter).
  • Decider: whatever picks the action (last week's steering_method_from_type dictionary lookup, and later in the semester, finite state machines and behavior trees).
  • Actuator: setting velocity and calling move_and_slide(), or any other call that actually changes something in the scene.

The value of naming these separately shows up as agents get more complex: it gives you a place to ask "where does this piece of logic belong," rather than letting perception, memory, decision-making, and action all blur together inside one long function. A lot of what's ahead this semester (state machines, behavior trees, even reinforcement learning) is really just different ways of building a more capable Decider, sitting on top of the same Perceptor/Memory/Actuator structure.

Checkpoint

Before moving on, make sure you can:

  1. Name all four units inside a SAM agent, and describe each one's job in a sentence.
  2. Explain why Memory is a separate unit from Perceptor, rather than the same thing.
  3. Point to a piece of GDScript (yours or an example) and say which unit it belongs to.
