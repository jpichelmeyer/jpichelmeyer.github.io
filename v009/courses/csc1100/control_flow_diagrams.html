Code reads top to bottom, but it doesn't always run top to bottom, an if can skip a block entirely, and later on a loop will run one back over and over. A control flow diagram (often just called a flowchart) draws the actual paths execution can take through a program, as a graph: shapes for what happens, arrows for which way control moves next.

Part 1. Why Diagram Code At All?

Two honest uses for this, not just "because it's traditional." First, planning: sketching the shape of a solution before writing a single line of Python often surfaces a missing case or a confused order of operations far more cheaply than debugging code already would. Second, communication: a flowchart is a language-independent way to describe what a program does, useful for explaining logic to someone (including yourself, later) without them needing to already read Python.

Part 2. The Visual Vocabulary

A handful of shapes, each with a fixed meaning. This is the full set you'll see used across the whole semester, including a couple you haven't written code for yet, loops and function calls specifically. That's intentional: learning the shapes once, now, means recognizing them instantly later, even before you've formally met the code they represent.

The full vocabulary. Only the first four (terminator, process, input/output, decision) show up in this lesson's worked examples; the last two are here so the shapes look familiar when we get to them.

One more convention, not a shape: every arrow shows the direction control flows, and a decision's two outgoing arrows are always labeled, Yes and No (or True and False), so there's never any ambiguity about which branch a condition being true actually leads to.

Part 3. A Straight-Line Program

No decisions yet, just a plan mapped straight across, one shape per line of code.

flow.py Python
x = 5 y = 10 total = x + y print(total)

Every arrow here only ever points one way, down. There's exactly one path through this program, which is exactly what a straight-line flowchart looks like: a single, unbroken line from Start to End.

Part 4. Adding a Decision

An if with no else is the simplest branch there is: one path splits into two, and both paths land right back on the same next step.

flow.py Python
age = 20 if age >= 18: print("adult") print("done")

Follow the No path with your finger: it skips straight past print('adult') entirely and rejoins the Yes path right before print('done'). That's the whole visual signature of an if with no else: a diamond that splits, and one side that does nothing at all before the paths merge back together.

Part 5. if / else

Give the No side something to actually do, and the diagram becomes symmetric: two real paths, each doing something different, both still merging back to the same place afterward.

flow.py Python
age = 15 if age >= 18: print("adult") else: print("minor") print("done")

Exactly one of the two branches ever actually runs on any given pass through this diagram, never both, never neither, but no matter which one it is, execution always ends up back at the same print('done'). A decision splits the path; it never permanently forks the program in two.

Part 6. Nested Decisions (elif, Drawn Out)

An elif chain is really just an if nested inside the previous one's else. Drawn as a flowchart, that nesting turns into a second diamond sitting inside the first one's No branch, and a third would sit inside that one's No branch, and so on, one diamond per elif.

flow.py Python
if score >= 90: print("A") elif score >= 80: print("B") else: print("F")

Notice the shape this makes: a staircase, not a tree. Each decision's Yes branch exits straight to its own outcome, while every No branch drops down into one more decision, until finally landing on a plain outcome with no more conditions left to check. This is exactly why elif chains read as a sequence of checks in a specific order, rather than a set of independent possibilities, each diamond only ever gets evaluated if every diamond above it came back No.

Part 7. A Peek Ahead: Loops

You haven't written a loop in Python yet, but now that the vocabulary includes one, here's what it looks like as a graph. The one genuinely new thing a loop introduces: an arrow that points backward, creating an actual cycle, something none of the diagrams above have. Every path so far has only ever moved forward and eventually reached an End; a loop is the first shape that can revisit somewhere it's already been.

The hexagon is checked before every pass, exactly like a decision, except one of its two exits leads back to itself instead of forward.

Nothing to trace here yet, just file the shape away. When loops actually show up in a couple of weeks, this is the picture to come back to.
