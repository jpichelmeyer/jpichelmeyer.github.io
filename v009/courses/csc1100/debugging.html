Every program you've written so far has probably broken at least once. That's normal, not a sign something's wrong with you. Debugging is a skill on its own, separate from writing code in the first place, and it's mostly about reading carefully rather than guessing.

Part 1. Reading a Traceback

When Python hits an error it can't recover from, it prints a traceback: where the problem happened, and what actually went wrong. It looks something like this.

(illustrative) Python
Traceback (most recent call last): File "program.py", line 3, in <module> print(nam) NameError: name 'nam' is not defined

Read it from the bottom up, not the top down. The very last line is the actual answer: an error type (NameError) and a message (name 'nam' is not defined). The lines above it are just the path Python took to get there, useful for locating the problem, but the type and message are what tell you what's actually wrong.

Part 2. Common Errors You'll Actually Hit

  • NameError: using a name that was never defined, almost always a typo.
  • TypeError: an operation given a type it doesn't know how to handle, like "Age: " + 25.
  • IndexError: asking a list or string for a position that doesn't exist.
  • ZeroDivisionError: dividing by zero.
  • SyntaxError: the code isn't even valid Python, a missing colon, an unclosed parenthesis. Python catches these before your code runs at all.

The error type alone usually tells you most of what you need before you even read the message: TypeError means two things don't mix the way you asked them to, IndexError means you asked for a position that isn't there.

Part 3. Print Debugging

When the bug isn't an outright crash, just wrong output, a well-placed print() is the fastest way to find out what a variable actually contains at a given point, rather than what you assumed it contained.

debugging.py Python
total = 0 for i in range(5): total += i print("i is", i, "total is", total) # temporary, delete once fixed print(total)

This isn't a permanent fix, it's a flashlight: add prints to see what's actually happening, narrow down where reality stops matching your expectations, fix the actual problem, then remove the temporary prints once you understand it.

Advanced

Exercise 7: Three Bugs, One Function. Orders of $50 or more are supposed to get free shipping. This function has three separate bugs: one NameError, one TypeError, and one logic error that only shows up once the crashes are fixed. Fix them one at a time, running after each fix.

Exercise 8: Returning Too Early. find_max should return the largest number in the list (9, then 100). It returns the wrong value, and never crashes. The bug is indentation. Trace the loop by hand for the first list to see how many times it actually runs.

Exercise 9: Following a Traceback Upstream. This crash has a traceback several frames deep. Read it bottom up: which line actually raised the error, and which call passed in the bad data? The real bug isn't on the line that crashed. Fix it so that a student with no scores is reported as no scores yet instead of crashing, by changing average.

Checkpoint

Before moving on, make sure you can:

  1. Read a traceback from the bottom up, and identify the error type and the message.
  2. Name at least four common error types and what typically causes each one.
  3. Use temporary print() statements to inspect a variable's value while debugging, then remove them.
  4. Fix a broken piece of code by reading the error it produces, not by guessing.
