Last unit, the Decider in your agent was small enough to live in one function: a dictionary lookup, an if/else chain, whatever picked a steering method. That was fine when there was only ever one thing the agent could be doing. Once an agent needs to behave differently depending on what's already happened, wander until something shows up, then chase it, then stand still for a moment, "what should I do right now" stops being a pure function of the current perception alone. It also depends on what the agent was already doing. That's what a finite state machine (FSM) is for: a Decider with memory of its own.

Part 1. States and Transitions

An FSM is a small, closed set of states (a fixed list of "modes" the agent can be in) and transitions (rules for switching from one state to another). At any instant, exactly one state is active; that state alone decides what the agent does this frame, and it alone decides when it's time to hand off to a different state. Nothing outside the active state gets a vote.

Watch the demo above for a minute: an agent wanders aimlessly until a target enters its sensor range, turns and closes in on it, then sits still for a moment once it arrives before wandering off again. Three states, three plain-English transition rules. That whole loop, described in one sentence, is the entire finite state machine.

The demo's three states. Notice the transitions are triggered three different ways: perception (target detected/lost), a computed condition (close enough to have arrived), and a plain timer (idle duration expires) -- an FSM doesn't care which kind of thing triggers a transition, only that something did.

Part 2. The FSM Is a Decider

Nothing about "finite state machine" is Godot-specific, and this project doesn't invent a new abstraction to build one; it just makes FSM a concrete Decider:

Part 3. States as Cartridges

Every concrete state (StateWander, StateSeek, StateIdle) extends one shared base, FSMState, and gets dropped in as a direct child of the FSM node in the scene tree, an interchangeable "cartridge" rather than a case in some giant switch statement:

fsm_state.gd GDScript
class_name FSMState extends Node var fsm:FSM var agent:Node2D var perceptor:Perceptor var actuator:Actuator ## Called once by the owning FSM after the whole tree is ready. func setup(fsm_ref:FSM, agent_ref:Node2D, perceptor_ref:Perceptor, actuator_ref:Actuator) -> void: fsm = fsm_ref agent = agent_ref perceptor = perceptor_ref actuator = actuator_ref ## Called once, the moment this state becomes the active state. func enter() -> void: pass ## Called once, the moment this state stops being the active state. func exit() -> void: pass ## Called every frame while this state is active. func update(_delta:float) -> void: pass ## Perception hooks: the FSM forwards Perceptor signals to whichever state ## is currently active, so each state decides for itself whether/how to react. func on_target_detected(_target:Node2D) -> void: pass func on_target_lost(_target:Node2D) -> void: pass

Five hooks, every one optional (the base versions do nothing), and that's the entire contract a state has to honor. A new state, say, a Flee state that runs from a threat, is nothing more than a new script extending FSMState, filling in whichever of those five hooks it actually needs, dropped in as another child of the FSM node. Nothing about FSM itself has to change to add it.

Part 4. The FSM Node Itself

FSM doesn't know how to wander, seek, or do anything else; it only knows how to hold a current state, route perception to it, and swap it out on request:

fsm.gd GDScript
@export var initial_state_name:StringName = &"" ## Shared "working memory" a state can stash things in (e.g. which target to ## chase) for another state to pick up later. Kept generic on purpose -- it's ## the FSM equivalent of a behavior tree's blackboard. var focus_target:Node2D var current_state:FSMState var _states_by_name:Dictionary = {} @onready var agent:Node2D = get_parent() @onready var actuator:Actuator = agent.get_node("Actuator") @onready var perceptor:Perceptor = agent.get_node("Perceptor") func _ready() -> void: for child in get_children(): if child is FSMState: _states_by_name[child.name] = child child.setup(self, agent, perceptor, actuator) perceptor.target_detected.connect(_on_target_detected) perceptor.target_lost.connect(_on_target_lost) var start_name:StringName = initial_state_name if start_name == &"" and get_child_count() > 0: start_name = get_child(0).name _enter_state(start_name) func _process(delta:float) -> void: if current_state != null: current_state.update(delta) ## The one and only way a state cartridge changes the active state. func transition_to(state_name:StringName) -> void: if not _states_by_name.has(state_name): push_warning("FSM: no state named '%s' among children of %s" % [state_name, name]) return if current_state != null: current_state.exit() _enter_state(state_name)

A few things worth noticing here:

  • States are found by name (_states_by_name, keyed off each child's node name), not by index or type. That's why the scene tree screenshot above matters: "StateWander" the string has to match StateWander the node's actual name exactly.
  • If initial_state_name is left blank, the FSM just starts in whichever state happens to be its first child. In this project that's StateWander, purely because of the order it was added in fsm.tscn, not because FSM has any special idea of a "start" state.
  • transition_to is the only way the active state ever changes, and notice who calls it: never FSM itself, only a state, on itself or (indirectly) on the machine it belongs to. The FSM is a container and a router, not a decision-maker; the decision to leave a state is made by that state, from inside update() or one of the perception hooks.
  • focus_target is memory that outlives any single state, exactly the kind of thing the SAM diagram called out as its own unit, separate from Perceptor. Watch for that same idea again next week under a different name.

Part 5. Three Kinds of Transition, Side by Side

The demo's three states were picked deliberately to show that "what triggers a transition" can be almost anything; the FSM's job is the same no matter which kind it is.

state_wander.gd GDScript
class_name StateWander extends FSMState func update(delta:float) -> void: actuator.rotate_wander(delta) actuator.move_forward(delta) func on_target_detected(target:Node2D) -> void: fsm.focus_target = target fsm.transition_to(&"StateSeek")

Wander leaves via a perception-driven transition: it does nothing about transitioning inside update() at all, it just reacts the moment on_target_detected fires, which the FSM only calls because it wired this state's hooks up to the Perceptor's signals back in _ready().

state_seek.gd GDScript
class_name StateSeek extends FSMState const ARRIVE_RADIUS:float = 40.0 func update(delta:float) -> void: var target:Node2D = fsm.focus_target if target == null or not is_instance_valid(target): fsm.transition_to(&"StateWander") return actuator.face_toward(delta, target.global_position) actuator.move_forward(delta) if actuator.distance_to(target.global_position) < ARRIVE_RADIUS: fsm.transition_to(&"StateIdle") func on_target_lost(target:Node2D) -> void: if target == fsm.focus_target: fsm.focus_target = null fsm.transition_to(&"StateWander")

Seek leaves two different ways at once: a computed condition checked every frame inside update() (close enough yet?), and a perception hook for the case where the target vanishes mid-chase. Both call the same transition_to; the FSM doesn't need to know or care which path triggered it.

state_idle.gd GDScript
class_name StateIdle extends FSMState const IDLE_DURATION:float = 1.5 var _timer:float = 0.0 func enter() -> void: _timer = 0.0 func update(delta:float) -> void: _timer += delta if _timer >= IDLE_DURATION: fsm.focus_target = null fsm.transition_to(&"StateWander")

Idle leaves via a plain timer, nothing about perception or distance at all. Notice enter() resets _timer to zero; without that reset, a second visit to StateIdle would inherit whatever the timer was left at from the first visit. enter()/exit() exist specifically so a state can set up and tear down its own local bookkeeping like this.

Part 6. Try It

  1. Open the FSM project and find fsm.tscn. Reorder StateWander and StateIdle in the scene tree (drag one above the other) without touching initial_state_name. Run it. What state does the agent start in now, and why?
  2. Add a fourth target to environment.tscn (copy an existing Target node, reposition it). No FSM code needs to change for this to work, confirm that, and be able to say why.
  3. Lower ARRIVE_RADIUS in state_seek.gd to something small, like 10.0. What visibly changes about the agent's behavior?
  4. Stretch: sketch (on paper, not in code) a fourth state, StateFlee, that runs directly away from a target instead of toward it. Which of the five FSMState hooks would it need? What would trigger entering it, and what would trigger leaving it?
