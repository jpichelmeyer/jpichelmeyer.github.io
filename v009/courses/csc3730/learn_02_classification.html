Classification is supervised learning where the output is one of a fixed set of discrete categories. Checker is this course's running example: every person who reaches the checkpoint gets sorted into exactly one of two categories, alien or human, based only on what's visible.

Part 1. Perceptor, Memory, and the Honesty Rule

Mapped onto SAM: Checker's Perceptor reads three features off whoever's waiting at the checkpoint — head_tone, shirt_color, pants_color — the only things it's ever allowed to look at before deciding. Whether that person is actually an alien (is_alien) is ground truth the simulation itself knows, but Checker's Decider is never handed that value directly as an input; it only reaches Memory afterward, once accepted or denied, as the label to learn from:

checker_agent.gd GDScript
func get_features() -> Array: return [head_tone, shirt_color, pants_color] # ... # Memory: features and, eventually, the ground truth, the same way # a real audit would confirm a decision after the fact. memory.append({"features": features, "alien": person.is_alien})

That ordering matters: features go in before a decision is made; the true label only gets appended after. A classifier that could peek at the label while deciding wouldn't be learning anything — it'd just be reading the answer.

Part 2. The Decider: Naive Bayes

Checker's Decider is a Naive Bayes classifier. The idea: for each class (alien, human), keep a running count of how often each feature value shows up among training examples of that class. To classify a new person, multiply together how "typical" each of their features is for each class, weighted by how common that class is overall, and pick whichever class comes out on top.

"Naive" refers to a simplifying assumption baked into that multiplication: it treats head tone, shirt color, and pants color as though they were independent of each other given the class, some combinations really are more or less likely together in reality, and the model ignores that. It's rarely exactly true, but it keeps the model simple and, for a project like this, works well enough.

checker_agent.gd GDScript
func _predict(features:Array) -> bool: var head:int = features[0] var shirt:int = features[1] var pants:int = features[2] var score_alien:float = log(max(prior_alien, 0.0001)) score_alien += log(float(head_counts_alien[head]) / float(head_total_alien)) score_alien += log(float(shirt_counts_alien[shirt]) / float(shirt_total_alien)) score_alien += log(float(pants_counts_alien[pants]) / float(pants_total_alien)) var score_human:float = log(max(prior_human, 0.0001)) score_human += log(float(head_counts_human[head]) / float(head_total_human)) score_human += log(float(shirt_counts_human[shirt]) / float(shirt_total_human)) score_human += log(float(pants_counts_human[pants]) / float(pants_total_human)) if is_equal_approx(score_alien, score_human): return randf() < 0.5 return score_alien > score_human

Two implementation details worth calling out by name:

  • Working in log-space. Multiplying several probabilities together (each less than 1) shrinks toward zero fast enough to lose precision. Adding their logarithms instead, and comparing sums, gives the same ranking without that problem.
  • Laplace smoothing. Every feature-count table starts at 1, not 0, for every possible value (see _ready()). Without that, a value never yet seen for some class would carry a raw count of zero, and log(0) is negative infinity — one unseen combination would completely veto that class, forever, the instant it showed up. A starting count of 1 keeps every value possible, just unlikely, until data says otherwise.

Part 3. Training: Counting, Not Gradient Descent

Unlike Sentry (next lesson) or a neural network, Naive Bayes doesn't inch its way toward better weights over many small steps. "Training" here just means recomputing the frequency tables directly from everything in Memory, all at once, replacing the old tables outright:

checker_agent.gd (excerpt) GDScript
for record in memory: var f:Array = record.features if record.alien: head_counts_alien[f[0]] += 1 shirt_counts_alien[f[1]] += 1 pants_counts_alien[f[2]] += 1 n_alien += 1 else: head_counts_human[f[0]] += 1 shirt_counts_human[f[1]] += 1 pants_counts_human[f[2]] += 1 n_human += 1

With a dataset this small, recomputing from scratch every cycle (rather than maintaining running totals incrementally) is simpler and no slower — worth noticing as a real engineering tradeoff, not a shortcut: the "right" way to update a model depends on how much data there is and how often you retrain, not on some universal rule.

Part 4. Two Ways to Be Wrong

Overall accuracy (total_correct / total_evaluations) hides an important asymmetry: this project tracks two specific mistakes separately, because they're not equally bad.

  • accepted_and_alien: an alien got waved through. The dangerous kind of mistake.
  • denied_but_human: an innocent human got turned away. The unfair kind of mistake.

A classifier that denies literally everyone would have zero of the dangerous mistakes and a perfect record on "letting no aliens through" — while being wrong (and unfair) constantly. Watching only overall accuracy can hide exactly that kind of failure; tracking both error types separately is what actually surfaces it.
