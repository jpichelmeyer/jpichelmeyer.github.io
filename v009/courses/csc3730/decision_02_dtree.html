Quick note before starting: "decision tree" means two different things in AI, and this course uses both, in two very different weeks. Later this semester, under Machine Learning, you'll meet decision trees that get learned from data (a training algorithm decides which questions to ask and in what order). This lesson is about the other kind: a decision tree you write by hand, as a fixed, symbolic flowchart. Same shape, completely different origin.

Part 1. A Decision Tree Is a Flowchart

A hand-written decision tree is exactly what it sounds like: a tree of yes/no (or multiple-choice) questions, where every leaf is an action. Start at the root, answer each question, follow the matching branch, and whichever leaf you land on is what the agent does. No state, no memory of last frame, nothing carried over; every single frame, the agent asks the same questions in the same order from the top.

A three-question decision tree for the same day/night creature the FSM lesson used. Every leaf is a final action; there's no path back up, and no memory of which leaf was reached last time.

Part 2. The Same Logic, Two Ways

Recall the FSM's day/night creature: wander by default, chase a target when one's detected, idle briefly on arrival. A decision tree for a similar (simpler) creature reads almost like the flowchart above, translated directly into GDScript:

(hand-written decision tree, not part of any project) GDScript
func decide(delta: float) -> void: if is_daytime(): if grass_nearby() != null: actuator.move_toward(grass_nearby()) else: actuator.wander(delta) else: actuator.move_toward(shelter_position)

Compare that against last lesson's FSM: no class_name hierarchy, no enter()/exit(), no node named "StateWander" to reorder in a scene tree. Just one function, evaluated top to bottom, every single frame. That's the whole appeal: for logic this size, it's less machinery, and it's easy to read start to finish in one sitting.

Part 3. Where It Breaks Down

Try extending the tree above with "but if it was just chasing something, keep chasing until it's lost, even if a closer target shows up" (exactly what StateSeek does with fsm.focus_target). There's nowhere to put that. A decision tree, as written here, has no memory between one evaluation and the next; it can only ever look at whatever is_daytime() and grass_nearby() report right now. Re-run the function next frame and, if a target changed, the whole tree can jump to a completely different leaf with no sense that anything changed, because as far as the tree's structure is concerned, nothing did; it re-asks every question from scratch every time.

That's the gap an FSM fills: a state persists across frames on purpose, which is exactly what let StateSeek keep chasing the same target rather than re-deciding "what's closest" every frame. It's also the gap the next lesson's behavior trees fill, a different way, worth having both fresh in mind for the comparison two lessons from now.

Part 4. Where It's the Right Tool

Not every decision needs memory. A one-shot classification ("what kind of terrain is the agent standing on, and what movement penalty does that imply") is naturally stateless, evaluate it fresh whenever it's needed, there's nothing to remember between calls. Decision trees are also easy to author from a domain expert's own words ("if the player is close and has low health, attack; otherwise retreat") without translating into states and transitions first, which is part of why they show up constantly in game AI design docs even when the actual code ends up using something else underneath.
