Steering gets an agent moving smoothly through continuous space, but it has no notion of planning a route: Seek always heads straight at the target, and nothing built so far has any way to react to an obstacle in between. Pathfinding is different: it asks "what's a good route from here to there," which means the agent needs some structure to actually search over. That structure is a graph, and a grid is one of the simplest ways to build one on top of continuous space (this is the same "tile graph" idea covered in Millington's AI for Games).

Part 1. Grid as Graph

A graph is just nodes and the connections between them. A grid gives you both for free: each cell is a node, and each cell connects to its neighbors. The only extra step is deciding which cells are usable at all, since a cell sitting on top of the obstacle from last lesson shouldn't be part of the graph. This lesson builds that: a PathGrid node that scans the Environment, marks every cell as walkable or blocked, and draws itself so you can see the graph directly. The next two lessons search across it.

Part 2. The PathGrid Node

Add a Node2D as a child of Environment, named PathGrid, and attach a new script, scripts/path_grid.gd.

path_grid.gd GDScript
extends Node2D class_name PathGrid @export var cell_size: float = 32.0 @export var grid_width: int = 20 @export var grid_height: int = 14 var blocked: Dictionary = {} var searched: Array[Vector2i] = []

class_name PathGrid gives the script a global type name, so PathGrid shows up as its own type in the Inspector later, rather than just a generic Node2D. blocked is the graph itself: a Vector2i cell coordinate mapped to true if that cell overlaps an obstacle. searched stays empty for now; it exists here because the drawing code in Part 5 already knows how to use it, even though nothing fills it in until the pathfinding lessons that follow.

Part 3. Detecting Obstacles

For each cell, ask the physics engine directly: does a small rectangle the size of this cell overlap anything, and if so, is that thing a StaticBody2D? Godot's intersect_shape does exactly this kind of query.

path_grid.gd GDScript
func _scan_obstacles() -> void: var space_state := get_world_2d().direct_space_state var shape := RectangleShape2D.new() shape.size = Vector2(cell_size, cell_size) for x in range(grid_width): for y in range(grid_height): var cell := Vector2i(x, y) var center: Vector2 = cell_to_world_center(cell) var query := PhysicsShapeQueryParameters2D.new() query.shape = shape query.transform = Transform2D(0, center) var is_blocked: bool = false for result in space_state.intersect_shape(query): if result.collider is StaticBody2D: is_blocked = true break blocked[cell] = is_blocked

Checking result.collider is StaticBody2D, rather than a group, is a perfectly reasonable choice here: the obstacle from last lesson already is a StaticBody2D, so there's nothing extra to tag.

Part 4. Cell / World Conversions

Both the scan above and every future lesson need to move between "which cell" and "where in the world," so these two are worth having early:

path_grid.gd GDScript
func world_to_cell(world_pos: Vector2) -> Vector2i: var local: Vector2 = world_pos - global_position return Vector2i(int(local.x / cell_size), int(local.y / cell_size)) func cell_to_world_center(cell: Vector2i) -> Vector2: return global_position + Vector2(cell.x + 0.5, cell.y + 0.5) * cell_size func is_walkable(cell: Vector2i) -> bool: return not blocked.get(cell, true)

is_walkable defaults an unknown cell to true (blocked), not false, so a cell outside the scanned range (a typo in coordinates, or a query past the grid's edge) fails safe as unwalkable rather than silently being treated as open ground.

Part 5. Drawing the Grid

A plain filled rectangle per cell works, but a little polish goes a long way: rounded corners and a small gap between cells make the grid read as a set of tiles rather than one solid wash of color. Godot's StyleBoxFlat resource gives you both for free, and building each style once (rather than recreating it every single frame) keeps _draw() cheap.

path_grid.gd GDScript
@export var cell_visual_padding: float = 4.0 @export var cell_corner_radius: int = 6 var _walkable_style: StyleBoxFlat var _blocked_style: StyleBoxFlat var _current_path: Array[Vector2i] = [] var _highlight_style: StyleBoxFlat func _make_cell_style(color: Color) -> StyleBoxFlat: var style := StyleBoxFlat.new() style.bg_color = color style.corner_radius_top_left = cell_corner_radius style.corner_radius_top_right = cell_corner_radius style.corner_radius_bottom_left = cell_corner_radius style.corner_radius_bottom_right = cell_corner_radius return style func _draw() -> void: if _walkable_style == null: _walkable_style = _make_cell_style(Color(1, 1, 1, 0.25)) if _blocked_style == null: _blocked_style = _make_cell_style(Color(1, 0, 0.2, 0.25)) var visual_size: float = cell_size - cell_visual_padding var half_padding: float = cell_visual_padding * 0.5 # Draw underlying base grid for x in range(grid_width): for y in range(grid_height): var cell := Vector2i(x, y) var top_left: Vector2 = Vector2(x, y) * cell_size + Vector2(half_padding, half_padding) var rect := Rect2(top_left, Vector2(visual_size, visual_size)) var style: StyleBoxFlat = _walkable_style if is_walkable(cell) else _blocked_style draw_style_box(style, rect)

_draw() is a built-in Godot callback: any node can implement it to draw custom shapes, and Godot calls it automatically whenever queue_redraw() is called. The two styles are only built the first time _draw() runs, then reused every call after; there's no reason to rebuild an identical StyleBoxFlat sixty times a second. _current_path and _highlight_style stay unused for now too, set up ahead of the pathfinding lessons that will draw a route on top of this same grid.

Part 6. Showing and Hiding the Grid

A grid overlay covering the whole scene all the time gets in the way once you're not actively looking at it. Wrap the scan-and-draw sequence in a pair of methods that turn the grid on and off:

path_grid.gd GDScript
func _ready() -> void: draw_grid() clear_grid() func clear_grid() -> void: visible = false _current_path.clear() searched.clear() queue_redraw() func draw_grid() -> void: clear_grid() visible = true await get_tree().physics_frame _scan_obstacles() queue_redraw()

Two things worth noting here. _ready() calls draw_grid() immediately followed by clear_grid(), which sounds backwards but isn't: draw_grid() contains an await, so it hands control back to _ready() right away rather than blocking, letting clear_grid() run immediately and hide the grid, while the awaited obstacle scan still finishes a moment later in the background (blocked ends up populated correctly either way, only the visual starts hidden). And await get_tree().physics_frame is there because newly added obstacle bodies aren't registered with the physics engine until the next physics step; skip it and the scan can run before the obstacles it's checking against actually exist as far as physics is concerned.

Add two buttons to the Camera's CanvasLayer, Clear and Generate Grid, and give Agent (not PathGrid) the handlers that connect to them:

agent.gd GDScript
func _on_clear_pressed() -> void: if target != null and path_grid != null: path_grid.clear_grid() func _on_gen_grid_pressed() -> void: if target != null and path_grid != null: path_grid.draw_grid()

Routing the button presses through the agent rather than straight to PathGrid is a deliberate choice this course keeps making: the agent is the thing with a target to check against, so it's a natural place to gate "does this even make sense right now" before touching the grid at all.

Part 7. Exposing the Grid to Agents

Add one export to agent.gd:

agent.gd GDScript
@export var path_grid: PathGrid

Because path_grid.gd declared class_name PathGrid, this field shows up in the Inspector as a proper PathGrid-typed slot, not just a generic node reference, so Godot will only let you drop the actual PathGrid node into it. Drag PathGrid from the Scene dock into that field on your agent.

Checkpoint

Before moving on, make sure you can:

  1. Explain what a graph is, and why a grid of cells is a graph without needing to build anything extra.
  2. Explain what intersect_shape is checking, and why the scan waits one physics frame first.
  3. Explain why is_walkable defaults unknown cells to blocked rather than open.
  4. Explain why _ready() calling draw_grid() then immediately clear_grid() isn't a contradiction.
  5. Get a PathGrid showing and hiding via buttons, with the obstacle reading clearly as a blocked cell.
