Every agent this course has built so far is the same basic shape: something with a position, a rotation, and a rule for updating both, one moving individual at a time. Cellular automata are a genuinely different model of emergent complexity: no agents at all, just a grid of cells, each one either alive or dead, each one updating from nothing but its neighbors' current state. Conway's Game of Life is the most famous example, and it's worth building for exactly that contrast, complexity without a single thing that could be called an agent.

Part 1. The Rules of Life

Every cell is alive or dead. Every generation, every cell looks at its eight neighbors (the Moore neighborhood: up, down, left, right, and the four diagonals) and applies two rules, usually written B3/S23:

  • Birth: a dead cell with exactly 3 live neighbors becomes alive.
  • Survival: a live cell with 2 or 3 live neighbors stays alive. Any other count, it dies (fewer than 2 is starvation, more than 3 is overcrowding).

That's the entire rule set. Everything Life does, still patterns, oscillators, gliders that travel indefinitely, comes out of those two lines applied to every cell, every generation, all at once.

Part 2. The CellGrid Node

This project is intentionally standalone, no agents, no PathGrid, nothing carried over from earlier lessons. Create a new project, add a Node2D named CellGrid, and attach a script.

cell_grid.gd GDScript
extends Node2D class_name CellGrid @export var grid_width: int = 48 @export var grid_height: int = 32 @export var cell_size: float = 20.0 @export var cell_visual_padding: float = 2.0 @export var cell_corner_radius: int = 3 @export var generation_interval: float = 0.12 @export var randomize_fill_probability: float = 0.3 var alive: Dictionary = {} var is_running: bool = false var _time_since_step: float = 0.0

alive is the whole simulation's state, a Vector2i cell coordinate mapped to true if it's alive; a cell simply isn't a key in the dictionary if it's dead, no need to store false for the (usually large) majority of empty cells.

Part 3. Choosing How Edges Connect

A finite grid has edges, and Life's neighbor-counting needs to decide what happens when a neighbor lookup steps off one. Five choices, each a different rule for what a lookup at x, y does once it's outside the grid:

  • No wrap: the edge is a true boundary; off-grid neighbors just don't exist.
  • Cylinder: left and right wrap into each other; top and bottom stay a true boundary.
  • Torus: both pairs of edges wrap, untwisted, the classic "Pac-Man" wraparound.
  • Klein bottle: left and right wrap plainly; crossing top or bottom also wraps, but mirrors x on the way, the defining Klein bottle "twist."
  • Cross-cap (RP²): both pairs of edges wrap, and each one mirrors the other axis when crossed. (This is the commonly used "twist both axes" construction for a cross-cap surface in grid demos like this one, not a claim to the one true minimal-polygon construction of RP²; surface topology has more than one standard way to build it.)
cell_grid.gd GDScript
enum EdgeMode { NONE, CYLINDER, TORUS, KLEIN_BOTTLE, CROSSCAP } const EDGE_MODE_NAMES: Dictionary = { EdgeMode.NONE: "No wrap", EdgeMode.CYLINDER: "Cylinder", EdgeMode.TORUS: "Torus", EdgeMode.KLEIN_BOTTLE: "Klein bottle", EdgeMode.CROSSCAP: "Cross-cap (RP2)", } @export var edge_mode: EdgeMode = EdgeMode.TORUS func wrap_cell(x: int, y: int) -> Variant: match edge_mode: EdgeMode.NONE: if x < 0 or x >= grid_width or y < 0 or y >= grid_height: return null return Vector2i(x, y) EdgeMode.CYLINDER: if y < 0 or y >= grid_height: return null return Vector2i(posmod(x, grid_width), y) EdgeMode.TORUS: return Vector2i(posmod(x, grid_width), posmod(y, grid_height)) EdgeMode.KLEIN_BOTTLE: var crossed_y: bool = y < 0 or y >= grid_height var wx: int = posmod(x, grid_width) var wy: int = posmod(y, grid_height) if crossed_y: wx = grid_width - 1 - wx return Vector2i(wx, wy) EdgeMode.CROSSCAP: var crossed_x: bool = x < 0 or x >= grid_width var crossed_y: bool = y < 0 or y >= grid_height var wx: int = posmod(x, grid_width) var wy: int = posmod(y, grid_height) if crossed_x: wy = grid_height - 1 - wy if crossed_y: wx = grid_width - 1 - wx return Vector2i(wx, wy) return null

posmod is a built-in Godot function that always returns a non-negative result (posmod(-1, 10) is 9, not -1), exactly what's needed to wrap a coordinate that's gone negative back around to the far side. wrap_cell returns null whenever a lookup genuinely has nowhere to go, a true boundary in No Wrap, or the closed-off axis in Cylinder.

Part 4. Counting Neighbors, Stepping a Generation

cell_grid.gd GDScript
func count_live_neighbors(cell: Vector2i) -> int: var count: int = 0 for dx in range(-1, 2): for dy in range(-1, 2): if dx == 0 and dy == 0: continue var neighbor = wrap_cell(cell.x + dx, cell.y + dy) if neighbor != null and alive.get(neighbor, false): count += 1 return count func step_generation() -> void: # Conway's rules (B3/S23), computed into a fresh dictionary so every # cell's next state is based on this generation, not one already # half-updated by cells processed earlier in the same pass. var next_alive: Dictionary = {} for x in range(grid_width): for y in range(grid_height): var cell := Vector2i(x, y) var live_neighbors: int = count_live_neighbors(cell) var currently_alive: bool = alive.get(cell, false) if currently_alive and (live_neighbors == 2 or live_neighbors == 3): next_alive[cell] = true elif not currently_alive and live_neighbors == 3: next_alive[cell] = true alive = next_alive queue_redraw()

The fresh next_alive dictionary matters more than it might look: every cell's next state has to be computed from this generation exactly as it was at the start, not a version already half-updated by whichever cells happened to be processed earlier in the same loop. Writing directly into alive while still reading from it partway through the same pass would let a cell's own fate influence its neighbors' fate in the same tick, which isn't the rule.

Part 5. Drawing and Clicking

cell_grid.gd GDScript
var _alive_style: StyleBoxFlat var _dead_style: StyleBoxFlat func _make_cell_style(color: Color) -> StyleBoxFlat: var style := StyleBoxFlat.new() style.bg_color = color style.corner_radius_top_left = cell_corner_radius style.corner_radius_top_right = cell_corner_radius style.corner_radius_bottom_left = cell_corner_radius style.corner_radius_bottom_right = cell_corner_radius return style func _draw() -> void: if _alive_style == null: _alive_style = _make_cell_style(Color(0.35, 0.95, 0.55, 0.95)) if _dead_style == null: _dead_style = _make_cell_style(Color(1, 1, 1, 0.08)) var visual_size: float = cell_size - cell_visual_padding var half_padding: float = cell_visual_padding * 0.5 for x in range(grid_width): for y in range(grid_height): var cell := Vector2i(x, y) var top_left: Vector2 = Vector2(x, y) * cell_size + Vector2(half_padding, half_padding) var rect := Rect2(top_left, Vector2(visual_size, visual_size)) var style: StyleBoxFlat = _alive_style if alive.get(cell, false) else _dead_style draw_style_box(style, rect)

Same cached-StyleBoxFlat pattern PathGrid uses elsewhere in this course, two styles built once and reused every frame rather than rebuilt sixty times a second.

Setting up a starting pattern by hand needs mouse input:

cell_grid.gd GDScript
func toggle_cell(cell: Vector2i) -> void: if alive.get(cell, false): alive.erase(cell) else: alive[cell] = true queue_redraw() func _unhandled_input(event: InputEvent) -> void: # _unhandled_input (rather than _input) means clicks on the UI buttons # never reach here, Godot marks those as handled first. if event is InputEventMouseButton and event.pressed and event.button_index == MOUSE_BUTTON_LEFT: var local: Vector2 = get_global_mouse_position() - global_position if local.x < 0 or local.y < 0: return var cell := Vector2i(int(local.x / cell_size), int(local.y / cell_size)) if cell.x < grid_width and cell.y < grid_height: toggle_cell(cell)

_unhandled_input, specifically, not _input: Godot marks a click on a UI button as handled before it would ever reach this method, so pressing a button never also toggles the cell sitting underneath it. get_global_mouse_position() already accounts for the Camera2D's pan and zoom automatically, no manual transform math needed.

Part 6. The Controls

cell_grid.gd GDScript
@onready var _edge_mode_label: Label = $EdgeModeLabel func _ready() -> void: _update_edge_mode_label() queue_redraw() func _process(delta: float) -> void: if not is_running: return _time_since_step += delta if _time_since_step >= generation_interval: _time_since_step = 0.0 step_generation() func randomize_cells() -> void: alive.clear() for x in range(grid_width): for y in range(grid_height): if randf() < randomize_fill_probability: alive[Vector2i(x, y)] = true queue_redraw() func clear_cells() -> void: alive.clear() is_running = false queue_redraw() func toggle_run() -> void: is_running = not is_running func step_once() -> void: step_generation() func cycle_edge_mode() -> void: edge_mode = (edge_mode + 1) % EDGE_MODE_NAMES.size() _update_edge_mode_label() queue_redraw() func _update_edge_mode_label() -> void: if _edge_mode_label != null: _edge_mode_label.text = "Edges: " + EDGE_MODE_NAMES[edge_mode]

Add a Label named EdgeModeLabel as a child of CellGrid, and five buttons on the Camera's CanvasLayer, connected straight to these methods: Randomize, Clear, Cycle Edge Mode, Run / Pause, and Step (advance exactly one generation, useful while paused for actually studying what a pattern does rather than watching it blur by). Every one connects directly to CellGrid, no intermediary script needed.

Part 7. Watching Topology Change Behavior

Click a small glider (a five-cell diagonal-moving pattern) onto the grid, or just press Randomize, then press Run. Watch the same starting pattern behave differently as you cycle edge modes: on No Wrap, anything that drifts off an edge is simply gone; on Torus, it reappears on the opposite side, unchanged; on Klein Bottle or Cross-cap, it reappears mirrored, an oscillator that looked symmetric can come back looking like its own reflection.

Checkpoint

Before moving on, make sure you can:

  1. State the B3/S23 rule from memory, and explain what each half means.
  2. Explain why step_generation writes into a fresh dictionary instead of updating alive in place.
  3. Explain what each of the five edge modes actually does to a neighbor lookup that steps off the grid.
  4. Explain why _unhandled_input is the right choice here instead of _input.
  5. Get a pattern running, and describe how the exact same starting cells behaved differently under at least two different edge modes.

Unlike every previous project this semester, nothing here has a position, a rotation, or a notion of "self." Worth sitting with that contrast: this is complexity from a rule applied everywhere at once, not complexity from anything that could be called an individual.
