Part 2. The Demo Project in One Picture

The bandit project, labeled with the Situated Agent Model. The reward is perceived, folded into memory, and memory drives the next decision.

Five script files make up the project:

  • bandit_agent.gd: the agent's brain (memory and decider). It knows nothing about pictures or buttons.
  • bandit.gd: one slot machine. It holds the true odds.
  • reward_chart.gd: the line chart.
  • main.gd: builds the world and the HUD, runs the loop, saves and loads.
  • main.tscn: a single Node2D that runs main.gd. Everything else is created in code.

Keeping the brain in its own file, free of any Godot node, is deliberate. BanditAgent extends RefCounted, the lightest base class there is, and you could test it with no screen at all. That is exactly how we tested the numbers in the last two lessons.

Part 3. The Environment: Bandit Nodes

Each machine is an instance of the Bandit class, created in build_world(). It stores its two secret numbers, and the estimates the HUD shows (est, pulls) are copied into it on each refresh.

main.gd GDScript
func build_world(seed_value: int) -> void: world_seed = seed_value for m in machines: m.queue_free() machines.clear() var params := _make_params(seed_value) best_value = -1.0 for i in ARMS: var m := Bandit.new() m.letter = char(65 + i) m.probability = params[i][0] m.payout = params[i][1] m.hue = float(i) / ARMS m.position = Vector2(180.0 + i * 230.0, MACHINE_Y) m.reveal = reveal_check != null and reveal_check.button_pressed add_child(m) machines.append(m) if m.expected_value() > best_value: best_value = m.expected_value() best_arm = i

The odds come from _make_params(seed). A seed of 0 returns the hand-picked PRESET list. Any other seed feeds a RandomNumberGenerator so the same seed always rebuilds the same five machines, which is what lets the save file store one number instead of ten.

Part 4. One Pull, End to End

Every pull, whether the agent chose it or you clicked a machine, goes through do_pull(). Reading it top to bottom gives you the whole learning loop in a dozen lines:

main.gd GDScript
func do_pull(arm: int, why: String) -> void: var m := machines[arm] var reward := float(m.payout) if rng.randf() < m.probability else 0.0 agent.update(arm, reward) var spin_time := 0.35 if auto_on: spin_time = 0.0 if speed > 12.0 else minf(0.35, 0.7 / speed) m.show_result(reward > 0.0, int(reward), spin_time) agent_target_x = m.position.x mood = why if arm == best_arm: optimal_pulls += 1 regret += best_value - m.expected_value() var cumulative := agent.total_reward / float(agent.total_pulls) chart.cumulative.append(cumulative) window_sum.append(reward) if window_sum.size() > 50: window_sum.pop_front() var s := 0.0 for v in window_sum: s += v chart.recent.append(s / window_sum.size()) refresh()

It rolls the machine, hands the reward to the agent's memory with agent.update(), tells the machine what to show, sends the agent sprite to that machine, and records bookkeeping for the chart. The agent's decision lives one function up:

main.gd GDScript
func agent_pull() -> void: var arm := agent.choose() do_pull(arm, "Exploring" if agent.last_explore else "Exploiting")

And Auto-play is just a timer accumulating in _process():

main.gd GDScript
func _process(delta: float) -> void: if auto_on: acc += delta * speed var count := 0 while acc >= 1.0 and count < 300: acc -= 1.0 count += 1 agent_pull() if count == 300: acc = 0.0

Instead of waiting for a timer node for each pull, the code adds up delta × speed and fires one pull for each whole unit that builds up. That is why the speed slider can go from one pull per second to hundreds: at high speeds the loop simply runs several pulls in one frame (with a cap, so a slow frame can't snowball).

Part 5. A Field Guide to Bandit Algorithms

Parts 2 to 4 showed one agent with epsilon-greedy and a few friends. The family tree above holds many more strategies, and they cluster into the families: semi-uniform (random exploration with simple rules), optimistic bounds (UCB and relatives), Bayesian (keep a belief, then sample or take a quantile), and contextual and non-stationary (use the situation, or forget the past), plus one preference based method. Each one below has the idea, a small Godot scenario, and a GDScript agent. All share the same Memory and Decider shape from Part 2 (Memory feeds the Decider): a choose() function and a learn() function. The code uses simplified sample scenes and a few approximations, noted where they apply.

Semi-uniform strategies

1. Epsilon-Greedy: The Foraging Bee

The idea. Epsilon-greedy is the simplest honest answer to the explore or exploit question. Most of the time the agent does the thing that has worked best so far. A small fraction of the time, it ignores its memory and picks at random, just in case its memory is wrong.

The scenario. A bee visits flower patches. Each visit yields a noisy amount of nectar, and the bee keeps a running average per patch. On each timer tick, one time in ten it flies to a random patch; otherwise it flies to the patch with the best average.

The bee usually flies to the patch with the best average, and now and then to a random one.
bee_forager.gd GDScript
extends Node2D const EPSILON := 0.1 @export var patches: Array[FlowerPatch] = [] var q: Array[float] = [] var n: Array[int] = [] func _ready() -> void: for i in patches.size(): q.append(0.0) n.append(0) $Timer.timeout.connect(_on_timer_timeout) func choose() -> int: if randf() < EPSILON: return randi() % patches.size() return q.find(q.max()) func learn(arm: int, nectar: float) -> void: n[arm] += 1 q[arm] += (nectar - q[arm]) / n[arm] func _on_timer_timeout() -> void: var arm := choose() var tween := create_tween() tween.tween_property(self, "position", patches[arm].position, 0.5) await tween.finished learn(arm, patches[arm].sample())

Takeaway. Exploration never stops. Even after the bee knows the best patch, it wastes about EPSILON of its trips, and when it explores it is just as likely to revisit a terrible patch as a promising one.

2. Epsilon-Decreasing: The Fishing Boat

The idea. Early on the agent knows nothing, so exploring is cheap and valuable. Later, exploring costs real reward. Epsilon-decreasing lets the exploration rate shrink as experience piles up, so the agent starts curious and ends focused.

The scenario. A boat chooses a fishing spot each morning. Epsilon starts at 1.0 (pure random) and is multiplied by 0.97 every day, with a floor of 0.02 so it never becomes completely stubborn. The day_started signal lets a HUD show epsilon falling.

Early on the boat tries spots at random. As epsilon decays, it settles on the spot it has learned is best.
fishing_boat.gd GDScript
extends Node signal day_started(day: int) const EPS_START := 1.0 const EPS_MIN := 0.02 const DECAY := 0.97 @export var spots: Array[FishingSpot] = [] var q: Array[float] = [] var n: Array[int] = [] var day := 0 func _ready() -> void: for i in spots.size(): q.append(0.0) n.append(0) func epsilon() -> float: return maxf(EPS_MIN, EPS_START * pow(DECAY, day)) func choose() -> int: if randf() < epsilon(): return randi() % spots.size() return q.find(q.max()) func learn(arm: int, fish: float) -> void: n[arm] += 1 q[arm] += (fish - q[arm]) / n[arm] func start_day() -> void: day += 1 day_started.emit(day) var arm := choose() learn(arm, spots[arm].cast())

Takeaway. You must pick the schedule by hand. Decay too fast and the boat locks onto a spot it only half understood; too slowly and it keeps wasting mornings.

3. Optimistic Initial Values: The Mining Bot

The idea. This one needs no random numbers at all. Start every estimate higher than any real reward could be. Each disappointing result pulls an estimate down toward reality, so the agent keeps drifting to whichever option it has not yet been disappointed by. Exploration falls out of the initial values.

The scenario. A mining bot sees three ore veins. It believes every vein is worth 10, which is more than any of them pays, and always drives to the vein it currently rates highest. Each visit nudges that vein's estimate toward the real ore yield with a fixed step size, so the bot soon tries the others.

The bot always drives to the tallest estimate. Each disappointment shortens a bar, so the bot moves on to the vein that has not let it down yet.
mining_bot.gd GDScript
class_name MiningBot extends CharacterBody2D const OPTIMISM := 10.0 const STEP := 0.1 const SPEED := 90.0 @onready var veins: Array[Node] = $Veins.get_children() var q: Array[float] = [] var target := 0 func _ready() -> void: q.resize(veins.size()) q.fill(OPTIMISM) target = q.find(q.max()) func learn(arm: int, ore: float) -> void: q[arm] += STEP * (ore - q[arm]) func _physics_process(_delta: float) -> void: var spot: Vector2 = veins[target].global_position velocity = global_position.direction_to(spot) * SPEED move_and_slide() if global_position.distance_to(spot) < 8.0: learn(target, veins[target].mine()) target = q.find(q.max())

Takeaway. It explores hard at the start and then stops, so it is good for stable problems and weak when payouts change later. The starting value must be on the same scale as your rewards.

4. Softmax (Boltzmann): The Cat and the Scratching Posts

The idea. Epsilon-greedy explores blindly. Softmax explores in proportion to how good things look: every arm gets a probability, higher estimates get larger probabilities, and a temperature number controls how sharply the agent favors the leader. High temperature acts nearly random, low temperature acts nearly greedy.

The scenario. A cat chooses among four scratching posts and purrs a different amount at each. An HSlider sets the temperature, so you can watch behavior slide from wandering to decisive. Subtracting the top value before exp() keeps the numbers from overflowing.

Every post keeps a chance. Better posts get more of it, and the slider decides how lopsided the chances are.
cat_posts.gd GDScript
extends Node2D @onready var temperature: HSlider = $UI/Temperature var q: Array[float] = [0.0, 0.0, 0.0, 0.0] var n: Array[int] = [0, 0, 0, 0] func choose() -> int: var tau := maxf(temperature.value, 0.01) var top: float = q.max() var weights: Array[float] = [] var total := 0.0 for value in q: var w: float = exp((value - top) / tau) weights.append(w) total += w var roll := randf() * total for i in weights.size(): roll -= weights[i] if roll <= 0.0: return i return weights.size() - 1 func learn(arm: int, purr: float) -> void: n[arm] += 1 q[arm] += (purr - q[arm]) / n[arm]

Takeaway. A second-best post gets visited more than a terrible one, which is the improvement over epsilon-greedy. Like epsilon, the temperature is a knob you have to tune.

Optimistic bounds strategies

5. UCB1: The Charging Drone

The idea. UCB1 gives each arm a score that is its average plus a bonus for how little it has been tried. Arms with few pulls get a big bonus, so they look promising until tested. As an arm is pulled, its bonus shrinks and the average takes over. The motto is optimism in the face of uncertainty, and it needs no randomness.

The scenario. A drone flies between charging stations that deliver different amounts of charge. Each time it docks, it updates the station's average and a global count t. It heads to the station with the highest q + C * sqrt(ln t / n). Untried stations go first.

The drone scores each station as estimate plus bonus. Station B has the lowest estimate, but it has been tried so rarely that its bonus wins.
charging_drone.gd GDScript
extends CharacterBody2D const C := 1.4 @export var stations: Array[ChargingStation] = [] var q: Array[float] = [] var n: Array[int] = [] var t := 0 func _ready() -> void: for i in stations.size(): q.append(0.0) n.append(0) stations[i].body_entered.connect(_on_station_entered.bind(i)) func choose() -> int: for i in n.size(): if n[i] == 0: return i var best := 0 var best_score := -INF for i in n.size(): var score := q[i] + C * sqrt(log(t) / n[i]) if score > best_score: best_score = score best = i return best func learn(arm: int, charge: float) -> void: t += 1 n[arm] += 1 q[arm] += (charge - q[arm]) / n[arm] func _on_station_entered(body: Node2D, arm: int) -> void: if body == self: learn(arm, stations[arm].recharge())

Takeaway. The constant C must match the scale of your rewards. If charge ranges from 0 to 50, a bonus near 1 is too timid to matter, so scale C to the reward range.

6. UCB2: The Turret and the Lanes

The idea. UCB2 is UCB1 with commitment. Once it chooses an arm, it sticks with it for a whole epoch before recomputing scores, and each epoch for the same arm is longer than the last. That means far fewer score calculations and a more patient style of play.

The scenario. A turret defends several lanes of enemies. Each time it picks a lane, it keeps firing at that lane for the epoch length given by tau(r), which grows by a factor of 1.5 each time. Only at the end of an epoch does it recompute the bonus.

The turret commits to a lane for a whole stretch before rescoring. The lane that keeps winning gets longer stretches each time.
turret_ucb2.gd GDScript
extends Node2D const ALPHA := 0.5 @export var lanes: Array[Lane] = [] var q: Array[float] = [] var n: Array[int] = [] var epoch: Array[int] = [] var t := 0 var current := 0 var remaining := 0 func _ready() -> void: for i in lanes.size(): q.append(0.0) n.append(0) epoch.append(0) func tau(r: int) -> int: return ceili(pow(1.0 + ALPHA, r)) func choose() -> int: if remaining > 0: remaining -= 1 return current for i in n.size(): if n[i] == 0: current = i return i var best_score := -INF for i in n.size(): var r := tau(epoch[i]) var bonus := sqrt((1.0 + ALPHA) * log(exp(1.0) * t / r) / (2.0 * r)) if q[i] + bonus > best_score: best_score = q[i] + bonus current = i remaining = tau(epoch[current] + 1) - tau(epoch[current]) - 1 epoch[current] += 1 return current func learn(arm: int, kills: float) -> void: t += 1 n[arm] += 1 q[arm] += (kills - q[arm]) / n[arm]

Takeaway. It is useful when switching is costly, such as a turret that has to rotate or a unit that has to walk across the map.

7. KL-UCB: The Shopkeeper

The idea. UCB1's bonus ignores what kind of rewards you get. KL-UCB asks a sharper question: what is the largest true success rate that still makes my observed results not too surprising? Surprise is measured with Kullback-Leibler divergence, and the answer is found by bisection. It suits win or lose rewards best.

The scenario. A shopkeeper pitches different wares and each customer either buys or does not. For every ware the code searches between the observed rate and 1.0 for the highest rate whose divergence from the observed rate fits inside a budget of ln t / n, then pitches the ware with the highest bound.

Ware A has a high observed rate but only ten pitches, so its believable ceiling is the highest. The shopkeeper pitches it next.
shopkeeper_klucb.gd GDScript
extends Node @export var wares: Array[Ware] = [] var wins: Array[int] = [] var tries: Array[int] = [] var t := 0 func _ready() -> void: for i in wares.size(): wins.append(0) tries.append(0) func kl(p: float, q: float) -> float: p = clampf(p, 1e-6, 1.0 - 1e-6) q = clampf(q, 1e-6, 1.0 - 1e-6) return p * log(p / q) + (1.0 - p) * log((1.0 - p) / (1.0 - q)) func upper_bound(arm: int) -> float: var mean := float(wins[arm]) / tries[arm] var budget := log(t) / tries[arm] var low := mean var high := 1.0 for step in 20: var mid := (low + high) / 2.0 if kl(mean, mid) > budget: high = mid else: low = mid return low func choose() -> int: for i in tries.size(): if tries[i] == 0: return i var best := 0 for i in tries.size(): if upper_bound(i) > upper_bound(best): best = i return best func pitch() -> void: var arm := choose() var sold: bool = wares[arm].customer_buys() t += 1 tries[arm] += 1 if sold: wins[arm] += 1

Takeaway. The bounds are tighter than UCB1's for yes or no outcomes, so it wastes fewer pitches. The price is a little extra math per decision.

Bayesian strategies

8. Thompson Sampling: The Shooting Gallery

The idea. Thompson sampling keeps a belief about each arm, not just a single number. To choose, it draws one random guess from each belief and plays the arm whose guess is highest. Uncertain arms have wide beliefs, so they often produce high guesses and get tried; well-understood arms produce steady guesses. Probability matching does the exploring.

The scenario. A fairground has several shooting booths, and every shot either hits or misses. The beliefs are Beta distributions built from hit and miss counts. To keep the GDScript short, the code draws from a normal curve with the same mean and spread as the Beta, using randfn().

Booth A is well understood, so its draws stay near 0.7. Booth B is a mystery, so its draws vary widely and this time one lands highest.
shooting_gallery.gd GDScript
extends Node2D @export var booths: Array[Booth] = [] var hits: Array[int] = [] var misses: Array[int] = [] func _ready() -> void: for i in booths.size(): hits.append(0) misses.append(0) func choose() -> int: var best := 0 var best_draw := -INF for i in booths.size(): var a := hits[i] + 1.0 var b := misses[i] + 1.0 var mean := a / (a + b) var spread := sqrt(a * b / ((a + b) * (a + b) * (a + b + 1.0))) var draw := randfn(mean, spread) if draw > best_draw: best_draw = draw best = i return best func learn(arm: int, hit: bool) -> void: if hit: hits[arm] += 1 else: misses[arm] += 1 func fire() -> void: var arm := choose() learn(arm, booths[arm].shoot())

Takeaway. There is no exploration constant to tune. This approximation is rough when counts are tiny, and an exact Beta sampler would be the next step.

9. Bayes-UCB: The Room Director

The idea. Bayes-UCB keeps the same beliefs as Thompson sampling but chooses deterministically: it takes a high quantile of each belief as an optimistic estimate of the arm and plays the highest. It is UCB, but with the width taken from a probability distribution.

The scenario. A roguelike room director chooses which room template to spawn next, hoping for the one players survive about half the time. Each template tracks rooms cleared and rooms failed. The upper bound is the mean plus sqrt(2 ln t) standard deviations, a simple stand-in for an exact quantile.

Each template gets a belief and an optimistic edge. The uncertain template B has the highest edge, so the director spawns it next.
room_director_bayesucb.gd GDScript
extends Node @export var templates: Array[PackedScene] = [] var cleared: Array[int] = [] var failed: Array[int] = [] var t := 1 func _ready() -> void: for i in templates.size(): cleared.append(0) failed.append(0) func upper_quantile(arm: int) -> float: var a := cleared[arm] + 1.0 var b := failed[arm] + 1.0 var mean := a / (a + b) var spread := sqrt(a * b / ((a + b) * (a + b) * (a + b + 1.0))) return mean + sqrt(2.0 * log(t)) * spread func choose() -> int: var best := 0 for i in templates.size(): if upper_quantile(i) > upper_quantile(best): best = i return best func spawn_next_room() -> void: var arm := choose() var room := templates[arm].instantiate() add_child(room) room.finished.connect(_on_room_finished.bind(arm)) func _on_room_finished(survived: bool, arm: int) -> void: t += 1 if survived: cleared[arm] += 1 else: failed[arm] += 1

Takeaway. Good when you want Bayesian beliefs but repeatable decisions, which helps when debugging.

Contextual strategies

10. LinUCB: The NPC Choosing Attacks

The idea. Everything so far assumed the best arm is the same every time. A contextual bandit sees a description of the situation first. LinUCB assumes each arm's reward is a weighted sum of context numbers, learns those weights, and adds an uncertainty bonus that is large in situations it has not seen.

The scenario. An NPC picks one of three attacks. The context is a Vector3: how far away the player is, the player's health, and a constant 1. Each attack stores a 3 by 3 matrix a (a Basis) and a vector b. The weights are a-1 b.

The NPC turns the situation into numbers, scores every attack for that exact situation, and picks the best. At another distance the ranking could flip.
npc_linucb.gd GDScript
extends CharacterBody2D const ALPHA := 0.8 var a: Array[Basis] = [] var b: Array[Vector3] = [] func _ready() -> void: for i in 3: a.append(Basis.IDENTITY) b.append(Vector3.ZERO) func context(player: Node2D) -> Vector3: var distance := clampf(global_position.distance_to(player.global_position) / 400.0, 0.0, 1.0) return Vector3(distance, player.health / 100.0, 1.0) func choose(x: Vector3) -> int: var best := 0 var best_score := -INF for i in a.size(): var inverse := a[i].inverse() var theta := inverse * b[i] var score := theta.dot(x) + ALPHA * sqrt(x.dot(inverse * x)) if score > best_score: best_score = score best = i return best func learn(arm: int, x: Vector3, damage: float) -> void: a[arm] = Basis(a[arm].x + x * x.x, a[arm].y + x * x.y, a[arm].z + x * x.z) b[arm] += x * damage

Takeaway. Close range might favor the sword and long range the bow; a plain bandit would average the two and learn neither.

11. Contextual Thompson Sampling: The Difficulty Director

The idea. This is Thompson sampling with context. Instead of sampling a reward, the agent samples a whole set of plausible weights for each arm, scores the current context with them, and plays the best score. Unsure arms vary more and get tried.

The scenario. A game director picks among three difficulty tweaks for a player and observes engagement. It uses the same a and b bookkeeping as LinUCB. To stay simple, it draws each weight independently using only the diagonal of the inverse matrix, which is an approximation.

A tight cloud means the director is sure about that tweak. A wide cloud means unsure, so the single draw can land high, and the director tries it.
director_cts.gd GDScript
extends Node const SPREAD := 0.5 var a: Array[Basis] = [] var b: Array[Vector3] = [] func _ready() -> void: for i in 3: a.append(Basis.IDENTITY) b.append(Vector3.ZERO) func sample_theta(arm: int) -> Vector3: var inverse := a[arm].inverse() var mean := inverse * b[arm] return Vector3( randfn(mean.x, SPREAD * sqrt(inverse.x.x)), randfn(mean.y, SPREAD * sqrt(inverse.y.y)), randfn(mean.z, SPREAD * sqrt(inverse.z.z))) func choose(x: Vector3) -> int: var best := 0 var best_draw := -INF for i in a.size(): var draw := sample_theta(i).dot(x) if draw > best_draw: best_draw = draw best = i return best func learn(arm: int, x: Vector3, engagement: float) -> void: a[arm] = Basis(a[arm].x + x * x.x, a[arm].y + x * x.y, a[arm].z + x * x.z) b[arm] += x * engagement

Takeaway. It often matches LinUCB in practice and needs one fewer bonus term, only a spread number to tune.

Non-stationary strategies

12. Discounted UCB: The Courier

The idea. Everything above assumes the world holds still. If payoffs change, old data becomes misleading. Discounted UCB multiplies all stored totals and counts by a number slightly below 1 every step, so old pulls fade and recent ones matter most. A sliding window does the same by simply dropping data older than N pulls.

The scenario. A courier chooses among roads whose speed changes as traffic builds and clears. After every trip all totals and weights shrink by GAMMA = 0.98, then the chosen road gets a fresh full-weight observation. UCB runs on these discounted values.

When traffic swaps the best road, the old data fades away. A few recent trips are enough to convince the courier to change roads.
courier_ducb.gd GDScript
extends CharacterBody2D const GAMMA := 0.98 const C := 1.0 @export var roads: Array[Road] = [] var total: Array[float] = [] var weight: Array[float] = [] func _ready() -> void: for i in roads.size(): total.append(0.0) weight.append(0.0) func choose() -> int: for i in weight.size(): if weight[i] < 0.001: return i var all_weight := 0.0 for w in weight: all_weight += w var best := 0 var best_score := -INF for i in weight.size(): var score := total[i] / weight[i] + C * sqrt(log(all_weight) / weight[i]) if score > best_score: best_score = score best = i return best func learn(arm: int, speed: float) -> void: for i in weight.size(): total[i] *= GAMMA weight[i] *= GAMMA total[arm] += speed weight[arm] += 1.0

Takeaway. The effective memory is about 1 / (1 - GAMMA) trips, here 50. Too short a memory makes the courier jumpy; too long and it stays loyal to a road that has jammed.

Preference based strategies

13. Gradient Bandit: The Conveyor Robot

The idea. Every strategy so far estimates how much each arm pays. The gradient bandit instead learns a preference for each arm and turns the preferences into probabilities with softmax. After a reward, it raises the preference of the chosen arm if the reward beat a running average baseline and lowers it if not, and does the opposite for the others.

The scenario. A robot sorts parcels into three bins. The bars in the HUD show its current probabilities, so you can watch the policy sharpen. The baseline is what lets it tell a good outcome from an ordinary one.

The robot nudges its preferences after every parcel. Over time the probability bars slide toward the bin that keeps paying more than average.
conveyor_robot.gd GDScript
extends Node const ALPHA := 0.1 @onready var bars: Array[Node] = $HUD/Bars.get_children() var h: Array[float] = [0.0, 0.0, 0.0] var baseline := 0.0 var steps := 0 func policy() -> Array[float]: var top: float = h.max() var pi: Array[float] = [] var total := 0.0 for x in h: var w: float = exp(x - top) pi.append(w) total += w for i in pi.size(): pi[i] /= total return pi func choose() -> int: var roll := randf() var pi := policy() for i in pi.size(): roll -= pi[i] if roll <= 0.0: return i return pi.size() - 1 func learn(arm: int, reward: float) -> void: steps += 1 baseline += (reward - baseline) / steps var pi := policy() var gap := ALPHA * (reward - baseline) for i in h.size(): if i == arm: h[i] += gap * (1.0 - pi[i]) else: h[i] -= gap * pi[i] pi = policy() for i in bars.size(): bars[i].value = pi[i]

Takeaway. It works well when only relative differences matter. The baseline matters: without it, a uniformly positive reward would push up whichever arm happened to be chosen.

Which one should I use?

  • A quick prototype or a stable game: epsilon-greedy or optimistic initial values.
  • Rewards that are wins or losses: Thompson sampling, or KL-UCB if you want deterministic choices.
  • The best option depends on the situation: LinUCB or contextual Thompson sampling.
  • Players or the world change over time: discounted UCB, or a constant step size in any of the others.

Exercises

Warm-up

  1. In the bee scenario, change EPSILON to 0.3 and describe how the trips change.
  2. In the cat scenario, drag the temperature slider from 0.01 to 5 and describe what the cat does at each end.

Intermediate

  1. Add a pull cost of 1 coin per pull so the reward is payout minus 1. How do the numbers in the chart change, and does the best machine change?
  2. Add a sixth strategy to BanditAgent: "Greedy with optimistic start." Wire it into the dropdown.

Advanced

  1. Make one machine non-stationary: its probability drifts by a small random amount each pull. Which strategy copes best?
  2. Build a second agent that plays the same machines at the same time and show both charts. Is it a fair comparison if they use different random numbers?
