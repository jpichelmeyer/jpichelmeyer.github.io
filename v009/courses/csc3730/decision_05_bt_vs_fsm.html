Two Deciders down, same original problem (decision trees have no memory) solved two different ways. This lesson doesn't introduce anything new; it puts the FSM and the behavior tree from the last three lessons directly side by side, focused specifically on the thing the schedule's title is pointing at: memory, what each one remembers between frames, and where that memory actually lives.

Part 1. Where "Current State" Lives

An FSM's memory is blunt and explicit: exactly one variable, current_state, always points at exactly one active FSMState node. That single reference is the machine's entire memory of "what was I just doing." Ask an FSM what it's doing and there's exactly one honest answer, always.

A behavior tree has no equivalent variable anywhere. There's no current_node field on BehaviorTree_Root; every single tick walks back down from the root, through the Selector, into whichever Sequencer doesn't fail, same as the very first tick ever did. "What was I just doing" isn't stored, it's recomputed, every frame, from the same fixed structure.

Part 2. Then How Does a Tree "Remember" Mid-Action?

RUNNING is the answer. Go back and look at bt_root.gd closely, specifically a block that's currently commented out:

bt_root.gd GDScript
func _physics_process(delta): # If RUNNING returned, tick directly to the running leaf # without going through the whole tree again """ if response_last == RUNNING: response_last = blackboard.board["Running leaf"].tick(actor, blackboard, delta) print(Time.get_ticks_msec(), " : Behavior tree root ticking running node directly") return """ print(Time.get_ticks_msec(), " : BT new tick") response_last = get_child(0).tick(actor, blackboard, delta) print(blackboard.board)

As written (that block commented out), the tree re-walks from the root every single frame, full stop, even while a Move to Move Target action is mid-move and returning RUNNING. That works, because every Condition along the way keeps re-passing (it's still daytime, the target's still set), so the Selector and Sequencer keep routing the tick to the same running leaf on their own, but it means the tree is repeating work it already did last frame just to arrive back at the same conclusion.

The commented-out block sketches the classic optimization: remember, on the blackboard, which leaf was left RUNNING (set_running_leaf, over in bt_blackboard.gd, exists for exactly this), and next frame tick straight to it, skipping the conditions above it entirely. That's memory, stored on the blackboard rather than in a dedicated variable, and it's memory of a specifically narrow kind: where the tick left off, not what the agent is doing in any broader sense. Turning it on is a real, if small, design decision, not a free lunch: skip the Conditions above a running leaf, and the tree stops re-checking whether they're still true until that leaf finishes.

Part 3. Two Different Shapes of "Interrupt"

Recall StateSeek's on_target_lost hook: the FSM reacts to a signal by explicitly calling fsm.transition_to(&"StateWander"), an interrupt with a name, aimed at a specific destination state.

A behavior tree interrupts differently, and more implicitly. Nothing in the Gatherer's tree has an "interrupt" concept at all; the daylight Condition is simply re-checked from the top on the very next tick (or the next un-skipped one, if the running-leaf optimization is on), and if it now fails where it used to succeed, the Selector just naturally falls through to the other branch. There's no line of code anywhere that says "abandon the grass branch"; abandoning it is just what re-ticking the same fixed structure does when a Condition's answer changes.

Same underlying problem, two different places the "memory" actually lives.

Part 4. So Which One?

Neither is strictly better; they trade off differently:

  • Reach for an FSM when the agent genuinely has a small number of clearly distinct modes, and the transitions between them are the interesting part worth naming and reasoning about explicitly (a boss fight's phases, a menu's screens).
  • Reach for a behavior tree when the interesting part is priority among many possible reactions (try this, then this, then this) and you expect to keep growing the list; adding a new fallback is dropping in one more Sequencer under a Selector, versus an FSM where a new state often means auditing every existing state for whether it should also know how to transition to it.
  • FSMs get spaghetti as transitions multiply (every state potentially wired to several others); behavior trees get unwieldy as depth grows instead (a deeply nested tree re-ticking Conditions every frame gets expensive and harder to read top to bottom, which is exactly what the running-leaf optimization in Part 2 exists to soften).

Worth saying plainly: real projects mix these. A behavior tree leaf can itself be "enter combat mode," handing off to a small FSM for the fight itself. Treat both as tools for the same Decider slot in SAM, not as competing religions.
