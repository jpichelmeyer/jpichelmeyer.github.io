The last four lessons were about ideas; this one opens the gridworld project and shows where each idea lives. Like the bandit project, it follows the Situated Agent Model, and like the bandit project, it keeps the learning code free of any pictures so the brain can be understood, and tested, on its own.

Part 1. Who Does What

The gridworld project. Main creates and connects everything else.
  • grid_data.gd: the Environment. Cells, rewards, the six presets, and the step() function from the MDP lesson. No pictures.
  • q_agent.gd: Memory (the Q table) and the Decider (epsilon-greedy), plus the learning rule for both Q-learning and SARSA. No pictures either.
  • main.gd: the Perceptor (observe()), the Actuator (take()), the training loop, the HUD controls, and save and load.
  • grid_view.gd: a Control that draws a grid. It appears twice, once large and interactive, once small as the policy map.
  • action_panel.gd: the four-box Options display.
  • main.tscn: a lone Node2D with main.gd attached. As with the bandits, everything else is built in code.

Part 2. Data You Can Read

The presets are plain text so you can see the map in the source. Each is a title, a step reward, and one string per row:

grid_data.gd GDScript
{ "title": "3. Cliff", "step": -1.0, "rows": ["............", "............", "............", "SCCCCCCCCCCG"], },

from_ascii() reads each character and turns it into a cell: S is the start, # a wall, G a +10 goal, X a −10 pit, C a cliff, b a breadcrumb, w a puddle, and everything else an ordinary cell that pays the grid's step reward. Adding a preset is one new entry in the list.

Underneath, a grid is two flat arrays, kinds and rewards, one entry per cell, and a cell at column x and row y lives at index y * width + x:

grid_data.gd GDScript
func index(c: Vector2i) -> int: return c.y * width + c.x

The same index is the agent's state number in the default "exact position" mode, which is why the Q table can simply be a dictionary from integers to four numbers.

Part 3. Perception, Action, and the Loop

You have already read observe() and sense() (the Perceptor), take() (the Actuator and the learning step), and run_step(). What remains is the driver that calls them. In _process(), the same accumulate-and-fire pattern from the bandit project turns the speed slider into a number of steps per frame. The fast button skips drawing entirely:

main.gd GDScript
func train(count: int) -> void: var target := agent.episodes + count var guard := 0 while agent.episodes < target and guard < 400000: run_step() guard += 1 refresh()

There is a guard on that loop. If a bad grid made an episode never end, guard would keep the game from freezing forever. Every loop in a program that a user can configure deserves one.

Part 4. Drawing and Editing the Grid

A GridView doesn't store any grid of its own. It is handed a GridData, a QAgent, and a Callable (a function reference) that turns a cell into an observation. Handing it the function is what lets the big view and the mini view show whichever perception mode is active without knowing anything about it. Everything is drawn from three small geometry functions:

grid_view.gd GDScript
func cell_size() -> float: if data == null: return 1.0 return minf((size.x - 8.0) / data.width, (size.y - 8.0) / data.height)
grid_view.gd GDScript
func origin() -> Vector2: var cs := cell_size() return Vector2((size.x - cs * data.width) / 2.0, (size.y - cs * data.height) / 2.0)
grid_view.gd GDScript
func cell_rect(c: Vector2i) -> Rect2: var cs := cell_size() return Rect2(origin() + Vector2(c) * cs, Vector2(cs, cs))

The cell size is the smaller of "how wide could a cell be" and "how tall could it be," which is why grids of any shape fit the same panel. The origin centers whatever is left over.

The same arithmetic runs backward for painting. A mouse press or drag becomes a cell coordinate, and the view announces it with a signal, leaving the decision about what to do to main.gd:

grid_view.gd GDScript
func _gui_input(event: InputEvent) -> void: if data == null: return var pressed := false if event is InputEventMouseButton and event.pressed and event.button_index == MOUSE_BUTTON_LEFT: pressed = true elif event is InputEventMouseMotion and (event.button_mask & MOUSE_BUTTON_MASK_LEFT) != 0: pressed = true if pressed: var cs := cell_size() var c := Vector2i(((event.position - origin()) / cs).floor()) if data.inside(c): cell_clicked.emit(c)
main.gd GDScript
func paint(c: Vector2i) -> void: if c == data.start and tool_index != 0: return make_custom() match tool_index: 0: data.start = c data.set_empty(c) 1: data.set_empty(c) 2: data.set_cell(c, GridData.Kind.WALL, 0.0) 3: data.set_cell(c, GridData.Kind.EMPTY, value_spin.value) 4: data.set_cell(c, GridData.Kind.TERMINAL, value_spin.value) 5: data.set_cell(c, GridData.Kind.CLIFF, value_spin.value) edited()

Here a signal keeps the pieces apart. The view knows about pixels and mouse clicks and nothing about tools or rewards. paint() knows about tools and rewards and nothing about pixels. The first edit to a preset makes a private copy (make_custom()), so the originals are never damaged, and every edit clears the agent's table, because a table learned on one set of rewards is a promise about a world that no longer exists. You met that idea in the bandit save file.

One more detail in the view makes it feel alive: the agent sprite doesn't jump from cell to cell, it glides.

grid_view.gd GDScript
func _process(delta: float) -> void: if data != null and sprite != null: var cs := cell_size() var target := center_of(agent_cell) if snap: sprite.position = target snap = false else: sprite.position = sprite.position.lerp(target, 1.0 - exp(-16.0 * delta)) var s := cs * 0.8 / sprite.texture.get_width() sprite.scale = Vector2(s, s) queue_redraw()

Each frame, the sprite moves a fraction of the remaining distance to its target. Writing that fraction as 1.0 - exp(-16.0 * delta) instead of a fixed number keeps the motion the same on a slow computer and a fast one. At very high training speeds the agent can't keep up with where it "really" is, and that is fine: the table is what matters, and the picture is just a window onto it.

Part 5. Saving the Agent and Its World

The bandit file stored a seed that could rebuild the machines. A grid can be edited, so a seed isn't enough. The gridworld save file stores the grid itself next to the agent, plus the settings that give the table meaning:

main.gd GDScript
func save_agent() -> void: var out := { "version": 1, "grid": data.to_dict(), "obs_mode": obs_mode, "rewards_mode": rewards_mode, "sarsa": agent.use_sarsa, "alpha": agent.alpha, "gamma": agent.gamma, "epsilon": agent.epsilon, "decay": agent.decay_episodes, "agent": agent.to_dict(), } var f := FileAccess.open(SAVE_PATH, FileAccess.WRITE) if f == null: status_label.text = "Could not write the save file." return f.store_string(JSON.stringify(out, " ")) f.close() status_label.text = "Saved the agent and its grid (%d episodes)." % agent.episodes

The list is worth reading as a checklist of "what does this knowledge depend on?" A Q table is indexed by observations, so the observation mode matters. Sensor-based entries mean different things depending on whether rewards were visible. SARSA and Q-learning tables are not interchangeable in spirit even if they are in shape. Loading restores all of it, and the grid arrives in the editable "Custom grid" slot. The loader checks that the grid's arrays have the right length before accepting it, the same defensive habit from the saving lesson.

Part 6. Exporting to the Web

The demos in these lessons are the same projects exported with Project > Export > Web using the GL Compatibility renderer and without thread support, so the page needs no special server headers. Exporting from the editor produces an HTML page, a JavaScript loader, a .wasm engine file, and a .pck with your scripts and assets. They must be served over HTTP (a double-clicked file won't run), and on the course site they are embedded with the godot-embed-wrap element that every lesson here uses.

Part 7. Try It

  1. Add a seventh preset to the list in grid_data.gd: a small grid of your own design. Run it and see whether the agent learns what you intended.
  2. Add a new tile letter to from_ascii(), for example "$" for a +5 terminal prize. Use it in a new preset.
  3. Change max_steps() to width * height. Which presets now behave differently, and why?
  4. Build a grid in the editor, train an agent, Save, close the page, reopen it, and Load. Confirm that both the grid and the policy come back.

Exercises

Warm-up

  1. Change the starting color of the grid cells and the arrow color in grid_view.gd.
  2. Display the current episode number in the window title.

Intermediate

  1. Add a "slippery floor" setting: with some probability a chosen move is replaced by a random move. Put the probability in GridData.step() and add a slider. What happens to the greedy path on the cliff?
  2. Add three save slots with a dropdown, following the bandit lesson's exercise.

Advanced

  1. Add a key and a locked door tile. The agent can only pass the door after stepping on the key. What does the state need to contain now, and how many states does a 5 × 5 grid have?
  2. Add a last_action to the sensor observation so the left-and-right-only agent has a one-step memory. Does it solve preset 5?
  3. Replace the Q table with a neural network that takes the (x, y) position as input. What new problems appear?
