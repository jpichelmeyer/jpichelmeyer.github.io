Step 2. The Node Program

All the pieces are in the files you have already written; the node program only arranges them. Read it before you run it: each Every(...) is a job with its own period, and notice that sampling rates (how often we measure) are different from publishing rates (how often we report).

The job table of the Lab 3 node. Sampling faster than you publish lets the filters work on many readings and sends only the result, which keeps the network quiet: about 7 messages per second in total, under the class limit of 10.
main.py MicroPython
# main.py for Lab 3: an instrumented node import net from machine import I2C, Pin from time import ticks_ms, ticks_diff from mpu6050 import MPU6050, roll_deg # from the I2C lesson from lcd1602 import LCD # from the I2C lesson from ranger import Ranger # from the Pulses lesson from pulsecounter import PulseCounter # from the Pulses lesson from every import Every # from the Pulses lesson from filters import EMA # from the Filtering lesson i2c = I2C(0, sda=Pin(4), scl=Pin(5), freq=400_000) imu = MPU6050(i2c) imu.calibrate() # keep the board still for this second lcd = LCD(i2c) ranger = Ranger() reed = PulseCounter(12) roll_f, cm_f = EMA(0.3), EMA(0.4) every_imu, every_range = Every(50), Every(100) # sampling: 20 Hz and 10 Hz pub_imu, pub_range = Every(200), Every(500) # publishing: 5 Hz and 2 Hz every_lcd, every_stats = Every(500), Every(5000) roll, cm = 0.0, None reed_seen = 0 loop_max, last = 0, ticks_ms() def on_status(s): lcd.line("net " + s, 1) net.link().on_status = on_status ranger.start() def step(): global roll, cm, reed_seen, loop_max, last now = ticks_ms() loop_max = max(loop_max, ticks_diff(now, last)) # the longest gap between passes last = now if every_imu.due(): (ax, ay, az), _, _ = imu.read() roll = roll_f.update(roll_deg(ax, ay, az)) if ranger.update() and ranger.cm is not None: cm = cm_f.update(ranger.cm) if every_range.due() and not ranger.busy: ranger.start() if pub_imu.due(): net.publish("tele/imu", {"roll": round(roll, 1)}) if pub_range.due() and cm is not None: net.publish("tele/range", {"cm": round(cm, 1)}) n = reed.count() if n != reed_seen: # an event: publish it when it happens reed_seen = n net.publish("evt/reed", {"n": n}) if every_lcd.due(): lcd.line("r%6.1f d%s" % (roll, "---" if cm is None else "%5.1f" % cm), 0) if every_stats.due(): lk = net.link() net.publish("tele/node", {"sent": lk.sent, "queued": len(lk.log), "dropped": lk.dropped, "loop_max_ms": loop_max}) loop_max = 0 while True: step()

The loop body is a function step(), called forever. That makes it testable (you can call step() yourself with a simulated clock) and keeps the structure plain: one pass is one trip around the cooperative loop of the Pulses lesson. loop_max records the longest gap between passes, which is the figure that tells you whether the node is keeping up.

The Lab 3 network budget. The messages are small, and the total stays under the class limit with room for event messages (reed passes, and later commands).

Step 4. The Offline Drill

Now break it. With your node publishing normally, take the network away: turn off your phone hotspot that the Pico is on, or ask the instructor to pause the class access point. Leave it off for 20 seconds, then restore it. Watch three things: the LCD, the loop_max_ms figure, and the message numbers arriving at the broker.

The offline drill and what you should observe. Each result has an explanation in the lessons: the stall is the blocking reconnect, the queue is net.py’s log, and the gap is a bounded buffer doing its job.

Record every number. The questions in the report ask you to explain each one, and to say what you would change to make the node better at surviving an outage. (Unit 2 shows how.)

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: How Long Can It Wait?

40 / 7.2 = 5.6 seconds. After that, every new message pushes the oldest one out and dropped starts counting up. A one-minute outage loses about 7.2 × 60 − 40 = 392 messages unless you reduce the rate while offline or store more.

Exercise 2: Budget Check

7.2 + 2 = 9.2 per second, under 10 with a margin of 0.8. It is a thin margin: another event type could push it over, so you might lower tele/imu to 2 Hz when events are busy.

Exercise 3: Size of a Message
size.py MicroPython
import json topic = "lab/jsmith/tele/imu" payload = json.dumps({"v": 1, "seq": 17, "t": 34120, "roll": 12.3}) size = len(topic) + len(payload) + 5 print(len(topic), len(payload), size, size * 5) # 19 45 69 345

About 69 bytes per message, or 345 B/s at 5 Hz. Almost all of it is the same text every time (the topic and the key names). Unit 2 shows how to shrink this with compact payloads.

Advanced

Exercise 4: Find the Gaps
gaps.py MicroPython
def find_gaps(seqs): """Given the seq numbers a receiver saw (in arrival order), return what is missing and which numbers arrived out of order.""" missing, late = [], [] top = None for s in seqs: if top is None: top = s elif s > top + 1: missing.extend(range(top + 1, s)) # we skipped some top = s elif s > top: top = s else: late.append(s) # at or below the highest seen already missing = [m for m in missing if m not in seqs] # a "missing" one that arrived later is not missing return missing, late
test_gaps.py MicroPython
print(find_gaps([1, 2, 3, 7, 8])) # ([4, 5, 6], []) lost print(find_gaps([1, 2, 3, 6, 4, 5, 7])) # ([], [4, 5]) arrived late, none lost

The first call is a loss: 4, 5 and 6 never came. The second is only reordering: 4 and 5 arrive after 6 but arrive. This is exactly what you see at the broker after an outage: the queued messages come back late and in order, so a receiver that looks at seq can tell an outage from real loss.
