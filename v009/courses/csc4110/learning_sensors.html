This lesson covers recording sensor data and learning from it in the smallest useful way. You log every message into a SQLite file and ask it questions with SQL, fit a calibration curve by least squares and choose its degree by testing on new data, see overfitting in numbers, classify motion with nearest centroid after scaling the features, read a confusion matrix, and ship the result as a file of numbers.

SAM lens. Calibration and classification are learned Perceptor stages: fitted on the hub from recorded data, run on the robot as a file of numbers. The Decider receives a cleaner percept and never depends on the model being right for safety. The log the models learn from is long-term Memory outside the agent, and it answers questions only if you decided in advance what to record.

“Machine learning” sounds like something that needs a data centre. In a robot it mostly means two small things done carefully: fitting a curve to turn a raw sensor value into a physical one (calibration), and choosing a label from a few measured features (is the robot still, walking or being shaken?). Both fit in a few lines of code, both are trained on a laptop from recorded data, and both are run on the Pico as a handful of numbers. The part that decides whether they work is not the code but the discipline around it: separate data for testing, honest error, and distrust of a model that looks too good.

Part 1. Recording Data to Learn From

Every model in this lesson is learned from a record, so learning starts with deciding what to record. Not all records are equal:

Not all records are equal. Events are rare and explain behaviour, so they are kept a long time. Samples are plentiful and cheap, so they are kept briefly and then replaced by summaries.

A useful test: for each line you log, write down the question it will answer. “Why did the motor stop?” is answered by a stop,deadman event. “Was the signal noisy?” is answered by a minute of samples, or by their standard deviation. A line that answers no question is storage spent on nothing.

The robot itself has little room to keep anything, but a laptop (or the class hub) can keep everything and query it. The simplest durable logger is a program that reads the stream from mosquitto_sub and writes each message to a SQLite file. SQLite is a database in one ordinary file, with SQL for asking questions, and Python includes it.

logger.py Python
# logger.py -- on the laptop or the hub: every message into one SQLite file # mosquitto_sub -h BROKER -u USER -P PW -t 'lab/#' -v | python3 logger.py lab.db import sys, sqlite3, time db = sqlite3.connect(sys.argv[1]) db.execute("""CREATE TABLE IF NOT EXISTS msgs ( ts REAL, user TEXT, topic TEXT, payload TEXT)""") db.execute("CREATE INDEX IF NOT EXISTS msgs_user_ts ON msgs (user, ts)") def user_of(topic): p = topic.split("/") return p[1] if len(p) > 2 and p[0] == "lab" else "" n, last = 0, time.time() for line in sys.stdin: topic, _, payload = line.rstrip("\n").partition(" ") db.execute("INSERT INTO msgs VALUES (?, ?, ?, ?)", (time.time(), user_of(topic), topic, payload)) n += 1 if time.time() - last >= 1.0: # commit once a second, not once a message db.commit() last = time.time() db.commit() print("logged", n, "messages")

It commits once a second, not once per message, because a commit waits for the disk and dominates the cost, and it has an index on (user, ts) so that “this student, this hour” does not read the whole table. A whole class at the message limit would add about 1.5 GB a day, so a log also needs a rule for what to throw away. Once the data is in, SQL answers questions in a line or two:

questions.sql SQL
-- how much did each student send in the last 10 minutes? SELECT user, COUNT(*) AS n, COUNT(*) / 600.0 AS per_s FROM msgs WHERE ts > strftime('%s','now') - 600 GROUP BY user ORDER BY n DESC; -- the last state each robot announced SELECT topic, payload, MAX(ts) FROM msgs WHERE topic LIKE '%/stat/state' GROUP BY topic; -- one-minute averages of a field (downsampling) SELECT CAST(ts / 60 AS INT) * 60 AS minute, AVG(json_extract(payload, '$.c')) AS mean_c, COUNT(*) AS n FROM msgs WHERE topic = 'lab/jsmith/tele/temp' GROUP BY minute ORDER BY minute; -- retention: keep seven days of raw messages DELETE FROM msgs WHERE ts < strftime('%s','now') - 7 * 86400;

The three queries answer the questions of the course: who is sending too much, what state is everyone in, and what did one signal do over time. The last statement is the retention rule, run once a day. Notice that each row keeps two clocks: the logger’s own arrival time ts, which is a real calendar time, and the robot’s t inside the payload, which orders that robot’s messages but restarts at every boot. Keep both.

Part 2. Learning a Calibration

A thermistor divider gives an ADC reading that is a smooth but nonlinear function of temperature. A straight line is a poor fit; a curve is better. Least squares finds the polynomial that minimises the sum of the squared differences between the curve and your reference measurements. You do this once, on the laptop, against a trusted thermometer; the node only evaluates the result.

fit.py Python
# fit.py -- run on the laptop: least-squares polynomial through (x, y) points def fit_poly(xs, ys, deg): """Coefficients c[0] + c[1] x + c[2] x^2 ... that minimise the squared error. Solves the normal equations by Gaussian elimination: fine for degree up to about 4.""" n = deg + 1 # A[i][j] = sum x^(i+j), b[i] = sum y x^i A = [[sum(x ** (i + j) for x in xs) for j in range(n)] for i in range(n)] b = [sum(y * x ** i for x, y in zip(xs, ys)) for i in range(n)] for col in range(n): # forward elimination with pivoting piv = max(range(col, n), key=lambda r: abs(A[r][col])) A[col], A[piv], b[col], b[piv] = A[piv], A[col], b[piv], b[col] for r in range(col + 1, n): f = A[r][col] / A[col][col] for c in range(col, n): A[r][c] -= f * A[col][c] b[r] -= f * b[col] coef = [0.0] * n for i in range(n - 1, -1, -1): # back substitution coef[i] = (b[i] - sum(A[i][j] * coef[j] for j in range(i + 1, n))) / A[i][i] return coef def predict(coef, x): y = 0.0 for c in reversed(coef): # Horner's rule: few multiplications y = y * x + c return y def rms(coef, xs, ys): return (sum((predict(coef, x) - y) ** 2 for x, y in zip(xs, ys)) / len(xs)) ** 0.5

That code, checked against numpy.polyfit on the same data, returned identical coefficients. Now to the question that matters: how complicated a curve? Twelve reference points were simulated from a 10 kΩ thermistor (β = 3950) in a divider, with the ADC noise of the lab (about 60 counts) and a reference thermometer good to 0.3 °C. Polynomials of degree 1, 3 and 7 were fitted, and then tested against 500 new points the fit had never seen:

Three fits through the same twelve points. The thermistor curve is only slightly bent over this range, and the straight line misses the bend by 0.7 °C RMS; the cubic follows it; the degree-7 curve passes closest to every point and then flies off at the end of the range, where it has no points to hold it.
Training error only ever falls as the curve gets more flexible; error on new data falls and then rises. Degree 3 is the sweet spot with this little data; degree 7 has memorised the noise (0.11 °C on its own points, 1.32 °C on new ones).

This is overfitting, the central danger of learning from data: a model flexible enough to follow the noise in twelve points will follow it. Two defences, both cheap. Keep some data out of the fit and judge the model on it (the test column above). And collect more data than the model has numbers: with 60 points instead of 12 the same degree-7 fit came back to 0.14 °C on new data, no worse than the cubic, because the noise averages out.

node.py MicroPython
# on the node: the model is three numbers in a file, the code is four lines import json coef = json.load(open("cal.json"))["coef"] # e.g. [12.4, -3.1, 0.7]; x is the scaled ADC value def calibrate(x): y = 0.0 for c in reversed(coef): y = y * x + c return y

On the node the calibration is a file of four numbers and the four-line calibrate above. Note that x must be scaled exactly as in training (the ADC reading divided by 65,535 here): a model is only valid for the inputs it was trained on, and mismatched scaling is the most common reason a calibration “works on the laptop and not on the board”.

Part 3. Learning a Label

The second job is classification: the features lesson used one feature and one threshold. With two or more features, the simplest method that works is nearest centroid: the average of the training examples of each class is its centroid, and a new example gets the label of the nearest one. Training is an average; classifying is a distance. Both are cheap enough for the Pico.

centroid.py MicroPython
# centroid.py -- classify by the nearest class average def train(samples): """samples: list of (features, label). Returns {label: centroid}.""" sums, counts = {}, {} for f, lab in samples: s = sums.setdefault(lab, [0.0] * len(f)) for i, v in enumerate(f): s[i] += v counts[lab] = counts.get(lab, 0) + 1 return {lab: [v / counts[lab] for v in s] for lab, s in sums.items()} def classify(model, f, scale): """The label whose centroid is nearest. scale[i] divides feature i first, so a feature measured in big numbers does not drown the others.""" best, best_d = None, None for lab, c in model.items(): d = sum(((a - b) / s) ** 2 for a, b, s in zip(f, c, scale)) if best_d is None or d < best_d: best, best_d = lab, d return best

Features must be scaled, or the one with the biggest numbers decides alone. To show it, the test below has three motion classes whose only difference is the standard deviation of acceleration (0.01 to 0.6 g), plus a second, irrelevant feature, the room temperature (15 to 35 °C), which every class shares. With 100 training examples per class and 300 test examples per class:

Scaling decides everything here. Unscaled, the temperature (range of 20) swamps the acceleration (range of 0.6) and the classifier is hardly better than guessing; scaled, it is right 86 % of the time, and removing the useless feature changes almost nothing.
The confusion matrix of the scaled classifier on 900 test examples. Still is always recognised; walk is sometimes taken for still (56) and shake for walk (67). The errors fall between neighbouring classes, where the ranges of the data overlap by design.

A confusion matrix tells you what a single accuracy number hides: which mistakes are made. For a robot the mistakes are not equal: taking “shake” for “walk” may be harmless, taking “walk” for “still” may let a motor start while someone is holding the robot. Choose the model, or the thresholds, on the cost of the mistake, not only on the count.

  • Always test on data the model has not seen. Record separate sessions for training and testing, not a random split of one session: neighbouring samples are nearly identical, and a random split lets the model peek.
  • Record your own data on your own robot. A model trained on someone else’s IMU, mounting and floor does not transfer.
  • Ship the numbers, not a program. The model is a JSON file of a few numbers (coefficients, centroids, scales), and an update is one message or one file copy. Publish its version on stat/ so you know which one is running.
  • Know when you are outside the training data. A feature value far from any centroid or training range should be reported as “unknown”, not forced into the nearest class.

Warm Up

Exercise 1: Pick the Kind

(a) sample: days, then a summary. (b) state change: long. (c) fault: longest, with the reset count. (d) event (a refused command): long enough to debug a client, and worth counting so that a client sending refused commands stands out.

Exercise 2: Count the Numbers

More points than coefficients: at least 8 to 12, ideally spread over the whole range of temperatures you will measure (the 12 above spanned 10 to 50 °C). Twelve readings at one temperature give the noise at that temperature but no information about the shape of the curve elsewhere: the fit is free to do anything away from that point, and the model is only valid for inputs like those it was trained on.

Exercise 3: Read the Table

A more flexible curve can pass closer to every training point, so training error can only fall as the degree rises. But part of what it matches is noise, which will be different next time, so on new data the curve is worse (1.32 °C against 0.16 °C). The model should be judged by its error on data it was not fitted to.

Intermediate

Exercise 4: Which Mistake?

56 of 300 walking examples were called still: 18.7 %. The rule starts the motor when the state is “still”, so calling a walking robot “still” is the dangerous error (someone is carrying it). Options: move the decision threshold toward “walk” so that borderline cases count as moving (accepting more false “walk” labels for still robots), require “still” for several seconds in a row (like the Stump’s hysteresis), and add a second feature that separates them better.

Exercise 5: Fit and Apply
cal.py MicroPython
c = fit_poly([0.2, 0.4, 0.6, 0.8], [12, 19, 33, 41], 1) print(c) # [1.0, 50.5] print(predict(c, 0.5)) # 26.25 # cal.json: {"coef": [1.0, 50.5]}

The least-squares line is y = 1.0 + 50.5 x (the residuals at the four points are −0.9, 2.2, −1.7 and 0.4), so x = 0.5 gives 26.25. The node needs only the file and the calibrate loop.

Exercise 6: Answer It With SQL

Paper Practice: Answers

Recall

P1. Two Jobs

Calibration (fitting a curve that turns a raw value into a physical one) and classification (choosing a label from a few features).

P2. Overfitting

A model flexible enough to follow the noise in its training data, so it fits those points well and new data badly. Defences: test on data kept out of the fit; collect more data than the model has numbers.

P3. Separate Sessions

Neighbouring samples are nearly identical; a random split puts near-copies in both sets, so the test measures memory, not generalisation.

P4. Events and Samples

Events are rare and explain behaviour: keep them a long time. Samples are plentiful: keep them briefly, then replace them with summaries.

P5. Two Clocks

The node's t (milliseconds since boot) orders messages from one node but restarts at every boot and is not a calendar; the hub's clock gives calendar time accurate to the network delay. Each answers different questions.

Apply

P6. Train Versus Test

Degree 3: lowest error on new data. Degree 7's tiny training error and large test error is overfitting.

P7. Nearest Centroid by Hand

Still: 4 + 1 = 5. Walk: 1 + 0 = 1. Shake: 1 + 9 = 10. Nearest is walk.

P8. Confusion Matrix

(300 + 244 + 233) / 900 = 777 / 900 = 86.3 %. Most common: shake taken for walk (67), then walk taken for still (56).

P9. Class Storage

24 × 10 × 71 ≈ 17 000 B/s; × 86 400 ≈ 1.47 GB per day.

Analyze and Design

P10. Cost of Mistakes

If "still" allows a motor to start, mistaking a carried (walking) robot for a still one could start a motor in someone's hands. Choose models and thresholds by the cost of each mistake, not only the total count.

P11. Works on the Laptop

The input on the board is not scaled exactly as in training (for example the raw ADC value instead of value / 65535). A model is only valid for inputs scaled the same way.

P12. Retention

For example: keep raw messages for 7 days; keep one-minute summaries (mean, min, max, count) per topic for a semester; keep events and state changes indefinitely. Run the deletion as a scheduled daily job, so the disk never fills.
