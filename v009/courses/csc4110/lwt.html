How does a dashboard know a Pico has died? The Pico cannot tell it, because the whole problem is that it can no longer speak. MQTT’s answer is the last will and testament: before it disappears, the Pico leaves a message with the broker to be published on its behalf if it ever vanishes without saying goodbye.

Part 1. The Will

When a client connects it can include a will: a topic, a payload, a retain flag and a QoS. The broker stores it. If the connection later ends without a proper DISCONNECT (a dropped network, a crash, a power cut, a keep-alive timeout), the broker publishes the will itself.

Last will and testament. The Pico hands the broker a message to publish on its behalf if it vanishes; the broker publishes it when the connection dies without a goodbye.
main.py MicroPython
ID = "pico01" ONLINE = ("lab/%s/stat/online" % ID).encode() client = MQTTClient(ID, BROKER_IP, user=ID, password=PASSWORD, keepalive=30) client.set_last_will(ONLINE, b"offline", retain=True) # BEFORE connect() client.connect() client.publish(ONLINE, b"online", retain=True)

set_last_will() only works if called before connect(), because the will is sent as part of the connection request. Notice the pair: the will says "offline", and the first thing the Pico does after connecting is to overwrite it with "online". Both are retained, so the topic always holds the latest truth.

Part 2. When Is It Sent?

When the will is sent. Only a connection that ends without a proper DISCONNECT triggers it, which is exactly what you want from a failure alarm.

A clean client.disconnect() does not send the will. That is deliberate: a planned shutdown is not an emergency. If you want a planned shutdown to show as offline as well, publish "offline" yourself first.

Part 3. An Availability Dashboard

Because the status is retained, one subscription gives a complete and current picture of the whole room, even to a dashboard that has only just started:

An availability dashboard built from retained stat/online topics. A dashboard that starts late still sees every device's last known status immediately.
Pi terminal Shell
mosquitto_sub -h localhost -u dashboard -P pw -v -t 'lab/+/stat/online' # lab/pico01/stat/online online # lab/pico02/stat/online offline

Part 4. How Fast Is It?

The broker notices a dead connection when the keep-alive runs out, which is up to one and a half times the keep-alive you set. A short keep-alive finds failures quickly but means more pings; a long one is cheap but slow to notice. The default of 0 (no keep-alive) means the broker may never notice, and the will will not fire for a long time.

How long it takes to notice. Detection takes up to one and a half times the keep-alive time, so a shorter keep-alive finds failures faster but costs more pings.

Warm Up

Exercise 1: Will or No Will?

(a) no: a clean disconnect. (b) yes, after the keep-alive timeout. (c) yes: the connection simply dies. (d) yes: the reset drops the connection without a DISCONNECT packet.

Exercise 2: How Long?

The broker gives up at 1.5 × 15 = about 22 seconds of silence, then publishes the will. With keepalive=0 there is no timeout, so the broker may not notice for a very long time, depending on when TCP itself gives up.

Intermediate

Exercise 3: Announce a Clean Shutdown
main.py MicroPython
def shutdown(): client.publish(ONLINE, b"offline", retain=True) client.disconnect()

Without the first line, a clean disconnect would leave the retained "online" message in place, and the dashboard would show a device that has gone as still present.

Advanced

Exercise 4: Build the Status Table
dashboard.py MicroPython
status = {} def on_message(topic, msg): device = topic.decode().split("/")[1] now = msg.decode() if status.get(device) != now: status[device] = now print(device, "is now", now)

Because the messages are retained, a dashboard that starts late receives one for every device immediately, so the table fills in without waiting for anything to change.
