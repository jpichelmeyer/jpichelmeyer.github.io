The topics lesson showed one way to package a reading: JSON. This lesson steps back to look at the choices. How you encode a payload affects how big it is, how easy it is to read while debugging, how easy it is to change later, and how much work a tiny processor spends producing it.

Part 1. A Payload Is Just Bytes

MQTT carries a payload as a string of bytes and never looks inside. Everything else, which bytes mean what, is a convention between the sender and every receiver. Turning a value into bytes is called serialization (or encoding); turning the bytes back into a value is deserialization (decoding).

A reading changes form several times between sensor and subscriber. Knowing which form you are holding at each step explains most serialization errors.

Part 2. JSON in More Detail

JSON has a small set of types, and Python values map onto them directly:

PythonJSON
dictobject {"a": 1}
list / tuplearray [1, 2]
strstring, always in double quotes
int / floatnumber
True / False / Nonetrue / false / null

Things that do not serialize: raw bytes, sets, and your own class instances. A tuple comes back as a list. Converting a float to text and back can introduce tiny rounding differences, so do not rely on exact equality after a round trip.

The same reading in four encodings, measured exactly. The terse formats are several times smaller but progressively harder to read and to change.

Verbose JSON is easy to read and to extend, but spends most of its bytes on punctuation and long key names. Compact JSON with short keys is a good compromise. CSV is smaller still but has no labels, so the order of the fields is a hidden rule. A binary format is the smallest, and the hardest to inspect or evolve:

A binary payload is just bytes in an agreed order. Nothing in the data says which byte is which; both ends must share the format string.

Part 3. Choosing

  • Default to JSON. You can read it in a terminal, parse it on any computer, and add fields later without breaking old receivers.
  • Shorten before you go binary. Shorter keys and sensible number precision usually save far more than they cost in readability.
  • Go binary only with a reason, such as a very slow link, a battery you need to stretch, or a very high message rate, and write the format down.

Part 4. Receiving Safely

Any client on the broker can publish anything to your topic, and a message can be cut short or corrupted. A receiver should never assume a payload is well-formed. It should also tolerate formats changing over time, by carrying a version number:

main.py MicroPython
import json def on_message(topic, msg): try: d = json.loads(msg) value = d["value"] if d.get("v", 1) == 1 else d["val"] except (ValueError, KeyError): print("ignored bad message", msg) return handle(value)

Part 5. Text Is Bytes Too

.encode() turns text into UTF-8 bytes. For plain English letters and digits that is one byte per character, but a symbol such as the degree sign takes two bytes, so "\u00b0C".encode() is three bytes long. Count bytes, not characters, when you are budgeting message size.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: What Does It Cost?

51 × 3600 = 183,600 bytes (about 184 KB) per hour; 16 × 3600 = 57,600 bytes (about 58 KB) per hour. The terser format uses under a third of the traffic.

Exercise 2: Parse the CSV
main.py MicroPython
value, unit, t = msg.decode().split(",") value = int(value) t = int(t) print(value, unit, t)

.decode() turns bytes into text, .split(",") breaks it into fields, and int() converts the numeric ones. Every field arrives as text.

Intermediate

Exercise 3: Pack and Unpack
main.py MicroPython
import struct packed = struct.pack("<HBI", 41230, 1, 123456) print(len(packed), packed) # 7 bytes value, unit, t = struct.unpack("<HBI", packed) print(value, unit, t)

Both ends must agree on the format string "<HBI" exactly; the bytes carry no labels at all.

Advanced

Exercise 4: Plan for Change
main.py MicroPython
import json def parse(msg): d = json.loads(msg) if d.get("v", 1) == 1: # no "v" field means version 1 return d["value"] return d["val"] # version 2 print(parse(b'{"value": 5}')) print(parse(b'{"v": 2, "val": 5}'))

The receiver is the part you cannot easily update on every device at once, so make it tolerant. A format with no version field is hard to evolve without breaking someone.

Checkpoint

Before moving on, make sure you can:

  1. Explain the difference between a value, its serialized form, and the bytes that cross the network.
  2. Say which Python types JSON can and cannot represent.
  3. Compare JSON, CSV and a binary struct for size, readability and ease of change.
  4. Write a receiver that rejects malformed messages and tolerates a format version change.
