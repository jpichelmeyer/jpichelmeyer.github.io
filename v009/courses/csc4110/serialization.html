This lesson covers how a measurement becomes bytes and back. You compare JSON, CSV and binary encodings of the same data, learn fixed-point scaling and version bytes, see how batching brings a 50 Hz sensor inside the class message limit, and write a decoder that never crashes on bad input.

MQTT carries bytes and has no opinion about what they mean. Somebody has to decide how a temperature, a timestamp and a sequence number become bytes at one end and numbers again at the other. That decision, serialization, sets the size of every message, how much work the Pico does to build and read it, and how hard the format is to change later. We have used JSON because you can read it. This lesson measures what that costs and what the alternatives buy.

Part 1. Same Data, Five Sizes

One accelerometer sample: a version number, a sequence number, a time, and three accelerations in g. The program below builds it three ways. Run it in a PC Python and on the Pico; the byte counts are the same.

formats.py MicroPython
import json import struct # One sample: the envelope (version, sequence number, time) and three accelerations in g. def to_json(seq, t, ax, ay, az): return json.dumps({"v": 1, "seq": seq, "t": t, "ax": round(ax, 2), "ay": round(ay, 2), "az": round(az, 2)}).encode() def to_csv(seq, t, ax, ay, az): return ("1,%d,%d,%.2f,%.2f,%.2f" % (seq, t, ax, ay, az)).encode() # Binary: acceleration as whole milli-g in a signed 16-bit integer (resolution 0.001 g). REC = "<BHIhhh" # version, seq, t, ax, ay, az; little-endian, no padding def to_bin(seq, t, ax, ay, az): return struct.pack(REC, 1, seq & 0xFFFF, t & 0xFFFFFFFF, round(ax * 1000), round(ay * 1000), round(az * 1000)) def from_bin(buf): if len(buf) != struct.calcsize(REC): raise ValueError("wrong length") v, seq, t, ax, ay, az = struct.unpack(REC, buf) if v != 1: raise ValueError("unknown version") return {"seq": seq, "t": t, "ax": ax / 1000, "ay": ay / 1000, "az": az / 1000}
The same sample in five encodings: 68, 57, 52, 26 and 13 bytes. The binary record is a fifth of the JSON message, and what it gives up is the ability to read it with your eyes.

The binary version works because both ends agree on a layout: one byte of version, two of sequence number, four of time, and three signed 16-bit integers for the accelerations, 13 bytes in all. There are no keys, no quotes, no digits spelled out. struct.pack and struct.unpack convert between Python values and exactly those bytes. The format string "<BHIhhh" is the whole definition: < means little-endian with no padding, B is one unsigned byte, H two, I four, h a signed two-byte integer.

The 13 bytes of the binary record. Reading a stream of these requires the table above: byte 0 is the version, bytes 1–2 the sequence number, and so on. The table is the contract.

Part 2. Numbers, Not Text

Two things make text expensive. The first is the digits themselves: a time of 34120 is five characters but fits in two bytes if it is small enough, and four in any case. The second is floating-point noise: 0.019775390625 is what a float prints as when it came from an ADC count divided by 4096, and it costs 14 characters where 0.02 costs 4. Rounding before sending (round(x, 2)) is the cheapest saving in the course, and it also shows what precision the sensor really has. In the binary record the same idea appears as fixed point: the acceleration is stored as a whole number of milli-g, so 0.98 g becomes the integer 980, and the receiver divides by 1000. A signed 16-bit integer holds ±32.767 g, far more than the ±2 g or ±16 g range of the MPU6050, with a resolution of 0.001 g, finer than the sensor’s noise.

That is the same reasoning as the ADC lesson: choose the number of bits by the precision the measurement deserves, not by the width of the variable it happens to sit in.

Part 3. Choosing

How the formats compare. A rule that serves well: use JSON for anything a human will read or that happens occasionally (commands, events, status), and binary for steady high-rate data that only programs read.

A mismatch is the danger of binary. If the sender and receiver disagree about the layout, the receiver does not get an error: it gets numbers, and they are wrong. This is why the first byte of the record is a version. A receiver that sees a version it does not know should discard the message, not guess. A format with no version byte cannot be changed without breaking every reader at once.

Part 4. Fewer, Bigger Messages

Now the payoff. An IMU read at 50 Hz is 50 samples a second. Sent as one JSON message each that is 3,400 bytes per second and 50 messages per second, five times the class limit of 10. Packing ten consecutive samples into one binary message, with a header that gives the time of the first and the interval between them, needs only 5 messages a second and 70 bytes each, 350 bytes per second. The receiver reconstructs every sample’s time from the header, so nothing is lost but the per-message overhead.

batch.py MicroPython
import struct HEAD = "<BHIHB" # version, seq, time of first sample, ms between samples, count SAMPLE = "<hhh" # ax, ay, az in milli-g def pack_batch(seq, t0, dt_ms, samples): """samples: list of (ax, ay, az) in g. One message instead of len(samples).""" out = bytearray(struct.pack(HEAD, 1, seq & 0xFFFF, t0 & 0xFFFFFFFF, dt_ms, len(samples))) for ax, ay, az in samples: out += struct.pack(SAMPLE, round(ax * 1000), round(ay * 1000), round(az * 1000)) return bytes(out) def unpack_batch(buf): hs = struct.calcsize(HEAD) v, seq, t0, dt, n = struct.unpack(HEAD, buf[:hs]) if v != 1 or len(buf) != hs + n * struct.calcsize(SAMPLE): raise ValueError("bad batch") rows = [] for i in range(n): ax, ay, az = struct.unpack_from(SAMPLE, buf, hs + i * 6) rows.append((t0 + i * dt, ax / 1000, ay / 1000, az / 1000)) return seq, rows
The same 50 Hz IMU stream sent two ways. Batching ten samples per message brings it under the class message limit and cuts the bytes by almost ten times. The price is latency: the first sample of a batch waits up to 180 ms before it leaves the board.

That last sentence is the real engineering trade. Batching saves overhead but delays data, so it is right for logging and analysis and wrong for a control loop that needs the newest value now. Week 14 returns to this under latency.

Part 5. Trust Nothing You Receive

Everything arriving from the network is input from outside your program: it may be truncated, from the wrong version, or not what you thought. A receiver that crashes on a bad packet lets any other node take it down. The decoder below turns bytes into a dictionary or None, and never raises an exception. Callers check for None and carry on.

decode.py MicroPython
import json def decode(payload): """Turn bytes from the network into a dict, or None. Never raises.""" try: d = json.loads(payload) except (ValueError, TypeError): return None # not JSON at all if not isinstance(d, dict) or d.get("v") != 1: return None # not an object, or a version we do not know if not isinstance(d.get("seq"), int) or not isinstance(d.get("t"), int): return None # the envelope is incomplete return d

Notice what it checks: it is JSON; it is an object (not a list or a number); the version is one we know; the envelope fields have the right types. It does not yet check ranges (is this roll angle possible?) or that the fields for this particular topic are present; that is the job of the contract in Week 11. The habit starts here.

Finally, measure. Run the benchmark on your Pico and write down the four times; they depend on the firmware version, and you should use your numbers, not anyone’s claims, for decisions about whether the processor or the network is the bottleneck in your node.

bench.py MicroPython
from time import ticks_us, ticks_diff from formats import to_json, to_bin, from_bin import json def time_it(f, n=200): t0 = ticks_us() for _ in range(n): f() return ticks_diff(ticks_us(), t0) / n # microseconds per call j = to_json(17, 34120, 0.02, -0.01, 0.98) b = to_bin(17, 34120, 0.02, -0.01, 0.98) print("json pack %6.0f us unpack %6.0f us %d bytes" % ( time_it(lambda: to_json(17, 34120, 0.02, -0.01, 0.98)), time_it(lambda: json.loads(j)), len(j))) print("bin pack %6.0f us unpack %6.0f us %d bytes" % ( time_it(lambda: to_bin(17, 34120, 0.02, -0.01, 0.98)), time_it(lambda: from_bin(b)), len(b)))

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Struct Size

"<BHIhhhhhh": 1 + 2 + 4 + 6 × 2 = 19 bytes. You can confirm with struct.calcsize("<BHIhhhhhh"). Without the < the library may insert padding bytes to align values, and the size would not match what the receiver expects.

Exercise 2: Fixed Point

round(−0.0734 × 1000) = −73. The receiver divides by 1000 and gets −0.073 g, an error of 0.0004 g, well below the sensor’s noise. In whole g the value would round to 0 and the whole signal, which is nearly all between −1 and +1, would be lost; the choice of unit sets the resolution, so choose the unit that makes the smallest interesting change at least one count.

Intermediate

Exercise 3: Pick Formats

(a) JSON: rare, hand-typed, must be readable and self-describing. (b) Binary batches: steady, high-rate, only programs read it; 100 Hz of JSON would break the message limit alone. (c) JSON: an event is rare, and its fields (what, where, how far) will evolve. (d) JSON: the saving would be a few bytes a minute, and human-readable is worth more. The pattern: bytes matter only where the rate is high.

Advanced

Exercise 4: Wrapping Sequence Numbers
missing.py MicroPython
def missing(prev, seq): """How many messages were skipped between two arrivals (16-bit sequence numbers).""" return (seq - prev - 1) & 0xFFFF print(missing(10, 11)) # 0 consecutive print(missing(10, 14)) # 3 11, 12, 13 were lost print(missing(65534, 1)) # 2 65535 and 0 were lost print(missing(65535, 0)) # 0 a normal wrap

Subtracting and masking with 0xFFFF performs the arithmetic modulo 65,536, so the wrap needs no special case: 1 − 65534 − 1 = −65534, and −65534 & 0xFFFF = 2. The same trick works for the millisecond clock, where ticks_diff does it for you. The one thing it cannot do is tell a loss of 65,536 messages from none at all, so keep the interval between arrivals short enough that this cannot happen.
