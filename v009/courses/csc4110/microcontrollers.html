Last lesson drew a rough line between "a computer" (the Pi 3B+) and "a microcontroller" (the Pico WH). This lesson makes that line precise: what's actually on a microcontroller, what isn't, and why those specific omissions are exactly what make it good at the one job this course needs it for, sitting physically next to a sensor or motor and talking to it directly.

Part 1. What's Inside the Pico WH

The Pico WH is built around a single chip, the RP2040: two small ARM processor cores, 264 KB of RAM, and essentially nothing else baked in, no graphics, no storage, no networking. Everything the board can do beyond raw computation comes from a few other chips soldered around it:

Everything on the board exists to support the RP2040: flash memory because the chip itself has none, a WiFi/Bluetooth chip because the RP2040 has no radio, and a row of GPIO pins because the whole point is to reach out into the physical world.

Three things from that diagram matter immediately:

  • The flash is separate from the RAM. Your saved main.py lives in flash (2 MB, survives power loss); variables and running state live in the 264 KB of RAM (gone the instant power drops). That's why last lesson's script kept blinking after a reboot, it was never "running" in some persistent sense, it was re-read from flash and re-executed from scratch every single time the board powered on.
  • "W" and "H" in the name are both real hardware. Without the W, there'd be no WiFi chip at all, no way to reach the MQTT broker later this unit. Without the H, you'd be soldering your own header pins on before a breadboard could touch this board.
  • GPIO is the entire interface to the physical world. No screen, no keyboard, no mouse. Every sensor reading in, every LED or motor signal out, happens through those 26 pins. Next lesson is entirely about how.
A Pico WH from above, USB at the top. Everything on it exists to support the one RP2040 chip: flash memory (because the RP2040 has none of its own), a WiFi/Bluetooth radio, a crystal to keep time, and a header of pins to reach the outside world.
Two kinds of memory on the board. Anything saved as a file lives in flash and survives a reboot; anything that is only a variable in running code lives in RAM and does not.

Part 2. Microcontroller vs. Single-Board Computer, For Real This Time

The Pi 3B+ you'll use later this unit as an MQTT broker is built differently on purpose. It runs a full Linux operating system from an SD card, manages dozens of processes at once, and has enough RAM (1 GB, roughly 4,000× the Pico's) to not think twice about it. That's exactly what a broker needs: something that can stay up, juggle many connections, and not care if one client misbehaves.

A microcontroller gives up all of that generality for something a full OS can't offer: a program that starts running within milliseconds of getting power, with completely predictable timing, and draws so little power it can run for days on a battery pack. That trade is the whole reason IoT devices are usually built on microcontrollers rather than tiny Linux computers, even though a Pi could technically do everything a Pico does.

A process on the Pi is one of many things the OS is juggling. On the Pico, your script isn't a process inside anything, it is the whole running system.

Part 3. Reading a Datasheet: GPIO Numbering

GPIO pins on the Pico are numbered GP0 through GP28 (not every number is physically present as a usable pin), and in MicroPython you refer to them by that number, not by their physical position on the board:

Pico WH pinout. Pins are numbered 1–40 by position (inside the board); MicroPython code uses the GP names. Only the orange pins can read analog voltages, and every GPIO pin is 3.3 V.
shell MicroPython
>>> from machine import Pin >>> p = Pin(15, Pin.OUT) # this is GP15, not "the 15th pin on the board" >>> p.value(1) # drive it HIGH (3.3V) >>> p.value(0) # drive it LOW (0V)

One detail worth flagging now because it causes real confusion later: on a plain (non-wireless) Pico, the onboard LED is Pin(25, Pin.OUT), a regular GPIO pin. On the Pico W and WH you're using, GP25 is busy talking to the CYW43439 chip instead, so the onboard LED moved to a special pin only reachable by name: Pin("LED", Pin.OUT), exactly what last lesson's blink script used. Code copied from an older Pico tutorial that says Pin(25, ...) for the LED will run without error on your board, it just won't control the LED, because GP25 means something different here.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Computer or Microcontroller?

The Pi has a full operating system (with many processes at once) and a lot more memory (1 GB versus 264 KB); it also has a filesystem on an SD card, HDMI, and USB ports. The Pico wins on instant, predictable start-up, very low power draw, and being cheap enough to dedicate to a single sensing job.

Exercise 2: Read the Pinout

(a) 3V3 (OUT) is physical pin 36. (b) GND at physical pin 18 sits right above GP14/GP15. (c) ADC0 is GP26, physical pin 31. Remember: MicroPython code uses the GP number (Pin(26)), never the physical pin number.

Intermediate

Exercise 3: How Much RAM?
shell MicroPython
import gc gc.collect() # tidy up first so the numbers are stable before = gc.mem_free() data = list(range(1000)) after = gc.mem_free() print(before, after, before - after)

The difference comes out close to 4,000 bytes: about 4 bytes per list slot (small integers are stored directly in the slot, not as separate objects). On a board with only 264 KB, that is why you cannot just keep every reading forever.

Advanced

Exercise 4: Why Doesn't It Blink?

On the Pico W/WH, GP25 is wired to the WiFi chip (CYW43439), not to an LED, so toggling it does nothing visible. The onboard LED hangs off the radio chip instead and is addressed by name. Fix 1: use Pin("LED", Pin.OUT). Fix 2: wire an external LED and resistor to a free GPIO such as GP15 and use Pin(15, Pin.OUT).
