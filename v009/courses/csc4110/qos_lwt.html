This lesson covers the two MQTT tools that matter most for robots that come and go. Retained messages hold the latest state for late subscribers, and are wrong for commands. The last will turns a node’s death into a message, and its detection delay follows directly from the keepalive. A short note on quality of service explains why the class sends almost everything at QoS 0.

SAM lens. Retained messages are Memory kept by the environment; the last will is the environment speaking for an agent that can no longer act. QoS decides how reliably one agent's Actuator reaches another's Perceptor.

A message crossing a WiFi link can be lost, duplicated, delayed or reordered by the network, and the node at either end can die in the middle of a conversation. MQTT gives you three tools for dealing with the unreliability and the dying: quality of service levels to control delivery, retained messages to keep the latest state, and the last will to announce a death. Each is easy to switch on and easy to misuse, and the class conventions say which to use where.

Part 1. A Word on Quality of Service

Every publish carries a quality of service (QoS) level. At QoS 0 a message is sent once and may be lost. At QoS 1 the sender repeats it until the broker acknowledges it, so it may arrive twice. The class sends almost everything at QoS 0, for a reason specific to the Pico: in umqtt.simple a QoS 1 publish does not return until the acknowledgement arrives, and it has no timeout of its own, so one lost packet can freeze a control loop. Reliability where it matters comes from the application instead: the ids and acks of the Topics and commands lesson already give you a command that is retried until answered and never carried out twice, and they never block. The one exception is presence (stat/online, Part 3), which is rare and outside any control loop.

Part 2. Retained Messages

A message published with the retain flag is stored by the broker, one per topic, and delivered to every client that subscribes to a matching filter afterwards, immediately, before anything else. That solves a real problem: a dashboard that opens at noon would otherwise have to wait for the next state change to learn what a robot is doing. Publishing an empty retained message to the topic deletes the stored one.

Retained delivery. The dashboard learns the node’s current state the instant it subscribes, without the node doing anything. The node’s own message, published an hour earlier, is the one it receives.

Retain is for state: things that are true until changed. It is wrong for events (a stale “door opened” would look like news), and dangerous for commands, as the next figure shows.

A retained command is a command that repeats itself. This sequence was run on the class’s test broker: after the reboot the node acted on the stale “on”. A command should be sent without retain, with an id, and with a short life.
presence.py MicroPython
import hub h = hub.Hub(keepalive=30) h.presence() # will: offline (retained). On every connect: online (retained). h.on(h.mine("cmd/#"), lambda topic, payload: None) def shutdown(): h.close() # publishes offline itself, then disconnects cleanly # Retained state, the sensible way: on change, once. def set_led(on): h.publish("stat/led", {"on": on}, retain=True)

Two cautions. A wildcard subscription receives every matching retained message at once, in a burst (twelve students’ stat/online arriving together), so the bounded dispatch in hub.py matters. And a retained message outlives its publisher: it describes the last time the node spoke, not necessarily now, which is the reason for the next tool.

Part 3. The Last Will

When a client connects it may register a will: a topic, a payload and a retain flag that the broker publishes on the client’s behalf if the client disappears without saying goodbye. The broker decides the client is gone when it has heard nothing for 1.5 times the keepalive, or when the TCP connection breaks. The pattern is two retained messages on one topic, stat/online: the node publishes online: true after connecting, and the broker publishes online: false for it when it dies. Whoever reads the topic always sees the truth, or at least the truth as of the last packet.

A clean disconnect is not a death, so the will is not published. A node that shuts down on purpose must therefore publish its own offline message first, which is what Hub.close() does. A node that is only rebooting should usually do the same, so that the “offline” blip is honest.

How long a death takes to be noticed. From a failure at a random moment, with the node pinging every half keepalive, detection takes between one and one and a half keepalives (measured on the class test broker, 12 random failures per setting). Halving the keepalive halves the delay.
The keepalive trade. A ping and its reply are four bytes, so the traffic is trivial; the real cost of a short keepalive is that the radio wakes more often, which matters on a battery. Choose it from how fast anyone needs to know: 30 seconds is the class default.

To measure it on real hardware, watch the status topic with timestamps and pull the power on a node: mosquitto_sub -t "lab/+/stat/online" -F "%I %t %p" prints the time of each change. The difference between the moment you pulled the plug and the “false” line is your detection delay.

Warm Up

Exercise 1: Choose the Settings

(a) QoS 0, not retained: the next reading replaces a lost one. (b) QoS 0, not retained, with a seq so a receiver can notice a gap (an event that matters can also be acknowledged). (c) QoS 0, never retained, with an id so the sender can retry and the robot can ignore repeats. (d) retained, QoS 0 or 1: a new reader needs the current mode. (e) retained, QoS 1, paired with a last will that publishes “offline”.

Exercise 2: Detection Window

The last packet the broker heard was between 0 and 10 s before the failure (the ping interval). The broker waits 1.5 × 20 = 30 s from that packet. So the will comes between 30 − 10 = 20 s and 30 s after the failure. In general: between keepalive and 1.5 × keepalive when pinging at half the keepalive.

Intermediate

Exercise 3: The Repeating Command

First, as in Figure 4: any time the robot reconnects (after a reboot, a WiFi drop or the broker restarting) the broker re-delivers the stored command and the robot obeys a request that is minutes or hours old. Second, the retained command also reaches anyone else who subscribes with a matching wildcard, such as a second robot or a logger, which may act on it. Instead publish the command without retain, give it an id, and let the controller retry until the ack arrives. If a robot must start in a particular position after a reboot, make that its own startup behavior, or have it read a retained stat topic of what it last did.

Advanced

Exercise 4: Predict the Delay
detect.py MicroPython
def detect_window(keepalive, ping_every): """Seconds from failure to will, for a node that sends something at least every ping_every s.""" deadline = 1.5 * keepalive # the broker's patience, counted from the last packet return deadline - ping_every, deadline # the last packet was 0..ping_every seconds before the failure print(detect_window(10, 5), detect_window(30, 15), detect_window(60, 30), detect_window(30, 30)) # (10.0, 15.0) (30.0, 45.0) (60.0, 90.0) (15.0, 45.0)

The first three match the measured ranges in the figure. With a ping every 30 s on a keepalive of 30 s the window widens to 15–45 s, because the node uses up more of the broker’s patience between packets. Pinging every 50 s is worse than that: 50 s exceeds the broker’s 45-second deadline, so detect_window would give a negative shortest time, which means the broker declares a perfectly healthy node dead and publishes its will. A node must always send something well inside the keepalive; half is the standard choice.

Paper Practice: Answers

Recall

P1. QoS Levels

Possible loss (QoS 0: at most once) against possible duplication (QoS 1: at least once).

P2. Blocking Publish

It blocks until the PUBACK arrives, with no timeout of its own; one lost packet can freeze the control loop.

P3. Retained

It stores the last retained message on each topic and delivers it immediately to every new subscriber whose filter matches. Publishing an empty retained message to the topic deletes it.

P4. Will

A topic, payload and retain flag the client registers when it connects. The broker publishes it if the client disappears without a clean disconnect: after 1.5 keepalives of silence or when the TCP connection breaks.

Apply

P5. Detection Window

Between 1 and 1.5 keepalives: 30 to 45 s after the failure, depending on when in the ping cycle it happens.

P6. Halve It

Worst case is 1.5 × keepalive, so keepalive ≤ 13 s (say 12 s). A ping and reply are 4 bytes, so traffic is trivial; the radio wakes more often, which matters only on a battery.

Analyze and Design

P7. Retained Command

On subscribing after the reboot, the node immediately receives the stale "on" and acts on it, although nobody wants it now. Commands must be sent without retain, with an id and a short life.

P8. Presence Pattern

The node publishes online: true retained after connecting; its will is online: false retained, published by the broker if the node dies. A clean disconnect does not trigger the will, so a node shutting down on purpose publishes online: false itself first; otherwise the retained true would stay forever.

P9. Application Reliability

Ids and acks give at-least-once delivery with duplicates removed, which QoS 1 alone does not; they work over QoS 0, never block, and confirm the receiving program actually handled the message, not just that the broker got it.

P10. Choose Settings

(a) QoS 0, not retained. (b) QoS 1 (rare, outside the control loop), retained. (c) QoS 0, not retained, with id and ack. (d) QoS 0, not retained.
