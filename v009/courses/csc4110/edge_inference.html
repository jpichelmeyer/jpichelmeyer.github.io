Last lesson you trained models on the hub from recorded data. This lesson puts them to work on the robot. You decide where inference should happen (on the node, at the hub, or split between them) by working out the link budget and measuring the time budget. You add two more model families that fit on a Pico: a decision tree written out as plain code and a small neural network run from a file of numbers. Then you measure what each one costs on your own board, and ship models from the hub to the robot safely. This is the TinyML half of Lab 8 and of Lab Practical 2.

Part 1. A Model Is a Stage of the Perceptor

As the architectures lesson argued, a classifier on a robot is a learned synthetic sensor: the last stage of the Perceptor. The picture to keep in mind is a funnel. Raw samples go in at a high rate, and each stage turns many numbers into fewer, more meaningful ones. By the time the label reaches the Decider (or the network), the data has shrunk by a factor of hundreds.

The inference funnel for a gesture classifier on a 50 Hz IMU. Box heights suggest how much data passes each stage. The model (gold) is a learned stage; the others are written by hand. Where you cut this funnel to cross the network is the placement decision of Part 2.

Part 2. Where Should Inference Happen?

Every computation happens somewhere: on the node (the edge, beside the sensor and the motor) or at the hub, which sees every node but is a network hop away. The edge is fast and keeps working without a network, but it is small. The hub is large but late. You choose where each job goes with budgets: bytes per second on the link, milliseconds per pass of the loop, bytes of RAM. Here is the link budget for three places to cut the funnel:

budget.py Python
# budget.py -- the link budget of three placements for one 50 Hz IMU TOPIC, HDR = 20, 5 # topic bytes, MQTT header bytes (about) def rate(msgs_per_s, payload): return msgs_per_s * (TOPIC + payload + HDR) raw = rate(50, 95) # every sample: {"v":1,"seq":..,"t":..,"ax":..,...,"gz":..} features = rate(2, 130) # 6 features every 0.5 s labels = rate(0.4, 45) # a label when it changes (~0.2/s) + a 5 s heartbeat print(raw, features, labels) # 6000 310 28.0
Three placements for the same gesture classifier (computed above, with the class broker's JSON envelope). Plan C sends one two-hundredth of plan A's traffic and is the only one that still classifies when the WiFi drops. Plan A is not wrong: it is the plan for collecting training data, when the hub needs every sample. A good system often uses both, raw bursts on request and labels all the time.

The rule of thumb that falls out: train where the data and the compute are (the hub), infer where the decision is needed (the edge). Plan C needs the model to fit in the node's time and memory budgets, which is what the rest of this lesson measures.

Part 3. The Time Budget, Measured

Time is the budget you cannot compute from a datasheet; you must measure it on the board. A 50 Hz loop has 20 ms per pass. This small profiler wraps any call, keeps the average and the worst case, and reports them as a share of the loop. Use it on every new piece of code you put in a loop.

profile.py MicroPython
# profile.py -- measure what a piece of code costs on THIS board from time import ticks_us, ticks_diff class Cost: def __init__(self): self.n = 0 self.total = 0 self.worst = 0 def run(self, fn, *a): t = ticks_us() r = fn(*a) d = ticks_diff(ticks_us(), t) self.n += 1 self.total += d if d > self.worst: self.worst = d return r def report(self, name, period_ms): avg = self.total // max(self.n, 1) print("%s: avg %d us, worst %d us, %.1f%% of a %d ms loop" % (name, avg, self.worst, 100.0 * avg / (period_ms * 1000), period_ms))
Inference makes the loop lumpy. Most ticks only sample; every half second one tick also computes features and runs the model. The numbers in the zoom are a plan to check against your profiler, not a measurement. If the heavy tick runs past 20 ms, the next sample is taken late, and late samples are uneven samples, which the sampling lesson showed is a source of error.

If the heavy tick does not fit, there are two fixes, in the order to try them. Shrink the work: fewer features, a smaller model (Part 4). Spread it out: update running sums on every sample so that features cost almost nothing at the end of the window, or compute features on one tick and run the model on the next.

Part 4. Models That Fit

Four model families cover almost everything a Pico should run. To compare them fairly, each was trained on the same synthetic gesture dataset: 2-second IMU windows of four gestures (still, tap, shake, tilt) generated with realistic noise, six features per window, 240 windows for training and 400 for testing. Your own recordings will be messier and your accuracies lower; the point is the comparison, not the numbers.

Four models on the same synthetic data. The stump cannot tell four classes apart (it answers one yes-or-no question), so it has no accuracy here; it remains the right model for “moving or still”. The others are close on this easy data, which is typical: the bigger model buys a little accuracy at a cost in memory, time and readability.

The stump is where you started: one feature, one threshold, with hysteresis against flicker. Keep it for any two-way question.

model.py MicroPython
# model.py -- the smallest model: one comparison, with a margin against flicker import json class Stump: def __init__(self, path="model.json", margin=0.1): m = json.load(open(path)) self.t = m["threshold"] self.margin = margin self.state = 0 def update(self, x): if self.state == 0 and x > self.t * (1 + self.margin): self.state = 1 elif self.state == 1 and x < self.t * (1 - self.margin): self.state = 0 return self.state

A decision tree asks a short sequence of threshold questions, choosing at each step the feature and threshold that best separate the classes. Its great virtue on a microcontroller is that it can be written out as ordinary code: no model file, no library, a few comparisons per inference, and a human can read exactly what it learned.

export_tree.py Python
# export_tree.py -- on the laptop: train a small tree and write it out as MicroPython from sklearn.tree import DecisionTreeClassifier def tree_to_python(clf, names): t, labels = clf.tree_, [str(c) for c in clf.classes_] lines = ["def classify(f):"] def leaf_label(n): # the label if every leaf below n agrees, else None if t.children_left[n] == -1: return labels[int(t.value[n][0].argmax())] a, b = leaf_label(t.children_left[n]), leaf_label(t.children_right[n]) return a if a == b else None def rec(n, depth): ind = " " * depth if leaf_label(n) is not None: lines.append(f"{ind}return {leaf_label(n)!r}") else: lines.append(f"{ind}if f[{t.feature[n]}] <= {t.threshold[n]:.4g}: # {names[t.feature[n]]}") rec(t.children_left[n], depth + 1) lines.append(f"{ind}else:") rec(t.children_right[n], depth + 1) rec(0, 1) return "\n".join(lines) NAMES = ["a_mean", "a_std", "a_range", "jerk_max", "g_mean", "g_std"] # X_train: one row of 6 features per 2 s window; y_train: 'still', 'tap', 'shake', 'tilt' tree = DecisionTreeClassifier(max_depth=3).fit(X_train, y_train) open("tree_model.py", "w").write(tree_to_python(tree, NAMES))
tree_model.py MicroPython
def classify(f): if f[2] <= 0.3914: # a_range if f[5] <= 5.388: # g_std return 'still' else: return 'tilt' else: if f[4] <= 15.43: # g_mean if f[5] <= 12.49: # g_std return 'tap' else: return 'tilt' else: return 'shake'
The same tree as a picture. It learned something physically sensible: a small range of acceleration means the board is not being jolted (still or slowly tilting, separated by how much it rotates), while a big range means a tap or a shake, separated by how much rotation goes with it. Reading a model like this is the best check that it learned the gesture and not an accident of your recordings.

A small neural network (a multilayer perceptron) is a stack of layers, each computing weighted sums of its inputs followed by a simple nonlinearity. A 6-8-4 network has 6 inputs (the features), one hidden layer of 8 neurons, and 4 outputs (one score per class). It stores 92 numbers and does 80 multiply-adds per inference. It is harder to read than a tree, but it draws curved boundaries between classes where a tree can only draw axis-aligned steps, and it is the same structure that, scaled up, runs speech and image models.

The 6-8-4 network. Every line is one stored weight: 48 into the hidden layer and 32 into the outputs, plus one bias per neuron, 92 numbers in all. Inference is just these weighted sums, layer by layer, which is why the whole thing fits in twenty lines of MicroPython.

Training happens on the laptop with scikit-learn; what crosses to the node is a JSON file of numbers. Note that the scaling travels with the weights: the network was trained on standardised features, so the node must standardise them in exactly the same way, or it will be fed numbers it has never seen.

export_mlp.py Python
# export_mlp.py -- on the laptop: train a 6-8-4 network and write model.json import json from sklearn.neural_network import MLPClassifier from sklearn.preprocessing import StandardScaler scaler = StandardScaler().fit(X_train) # remember the scaling: the node needs it mlp = MLPClassifier(hidden_layer_sizes=(8,), max_iter=3000).fit(scaler.transform(X_train), y_train) layers = [] for W, b in zip(mlp.coefs_, mlp.intercepts_): # sklearn stores W as n_in x n_out layers.append({"n_in": W.shape[0], "n_out": W.shape[1], "W": [round(float(v), 5) for v in W.T.ravel()], # row j = weights into neuron j "b": [round(float(v), 5) for v in b]}) json.dump({"version": 1, "labels": [str(c) for c in mlp.classes_], "features": NAMES, "mu": list(scaler.mean_), "sd": list(scaler.scale_), "layers": layers}, open("model.json", "w"))
mlp.py MicroPython
# mlp.py -- run a small trained network on the Pico (pure MicroPython, no libraries) import json from array import array class MLP: def __init__(self, path="model.json"): d = json.load(open(path)) self.version, self.labels = d["version"], d["labels"] self.mu, self.sd = array("f", d["mu"]), array("f", d["sd"]) # scaling from training self.layers = [(L["n_in"], L["n_out"], array("f", L["W"]), array("f", L["b"])) for L in d["layers"]] # 4 bytes per number def predict(self, features): x = [(f - m) / s for f, m, s in zip(features, self.mu, self.sd)] last = len(self.layers) - 1 for k, (n_in, n_out, W, b) in enumerate(self.layers): y = [] for j in range(n_out): acc, row = b[j], j * n_in for i in range(n_in): acc += W[row + i] * x[i] y.append(acc if k == last or acc > 0 else 0.0) # ReLU on hidden layers x = y best = max(range(len(x)), key=lambda j: x[j]) return self.labels[best], x

Weights are held in array("f"), 4 bytes each, rather than in Python lists, where every float is a separate object costing several times more. Run on the laptop against the 400 test windows, this class gives exactly the same labels as scikit-learn (100 % agreement), which is the check to do before trusting any hand-written inference code.

Part 5. Measure It on Your Board

Accuracy is measured on the laptop; cost must be measured on the Pico. This script reports the RAM the model takes and the time per inference for the tree and the network.

bench.py MicroPython
# bench.py -- on the Pico: what does the model cost on THIS board? import gc from time import ticks_us, ticks_diff from mlp import MLP from tree_model import classify gc.collect(); free0 = gc.mem_free() model = MLP("model.json") gc.collect(); print("model RAM:", free0 - gc.mem_free(), "bytes; free now:", gc.mem_free()) f = [1.0, 0.09, 0.9, 0.85, 4.3, 4.3] # one feature vector (a 'tap') for name, fn in (("tree", classify), ("mlp", model.predict)): t0 = ticks_us() for _ in range(100): fn(f) print(name, ticks_diff(ticks_us(), t0) / 100, "us per inference")

Write your numbers into the table for Lab 8. Expect the tree to take tens of microseconds and the network somewhere around a millisecond in pure MicroPython; your measurement is the only number that counts. Then compare with the budget: one inference every 0.5 s costing 1 ms is 0.2 % of the processor, which is nothing. The same network run on every 20 ms sample would be 5 %, still affordable. A network ten times bigger on every sample would not be. That is the alignment between processing and data rate that this course keeps asking you to analyse.

Part 6. Shipping a Model from Hub to Robot

Models change: you record more data, retrain, and want the new version on every robot of that role. A model file is configuration, and it deserves the same care as any message that changes a robot's behaviour.

The model update loop. The hub trains and tests; the robot validates before it trusts. A model that fails a check is refused and the old one stays in use, so a bad upload degrades nothing. The robot announces the version it is running, so the hub (and you, in the lab report) always know which model produced which labels.

The fourth check is the cheapest and catches the most: the hub puts one feature vector and its expected label into the file, and the robot runs it before accepting the model. A mismatch means a scaling or ordering error, the commonest TinyML bug of all (“it works on the laptop and not on the board”), and it is caught before the model ever sees a real sample.

Exercise 3: Does It Fit?

Average heavy tick: 0.9 + 4.2 + 2.8 + 3.5 = 11.4 ms, under 20 ms. Worst case: 0.9 + 4.2 + 2.8 + 9 = 16.9 ms, which fits but leaves only 3 ms of slack, and any other slow call breaks it. Exercise 4: Validate Before You Trust
accept.py MicroPython
def accept(model, current_version, n_features, predict): """predict(model, f) -> label. Returns (ok, reason).""" if model.get("version", 0) <= current_version: return False, "not newer" if len(model.get("mu", [])) != n_features or len(model.get("sd", [])) != n_features: return False, "feature count mismatch" n_in = n_features for L in model.get("layers", []): if L["n_in"] != n_in or len(L["W"]) != L["n_in"] * L["n_out"] or len(L["b"]) != L["n_out"]: return False, "layer sizes inconsistent" n_in = L["n_out"] if n_in != len(model.get("labels", [])): return False, "output size != number of labels" t = model.get("test") if not t or predict(model, t["f"]) != t["label"]: return False, "self-test failed" return True, "ok"

Here run is a small function that builds an MLP from the dictionary and returns its label. Load the candidate into a temporary name, check it, and only then replace the old model, so a failure leaves the robot exactly as it was.

Paper Practice: Answers

Recall

P1. The Funnel

Raw samples (50 Hz) → a window (for example 2 s) → features (a few numbers, 2 Hz) → the model (a label) → an event published only when the label changes.

P2. Train Here, Infer There

Train where the data and compute are (the hub); infer where the decision is needed (the edge).

P3. Validate First

The version is newer; the feature count matches the Perceptor; the layer sizes are consistent; a self-test vector in the file gives the expected label.

Apply

P4. Parameter Count

Weights 6 × 10 + 10 × 3 = 90; biases 10 + 3 = 13; 103 numbers = 412 bytes.

P5. Multiply-Adds

6 × 8 + 8 × 4 = 80. 6 × 32 + 32 × 32 + 32 × 4 = 192 + 1024 + 128 = 1344.

P6. Link Budgets

(a) 50 × 120 = 6000 B/s. (b) 2 × 155 = 310 B/s. (c) 0.4 × 70 = 28 B/s.

Analyze and Design

P7. Heavy Tick

Average 11.4 ms, fits in 20 ms. Worst 16.9 ms, fits with only 3 ms slack. Move the publish to the next tick, or compute features incrementally with running sums so little work remains at the end of the window.

P8. Choose a Placement

(a) Raw: training needs every sample. (b) Labels: only edge inference works offline. (c) Raw (or features if the new ones can be computed from the old).

P9. Tree or Network

Tree: written as plain code with a few comparisons per inference (fast, no model file, no library); a human can read what it learned. Network: draws curved boundaries between classes where a tree only makes axis-aligned steps, often a little more accurate.

P10. Scaling Travels

The network was trained on standardised features; the node must standardise them in exactly the same way. Weights without the scaling, or with a different one, feed the network numbers it has never seen.
