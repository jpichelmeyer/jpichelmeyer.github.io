This lesson covers deciding where computing happens. You work out the link budget of a data stream before building it, measure the time budget on the board with a profiler, and put a one-number model on the node, trained at the hub, with hysteresis against flicker.

Every computation in a robot system has to happen somewhere: on the node (the edge, close to the sensor and the motor) or at the hub, the laptop or the Pi that sees many nodes. The edge is fast and works without a network, but it is small. The hub is large and sees everything, but it is a network hop away. Deciding where each job goes is a design decision, and it is made with budgets: how many bytes per second the link may carry, how many milliseconds the loop may spend, how much memory is left. This lesson gives you the arithmetic, a profiler to measure the real costs, and a way to put a small piece of learning on the node.

Part 1. Four Budgets

The four budgets of a node. The first two are the ones you will meet in every lab. Each is a rate or a size, which makes them possible to calculate before you build.

Part 2. The Link Budget, Worked

A node samples the IMU at 100 Hz: six numbers per sample. Three ways to get the information to the hub, with the real message sizes (a JSON envelope with v, seq, t and the fields, and 12 bytes of binary for six 16-bit values):

The same IMU, three plans. Plan B keeps every sample and uses the whole budget; plan C throws the waveform away and keeps what the hub needs to know. Neither is right in general: the question is what the receiver does with the data.

Ask what the receiver needs. A controller that tunes a stabiliser from the raw waveform needs plan B. A dashboard that shows “moving or still, how much” needs plan C, with one-fiftieth of the traffic. Often the answer is both, at different rates: features all the time on tele, and a burst of raw data on request or when an anomaly fires, so that the interesting seconds are kept in full. (Plan B’s 137-byte message also leaves little room under the 200-byte limit: count it before you trust it.)

Part 3. The Time Budget, Measured

Time is the budget you cannot compute from a datasheet; you must measure it on the board. A control loop at 50 Hz has 20 ms per pass. A plan for how to spend them is the start of a design, and the measurement is what turns it into a fact.

A time budget for one pass of a 50 Hz loop. The numbers are a plan: measure each part and compare. Slack absorbs the occasional slow pass; without it, one slow pass means a missed deadline.
profile.py MicroPython
# profile.py -- measure what a piece of code costs on THIS board from time import ticks_us, ticks_diff class Cost: def __init__(self): self.n = 0 self.total = 0 self.worst = 0 def run(self, fn, *a): t = ticks_us() r = fn(*a) d = ticks_diff(ticks_us(), t) self.n += 1 self.total += d if d > self.worst: self.worst = d return r def report(self, name, period_ms): avg = self.total // max(self.n, 1) print("%s: avg %d us, worst %d us, %.1f%% of a %d ms loop" % (name, avg, self.worst, 100.0 * avg / (period_ms * 1000), period_ms))

Use it by wrapping the calls: cost_feat.run(window.features), then after a few hundred passes cost_feat.report("features", 20). Look at the worst case as well as the average: a loop that averages 8 ms and sometimes takes 40 ms misses its deadline 1 time in 50, and that is the time that matters for a stop command. Floating-point work, string formatting and JSON are the usual suspects; reading a pin and comparing two integers are cheap.

Part 4. A Small Model on the Node

“Learning from sensor data” does not have to mean a neural network. The smallest useful model is a threshold: one feature and one number, found from data. “Is the robot moving?” can be answered by comparing the window’s standard deviation of acceleration with a threshold. The pattern is: train at the hub (where the data and the computing are), run at the edge (where the decision is needed), and move only the numbers between them.

train.py Python
# train.py -- on the laptop: find the best threshold for one feature, then export it import json def best_threshold(xs, labels): """xs: feature values; labels: 0 or 1. Returns (threshold, accuracy) for 'x > t means 1'.""" pairs = sorted(zip(xs, labels)) best = (0.0, 0.0) for i in range(1, len(pairs)): t = (pairs[i - 1][0] + pairs[i][0]) / 2 ok = sum((x > t) == bool(y) for x, y in pairs) acc = ok / len(pairs) if acc > best[1]: best = (t, acc) return best # data: (window_std, moving?) recorded from the IMU in your own lab # t, acc = best_threshold(stds, moving) # json.dump({"feature": "std", "threshold": t, "acc": acc}, open("model.json", "w"))
model.py MicroPython
# model.py -- the whole model on the node: one comparison, with a margin against flicker import json class Stump: def __init__(self, path="model.json", margin=0.1): m = json.load(open(path)) self.t = m["threshold"] self.margin = margin self.state = 0 def update(self, x): if self.state == 0 and x > self.t * (1 + self.margin): self.state = 1 elif self.state == 1 and x < self.t * (1 - self.margin): self.state = 0 return self.state
Training at the hub and inference at the edge. The model is a file of a few bytes; replacing it does not change a line of node code.

On a simulated recording (60 still and 60 moving recordings of 40 windows each, with deliberate overlap, because real “slow movement” and “vibration” overlap), the best threshold on the window standard deviation was 0.049 g, with 90.6 % accuracy on the training windows and 87.3 % on fresh data. A model that was 100 % right would be a sign that the test is too easy. The 13 % of errors are the price of a one-number model; a second feature (the slope, or the range) would shrink it, and a table of two weights is still a tiny model.

The margin in Stump is hysteresis: the output turns on above 1.1× the threshold and off below 0.9×. On a stream of 40 alternating periods (39 true changes), the output with no margin changed state 109 times, because noise kept pushing the feature back and forth over the line; with a 10 % margin it changed 61 times, and with 20 % it changed 37 times but also became less accurate (83.5 % against 86.3 %). Hysteresis is always a trade between flicker and delay, and the chosen margin should be part of the model file.

  • Edge: anything the robot needs to act on in a few control periods, anything that must work with the network down, and the safety limits.
  • Hub: training, logs, long histories, comparisons between nodes, anything that needs more memory or more time than the loop has.
  • Between: the result of computing, in small messages, at a rate chosen for the receiver.

Exercises

Practice problems in three tiers. Do each on paper or on your own board first, and only then open its solution below. Many problems have more than one correct answer; if yours behaves the same way, it is right even if it looks different.

Warm Up

Exercise 1: Plan B Honestly. Plan B packs 10 samples of 12 bytes into one binary message, with 17 bytes of header and fields. What is the payload size, and does it satisfy the 200-byte limit? At 100 Hz how many messages per second?

Exercise 2: Where Does It Go?. Say edge or hub for each: (a) stop the motor if the range is under 10 cm, (b) the last hour’s average temperature of 12 nodes, (c) decide whether the robot is moving, (d) train the threshold for (c).

Intermediate

Exercise 3: The Slow Pass. A loop averages 8 ms per pass but 1 pass in 50 takes 40 ms, at 20 ms per period. How often is the deadline missed? What does that do to a deadman timer set at 2 s, and to a PID loop?

Advanced

Exercise 4: Hysteresis. With threshold 0.05 and margin 0.1, the feature sequence 0.04, 0.052, 0.056, 0.048, 0.044, 0.060 arrives. Starting from state 0, what is the output sequence, and what would it be with no margin?

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Plan B Honestly

10 × 12 + 17 = 137 bytes, under the 200-byte limit, at 100 / 10 = 10 messages per second: exactly the class limit. It passes with no margin. A student who also publishes health and state would exceed the limit, so plan C, or a lower sample rate, is safer. This is why a budget is calculated before the code is written.

Exercise 2: Where Does It Go?

(a) edge: it is a safety action and must work without the network. (b) hub: it needs data from many nodes and long history. (c) edge (using a threshold the hub produced): it feeds a decision that should not wait for the network. (d) hub: it needs the data and the computing, and happens once, not every loop.

Intermediate

Exercise 3: The Slow Pass

The deadline is missed once in 50 passes, about once a second at 50 Hz (a pass of 40 ms takes two periods). The 2-second deadman is unaffected: one late pass costs 20 ms against a 2 s allowance. A PID loop is affected: its derivative and integral terms assume a fixed period, so the slow pass causes a small jolt every second, which can be audible in a servo. Fix the slow pass (find it with the profiler), do not average it away.

Advanced

Exercise 4: Hysteresis

The on-level is 0.05 × 1.1 = 0.055 and the off-level is 0.05 × 0.9 = 0.045. With the margin: 0.04 → 0; 0.052 → 0 (below 0.055); 0.056 → 1; 0.048 → 1 (above 0.045, so stays on); 0.044 → 0; 0.060 → 1. Output: 0, 0, 1, 1, 0, 1. With no margin (threshold 0.05 both ways): 0, 1, 1, 0, 0, 1. The margin delays the first switch by one sample and the second by one, and removes the chance of flicker from a feature hovering near the threshold.
