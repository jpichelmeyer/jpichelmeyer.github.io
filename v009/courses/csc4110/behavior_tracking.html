This lesson covers reactive control. You build a priority arbiter over small behaviors, use a two-look comparison to track a target with a wide-beam sensor, measure the speed limit of the tracker and see why it is a cliff, and place the network’s pan command as one more behavior beneath a stop.

A robot that works from a plan (“go to this point, then that point”) fails the moment the world differs from the plan. A robot built from behaviors does not need the plan to be right: it has several small rules, each reacting to what the sensors say now, and a way to decide which rule is in charge. Complicated-looking activity (searching, following, stopping when it must) emerges from rules that are each a few lines long. This lesson builds that structure and applies it to the problem of Lab 10 and Lab 12: keeping a scan head pointed at a moving object using only a pan servo and a range sensor.

Part 1. Behaviors and Who Wins

A behavior looks at the current state of the world and either proposes an action or has no opinion. Behaviors are ranked, and the highest-ranked one that has an opinion gets to act. This is a simplified form of what robotics calls a subsumption or priority architecture: safety behaviors sit on top and can override everything below them, and the lowest behavior (here, searching) always has something to do, so the robot is never idle.

behaviors.py MicroPython
# behaviors.py -- many small rules, one winner per pass class Behavior: name = "?" def propose(self, s): """Return a pan angle (degrees) if this behavior wants control now, or None.""" return None class Arbiter: """Behaviors in priority order, highest first. The first one with an opinion wins.""" def __init__(self, behaviors): self.behaviors = behaviors self.winner = None def step(self, s): for b in self.behaviors: pan = b.propose(s) if pan is not None: self.winner = b.name return pan self.winner = None return s["pan"]
Four behaviors in priority order. On each pass the arbiter asks them from the top; the first with an opinion decides the pan angle and the rest are not even consulted.

Notice what is not here: a state machine that says “now we are in the tracking mode”. The mode is implicit: it is whichever behavior is winning, and it changes by itself when conditions change. That is the strength of the approach and also its trap: with many behaviors it becomes hard to say what the robot will do. Keep the list short, keep each behavior stateless where you can, and print the winner on every pass during testing.

Part 2. Tracking With a Fan-Shaped Eye

The HC-SR04 sees a cone about 15 degrees wide, so it cannot tell where inside the cone the target is. A trick: look a few degrees to the left, then a few degrees to the right of your best guess, and compare. If only the left look sees the target, the target is further left; if only the right look does, further right; if both, you are centred. Each pair of looks takes two control steps, and you correct by a small step.

tracker.py MicroPython
# tracker.py -- keep a scan head pointed at the nearest thing, using three behaviors SEE_CM = 100.0 # a range shorter than this is "something there" class Stop(Behavior): name = "stop" def propose(self, s): if s["halt"]: return s["pan"] # hold still: safety beats everything class Track(Behavior): """Look a little left and a little right of the best guess, and move toward the side that sees it.""" name = "track" STEP, DITHER, LOST_AFTER = 3.0, 4.0, 5 def __init__(self): self.active, self.c, self.phase = False, 0.0, 0 self.seen_left = False self.miss = 0 def propose(self, s): if not self.active: if s["found"] is None: return None # nothing to track: let the lower behavior act self.active, self.c, self.phase, self.miss = True, s["found"], 0, 0 s["found"] = None seen = s["range"] is not None and s["range"] < SEE_CM if self.phase == 1: # the range we just got was taken LEFT of c self.seen_left = seen elif self.phase == 0 and s["aimed"]: # ... and this one RIGHT of c: decide now if self.seen_left and seen: self.miss = 0 # both sides see it: centred elif self.seen_left: self.c -= self.STEP; self.miss = 0 elif seen: self.c += self.STEP; self.miss = 0 else: self.miss += 1 if self.miss >= self.LOST_AFTER: # gone: hand back to the search behavior self.active = False return None s["aimed"] = True self.phase = 1 - self.phase return self.c - self.DITHER if self.phase == 1 else self.c + self.DITHER class Search(Behavior): name = "search" def __init__(self, lo=-60.0, hi=60.0, step=6.0): self.lo, self.hi, self.step, self.dir = lo, hi, step, 1 def propose(self, s): if s["range"] is not None and s["range"] < SEE_CM: s["found"] = s["pan"] # tell Track where we saw it pan = s["pan"] + self.dir * self.step if pan > self.hi or pan < self.lo: self.dir = -self.dir pan = max(self.lo, min(self.hi, pan)) return pan
The two looks of Track (not to scale). The dither is ±4 degrees, smaller than the beam, so both looks usually see a centred target and the difference tells which way it has drifted.

One decision takes two 100 ms steps, and each moves the estimate by at most 3 degrees, so the tracker can follow a target at about 15 degrees per second, and no faster. That limit is a property of the design, and the simulation shows it as a cliff, not a slope. A target swinging through plus and minus 40 degrees was followed for 60 s of simulated time (10 Hz loop, 1 cm of range noise, a 15° beam):

The tracker’s speed limit. Up to 16°/s it holds the target the whole time; at 20°/s it is locked on 39 % of the time; at 30°/s, 19 %. Doubling the step to 6° moves the cliff to about 35°/s, with no cost visible in the simulation (mean error 1.6 to 2.0° against 2.0 to 2.4° for the 3° step). On a real servo a bigger step jerks the head and a noisy range can make it chatter, so test it on your hardware.

This is how to think about a behavior’s performance: not “it works”, but “it works up to this speed, and then fails like this”. The cliff is predictable (step / (2 × period)), so you can design for it: choose the step from the fastest target you need to follow, and check it against how fast the servo can really move.

Part 3. Putting the Network In

Where do the commands of Unit 2 fit? A pan command from the robot’s owner is one more behavior. It belongs below stop (a stop is always honoured) and above track (the owner’s wish beats the head’s own interest), and it holds for a limited time, so that a lost owner does not leave the head pointing where the last command said.

remote.py MicroPython
# remote.py -- the owner's pan command is one more behavior, below Stop and above Track from time import ticks_ms, ticks_diff class Remote(Behavior): name = "remote" HOLD_MS = 2000 # a pan command is obeyed for 2 s, then the head goes back to its own devices def __init__(self): self.deg, self.t = None, None def command(self, deg): # called by the command handler (Unit 2's Robot logic) self.deg, self.t = deg, ticks_ms() def propose(self, s): if self.deg is not None and ticks_diff(ticks_ms(), self.t) < self.HOLD_MS: return self.deg return None
Which behavior wins, from a 60 s simulation: search finds the target about 0.1 s after it appears (it happened to pass in front of the head), tracking takes over for 30 s, the head resumes searching about a second after the target is gone (five misses), and stop takes everything from 50 s.

In the scenario of the figure the tracker kept an error of 2.5 degrees on average and was within the beam 99 % of the time the target was present. With Remote in the list and a pan command of −45° at 1.0 s, the head went there at once and held it for exactly two seconds, and at 3.0 s search resumed from that angle: the trace showed remote at 1.0 s and 2.9 s and search at 3.0 s.

  • A behavior should be quick. It runs every pass of the control loop. No waiting, no network calls; it reads the shared state s and answers.
  • Put safety on top, and test it first. The halt flag could come from a bumper, a distance limit or a stop message; the arbiter makes it override everything with one line.
  • Behaviors are agents in miniature. They sense, decide, and the arbiter acts. At the next level, whole robots, each running its own arbiter, are the behaviors of a team, and the broker is the arbiter’s input.

Exercise 2: The Speed Limit. A tracker looks left and right alternately every 50 ms and moves the estimate 2 degrees per decision. What is its speed limit? Is a target moving at 25 degrees per second inside it?

Intermediate

Exercise 3: Lost and Found. The tracker loses the target when it passes behind an obstacle for 3 seconds. Use the code to say what happens, what the head does while it waits, and how it reacquires the target. What would you change to reacquire faster?

Advanced

Exercise 4: Add a Behavior. Add a behavior Center between track and search that, if the head has been searching for more than 10 seconds without finding anything, returns the head to 0° and holds it there for 2 seconds before searching again. Say what extra state it needs.

Warm Up

Exercise 1: Who Wins?

(a) track. (b) remote (within its 2 s hold, and above track). (c) search: the hold has expired, and with no target Track has no opinion. (d) stop: it is on top, so the head holds still and the owner’s command is ignored until halt clears.

Exercise 2: The Speed Limit

A decision needs two looks, so 100 ms, and moves 2°: the limit is 2° / 0.1 s = 20°/s. A target at 25°/s is outside it, and the head will fall behind and lose it; at about 17 to 20 simulated degrees per second (for a limit of 15) the same cliff appeared. To follow 25°/s with these timings the step would have to be at least 2.5°; choose 3° or more for some margin.

Intermediate

Exercise 3: Lost and Found

After five misses (one per two-look decision, 0.2 s each, so about 1 s) Track sets active = False and returns None; Search takes over from the current pan angle and sweeps ±60° at 6° per step. When the target reappears and passes in front of the beam, Search sets found, and Track starts again. To reacquire faster, make Search sweep a narrow range around the last known angle first (a remembered position, the subject of the state tracking lesson), and widen only if that fails.

Exercise 4: Add a Behavior
center.py MicroPython
from time import ticks_ms, ticks_diff class Center(Behavior): name = "center" def __init__(self): self.started = ticks_ms() # when we last had a target, or started self.hold_until = None def propose(self, s): now = ticks_ms() if s["found"] is not None or s["range"] is not None and s["range"] < 100: self.started = now # we see something: restart the 10 s clock return None if self.hold_until is not None: if ticks_diff(now, self.hold_until) < 0: return 0.0 # holding at centre self.hold_until, self.started = None, now return None if ticks_diff(now, self.started) > 10000: self.hold_until = now + 2000 return 0.0 return None

It needs two pieces of state: when it last saw anything (started) and, while it is holding, until when (hold_until). Put it between Track and Search: [Stop(), Remote(), Track(), Center(), Search()]. It has an opinion only in the rare case, so the simpler behaviors keep their lines.
