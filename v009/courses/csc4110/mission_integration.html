This is the week the course comes together. Your specialised robots, the shared world model and the coordination patterns of the last three weeks become one team that carries out a mission: find a target in the arena, work out where it is, identify it, get a human's approval, and mark it. No robot can do it alone. This lesson describes the mission, the coordinator that runs it on the hub, the contract every role must meet, how to integrate a team without drowning in bugs, and the faults Lab Practical 3 will throw at it.

Part 1. The Mission: Find, Identify, Mark

The arena is a table about 120 × 90 cm. The instructor places a target somewhere in it: a cardboard tube carrying a small coloured beacon (an LED behind a red, green or blue filter, which the instructor can change between runs). The team must report the target's position to within a few centimetres, name its colour, wait for the operator to approve, and hold the Pointer's beam on it.

The arena, from above. Two Scouts on a known baseline each find the tube with ultrasound and report only its direction; crossing the two bearings gives its position (the fuser of Lab 12). The Watcher turns its filtered eyes to that position and names the beacon's colour. The Pointer holds a beam on the target once the operator, through the Signaler, approves. The Sentinel feels the table for bumps, which invalidate everyone's position. The hub keeps the world model and runs the mission.

By the mission, each robot is in its Stage 3 form: untethered on a power bank, labelled with its broker name, its pose origin (the servo axis) marked and measured, and its role hardware finished: hoods on the Watcher's eyes, a beam on the Pointer, a hand grip and a big acknowledge button on the Signaler, a housed puck for the Sentinel.

Stage 3, the mission-ready robots. Badges show where each finishing touch comes from (L10, L11, L12 for the labs; S3 for the stage). The red dashed crosshair on the turret robots marks the pose origin that goes into stat/role: every arena coordinate in the world model is measured from it.

Every robot runs the architecture of Week 8: a reactive layer (PID, safety) and an executive layer (an arbiter or state machine) on the Pico. The new piece is the top layer: a mission coordinator on the hub, which reads the world model, decides which phase the mission is in, and sends each role a goal. Goals are not commands to move a servo. They are parameters for the robot's own behaviours: “scan”, “track”, “look at (31, 48)”, “point at (31, 48)”. Each robot still decides how.

Part 2. The Mission as a Distributed State Machine

The mission's phases. The black and coloured arrows move the mission forward; the red ones send it back. Every forward transition depends on a belief in the world model or on an event from a robot, and the gold one also needs Memory (the fix must stay good for two seconds). The coordinator holds the phase; each robot holds only its own behaviour state.

Notice what is not in this machine: servo angles, pings, PID gains. Those live in the robots. The coordinator works only with beliefs (fresh or not, good enough or not) and events (ack, marked, disturb). That separation is what lets a team built by six different students work at all: the coordinator depends on the contract, never on how a particular robot meets it.

Part 3. The Coordinator

As with the world model, the logic is written with no network code so that it can be tested end to end on a laptop. step moves the phase on from the world snapshot and the events since the last step, and returns the goal for every role in the current phase. Interrupts are checked first, in priority order (team, bump, lost target), which should look familiar: it is the arbiter of Week 8 again, one level up.

mission.py Python
# mission.py -- the deliberative layer: one coordinator on the hub (pure logic, no network) NEED = {"scout": 2, "watcher": 1, "pointer": 1, "signaler": 1} def alive_by_role(w): out = {} for user, r in w.get("world/roster", {}).items(): if r["online"] and r["role"]: out.setdefault(r["role"], []).append(user) return out def ready(w): have = alive_by_role(w) return all(len(have.get(role, [])) >= n for role, n in NEED.items()) class Mission: HOLD_S, Q_MIN, CONF_MIN = 2.0, 0.5, 0.8 # target good for 2 s; quality; confidence def __init__(self, now): self.phase, self.since, self.t0 = "WAIT_TEAM", now, now self.log = [(now, "WAIT_TEAM")] self.good_since = None # when the target became good enough def go(self, phase, now): if phase != self.phase: self.phase, self.since = phase, now self.log.append((now, phase)) if phase == "SEARCH": self.good_since = None # after a bump, the target must prove itself again def step(self, w, events, now): """w: the world snapshot; events: set of 'disturb', 'ack', 'marked' since the last step. Moves the phase on, then returns the goals for every role in the new phase.""" tgt, idn = w.get("world/target"), w.get("world/ident") t_ok = bool(tgt and tgt["fresh"] and tgt["value"]["q"] >= self.Q_MIN) i_ok = bool(idn and idn["fresh"] and idn["value"]["conf"] >= self.CONF_MIN) self.good_since = (self.good_since or now) if t_ok else None p = self.phase if p != "DONE": if not ready(w): self.go("WAIT_TEAM", now) # degrade: someone needed is gone elif p == "WAIT_TEAM" or "disturb" in events: self.go("SEARCH", now) # (re)start, or start again after a bump elif p != "SEARCH" and not t_ok: self.go("SEARCH", now) # lost the target elif p == "SEARCH" and t_ok and now - self.good_since >= self.HOLD_S: self.go("IDENTIFY", now) elif p == "IDENTIFY" and i_ok: self.go("CONFIRM", now) elif p == "CONFIRM" and "ack" in events: self.go("MARK", now) # a human said yes elif p == "MARK" and "marked" in events: self.go("DONE", now) return self.goals(w, now) def goals(self, w, now): tgt = (w.get("world/target") or {}).get("value") or {} at = [tgt.get("x"), tgt.get("y")] label = ((w.get("world/ident") or {}).get("value") or {}).get("label", "?") track = {"do": "track"} return { "WAIT_TEAM": {"signaler": {"show": "waiting for team"}}, "SEARCH": {"scout": {"do": "scan"}, "signaler": {"show": "searching"}}, "IDENTIFY": {"scout": track, "watcher": {"do": "look", "at": at}, "signaler": {"show": "identifying"}}, "CONFIRM": {"scout": track, "signaler": {"ask": "mark %s at %s?" % (label, at)}}, "MARK": {"scout": track, "pointer": {"do": "point", "at": at}, "signaler": {"show": "marking %s" % label}}, "DONE": {"pointer": {"do": "point", "at": at}, "signaler": {"show": "done in %.1f s" % (self.since - self.t0)}}, }[self.phase]

The test drives the real WorldModel from last week with scripted reports, so it checks the two programs together: the team assembles over two seconds, the fix arrives at 5 s, the Watcher's verdict at 9 s, the operator approves at 11.5 s, someone bumps the table at 13 s, and the Pointer locks at 21 s.

The test run as a timeline (drawn from the coordinator's log above). The bump at 13 s throws the mission back to SEARCH; the fix must then hold for two fresh seconds before identification resumes, and the operator must approve again. The mission returns to MARK 5 s after the bump, which is exactly the recovery time that Lab Practical 3 measures.

The service around it is as thin as the world model's. It keeps the latest world/# messages, collects events, steps once a second, and sends each goal to every robot that holds the role. Goals are re-sent every second on purpose: each robot's Obey behaviour treats a goal older than two seconds as stale and falls back to its own behaviours, so if the coordinator dies, the team degrades gracefully instead of freezing on its last order.

missionsvc.py Python
# missionsvc.py -- runs on the class Pi as user "mission": reads world/#, sends goals import json, time import paho.mqtt.client as mqtt from mission import Mission, alive_by_role world, events = {}, set() def on_message(client, userdata, msg): try: d = json.loads(msg.payload) except ValueError: return if msg.topic.startswith("world/"): world[msg.topic] = d elif msg.topic.endswith("/evt/disturb"): events.add("disturb") elif msg.topic.endswith("/evt/ack"): events.add("ack") elif msg.topic.endswith("/stat/mark") and d.get("locked"): events.add("marked") def on_connect(client, userdata, flags, reason_code, properties): for t in ("world/#", "lab/+/evt/disturb", "lab/+/evt/ack", "lab/+/stat/mark"): client.subscribe(t) c = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2, client_id="mission") c.username_pw_set("mission", "PASSWORD") c.will_set("lab/mission/stat/phase", json.dumps({"phase": "OFFLINE"}), qos=1, retain=True) c.on_connect, c.on_message = on_connect, on_message c.connect("localhost") c.loop_start() m, seq = Mission(time.monotonic()), 0 while True: now = time.monotonic() ev = set(events) events.clear() goals = m.step(world, ev, now) c.publish("lab/mission/stat/phase", json.dumps({"phase": m.phase}), qos=1, retain=True) who = alive_by_role(world) for role, goal in goals.items(): # goals are refreshed every second, for user in who.get(role, []): # so a robot's Obey behaviour sees them fresh seq += 1 c.publish("lab/mission/cmd/goal", json.dumps(dict(goal, to=user, id=seq)), qos=1) time.sleep(1.0)

The coordinator writes only inside its own subtree (lab/mission/…), so the access list needs no change beyond a broker user named mission. Its goals follow the command convention of Week 11: published in the sender's subtree, addressed with a to field, numbered with an id.

Part 4. The Mission Contract

Every robot of a role must meet the same contract, so that any Scout works with any fuser and any Pointer with any coordinator. This is the full table. Check every message against it with contract.py, on both sides.

The mission contract. Every message also carries the envelope (v, seq, t). Add up the rates for your team before the practical: with two Scouts, a fuser and five goal streams, the team stays well inside the class limit, but only if nobody publishes at the raw sample rate.

Part 5. Integrate Up a Ladder, Not All at Once

The commonest way to fail a multi-agent project is to build every robot separately and switch them all on together the day before the demo. Every bug then appears at once, in a system where nothing can be observed in isolation. Climb a ladder instead: each rung adds one thing, and you do not climb until the rung you are on passes.

The integration ladder. Lower rungs are cheap and fast (seconds on a laptop) and find most of the bugs; higher rungs are slow (the whole team, the arena, the instructor's broker) and should find only the bugs that genuinely need the whole system. The coordinator test in Part 3 is rung 1 for the hub programs.

Rung 3 is where stubs earn their keep. A stub is a fake teammate that behaves just well enough: a three-line loop that publishes a plausible tele/fix lets the Watcher's student work while the Scouts are still being built. Lab 9 gave you simulated peers with mosquitto_pub; for the mission, every role should have a stub, and every robot should pass rung 3 against stubs before it meets a real teammate.

Part 6. Faults, Degraded Modes and Recovery

A mission that works only when nothing goes wrong has not been validated. Lab Practical 3 runs the mission and injects faults while it runs. For each one, you must say in advance what the team should do (its degraded mode) and how quickly it should recover, then measure whether it did.

The Lab Practical 3 fault list, with example requirements. Your team writes its own numbers into the right-hand column before the practical, as part of the test plan from the validation lesson; the practical then measures them. A requirement such as “no wrong mark, ever” is not a time: it is a property the design must guarantee, here by the operator's approval.

The coordinator's phase log is the evidence. A few lines turn it into the numbers the practical grades: time to first mark, time in each phase, and recovery time after each fault. For the test run of Part 3 they are:

metrics.py Python
# metrics.py -- turn the coordinator's phase log into the numbers Lab Practical 3 grades def phase_times(log, end): """Seconds spent in each phase, summed over every visit.""" out = {} for (t0, p), (t1, _) in zip(log, log[1:] + [(end, None)]): out[p] = round(out.get(p, 0) + t1 - t0, 1) return out def time_to(log, phase): return next((t for t, p in log if p == phase), None) def recoveries(log, fault_times): """For each fault, seconds until the mission is back in the phase it was in before.""" out = [] for tf in fault_times: before = [p for t, p in log if t < tf][-1] back = next((t for t, p in log if t > tf and p == before), None) out.append(None if back is None else round(back - tf, 1)) return out
using it Python
print(phase_times(m.log, 24.0)) # {'WAIT_TEAM': 2.0, 'SEARCH': 7.5, 'IDENTIFY': 2.5, 'CONFIRM': 4.5, 'MARK': 4.5, 'DONE': 3.0} print(time_to(m.log, "DONE")) # 21.0 print(recoveries(m.log, [13.0])) # [5.0]

Notice how much of the run was spent in CONFIRM, waiting for a human. That is not a defect. It is the price of the requirement that the team never marks the wrong target, and the report should say so. Trading speed for a guarantee, and being able to show the trade in numbers, is the kind of engineering judgement this course has been building toward since the first sense-decide-act loop.

Warm Up

Exercise 1: Which Layer?

(a) Deliberative (the coordinator): it concerns the whole team's plan. (b) Reactive: a PID on the Pointer. (c) Executive, with a parameter set by the deliberative layer: the Scout's Scan behaviour runs the sweep, the hub only chose its limits. (d) Reactive: a safety reflex must never wait for any other layer, or for the network.

Exercise 2: Trace the Mission

Nothing: CONFIRM only checks the team, a bump, the target's freshness and the ack. The operator would be asked to approve a colour that the team no longer currently believes. Arguably that is wrong: add elif p in ("CONFIRM", "MARK") and not i_ok: self.go("IDENTIFY", now) after the lost-target rule, so the question is withdrawn when its basis goes stale. Whether MARK should also fall back is a design decision: once a human has approved, you might keep marking. Write the choice into your test plan.

# stub_watcher.py -- a fake Watcher, for rung 3 of the ladder import json, time import paho.mqtt.client as mqtt ME = "raj" # the Watcher's user name in the roster pending = [] # times at which to answer def on_message(client, userdata, msg): d = json.loads(msg.payload) if d.get("to") == ME and d.get("do") == "look": pending.append(time.monotonic() + 1.0) c = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2, client_id="stub-" + ME) c.username_pw_set(ME, "PASSWORD") c.on_message = on_message c.connect("BROKER") c.subscribe("lab/mission/cmd/goal") c.publish("lab/%s/stat/role" % ME, json.dumps({"v": 1, "seq": 0, "t": 0, "role": "watcher"}), retain=True) c.loop_start() seq = 0 while True: if pending and time.monotonic() >= pending[0]: pending.pop(0) seq += 1 c.publish("lab/%s/evt/ident" % ME, json.dumps({"v": 1, "seq": seq, "t": seq, "label": "red", "conf": 0.9})) time.sleep(0.05)

The coordinator re-sends goals every second, so this stub answers every second while the mission is in IDENTIFY, which is harmless (the world model keeps only the latest verdict) and also a useful rate test. A better stub answers once per goal id that it has not seen before.

Advanced

Exercise 4: Degrade Instead of Wait

What changes: NEED becomes a list of acceptable teams (two scouts, or one scout in degraded mode); the fuser (or the world model) computes a fix from one bearing and one range, x = xs + r cos θ, y = ys + r sin θ, and gives it a lower quality (say 0.5 instead of 0.7 to 0.9); the coordinator lowers nothing else, so the 0.5 threshold still applies. The Signaler should show “degraded: one scout”. What does not change: the robots, their behaviours, the contract and the Watcher and Pointer, because they consume world/target, not bearings. That is the payoff of the world model's single writer. New risk: ultrasonic range to a round tube is biased (the echo comes from the near surface, not the centre), so a one-scout fix is offset by about the tube's radius; and with one sensor there is no cross-check, so a wrong echo produces a confident wrong position. The operator's approval remains the guard against marking it.

Paper Practice: Answers

Recall

P1. The Mission

Find, identify and mark a target in the arena. Scouts find it and report bearings; a fuser crosses them into a position; the Watcher identifies the beacon's colour; the Signaler asks the operator to approve and shows status; the Pointer holds a beam on it; the Sentinel reports bumps; the hub keeps the world model and runs the coordinator.

P2. Goals, Not Commands

Goals that set parameters for a robot's own behaviours ("scan", "track", "look at (x, y)", "point at (x, y)"), not servo angles. Each robot still decides how.

P3. Phases

WAIT_TEAM → SEARCH (team ready) → IDENTIFY (fix with q ≥ 0.5 held for 2 s) → CONFIRM (identification with confidence ≥ 0.8) → MARK (operator ack) → DONE (pointer locked).

P4. Ladder

Unit; contract; robot plus stubs; pairs; team; faults.

Apply

P5. Trace the Coordinator

(0, WAIT_TEAM), (2, SEARCH), (7, IDENTIFY: 2 s after the fix), (9, CONFIRM), (11.5, MARK), (14, DONE).

P6. After a Bump

With the coordinator stepping every 0.5 s: (12.5, SEARCH); the hold restarts at the next step, 13.0, so (15.0, IDENTIFY); the identification is still fresh, so (15.5, CONFIRM) at the next step; (16, MARK); (18, DONE).

P7. Recovery Time

16 − 12.5 = 3.5 s; the mission took 18 s.

P8. Goal Freshness

Within about 2 s of the last goal (between 1 and 2 s after the coordinator's last publish, plus the network delay).

Analyze and Design

P9. Degraded Mode

The roster marks B offline (will or 10 s silence); the coordinator goes to WAIT_TEAM; the Signaler shows "need scout"; the Pointer's beam is off. Recovery: back to the same phase within, say, 30 s of B being powered again.

P10. Human in the Loop

Not a defect: it is the price of "never mark the wrong target", guaranteed by the operator's approval. Report it as a measured trade (time in CONFIRM against the guarantee), not hide it.

P11. Stubs

Stubs isolate one robot's faults from a teammate's, and let work proceed while others are not ready. A Pointer stub subscribes to the coordinator's goals and, on a point goal addressed to it, publishes stat/mark with locked: true after a short delay (and keeps a heartbeat so the roster sees it alive).

P12. Withdraw the Question

Arguably yes: the operator is being asked to approve a colour the team no longer currently believes. Rule: elif p in ("CONFIRM",) and not i_ok: go("IDENTIFY"). Whether MARK should also fall back (after a human approved) is a design decision to write into the test plan.
