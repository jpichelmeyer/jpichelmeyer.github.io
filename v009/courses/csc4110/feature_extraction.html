A sensor produces numbers faster than anyone needs to read them. What a decision usually depends on is not any single sample but a description of the last few seconds: where the signal is, how much it wobbles, whether it is rising. Feature extraction is the step that turns a window of samples into that handful of descriptive numbers.

Part 1. Windows

A window is a run of consecutive samples treated as one unit. The two common arrangements are tumbling windows, which sit side by side and give one result per window, and sliding windows, which overlap and give results more often at the price of more computation.

Two ways to cut a stream into windows. Tumbling windows do not overlap and give one result per window; sliding windows overlap and give results more often, at more computing cost.

The window length is a trade-off. A longer window gives steadier features but reacts slowly and uses more memory if you store it; a shorter one reacts quickly but is noisy. Choose it from the physics: long enough to contain a few cycles of whatever you care about, short enough that the answer is still useful when it arrives.

Part 2. The Everyday Features

A window of samples and the numbers that summarise it. Each feature answers a different question: where is it, how wide, how jumpy.
  • mean: the centre, a smoothed level. min and max: the extremes; their difference is the peak-to-peak range.
  • variance and standard deviation: the typical spread. A signal that has gone quiet or turned jumpy shows up here long before the mean moves.
  • RMS (root mean square): the overall strength of a signal regardless of its sign, useful for vibration and sound.
  • slope: the trend across the window, from the first and last values or a fitted line.
Two features worth knowing. RMS measures how strong a signal is regardless of its sign; zero crossings count how often it changes direction, a cheap way to estimate frequency.

Part 3. Computing Them Without Storing the Window

A Pico cannot afford to keep every window in memory. All the features above can be built up one sample at a time from a few running totals, so the memory use is the same however long the window is. Because ADC readings are integers, the sums can be kept exactly:

features.py MicroPython
class Window: def __init__(self, n): self.n = n self.reset() def reset(self): self.count = 0 self.total = 0 # exact integer sums: no rounding error self.sumsq = 0 self.lo = None self.hi = None def add(self, x): """Add an int reading. Returns True when the window is full.""" self.count += 1 self.total += x self.sumsq += x * x if self.lo is None or x < self.lo: self.lo = x if self.hi is None or x > self.hi: self.hi = x return self.count >= self.n def features(self): n = self.count mean = self.total / n var = (n * self.sumsq - self.total * self.total) / (n * n) # exact numerator return {"n": n, "mean": round(mean, 1), "std": round(var ** 0.5, 1), "min": self.lo, "max": self.hi, "p2p": self.hi - self.lo}

Look at the line computing var. It uses the integer form (n·Σx² − (Σx)²) / n² deliberately. The tempting textbook version, Σx²/n − mean², subtracts two huge, nearly equal numbers. In the Pico’s 32-bit floats that cancellation destroys most of the precision: for 100 readings near 40000 with a true variance of 512, it gave 753. Exact integer sums, or the method in the next lesson, avoid the problem.

Part 4. Features Are Compression

Features are compression. One hundred raw readings become a handful of numbers, so the broker and network carry a fraction of the data while still saying what the signal is doing.

Publishing the features once per window, instead of every sample, reduces the traffic by roughly the window length while keeping what a dashboard or a detector actually needs. When something looks interesting, you can still switch to publishing raw samples for a short while.

Warm Up

Exercise 1: By Hand

mean = 60 / 5 = 12; min 10; max 14; peak-to-peak 4. Squared deviations from 12: 4, 0, 1, 1, 4 = 10, so variance = 10 / 5 = 2 (standard deviation about 1.41).

Exercise 2: Window Arithmetic

100 / 50 = a 2 s window. (a) tumbling: one result every 2 s. (b) sliding by 25 samples (0.5 s): one result every 0.5 s, four times as often, each reusing three-quarters of the previous window.

Intermediate

Exercise 3: Add RMS and Slope
features.py (additions) MicroPython
# in reset(): self.first = None; self.last = None # in add(x): if self.first is None: self.first = x; self.last = x def rms(self): return (self.sumsq / self.count) ** 0.5 def slope(self): if self.count < 2: return 0.0 return (self.last - self.first) / (self.count - 1)

Both come from totals already kept (sumsq) or two extra numbers. Nothing grows with the window length, which is what keeps this feasible on 264 KB.

Advanced

Exercise 4: Sliding Without Storing Everything
features.py MicroPython
class Sliding: def __init__(self, n): self.n = n self.buf = [0] * n # fixed memory: n integers self.i = 0 self.count = 0 self.total = 0 self.sumsq = 0 def add(self, x): old = self.buf[self.i] self.total += x - old # new in, oldest out self.sumsq += x * x - old * old self.buf[self.i] = x self.i = (self.i + 1) % self.n if self.count < self.n: self.count += 1 def mean(self): return self.total / self.count

Memory is one list of 50 integers, about 200 bytes plus the list header, and each update does a fixed amount of work. Min and max are harder to maintain this way, since removing the oldest value may remove the maximum; for those you scan the buffer or use a smarter structure.
