This lesson covers how to know that a system works. You write requirements that can fail, test the logic on a laptop with the same files as the Pico, check your tests by damaging the code, inject lost, duplicated and delayed messages, count how many trials a claim needs, keep a plan and a log, and prepare for a demonstration.

Every lab so far ended with a check: the LED lit, the number matched, the message arrived. That is demonstration: it shows the system can work. Validation asks a harder question: does it work when it is supposed to, every time that matters, and when things go wrong? A robot that stops in 100 ms on the bench and in 600 ms in the demo has passed a demonstration and failed a validation. This lesson is about getting from the first to the second: requirements you can fail, tests that run before the hardware does, deliberate faults, honest counts of trials, and evidence you can hand to someone else. It is also how Lab Practical 3 and the capstone lab will be judged.

Two words are used loosely. Verification asks “did we build it the way we said?” (the code does what the specification says). Validation asks “did we build the right thing?” (the specification, and the system built from it, serve their purpose). Both need tests; validation also needs a requirement that someone cares about.

Part 1. A Requirement You Can Fail

“The robot should respond quickly and be reliable” cannot fail, so it cannot be tested, so it can never be satisfied or violated. A testable requirement has five parts: a stimulus (what happens), a response (what the system does), a limit (how fast, how far, how accurate), a condition (load, link quality, the state it starts in), and a pass rule (how many of how many, or which percentile).

Four requirements made testable. Each names a stimulus and a response, a limit, a condition and a pass rule. Notice that the second is a property (it must hold for all inputs) and the others are measurements; both are legitimate tests, and they are built differently.

Write the requirement before building, and keep it next to the test. Writing it afterwards means writing what the system happens to do. If a requirement cannot be written as above, you do not yet know what you are building, and that is useful to discover on the first day, not the last.

Part 2. Test on the Laptop First

A Pico takes seconds to flash and cannot be single-stepped, and a failure on it could be the code, the wiring, the WiFi or the broker. A laptop runs the same Python in milliseconds, with a debugger, and with nothing else that can be wrong. So the order is: test the logic on the laptop, test the pieces together on the laptop with fake devices, then test on the hardware, where only hardware problems remain.

Four levels of test. Push every check as far left as it can go: what can be tested without hardware should be, because that is where tests are cheap enough to repeat after every change.

The lease from Lab 11 is a good example, because it takes the time as an argument rather than reading a clock, so it can be tested with no hardware and no fake clock at all. The file below is ordinary Python. It imports the same lease.py that runs on the Pico, and it runs in under a second with python3 -m unittest test_lease -v.

test_lease.py MicroPython
# test_lease.py -- run on your laptop with: python3 -m unittest test_lease -v import time, random, unittest time.ticks_diff = lambda a, b: a - b # MicroPython's clock helper, for ordinary Python from lease import Lease # the SAME file that runs on the Pico class LeaseTests(unittest.TestCase): def setUp(self): self.L = Lease(lease_ms=10000, max_queue=2) def test_first_claim_is_granted(self): self.assertEqual(self.L.claim("a", 0), ("granted", 0)) def test_second_claim_queues_in_order(self): self.L.claim("a", 0) self.assertEqual(self.L.claim("b", 10), ("queued", 1)) self.assertEqual(self.L.claim("c", 20), ("queued", 2)) self.assertEqual(self.L.claim("d", 30), ("full", 0)) def test_repeating_a_claim_keeps_your_place(self): self.L.claim("a", 0); self.L.claim("b", 10); self.L.claim("c", 20) self.assertEqual(self.L.claim("b", 30), ("queued", 1)) # not moved to the back def test_owner_renews(self): self.L.claim("a", 0) self.L.claim("a", 9000) self.assertTrue(self.L.holds("a", 18000)) # 9000 + 10000 is not over yet def test_expiry_is_exact(self): self.L.claim("a", 0) self.assertTrue(self.L.holds("a", 9999)) self.assertFalse(self.L.holds("a", 10000)) # the lease is over AT 10 s def test_expiry_hands_over_to_the_queue(self): self.L.claim("a", 0); self.L.claim("b", 5) self.L.tick(10000) self.assertTrue(self.L.holds("b", 10001)) def test_release_by_a_non_owner_does_nothing(self): self.L.claim("a", 0) self.assertFalse(self.L.release("b", 5)) self.assertTrue(self.L.holds("a", 6)) def test_never_two_owners(self): # a property, tried 20,000 times rnd = random.Random(1); now = 0 for _ in range(20000): now += rnd.randint(0, 3000) who = rnd.choice("abcde") op = rnd.choice(("claim", "claim", "release", "tick")) if op == "claim": self.L.claim(who, now) elif op == "release": self.L.release(who, now) else: self.L.tick(now) holders = [u for u in "abcde" if self.L.holds(u, now)] self.assertLessEqual(len(holders), 1) self.assertNotIn(self.L.owner, self.L.queue) def test_release_hands_over_in_order(self): self.L.claim("a", 0); self.L.claim("b", 10); self.L.claim("c", 20) self.assertTrue(self.L.release("a", 100)) self.assertTrue(self.L.holds("b", 101)) # b was first in the queue self.assertEqual(self.L.claim("c", 102), ("queued", 1)) # and c moved up

The last test is a property test: instead of one chosen example, it tries 20,000 random operations and checks, after every one, that at most one user holds the lease and that the owner is never also in the queue. Random inputs find the case you did not think of. Fix the random seed (Random(1)) so that a failure can be repeated.

A Test You Have Never Seen Fail Proves Nothing

Passing tests are reassuring only if they would have failed on a broken lease. One way to check is mutation: deliberately damage the code, one small change at a time, and see whether any test notices. Six mutations of the lease were tried against the tests above (the original passed all of them):

Mutation testing of the lease: every change was caught, and each by a test written for that behaviour. The one-tick-late expiry is the instructive case: no timing test with “roughly” in it would have seen it, and it is exactly the boundary where a real lease is off by one message.

Notice that the boundary tests (9999 holds, 10000 does not) are the ones that catch the off-by-one. Test at the edge of every limit: just inside, exactly on, just outside.

Part 3. Break It on Purpose

Unit tests check that the logic is right when everything arrives. Validation of a networked system must check what happens when it does not. Fault injection puts a deliberately bad link between the parts and watches. The class below wraps a hub so that its outgoing messages are lost, duplicated or delayed with chosen probabilities, from a fixed seed so that a failing run can be repeated.

flaky.py MicroPython
# flaky.py -- a link that misbehaves on purpose, for testing (never ship it on the robot) import random class Flaky: """Wrap a Hub. Outgoing messages may be lost, duplicated or delayed. Everything else (on, poll, root, ...) is passed straight through.""" def __init__(self, hub, loss=0.0, dup=0.0, delay_ms=(0, 0), seed=0): self.hub = hub self.loss, self.dup, self.delay = loss, dup, delay_ms self.rnd = random.Random(seed) # a fixed seed makes a failure repeatable self.pending = [] # (due_ms, topic, data, retain) self.lost = self.sent = 0 def __getattr__(self, name): return getattr(self.hub, name) def publish(self, topic, data, retain=False): self.sent += 1 if self.rnd.random() < self.loss: self.lost += 1 return True # the sender is told nothing: that is the point copies = 2 if self.rnd.random() < self.dup else 1 for _ in range(copies): lo, hi = self.delay self.pending.append((self.now() + self.rnd.randint(lo, hi), topic, data, retain)) return True def now(self): from time import ticks_ms return ticks_ms() def flush(self): """Call once per loop: really send what is due.""" from time import ticks_diff now = self.now() due = [p for p in self.pending if ticks_diff(now, p[0]) >= 0] self.pending = [p for p in self.pending if ticks_diff(now, p[0]) < 0] for _, topic, data, retain in due: self.hub.publish(topic, data, retain)

It was applied to the Lab 11 system (one manager, three clients, 15 pans in all, simulated) with every node’s outgoing link made faulty, 20 runs per setting, each given 90 simulated seconds. The first version of the manager failed immediately:

Runs (of 20) in which all three clients completed within 90 s, before and after the fix, and the median and worst finish time after it. Slow is acceptable under heavy loss, stuck is not. Even with half the messages lost every run finished, in a median 27 s instead of 4.7 s.

The failures were not slowness; they were deadlock. The manager published stat/owner only when the owner changed. If that one message was lost, every client waited in WAIT for a state it never heard, while the manager believed amy owned the servo, and amy’s repeated claim kept renewing her lease for ever. Nothing was broken in any single component, and on a good link it never happened. The fix is a single line: repeat the state every three seconds, even when it has not changed. The test then passed everywhere, and every run was repeatable from its seed.

Two lessons beyond this one bug. First, this kind of fault is almost impossible to find by trying the system on the bench: the bug needs a message to be lost at one particular moment, which is rare on a good link and certain somewhere in a classroom of thirty. Second, the duplicate case passed without any special code, because the manager already refused a second pan within 200 ms and ignored a repeated claim: a design that is idempotent (repeating a message changes nothing) is tolerant of duplicates for free.

Run the same kinds of fault, by hand, on the real hardware too: unplug the WiFi, restart the broker, power-cycle one Pico mid-run, hold a sensor at an impossible value, and cover the sensor. These are the drills of Labs 7, 9 and 11; this lesson is the reason they are in the labs.

Part 4. How Many Times Is Enough?

A test that passed once has shown very little. Suppose the guard of the collision lesson stopped the object in 30 runs out of 30. Can you say that it works? You can say it failed fewer than about one time in ten: if the true failure rate were higher, 30 clean runs in a row would be unlikely. With zero failures in n trials, the 95 % upper bound on the failure rate is 1 − 0.05^(1/n), close to 3/n (the “rule of three”):

What a clean run of trials proves. To claim “fewer than 1 in 100” takes about 300 failure-free runs, and 1 in 1000 takes 1000. A claim of “never fails” cannot be proved by testing at all, only bounded.

The practical rules are these. State the number of trials with the result (“0 of 30”, never “it works”). Do not claim a rate you did not test enough to claim. If you must be better than testing can show, change the design so that the failure is harmless (a deadman, a lease, a limit in hardware) and test that instead; a failure that is harmless needs far fewer trials. And report every run: a test repeated until it passes, with the failures left out, is not evidence.

Part 5. Evidence You Can Hand to Someone Else

A test result is worth what someone else can do with it. Keep a test plan: one row for each requirement, written before testing, filled in after. A reader (the instructor, a teammate, you in three weeks) should be able to repeat a test from its row and compare.

A test plan with three rows (the figures are an illustration, not measurements). T3 fails (97 of 100): that is a valid and useful row. A plan with no failed row either has easy tests or untold results.

Evidence is logged, not remembered. Have every agent keep a record of what it sent and received, with the time and the state (the ring log of the data-logging lesson is enough). When a test fails, the log is what lets you find out why. And with a log of messages you can go one better: replay it. The function below feeds a recorded log to the code under test on the laptop, advancing a fake clock in 20 ms steps, so a failure seen once on the hardware can be reproduced as many times as you like, and with a debugger.

replay.py MicroPython
# replay.py -- feed a recorded log to the code under test, as if it were arriving live import json def replay(lines, agent, clock): """lines: the text of a log with one JSON message per line: {"ms": 1200, "topic": "...", "p": {...}}. agent: an object with on_message(topic, payload_bytes) and tick(now_ms). clock: an object with a settable .ms that the code under test reads in place of ticks_ms().""" prev = None n = 0 for line in lines: rec = json.loads(line) while prev is not None and prev < rec["ms"]: # let time pass, a tick at a time prev += 20 clock.ms = prev agent.tick(prev) clock.ms = prev = rec["ms"] agent.on_message(rec["topic"].encode(), json.dumps(rec["p"]).encode()) n += 1 return n

This closes a loop that is otherwise open: a bug seen on the class WiFi at 2 p.m. becomes a laptop test by 3 p.m., and stays in the test suite as a regression test, so that it can never come back unnoticed. After every change to the code, run the whole suite again; the cost of a test is paid once, and the benefit every time.

Part 6. Before the Demonstration

  • Freeze the code a day before. The version you tested is the version you demonstrate; a “small fix” on the morning has no test.
  • Run the full plan on the frozen files, on the hardware, in the room (or one like it). WiFi in an empty lab is not WiFi in a full one.
  • Start from cold. Power everything off and on, in the order you will use on the day. Many failures live in start-up: a retained message from yesterday, a lease that never expired, a clock that starts at zero.
  • Know the fail-safe. Say, before it happens, what each agent does when its partner or the network disappears. Then pull the plug and show it.
  • Have a recovery story. When something fails on the day, a calm “this is the fault, this is what the system does, this is how I recover” scores higher than silence. It is the same skill as the drills.
  • Keep the spares and the log. A second Pico already flashed, the test plan open, and the log of the last good run.

Exercises

Practice problems in three tiers. Do each on paper or on your own board first, and only then open its solution below. Many problems have more than one correct answer; if yours behaves the same way, it is right even if it looks different.

Warm Up

Exercise 1: Make It Testable. Rewrite “the scan head should track the target well” as a testable requirement, with a stimulus, a limit, a condition and a pass rule.

Exercise 2: How Much Does 20 of 20 Show?. A teammate says: “I ran the stop test 20 times and it worked every time, so it is reliable.” What can honestly be claimed, and what would you ask for?

Intermediate

Exercise 3: Which Test Notices?. Someone changes if len(self.queue) >= self.max_queue to > in the lease. Which test catches it, and why does the property test not?

Exercise 4: Design a Fault. The tracker agent publishes tele/bearing at 5 Hz and the arbiter uses the latest value. Name three faults you would inject between them and the behaviour you would expect from the arbiter in each.

Advanced

Exercise 5: Test a Property. Write one more test for test_lease.py: a lease with lease_ms=1000, one owner and three users waiting, none of whom ever renews. Check that each holds it for exactly one second, in order, and that nobody holds it after four seconds.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Make It Testable

One good answer: “When the target moves at up to 10°/s with 3° of sensor noise, the scan head’s published bearing is within 2° (RMS) of the true bearing over a 30 s run, in 5 of 5 runs, with 30 % of readings missing.” The stimulus is the moving target, the limit is 2° RMS, the condition is the speed, noise and loss, and the pass rule is 5 of 5. Any version that has a number, a condition and a count is acceptable; “well” is not.

Exercise 2: How Much Does 20 of 20 Show?

With 0 failures in 20 trials the 95 % upper bound on the failure rate is 1 − 0.05^(1/20) = 13.9 % (the rule of three gives 15 %). So: “it failed fewer than about 1 time in 7, probably far fewer”, not “reliable”. Ask for the conditions (which network, how many other users), for more trials if a rate of 1 % matters (about 300), and for the log of all 20. Better: ask whether the safe behaviour depends on the stop message at all.

Intermediate

Exercise 3: Which Test Notices?

test_second_claim_queues_in_order catches it: with max_queue=2 the fourth claim is expected to be “full”, but with > the third waiter is let in (position 3). The property test checks only that there is at most one owner and that the owner is not in the queue, which stay true when the queue is a little too long: a different property. Every test checks something specific, which is why a set of tests is needed, and why mutation shows which behaviours have no test.

Exercise 4: Design a Fault

Loss of 40 % of the messages: the arbiter still has a recent value most of the time, so it should keep tracking with a slightly larger error, and a gap longer than the stale limit must make it stop or search. A 2 s delay burst: the values are old when they arrive; the arbiter should judge staleness by arrival time, discount them, and not command a target the tracker has since left. Duplicates and reordering: an older message arriving after a newer one must not move the estimate backwards, so check the sequence number. Also acceptable: a stuck value (the same bearing for ever), which the arbiter should treat as a fault after a while.

Advanced

Exercise 5: Test a Property
test_turns.py MicroPython
class TurnTests(LeaseTests): # added at the end of test_lease.py def test_each_waiter_gets_exactly_one_turn(self): L = Lease(lease_ms=1000, max_queue=3) for u in "abcd": L.claim(u, 0) # a owns it; b, c, d queue up in order owners = [] for t in range(0, 4001, 100): L.tick(t) if not owners or owners[-1][1] != L.owner: owners.append((t, L.owner)) self.assertEqual(owners, [(0, "a"), (1000, "b"), (2000, "c"), (3000, "d"), (4000, None)])

The test steps a fake time in 100 ms ticks and records every change of owner. Each handover starts a new full lease at the moment of the handover, so the changes fall on exact seconds. If this test fails after an edit, the handover now starts its clock somewhere else (for example, from the end of the previous lease rather than from the time it was noticed).

Checkpoint

Before moving on, make sure you can:

  1. Write a requirement with a stimulus, a response, a limit, a condition and a pass rule.
  2. Run unit and property tests on a laptop against the code that runs on the Pico.
  3. Use mutation to check that tests would catch a defect, and test at the edge of every limit.
  4. Inject loss, delay and duplication, and explain a failure that appears only under faults.
  5. State what a number of clean trials proves, and keep evidence others can repeat.
