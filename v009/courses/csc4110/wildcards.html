A well-shaped topic tree pays off the moment you subscribe. Wildcards let one subscription cover many topics, so a dashboard does not need to know how many devices exist. They are simple, with a few sharp edges that cause most of the confusion.

Part 1. The Single-Level Wildcard: +

+ stands for exactly one level. It can appear several times, and in any position, as long as it fills a whole level by itself (lab/pico+ is not a valid filter).

The + wildcard stands for exactly one level. This filter picks out every device's light reading, however many devices there are, and ignores everything else.

A subscription is called a filter to distinguish it from a topic: a topic names one place, a filter describes a set of them. When a new pico04 starts publishing, this filter already includes it; nothing about the dashboard changes.

Part 2. The Multi-Level Wildcard: #

# stands for everything from here down, any number of levels, and it must be the last character of the filter. It also matches the parent level itself, which surprises people.

The # wildcard stands for everything below this point, and it must be last. Note that lab/pico01/# also matches lab/pico01 itself.

Part 3. The Rules in One Place

Three rules cover almost every case. Wildcards belong in subscriptions only; a publish always names one exact topic.

Edge cases are easiest to remember from a table worked out with the same rules the broker uses. Look at the last column in particular: a bare # or + at the first level deliberately does not match topics that start with $. Those belong to the broker itself (next lesson), and a general subscription should not be flooded with them.

Which filters match which topics, worked out by the same rules the broker uses. Two surprises: # alone does not match topics that start with $, and lab/# does match lab itself.

Part 4. Subscribing Sensibly on a Pico

A broad filter is cheap for a laptop and expensive for a Pico. Every message that matches must be received, parsed from the socket and passed to your callback, using RAM and time, so a device should subscribe to as little as it needs: its own command subtree and perhaps one shared topic.

main.py MicroPython
DEVICE = b"pico01" client.set_callback(on_message) client.subscribe(b"lab/" + DEVICE + b"/cmd/#") # my own commands client.subscribe(b"lab/all/cmd/#") # commands for everyone # NOT this: every message from every device would reach a 264 KB board # client.subscribe(b"lab/#")

Two overlapping filters can match the same topic. The broker may then deliver the message once per matching subscription, so a handler should not assume it will see each message exactly once.

Exercise 3: Write a Matcher
match.py MicroPython
def matches(f, t): if t.startswith("$") and f[:1] in ("#", "+"): return False fs, ts = f.split("/"), t.split("/") for i, part in enumerate(fs): if part == "#": return True # matches the rest, and the parent if i >= len(ts): return False if part != "+" and part != ts[i]: return False return len(fs) == len(ts) print(matches("lab/+/tele/light", "lab/pico01/tele/light")) # True print(matches("lab/#", "lab")) # True print(matches("#", "$SYS/broker/uptime")) # False

The loop walks the filter level by level. # ends the comparison successfully; a missing level or a mismatched literal ends it unsuccessfully; and if the filter runs out exactly as the topic does, it matched.

Exercise 4: Who Is Talking?
main.py MicroPython
def on_message(topic, msg): parts = topic.decode().split("/") # ["lab", "pico01", "tele", "light"] device, name = parts[1], parts[3] print(device, name, msg.decode()) on_message(b"lab/pico01/tele/light", b"41230") # pico01 light 41230

This only works because the template fixes what each level means. Had the device id sat at a different depth in different topics, no fixed index would be right, which is why consistent shape matters.
