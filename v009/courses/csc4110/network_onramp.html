A node that can sense and act is useful; a node that can also tell the network what it senses is the starting point of the Internet of Things. This lesson gets your Pico onto the class network and publishing to the class broker with a small helper, so that from this week onward every lab can end by sending its data somewhere. You do not need to understand the protocol yet; you do need to know how to use the helper and how to read what it tells you.

SAM lens. Publishing is the Actuator's network voice: a message changes what other agents can observe. From this week the robot acts on two environments, the physical one and the broker.

Part 1. The Path from Your Board to the Broker

Your node will report to a broker, a program on the class Raspberry Pi whose only job is to receive messages and pass them on to whoever wants them. Think of it as a post office: you drop a message into a labelled box (a topic), and anyone who has asked for that box receives it. The protocol that the Pico and the broker speak is called MQTT, and you will study it properly in Unit 2. For now it is a service you can use: the helper below hides the details.

The path a message takes. Every step can fail in its own way, and the helper reports which one did, so you can tell a network problem from a code problem. A laptop (or another student’s program) can subscribe to the broker and see what you publish.

Part 2. What Your Instructor Gives You

Three things: the name and password of the class WiFi network, the address of the broker (an IP address on that network), and your own broker login (a user name and password). Put them in a file called config.py on the Pico, in exactly this form:

config.py MicroPython
# config.py -- your own settings. Never share this file or put it online. WIFI_SSID = "class-network-name" # given to you in class WIFI_PASSWORD = "wifi-password" BROKER = "192.168.1.50" # the address of the class Raspberry Pi broker BROKER_PORT = 1883 MQTT_USER = "jsmith" # your own login for the broker MQTT_PASSWORD = "your-broker-password"

Keep this file on your board and your laptop only. It holds passwords, so it must never be pasted into a chat, a report or a public repository. Your broker login is yours alone: the broker lets you publish only under lab/<your user name>/ and lets you read other topics, so a mistake in your program cannot damage anyone else’s.

What lives on your board. main.py is your program; net.py and config.py sit beside it, and the MQTT client library is in a lib folder (it may already be built into the firmware: check with import umqtt.simple, as in the Thonny lesson).

Part 3. The Helper: net.py

Here is the whole file. You do not have to write it, but you should read it, because Unit 2 is largely about the ideas inside it. The key design goals are that publish never raises an error (a robot should not crash because the WiFi dropped) and never waits long (a lost network should not freeze your control loop):

net.py MicroPython
# net.py -- the class network helper for CSC/EGR 4110. # Copy it to the Pico next to main.py, and put your settings in config.py. # # import net # net.publish("tele/range", {"cm": 23.4}) # never raises, never blocks for long # import json import network from time import ticks_ms, ticks_diff, sleep_ms import config try: from umqtt.simple import MQTTClient except ImportError: MQTTClient = None NO_WIFI, NO_BROKER, ONLINE, NO_LIB = "NO WIFI", "NO BROKER", "ONLINE", "NO MQTT LIB" class Link: def __init__(self, retry_s=15, wifi_timeout_s=8, log_max=40): self.wlan = network.WLAN(network.STA_IF) self.client = None self.status = NO_WIFI self.on_status = None # optional: a function(status) called on every change self.retry_ms = retry_s * 1000 # how long to leave a dead network alone self.wifi_timeout_ms = wifi_timeout_s * 1000 self.last_try = None self.seq = 0 # counts every message you ask to send self.log = [] # messages that could not be sent yet self.log_max = log_max self.sent = 0 self.dropped = 0 self.root = "lab/%s/" % config.MQTT_USER self.keepalive = 0 # seconds; 0 means "no keepalive" (Unit 2 changes this) self.cid = b"pico-" + config.MQTT_USER.encode() # the broker allows one connection per id def _set(self, status): if status != self.status: self.status = status if self.on_status: self.on_status(status) def _wifi_up(self): if self.wlan.isconnected(): return True self.wlan.active(True) self.wlan.connect(config.WIFI_SSID, config.WIFI_PASSWORD) t0 = ticks_ms() while not self.wlan.isconnected(): if self.wlan.status() < 0: # negative codes mean a definite failure return False if ticks_diff(ticks_ms(), t0) > self.wifi_timeout_ms: return False sleep_ms(100) return True def _make_client(self): return MQTTClient(self.cid, config.BROKER, config.BROKER_PORT, config.MQTT_USER, config.MQTT_PASSWORD, keepalive=self.keepalive) def connect(self): """Try to get all the way to the broker. Returns True if online.""" self.last_try = ticks_ms() if not self._wifi_up(): self.client = None self._set(NO_WIFI) return False if MQTTClient is None: self._set(NO_LIB) return False try: c = self._make_client() c.connect() self.client = c self._set(ONLINE) return True except OSError: self.client = None self._set(NO_BROKER) return False def _drop(self): try: self.client.disconnect() except Exception: pass self.client = None self._set(NO_WIFI if not self.wlan.isconnected() else NO_BROKER) def _stash(self, topic, payload, retain): self.log.append((topic, payload, retain)) if len(self.log) > self.log_max: self.log.pop(0) # keep the newest; forget the oldest self.dropped += 1 def _flush(self, limit): """Send up to `limit` queued messages, oldest first.""" while self.log and limit > 0 and self.client: topic, payload, retain = self.log[0] try: self.client.publish(topic, payload, retain) except OSError: self._drop() return self.log.pop(0) # forget it only after it was sent self.sent += 1 limit -= 1 def publish(self, topic, data, retain=False): """Send data (a dict or a single value) to lab/<you>/<topic>. Returns True if everything, including any backlog, has now left the board.""" self.seq += 1 body = {"v": 1, "seq": self.seq, "t": ticks_ms()} if isinstance(data, dict): body.update(data) else: body["value"] = data self._stash(self.root + topic, json.dumps(body), retain) # everything is queued first, if self.status != ONLINE: # so order is always kept if self.last_try is None or ticks_diff(ticks_ms(), self.last_try) >= self.retry_ms: self.connect() if self.status == ONLINE: self._flush(5) # a few per call: a long backlog never stalls the loop return not self.log _link = None def link(): global _link if _link is None: _link = Link() return _link def publish(topic, data, retain=False): return link().publish(topic, data, retain) def status(): return link().status

Read it in three layers. At the bottom, Link.connect climbs the ladder: join the WiFi, then log in to the broker, and record in status how far it got. In the middle, publish builds the message (a small envelope plus your data), puts it in a queue, and, if online, sends the oldest few messages. At the top, the module-level publish(topic, data) creates one shared Link the first time you call it, so you never construct anything.

Part 4. Using It

The smallest working node needs no extra wiring: the Pico’s own temperature sensor and LED are enough.

main.py MicroPython
import net from machine import ADC, Pin from time import sleep_ms adc = ADC(4) # the chip's internal temperature sensor led = Pin("LED", Pin.OUT) def temp_c(): return 27 - (adc.read_u16() * 3.3 / 65535 - 0.706) / 0.001721 net.link().on_status = lambda s: print("net:", s) # print every change of network state while True: delivered = net.publish("tele/temp", {"c": round(temp_c(), 1)}) led.value(delivered) # LED on = this message (and any backlog) got out sleep_ms(2000)
Topic and payload. net.publish("tele/temp", {"c": 27.4}) sends this message to lab/jsmith/tele/temp. The helper adds v (format version), seq (a counter that rises with every call) and t (milliseconds since the board started); your own fields come after them.

The tele/ in the topic is a convention that we keep all term: telemetry, readings that a node reports. Later you will use cmd/ for commands sent to a node and stat/ for state it announces. Following the convention means other people’s programs can find your data without asking you.

Show the network state on the node itself. A robot in a field has no laptop beside it:

status_lcd.py MicroPython
# with the LCD from the I2C lesson already created as `lcd` def show(status): lcd.line("net " + status, 1) # second line of the display net.link().on_status = show

Part 5. What Happens When It Fails

The three network states. The helper moves between them by itself. A reconnect attempt can block for up to about 8 seconds (waiting for WiFi), so a loop that must never stall needs the non-blocking style that Unit 2 develops; for now, the 15 s spacing keeps the cost small.
An outage, as the broker sees it. Messages 5 to 9 were taken while the WiFi was down and were kept; when the network returned they were delivered oldest first, a few per call. Because seq and t travel with each message, a receiver can tell exactly what happened.

Part 6. Watching the Broker

To see your own messages, subscribe from a laptop on the class network. If you have the Mosquitto client tools installed, one command does it (# means "everything below this topic"):

shell Shell
mosquitto_sub -h 192.168.1.50 -u jsmith -P your-broker-password -t "lab/jsmith/#" -v

A desktop MQTT viewer (such as MQTT Explorer) does the same with a window and a tree of topics, and needs the same four things: the broker address, port 1883, your user name and your password. You are allowed to subscribe to the other students’ topics (lab/+/tele/#, where + means "any one name") but not to publish to them.

Class rules: publish at most about 10 messages per second from one node in total, keep payloads under about 200 bytes, and publish telemetry only under your own name. The broker is shared by everyone, and a program stuck in a fast loop sending thousands of messages can slow the whole class (and the lab practical) down.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Build the Topic

The topic is lab/ajones/tele/range: the helper puts lab/<user>/ in front. The payload contains v, seq, t and cm, in that order, for example {"v": 1, "seq": 1, "t": 5120, "cm": 23.4}.

Exercise 2: Read the Status

NO BROKER means the WiFi joined (the helper only tries the broker after that) but the connection to the broker failed. Likely causes: the broker address in config.py is wrong, the broker is not running or not reachable from this network, or the user name or password is wrong. It is not the WiFi password, which would give NO WIFI.

Intermediate

Exercise 3: Too Many Messages

Combine the three readings into one message and send it at 5 Hz: net.publish("tele/all", {"light": l, "cm": d, "roll": r}). That is 5 messages per second (under the limit). If you need more time resolution, include a short list for each field (the last four readings at 20 Hz) in each message. Bandwidth: 5 × 90 = 450 B/s, down from 3 × 20 messages of about 75 bytes each, or 4500 B/s. Fewer, fuller messages waste less on envelope.

Advanced

Exercise 4: Average, Then Report

Take the current time as a parameter instead of reading the clock inside. Then a test can drive it with any sequence of times, and the main loop simply passes ticks_ms():

report.py MicroPython
class Reporter: def __init__(self, publish): self.publish = publish self.window = [] self.next_sample = 0 self.next_report = 500 def tick(self, now, read): if now >= self.next_sample: self.window = (self.window + [read()])[-5:] # keep only the last five self.next_sample += 100 # 10 readings per second if now >= self.next_report and self.window: self.publish("tele/avg", {"avg": sum(self.window) / len(self.window)}) self.next_report += 500 # twice per second # on the board: # r = Reporter(net.publish) # while True: # r.tick(ticks_ms(), adc.read_u16)
test_report.py MicroPython
sent = [] r = Reporter(lambda topic, data: sent.append(data["avg"])) for now in range(0, 10_001, 10): # ten simulated seconds in 10 ms steps r.tick(now, lambda: 20) print(len(sent), sent[0]) # 20 20.0

Twenty messages in ten seconds, as designed. The class has two timers and no sleep, the same cooperative-loop shape as the Pulses lesson, and because time is an argument the test needs no hardware and no waiting.

Paper Practice: Answers

Recall

P1. The Broker

A program that receives published messages and passes each one to every client subscribed to its topic; it runs on the class Raspberry Pi.

P2. Envelope

v: format version; seq: a counter that rises with each message; t: milliseconds since the board started. A receiver can detect a changed format, lost or reordered messages (gaps in seq), and when each reading was taken (t), even if delivered late.

P3. Topic Conventions

tele: telemetry, readings a node reports. cmd: commands sent to a node. stat: state a node announces.

P4. Secrets

It holds the WiFi password and your personal broker login; anyone with them can connect as you.

Apply

P5. Full Topic

lab/jsmith/tele/imu.

P6. Wildcards

(a) yes; (b) no (stat, not tele); (c) yes (# matches any number of levels); (d) no (+ must match exactly one level, and the next level must be tele).

P7. Sequence Gaps

Messages 42, 43 and 44 were lost (or are still in flight and will arrive late, out of order).

P8. Class Limits

No: 15 messages per second exceeds about 10 per second (the payload size is fine). Combine the three into one message at 5 Hz, or lower the rates.

P9. Byte Rate

(20 + 60 + 5) × 2 = 170 B/s.

Analyze and Design

P10. Read the Ladder

The radio joined the network, so the WiFi name and password are right; suspect the broker address, port, user name or password, or the broker being down. WIFI FAIL points at the network name or password, distance from the access point, or a network the Pico cannot join.

P11. Blocking Reconnect

The loop stalls for up to 8 s, missing up to 400 ticks. Acceptable while the node only reports (the 15 s spacing limits how often it happens), but not for a robot that must keep control; Unit 2 develops a non-blocking reconnect.

P12. What to Send

Telemetry (tele/... with setpoint, measurement, output) at a modest rate such as 2 to 5 Hz, enough to plot behaviour within the class limit; an event (evt/lock) the moment it gains or loses lock, because a fixed-rate sample might miss the moment. The controller itself never waits for the network.
