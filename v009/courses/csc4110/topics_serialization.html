Last lesson's topics, lab/pico01/status and lab/pico01/cmd, weren't arbitrary strings, MQTT topics follow a deliberate naming convention, and designing that hierarchy well is most of what separates an MQTT setup that scales cleanly from one that becomes unmanageable the moment a second or third device joins. This lesson also covers the other half of every message: not just where it goes, but how its contents are packaged.

Part 1. Topics Are a Tree, Not a Flat List

MQTT topics are hierarchical strings, segments separated by /, read as a path from general to specific, much like a file path. There's no requirement to register a topic in advance; publishing to a topic that's never been used before simply creates it, from the broker's point of view, the instant the first message arrives.

This specific layout, lab/<device>/<kind>, is this course's convention, not a rule MQTT itself imposes. The broker treats every topic as just a string; the tree structure is a human organizing principle laid on top.

Part 2. Wildcards

Topic hierarchies pay off most clearly when subscribing, not publishing. A + matches exactly one segment, a # matches any number of remaining segments:

  • lab/+/status subscribes to every device's status, pico01, pico02, any future one, without listing them individually.
  • lab/pico01/# subscribes to everything under pico01, status, temp, cmd, and anything added later, in one subscription.
  • # alone subscribes to literally everything on the broker, useful for debugging, rarely appropriate in real device code.

This is the direct payoff of a well-organized topic tree: a dashboard watching every device's status doesn't need to know how many devices exist, it subscribes to lab/+/status once, and a new Pico joining tomorrow is automatically included without changing a single line on the dashboard side.

Part 3. Payload Serialization: Why Not Just Send a Number?

An MQTT message's payload is just bytes, MQTT has no opinion on what's inside, "online" from last lesson worked fine as a raw string. The moment a message needs to carry more than one piece of information, a reading plus the time it was taken, say, raw text stops scaling and you need a convention both the sender and every receiver agree on in advance. That convention is serialization: a consistent way to turn a Python value (a number, a dictionary) into bytes, and back again on the other end.

JSON is this course's serialization format, for the same reason it's extremely common in IoT generally: it's human-readable (useful for debugging with mosquitto_sub directly), and MicroPython's json module makes converting to and from it trivial.

main.py MicroPython
import json reading = {"value": 41230, "unit": "raw_adc"} payload = json.dumps(reading) # '{"value": 41230, "unit": "raw_adc"}' (a str) client.publish(b"lab/pico01/temp", payload.encode()) # publish() needs bytes

json.dumps() returns a str, and .encode() converts that str to the bytes that publish() actually requires, the same bytes-not-string requirement last lesson's b"online" satisfied directly by being written as a byte literal in the first place. On the receiving end, the reverse:

main.py MicroPython
def on_message(topic, msg): reading = json.loads(msg) # bytes -> dict print(reading["value"], reading["unit"])
The parts of a JSON object. It is plain text, so people can read it in mosquitto_sub, and any language can parse it.
A reading changes form several times between sensor and subscriber. Knowing which form you are holding at each step explains most serialization errors.

Exercise 3: Round Trip
main.py MicroPython
import json # sender reading = {"value": 123, "unit": "adc"} client.publish(b"lab/pico01/data", json.dumps(reading).encode()) # receiver def on_message(topic, msg): data = json.loads(msg) # bytes -> dict print(data["value"])

json.loads accepts the bytes directly in MicroPython, so no extra decode step is needed.

Advanced

Exercise 4: Survive Bad Data
main.py MicroPython
def on_message(topic, msg): try: data = json.loads(msg) value = data["value"] except (ValueError, KeyError): print("ignored bad message on", topic, msg) return print(value)

Never trust incoming data: any other client on the broker can publish anything to your topic. ValueError covers broken JSON; KeyError covers valid JSON with the wrong shape.
