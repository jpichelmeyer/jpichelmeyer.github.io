This lesson covers what to record and where. You separate events from samples, bound the node’s own log with a ring in flash, write the hub’s log to SQLite and ask it questions with SQL, and keep storage finite with downsampling and an explicit retention rule.

A robot that works is nice; a robot that works and can explain what it did is engineering. When the arm jerked at 14:07, when two agents disagreed, when the node reset at night, the only way to find out why is a record. Logging is the discipline of deciding what to keep, where to keep it, and for how long, with storage that is finite at both ends: a few kilobytes of flash on the Pico, a few gigabytes of disk on the hub. This lesson builds one logger for each end, and a rule for what to throw away.

Part 1. What Is Worth Keeping

Not all records are equal. Events are rare and explain behaviour, so they are kept a long time. Samples are plentiful and cheap, so they are kept briefly and then replaced by summaries.

A useful test: for each line you log, write down the question it will answer. “Why did the motor stop?” is answered by a stop,deadman event. “Was the signal noisy?” is answered by a minute of samples, or by their standard deviation. A line that answers no question is storage spent on nothing.

Part 2. A Log in the Node’s Flash

The node’s own log is its black box: what it did and why, kept even when the network is gone. The constraint is hard: the flash holds perhaps a megabyte of free space, it wears out, and it must never fill up and break the program. The solution is a ring log: a fixed number of fixed-size segments, and when the newest is full the oldest is deleted. The log occupies at most segs × seg_bytes, and holds the newest history.

ringlog.py MicroPython
# ringlog.py -- a bounded log in flash: the newest few kilobytes, never more import os class RingLog: def __init__(self, prefix="log", seg_bytes=4096, segs=4): self.prefix, self.seg_bytes, self.segs = prefix, seg_bytes, segs names = [n for n in os.listdir() if n.startswith(prefix + ".")] nums = [int(n.split(".")[1]) for n in names if n.split(".")[1].isdigit()] self.cur = max(nums) if nums else 0 self.size = self._size(self.cur) def _name(self, n): return "%s.%d" % (self.prefix, n) def _size(self, n): try: return os.stat(self._name(n))[6] except OSError: return 0 def add(self, line): data = line + "\n" if self.size + len(data) > self.seg_bytes: self.cur += 1 self.size = 0 try: os.remove(self._name(self.cur - self.segs)) # drop the oldest segment except OSError: pass with open(self._name(self.cur), "a") as f: f.write(data) self.size += len(data) def lines(self): for n in range(max(0, self.cur - self.segs + 1), self.cur + 1): try: with open(self._name(n)) as f: for ln in f: yield ln.rstrip("\n") except OSError: pass
use.py MicroPython
import time from ringlog import RingLog log = RingLog("log", seg_bytes=4096, segs=4) # about 16 kB at most def note(kind, *vals): log.add("%d,%s,%s" % (time.ticks_ms(), kind, ",".join(str(v) for v in vals))) note("boot", reset_cause()) note("link", "down") note("cmd", "pan", 30, "ok") note("stop", "deadman")
The ring log. The storage is bounded by construction, so the log can never take the flash away from the program.

Writing 1,000 lines like 2150,cmd,pan,215,ok produced exactly four files, log.1 to log.4, holding 15,700 bytes together (under the 16,384 limit), and lines() returned the newest 785 of them, the first being line 215. A restarted RingLog found the highest segment number on flash and carried on from it. Two cautions. Each add opens, appends and closes the file, which costs a few milliseconds and some wear: log events, not samples. And on a power cut the last line can be half written, so a reader should ignore a final line that does not parse.

Part 3. A Log at the Hub

The hub has no such limits, so it can keep everything, and it can query it. The simplest durable logger is a program that subscribes to everything and writes each message to a SQLite file. SQLite is a database in one ordinary file, with SQL for asking questions, and Python includes it.

logger.py Python
# logger.py -- on the laptop: every message into one SQLite file # mosquitto_sub -h BROKER -u USER -P PW -t 'lab/#' -v | python3 logger.py lab.db import sys, sqlite3, time db = sqlite3.connect(sys.argv[1]) db.execute("""CREATE TABLE IF NOT EXISTS msgs ( ts REAL, user TEXT, topic TEXT, payload TEXT)""") db.execute("CREATE INDEX IF NOT EXISTS msgs_user_ts ON msgs (user, ts)") def user_of(topic): p = topic.split("/") return p[1] if len(p) > 2 and p[0] == "lab" else "" n, last = 0, time.time() for line in sys.stdin: topic, _, payload = line.rstrip("\n").partition(" ") db.execute("INSERT INTO msgs VALUES (?, ?, ?, ?)", (time.time(), user_of(topic), topic, payload)) n += 1 if time.time() - last >= 1.0: # commit once a second, not once a message db.commit() last = time.time() db.commit() print("logged", n, "messages")

Two details make it fast enough. It commits once a second, not once per message (a commit waits for the disk, and dominates the cost), and it has an index on (user, ts) so that “this student, this hour” does not read the whole table. On the test machine, 30,000 messages went into the database in 0.12 s (including starting Python), at about 71 bytes per row on disk. With the class traffic of 24 students at the limit of 10 messages per second, that is about 17 kB/s, or 1.5 GB per day: a real number, and it leads to the next part.

questions.sql SQL
-- how much did each student send in the last 10 minutes? SELECT user, COUNT(*) AS n, COUNT(*) / 600.0 AS per_s FROM msgs WHERE ts > strftime('%s','now') - 600 GROUP BY user ORDER BY n DESC; -- the last state each robot announced SELECT topic, payload, MAX(ts) FROM msgs WHERE topic LIKE '%/stat/state' GROUP BY topic; -- one-minute averages of a field (downsampling) SELECT CAST(ts / 60 AS INT) * 60 AS minute, AVG(json_extract(payload, '$.c')) AS mean_c, COUNT(*) AS n FROM msgs WHERE topic = 'lab/jsmith/tele/temp' GROUP BY minute ORDER BY minute; -- retention: keep seven days of raw messages DELETE FROM msgs WHERE ts < strftime('%s','now') - 7 * 86400;

The three queries answer the questions of the course: who is sending too much, what state is everyone in, and what did one signal do over time. The last statement is the retention rule, run once a day.

Part 4. Keep Less, Keep Better

Downsampling is a trade of detail for time. A minute of 10 Hz data becomes one row: six hundred times smaller, and still enough to see a drift or an outage.

The test run turned 10,000 rows of one signal into a single one-minute row with AVG, COUNT and a GROUP BY. In practice, store the mean, the minimum, the maximum and the count (n): the mean alone hides the spikes that you are often looking for, and n shows when data is missing, because an outage appears as a minute with a small n. Make the retention rule explicit, and put it in a scheduled job, because a disk that fills is a failure like any other.

  • Time. The node’s ticks_ms restarts at every boot and is not a calendar. The hub stamps messages with its own clock on arrival, which is accurate to the network delay; the node’s t in the message envelope orders messages from one node. Keep both.
  • Privacy and honesty. A log is evidence. Do not edit it, and do not log secrets: passwords never belong in a message or a log line.
  • Use the log. A log nobody reads is only a disk heater. Look at it after every lab drill; most of the next lesson’s statistics start there.

Warm Up

Exercise 1: Pick the Kind. For each, say whether it is an event, a state change, a fault or a sample, and how long you would keep it: (a) range 41.8, (b) owner changed to amy, (c) reset cause WDT, (d) pan command refused: too fast.

Exercise 2: How Much Flash?. A ring log has 6 segments of 2,048 bytes. Each line is about 25 bytes and the node logs one event every 10 seconds. How many bytes does it hold at most, and about how long a history is that?

Intermediate

Exercise 3: The Row Count. A class of 24 students each sends 10 messages per second for a 3-hour lab. How many rows does the logger write, and how large is the database at 71 bytes per row?

Advanced

Exercise 4: Answer It With SQL. Write a query on msgs that lists, for each topic of the form lab/<user>/evt/ack, how many acks arrived in the last hour, most first. Then say which of the columns benefits from an index.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Pick the Kind

(a) sample: days, then a summary. (b) state change: long. (c) fault: longest, with the reset count. (d) event (a refused command): long enough to debug a client, and worth counting so that a client sending refused commands stands out.

Exercise 2: How Much Flash?

6 × 2,048 = 12,288 bytes, which holds about 12,288 / 25 = 491 lines, so 491 × 10 s = about 4,900 seconds, roughly 80 minutes of history. If you need a day, either log less often, log shorter lines, or send older lines to the hub.

Intermediate

Exercise 3: The Row Count

24 × 10 × 3 × 3,600 = 2,592,000 rows, and 2,592,000 × 71 ≈ 184 MB. It is fine for a laptop, but a week of such labs without the retention rule would be over a gigabyte. Note that this is the limit; the real load is usually much lower, which is the reason to measure it with the first query.

Advanced

Exercise 4: Answer It With SQL
acks.sql SQL
SELECT topic, COUNT(*) AS n FROM msgs WHERE topic LIKE 'lab/%/evt/ack' AND ts > strftime('%s','now') - 3600 GROUP BY topic ORDER BY n DESC;

The ts condition benefits from an index on time; the LIKE with a leading wildcard cannot use an index on topic. To make this query cheap, add an index on (ts) or add a column for the kind (ack, tele, stat) filled in by the logger, and filter on that. Design the table for the questions you will ask.
