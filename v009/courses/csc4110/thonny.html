Every board in this course starts life blank: no code, not even an operating system. The very first thing you'll do with your Raspberry Pi Pico WH is give it a language to speak, MicroPython, and an editor to speak it in, Thonny. Everything else this semester, from blinking an LED to streaming sensor data to a broker across the room, happens inside the loop you set up today: write code in Thonny, run it on the Pico, watch what happens, repeat.

Part 1. Two Very Different Kinds of "Computer"

The Pico WH has no operating system, no files-and-folders desktop, no way to plug in a monitor. It runs exactly one program at a time, starting the instant it gets power, and that program is the whole machine's purpose until you change it. MicroPython is what makes that programmable: a slimmed-down implementation of Python designed to run directly on hardware like this, with no OS underneath it at all.

Flashing MicroPython onto a blank Pico means copying a single firmware file onto it while it's pretending to be a USB flash drive. After that one-time step, the Pico boots straight into a Python interpreter every time it gets power, no further flashing needed for ordinary code changes.

The Pi 3B+ you'll use as this course's broker is a full computer; the Pico WH each of you is building with is not. Next lesson digs into exactly what "microcontroller" means -- for now, just notice there's no desktop to boot into.

Part 2. Installing Thonny

Thonny is a free, beginner-oriented Python editor that happens to also be one of the most common tools for MicroPython development, which is why it's this course's default. Download it from thonny.org for your own OS (Windows, macOS, or Linux) and install it like any other application. No account, no configuration needed to get started.

Thonny's layout, with the four parts you will use constantly: 1 the script editor, 2 the shell (a live MicroPython prompt on the Pico), 3 the green Run and red Stop buttons, and 4 the interpreter shown at the bottom right, which must say MicroPython (Raspberry Pi Pico), not "Local Python 3".

Part 3. Flashing MicroPython

A brand-new Pico WH (or one that's been used for something else before) needs the MicroPython firmware installed once. Do this exactly once per board, not every time you write new code:

  1. Unplug the Pico WH from USB if it's connected.
  2. Find the small white BOOTSEL button on top of the board.
  3. Hold BOOTSEL down, plug the USB cable into your computer while still holding it, then let go after a second or two.
  4. The Pico should appear on your computer as a USB drive named something like RPI-RP2, the same way a USB flash drive would.
  5. In Thonny: Run → Select interpreter..., choose "MicroPython (Raspberry Pi Pico)" as the interpreter, and use the "Install or update firmware" link Thonny shows there. Point it at the RPI-RP2 drive and let it install.
  6. The board will reboot on its own once firmware is written. The RPI-RP2 drive disappears, and Thonny should now show a live MicroPython shell at the bottom of its window.

If you ever want to start over (a board behaving strangely, say), BOOTSEL + replug gets you right back to step 4; flashing firmware again doesn't erase working hardware, only the software on it.

The one-time firmware install. Holding BOOTSEL while plugging in makes the Pico present itself as a flash drive instead of running code; once MicroPython is on it, you never need to do this again for ordinary programming.

Part 4. Shell vs. Script: Two Ways to Run Code

Thonny gives you two genuinely different ways to run MicroPython, and knowing which one you're in matters all semester.

The shell is for poking at things interactively, trying one line, seeing what it does, trying the next. A file saved onto the Pico as main.py is what actually turns your board into a standalone device -- unplug it from your laptop, plug it into a wall charger, and it still runs.

In Thonny, the bottom panel is the shell. The top panel is a script editor; Ctrl+S (or Cmd+S) there asks where to save, and choosing "Raspberry Pi Pico" as the destination (rather than your own computer) saves the file onto the board itself. Name a file exactly main.py on the Pico and it becomes the program that runs automatically every time the board gets power, with or without Thonny open.

main.py MicroPython
from machine import Pin from time import sleep led = Pin("LED", Pin.OUT) while True: led.toggle() sleep(0.5)

Type that into the editor, save it to the Pico as main.py, and press the green Run arrow (or F5). The onboard LED should start blinking. Don't worry yet about what Pin("LED", Pin.OUT) actually means, that's next lesson, this is just confirming the whole chain (Thonny → USB → Pico → running code) genuinely works end to end.

Part 5. A Few Early Habits

  • Stop before you unplug. Use Thonny's Stop button (red square) before disconnecting, rather than yanking the USB cable while code is running.
  • One Thonny, one Pico. Only one program can talk to the Pico's USB serial connection at a time. If Thonny can't connect, check that nothing else (another Thonny window, a terminal program) is already holding that connection open.
  • The shell survives a crashed script. If your main.py has an error, the Pico drops back to the interactive shell rather than bricking itself. Read the error message in the shell panel, it names the exact line.

Exercises

Practice problems in three tiers. Do each on paper or on your own board first, and only then open its solution below. Many problems have more than one correct answer; if yours behaves the same way, it is right even if it looks different.

Warm Up

Exercise 1: Shell or Script?. For each job, say whether you would use the shell or a saved main.py, and why: (a) checking what 2 ** 10 is; (b) making the board blink when it is plugged into a wall charger with no computer; (c) trying different pin numbers to see which one lights an LED.

Exercise 2: Wrong Interpreter. A classmate runs from machine import Pin in Thonny and gets ModuleNotFoundError: No module named 'machine'. The bottom-right of their Thonny window says "Local Python 3". What is wrong, and how do they fix it?

Intermediate

Exercise 3: Triple Blink. Write a main.py that blinks the onboard LED three times quickly (0.1 s on, 0.1 s off), pauses for 2 seconds, and repeats forever.

Advanced

Exercise 4: SOS. Write a function blink(seconds) that lights the LED for that long and then turns it off with a short gap, and use it to flash the Morse code for SOS (three short, three long, three short) repeatedly. Then answer: your script has an endless loop and is saved as main.py. How do you get control of the board back?

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Shell or Script?

(a) Shell: a one-off calculation needs no saving. (b) main.py: only a file saved on the Pico runs by itself at power-up, with nothing attached. (c) Shell: quick experiments are exactly what a live prompt is for, and nothing needs to survive a reboot.

Exercise 2: Wrong Interpreter

Thonny is running the code on the computer's ordinary Python, which has no machine module (that module only exists in MicroPython, on the board). Switch the interpreter to MicroPython (Raspberry Pi Pico) from the bottom-right selector or Run → Configure interpreter, and make sure the Pico is plugged in.

Intermediate

Exercise 3: Triple Blink
main.py MicroPython
from machine import Pin from time import sleep led = Pin("LED", Pin.OUT) while True: for _ in range(3): led.value(1) sleep(0.1) led.value(0) sleep(0.1) sleep(2)

The inner for loop does the three blinks; the outer while True repeats the whole pattern forever.

Advanced

Exercise 4: SOS
main.py MicroPython
from machine import Pin from time import sleep led = Pin("LED", Pin.OUT) def blink(seconds): led.value(1) sleep(seconds) led.value(0) sleep(0.2) # gap between flashes while True: for _ in range(3): blink(0.2) # S for _ in range(3): blink(0.6) # O for _ in range(3): blink(0.2) # S sleep(1.5)

To regain control, press Thonny's red Stop button (or Ctrl+C in the shell), which interrupts the running program and returns you to the prompt. The saved file is untouched, so it will start again the next time the board gets power.
