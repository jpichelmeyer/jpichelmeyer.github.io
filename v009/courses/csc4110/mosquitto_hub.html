This lesson opens the class broker. You learn what Mosquitto is, how its configuration, password and access-list files decide who may connect and what each user may read and write, how to watch it with the command-line tools and its $SYS statistics, and how to read its log when a node cannot connect or a message never arrives.

Up to now the broker was somebody else’s machine. This lesson opens it: what Mosquitto is, how its three small files decide who may connect and what each user may read and write, and how to watch it work. Students normally only use the instructor’s broker, but you will run your own on a laptop in Lab 5, and a robot team that cannot read a broker log cannot find its own faults.

Part 1. A Hub in Three Files

The class hub. Every client talks only to the broker. Three files decide its behavior: the configuration, the list of users and passwords, and the access list. Change any of them and restart (or reload) the service.

Mosquitto is a small, open-source MQTT broker that runs happily on a Raspberry Pi. It starts as a system service, reads its configuration, and from then on does nothing but accept connections and move messages. It stores nothing except retained messages and the sessions of clients that asked for them.

Part 2. Installing and Configuring

On the Pi (or any Debian machine) the package is called mosquitto, and the command-line tools you used in Unit 1 come in mosquitto-clients. On a Mac, brew install mosquitto installs both; on Windows use the installer from the Mosquitto website. Then write a configuration file:

install Shell
sudo apt update sudo apt install mosquitto mosquitto-clients sudo systemctl enable --now mosquitto
class.conf Config
# /etc/mosquitto/conf.d/class.conf listener 1883 # without this, Mosquitto 2.x listens on localhost only allow_anonymous false # everyone must log in password_file /etc/mosquitto/passwd acl_file /etc/mosquitto/acl persistence true # keep retained messages across a restart persistence_location /var/lib/mosquitto/ message_size_limit 1024 # refuse payloads over 1 kB max_queued_messages 200 # per offline client with a persistent session connection_messages true # log every connect and disconnect log_type error log_type warning log_type notice

Two lines deserve attention. Since version 2.0 Mosquitto will not accept connections from other machines unless you declare a listener, a deliberate default meant to stop accidental exposure. And allow_anonymous false forces a login: without it, anybody who can reach the port can publish to anything. The class network is private, but a broker reachable from the internet with no login is found by scanners within hours.

Part 3. Users and the Access List

users.sh Shell
# on the Pi (creates the file with the first user; -c would erase an existing file, so use it only once) sudo mosquitto_passwd -c /etc/mosquitto/passwd instructor sudo mosquitto_passwd /etc/mosquitto/passwd jsmith # prompts for jsmith's password sudo mosquitto_passwd -D /etc/mosquitto/passwd jsmith # removes a user # after any change to the files: sudo systemctl restart mosquitto sudo journalctl -u mosquitto -f # watch the log

Passwords are stored as salted hashes, not as text, so the file does not reveal them (but it should still be readable only by the broker). The next file says what each logged-in user may do. Lines starting with pattern apply to every user, with %u replaced by the user’s name; lines under a user heading apply to that user alone.

acl Config
# /etc/mosquitto/acl # The instructor can do anything. user instructor topic readwrite # # Everyone else (patterns apply to every logged-in user; %u is the user name): pattern write lab/%u/# # write only inside your own subtree pattern read lab/# # read everyone's data pattern read robot/# # read the instructor's robot pattern read $SYS/# # read the broker's own statistics
What the access list above allows for the user jsmith. The most important property is the second row: a publish that the ACL denies is not an error the client sees. The message simply never arrives.

That last point causes more lost afternoons than any other. With MQTT 3.1.1, the version umqtt speaks, the broker has no way to say “not authorised” to a publisher, so it quietly discards the message (it may even acknowledge it at QoS 1). The same applies to a subscription to a forbidden topic: you are subscribed, and you will hear nothing. The only evidence is the broker’s log, and a message that never shows up at a subscriber. When a publish does not arrive, check the topic’s spelling against the access list before you debug your code.

Part 4. Watching the Broker

Two tools, both in mosquitto-clients, are enough for nearly everything:

cheatsheet.sh Shell
# watch everything in the class, with topic names (-v) mosquitto_sub -h BROKER -u USER -P PASS -v -t "lab/#" # only five messages, then stop (-C), give up after ten seconds (-W) mosquitto_sub -h BROKER -u USER -P PASS -v -t "lab/+/tele/#" -C 5 -W 10 # publish once; -r makes it retained mosquitto_pub -h BROKER -u USER -P PASS -t "lab/USER/stat/note" -m "hello" -r # clear a retained message: publish an empty one mosquitto_pub -h BROKER -u USER -P PASS -t "lab/USER/stat/note" -n -r # show the packets (PINGREQ and all) as they happen mosquitto_sub -h BROKER -u USER -P PASS -d -t "lab/USER/#" # the broker's own statistics mosquitto_sub -h BROKER -u USER -P PASS -v -t "$SYS/broker/clients/connected" -t "$SYS/broker/load/messages/received/1min"

The broker also publishes statistics about itself on topics beginning with $SYS. Wildcards at the first level do not match them (a plain # will not show them), so you ask for them by name.

Useful statistics. The first number to watch during a lab is the count of connected clients: if it is one short of what you expect, someone’s board has not reached the broker, and you have a lower-layer problem.

A class shares one hub, so a node that publishes too fast hurts everyone. Mosquitto has no per-user rate limit built in; the class limit of 10 messages per second per student is an agreement, and the following program lets any student (or the instructor) see who is over it. It reads the stream from mosquitto_sub on its standard input.

rate_watch.py Python
# rate_watch.py: run on a laptop. # mosquitto_sub -h BROKER -u USER -P PASS -v -t "lab/#" | python3 rate_watch.py import sys, time, select from collections import defaultdict, deque LIMIT = 10 # the class limit: messages per second per user def user_of(topic): parts = topic.split("/") return parts[1] if len(parts) > 2 and parts[0] == "lab" else None class Tally: def __init__(self, window=1.0, limit=LIMIT): self.window, self.limit = window, limit self.q = defaultdict(deque) # user -> arrival times inside the window def add(self, t, topic): u = user_of(topic) if u: self.q[u].append(t) def rates(self, now): out = {} for u, d in self.q.items(): while d and d[0] <= now - self.window: d.popleft() # forget arrivals older than the window out[u] = len(d) / self.window return out def over(self, now): return sorted(u for u, r in self.rates(now).items() if r > self.limit) if __name__ == "__main__": tally, last = Tally(), time.time() while True: ready, _, _ = select.select([sys.stdin], [], [], 1.0) now = time.time() if ready: line = sys.stdin.readline() if not line: break # the pipe closed tally.add(now, line.split(" ", 1)[0]) if now - last >= 1.0: last = now rates = tally.rates(now) print(" ".join("%s:%.0f" % (u, r) for u, r in sorted(rates.items())), " TOO FAST: " + ",".join(tally.over(now)) if tally.over(now) else "")

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Read the ACL

(a) yes: it is inside lab/bob/. (b) no, silently dropped: only lab/bob/ is writable. (c) yes: everything under lab/ is readable. (d) The subscription is accepted, but he only receives messages on topics he may read: lab/, robot/ and $SYS; a plain # does not match $SYS in any case. (e) no: robot/ is read-only for students.

Exercise 2: Why Hash?

It protects against someone who reads the file (a stolen SD card, a backup) learning the passwords. It does not protect passwords on the wire: with listener 1883 and no TLS, the CONNECT packet carries the user name and password as plain text, so anyone who can capture traffic on the network sees them. That is acceptable on a private classroom network and is why config.py must never hold a password that you also use anywhere else.

Intermediate

Exercise 3: Diagnose

First, the user name in the topic: the node’s MQTT user may be jsmith2 while the topic says jsmith, so the ACL silently drops every message. Second, the topic itself: a typo, a leading slash (/lab/... is a different topic), or capitals. Third, a subscriber problem specific to this student’s node: the callback never runs because check_msg() is not called, or the client id collides with another and the first is being kicked off (the log will say “already connected”). The broker log and mosquitto_sub -d separate these quickly.

Advanced

Exercise 4: Who Is Flooding?
test_tally.py MicroPython
t = Tally() for i in range(25): t.add(100 + i * 0.04, "lab/jsmith/tele/imu") # 25 messages in about a second for i in range(5): t.add(100 + i * 0.2, "lab/bob/tele/imu") t.add(100.5, "robot/tele/pose") print(t.rates(101.0), t.over(101.0)) # {'jsmith': 24.0, 'bob': 4.0} ['jsmith'] print(t.rates(101.5), t.over(101.5)) # {'jsmith': 12.0, 'bob': 2.0} ['jsmith'] print(t.rates(103.0), t.over(103.0)) # {'jsmith': 0.0, 'bob': 0.0} []

The window is one second wide, so each reading counts only arrivals in the last second. At 101.0 it holds 24 of jsmith’s messages (the one at exactly 100.0 has just left the window); half a second later only the second half of the burst is inside, so the rate is 12, and by 103 the burst has gone. jsmith is flagged twice, because even 12 per second is over the limit of 10. user_of returns None for topics that do not start with lab/<user>/…, so the robot’s traffic is not charged to a student.
