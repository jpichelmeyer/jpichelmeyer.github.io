“Machine learning” sounds like something that needs a data centre. Some of it does. A great deal of useful sensing, though, is a small calculation on a few numbers, and running it where the data is produced can be faster, cheaper and more private than sending everything away. This lesson is about deciding where a decision should be made, and what a modest board like the Pico can realistically do.

Part 1. Three Places to Decide

Think of three tiers. The device (your Pico) sees the data first and can react in milliseconds without any network. The edge (the Pi 3B+ on your own network) has far more memory and speed and is still local. The cloud is effectively unlimited, but is a network trip away and means your data leaves the room.

Three places a decision can be made. The closer to the sensor, the faster and more private; the further away, the more computing power and data you can bring to bear.

“Edge AI” means running the intelligence at the device or nearby, rather than shipping raw data to a distant server. “Cloud ML” means the opposite. Real systems mix them: a cheap check on the device decides what is worth sending onward.

Part 2. Every Model Has the Same Shape

However sophisticated, a sensing model follows one pipeline. Raw samples are gathered into a window; the window is reduced to a few features; a model maps the features to a decision. The model may be a hand-written rule, a statistic such as a z-score, a decision tree, or a neural network, but the stages before and after it are the same.

The common shape of every sensing model, big or small. Raw samples are turned into a few features, a model turns features into a decision, and only the decision (or the features) needs to leave the device.

Most of the engineering, and most of the data reduction, happens in the middle stage. The next three lessons build that pipeline for the Pico: windows and features, then a statistical detector, then the smoothing average it relies on.

Part 3. What Fits on a Pico

The RP2040 has 264 KB of RAM, shared with MicroPython itself, your program, the network stack and every buffer you have. There is no floating-point hardware, and floats are 32-bit. That rules some things out and leaves a lot in:

Rough sizes of different models against the Pico's RAM (log scale, orders of magnitude only). Statistics and small trees fit easily; neural networks need care; image models do not fit at all.
  • Fits easily: threshold rules, z-scores, moving statistics, small decision trees written as nested if statements.
  • Possible with care: tiny neural networks, quantized to 8-bit integers. These are normally run with compiled code (for example the C/C++ SDK with TensorFlow Lite for Microcontrollers, or specialised MicroPython modules), not plain MicroPython.
  • Does not fit: image or audio models of any size; these belong on the edge or in the cloud.

Part 4. Choosing Where to Run It

A quick way to decide where to run a model. Start from what you cannot compromise on: how fast the answer is needed, whether the data may leave, and how much computing it takes.

A useful default for this course: run the cheap, fast check on the Pico (a z-score, a threshold), and publish its decision and the features, not the raw stream. If something needs a heavier model, a program on the Pi can subscribe to the features and run it there, still on your own network.

Exercises

Practice problems in three tiers. Do each on paper or on your own board first, and only then open its solution below. Many problems have more than one correct answer; if yours behaves the same way, it is right even if it looks different.

Warm Up

Exercise 1: Place the Task. Say which tier is best, and why: (a) switch a light off in under 50 ms when it gets bright, (b) classify bird calls from a microphone, (c) log a month of room temperature for a chart, (d) alert when a machine’s vibration changes.

Exercise 2: How Much Is Saved?. A vibration sensor is read 100 times a second. Sending each reading costs about 6 bytes as JSON; a summary (mean, std, min, max, count) sent once a second costs about 65 bytes. Compare the data per second.

Intermediate

Exercise 3: A Rule-Based “Model”. Write classify(level) for an LDR reading (0 to 65535) that returns "dark" below 15000, "bright" above 45000 and "normal" otherwise, and publish only when the class changes.

Advanced

Exercise 4: Design a Split. A farm monitors soil moisture on 20 battery-powered Picos. Decide what runs on each Pico, what runs on a Pi in the barn, and what (if anything) goes to the cloud. Say what you are trading.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Place the Task

(a) device: the speed requirement rules out a network trip. (b) edge or cloud: audio models are far too big for a Pico. (c) edge (the Pi): lots of storage, no internet needed. (d) device for the cheap statistical check, with the features forwarded to the edge for a closer look.

Exercise 2: How Much Is Saved?

Raw: 100 × 6 = 600 bytes/s. Summary: 65 bytes/s, about 9 times less, while still saying what the signal is doing. Over a day that is about 52 MB against 5.6 MB, before counting the packets’ own overhead.

Intermediate

Exercise 3: A Rule-Based “Model”
main.py MicroPython
last = None def classify(level): if level < 15000: return "dark" if level > 45000: return "bright" return "normal" def update(level): global last c = classify(level) if c != last: # a decision, not a stream client.publish(b"lab/pico01/tele/light_class", c.encode(), retain=True) last = c

This is a complete (if very small) model: a window of one reading, one feature, a rule, a decision. Publishing on change keeps traffic near zero when nothing is happening.

Advanced

Exercise 4: Design a Split

Pico: read, filter, compute a few features, and publish every few minutes (deep sleep between, to save battery). Pi in the barn: subscribe to all 20, store history, run a heavier model that predicts when to irrigate, and drive the pumps (it has power and speed). Cloud: only a daily summary for a phone dashboard, if the farmer wants remote access. Trade-offs: keeping the heavy work local avoids depending on an internet link and avoids sending field data away; the cost is that you maintain the Pi.
