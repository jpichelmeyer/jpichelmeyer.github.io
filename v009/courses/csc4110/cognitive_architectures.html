Your robot can now hear and speak on the network, and it survives outages. This lesson is about the part of the agent that decides what to do: the Decider. The Perceptor, Memory and Actuator stay as they are. A cognitive architecture is a way of organising the Decider, and roboticists have a handful of them, each good at different things. You have already built two without naming them. By the end of the lesson you will pick a role for your robot for the rest of the term, and choose the body and the architecture that suit that role.

Part 1. Same Body, Different Deciders

SAM gives you a fixed frame: percepts come in, actions go out, Memory sits beside the Decider. Everything in this lesson is a different answer to one question: how does the Decider turn percepts and Memory into an action?

The rest of the agent stays fixed; only the inside of the Decider changes. The five architectures are not rivals. Real robots stack them: reactive control inside a state machine, behaviours chosen by an arbiter, all of it under a slower planner, with learned parts wherever hand-written rules fall short.

Part 2. Reactive: Wire Percepts Straight to Actions

The simplest Decider has no Memory at all. Each tick it maps the current percept straight to an action. The classic example is Braitenberg's vehicle: two light sensors and two wheels, each sensor wired to the wheel on the opposite side. The brighter side's sensor drives the far wheel harder, the vehicle turns toward the light and drives into it. Nothing inside the vehicle represents “the light” or “a goal”, yet an observer sees it seek the light. The behaviour comes from the loop through the world, not from the Decider.

Braitenberg's light-seeking vehicle (from Vehicles, 1984). Light on the left makes the left sensor drive the right wheel harder, which turns the vehicle left, toward the light. Wire the sensors straight instead of crossed and the same parts make a vehicle that turns away from light. The architecture is the wiring.

Your Lab 4 turret has a reactive core too. Strip away the state machine and the integral term, and the eyes drive the servo directly:

reactive.py MicroPython
def reactive(p, pan, dt, gain=120): """Pan rate proportional to the balance. No state of its own: the servo's position is the only 'memory', and it lives in the body.""" rate = -gain * p["balance"] # deg/s: turn toward the brighter eye return max(20, min(160, pan + rate * dt))

Reactive Deciders are fast (one line of arithmetic per tick), robust (no state to corrupt) and easy to test. Their weakness is everything that needs history. Take the light away and a reactive turret simply stops wherever it is, because a balance of zero is indistinguishable from “aimed perfectly”. To search, it needs to know it has lost something, and that is Memory.

Part 3. State Machines: Memory Holds a Mode

A state machine adds one piece of Memory, the current mode, and lets the mode decide which reactive rule runs. You built two: the Lab 1 sentry (IDLE, ARMED, ALARM) and the Lab 4 turret (IDLE, SEARCH, TRACK, LOCKED). The strength of a state machine is that every situation the robot can be in is written down, so you can test every transition. The weakness shows up as the robot grows. Add an operator command and a bumper to the turret, and every state needs arrows for both. Four states and two new events is already eight new arrows, most of them saying the same thing: “if the bumper is hit, stop, whatever you were doing.”

Why flat state machines get crowded. Two new situations that can interrupt anything need an arrow from every existing state, plus a rule for where to return afterwards. The meaning is simple (“safety first, then commands, then whatever you were doing”) but the diagram does not say it simply. Priority arbitration does.

Part 4. Behaviour Arbitration: Competences in Priority Order

In the 1980s Rodney Brooks built robots that had no central plan at all. Each robot was a stack of simple behaviours (avoid obstacles, wander, head for a goal), each one a complete little sense-act loop, with higher-priority behaviours able to take over from lower ones. His subsumption architecture made robots that worked in messy real rooms when planning-based robots stalled. The practical form used everywhere today is priority arbitration: every behaviour says whether it wants control right now, and an arbiter gives control to the highest-priority one that does.

Priority arbitration. Every behaviour sees the same percepts and answers one question, “do I want control?”. The arbiter walks down the list and hands control to the first behaviour that says yes. Adding the bumper rule is now one new behaviour at the top of the list, instead of an arrow from every state.

Here is a complete arbiter for the Lab 4 turret extended with a bumper, operator commands from the network (the cmd/ topics of Week 7) and a beam it can switch. Each behaviour is a few lines and none of them knows the others exist.

arbiter.py MicroPython
# arbiter.py: a behaviour-based Decider (priority arbitration) class Behaviour: """One competence. wants() says whether it should be in control now; act() returns the command it would issue. Neither touches hardware.""" name = "base" def wants(self, p, m): return False def act(self, p, m, dt): return {} class Safe(Behaviour): # priority 1: never hurt anything name = "safe" def wants(self, p, m): return p["bumper"] or p["fault"] def act(self, p, m, dt): return {"pan": m.pan, "beam": False} # freeze, beam off class Obey(Behaviour): # priority 2: a fresh operator command name = "obey" FRESH_MS = 2000 def wants(self, p, m): return p["cmd"] is not None and p["cmd_age_ms"] < self.FRESH_MS def act(self, p, m, dt): return {"pan": p["cmd"]["pan"], "beam": p["cmd"].get("beam", False)} class Track(Behaviour): # priority 3: face the light name = "track" def __init__(self, kp=0.5, ki=1.0): self.kp, self.ki, self.i = kp, ki, 0.0 def wants(self, p, m): return p["bright"] >= 1.25 def act(self, p, m, dt): if m.active != self.name: # just took over: start from here self.i = (m.pan - 90) / 80 e = 0.0 - p["balance"] self.i = max(-1, min(1, self.i + self.ki * e * dt)) u = max(-1, min(1, self.kp * e + self.i)) return {"pan": 90 + 80 * u, "beam": False} class Search(Behaviour): # priority 4: always willing name = "search" def wants(self, p, m): return True def act(self, p, m, dt): pan = m.pan + m.sweep_dir * 60 * dt if not 20 <= pan <= 160: m.sweep_dir = -m.sweep_dir return {"pan": pan, "beam": False} class Arbiter: """The highest-priority behaviour that wants control gets it.""" def __init__(self, behaviours): self.behaviours = behaviours # highest priority first def decide(self, p, m, dt): for b in self.behaviours: if b.wants(p, m): cmd = b.act(p, m, dt) if b.name != m.active: m.switches += 1 m.active = b.name m.pan = max(20, min(160, cmd["pan"])) return b.name, m.pan, cmd["beam"] class Memory: def __init__(self): self.pan, self.sweep_dir = 90.0, 1 self.active, self.switches = None, 0

Feed it a scripted run: a light appears at 3 s, an operator sends a pan command at 5 s, someone knocks the robot at 7.5 s, and the light goes away at 9 s.

test_arbiter.py Python
# test_arbiter.py: scripted percepts, 10 Hz, 12 seconds def percept(t): p = {"bumper": False, "fault": False, "cmd": None, "cmd_age_ms": 99999, "bright": 1.0, "balance": 0.0} if 3.0 <= t < 9.0: p["bright"], p["balance"] = 2.0, -0.2 # a light appears on one side if 5.0 <= t < 6.0: p["cmd"], p["cmd_age_ms"] = {"pan": 45}, int((t - 5.0) * 1000) if 7.5 <= t < 8.0: p["bumper"] = True # someone knocks the robot return p arb = Arbiter([Safe(), Obey(), Track(), Search()]) m, dt, log = Memory(), 0.1, [] for k in range(120): t = k * dt name, pan, beam = arb.decide(percept(t), m, dt) if not log or log[-1][1] != name: log.append((round(t, 1), name)) print(log) print("switches:", m.switches)
output Output
[(0.0, 'search'), (3.0, 'track'), (5.0, 'obey'), (6.0, 'track'), (7.5, 'safe'), (8.0, 'track'), (9.0, 'search')] switches: 7
The same run drawn as who is in control over time (computed from the program above). Control falls back to Track by itself when the command goes stale at 6 s and when the bumper is released at 8 s. Nobody wrote “return to tracking after a command”: it happens because Track still wants control and nothing above it does.

Two design rules keep arbiters honest. First, a behaviour's wants must be cheap and side-effect free, because it runs for every behaviour on every tick. Second, watch the switch count. A robot that flips between two behaviours every tick (Track wants control, its action moves the head so the light drops below the threshold, Search takes over, its sweep finds the light again) is dithering. The cure is the hysteresis of the architecture lesson: a higher threshold to take control than to keep it.

Part 5. Layered (Hybrid) Architectures: Fast Under Slow

Reactive control and behaviours are fast but short-sighted. Planning (“go to the far corner, then search there”) needs a model of the world and time to think, which a 20 Hz loop on a Pico does not have. The answer most real robots use is layers that run at different speeds: a fast reactive layer that keeps the robot safe and on target every few milliseconds, a middle layer that picks the current behaviour every tenth of a second or so, and a slow deliberative layer that plans over seconds. Each layer sets goals for the one below and never waits for the one above.

A three-layer architecture, mapped onto this course's hardware. The bottom two layers run on each robot; the top layer runs on the hub, where the large Memory and the view of every robot are. The network sits between the executive and deliberative layers, so a network outage removes planning but never removes safety or aiming. This is the edge-versus-hub rule of Week 1, stated as an architecture.

You already have the bottom two layers: the PID and the safety stop are the reactive layer, and the turret's state machine (or the arbiter above) is the executive. In Unit 3 the hub gains the top layer: a coordinator that knows every robot's role and position and sends each one goals such as “scan the left half” or “point at bearing 40°”. Notice the direction of the messages. Goals flow down, status flows up, and every layer must keep doing something sensible with the last goal it received.

Part 6. Where Learning Fits

Next week your robot learns from data. It is worth deciding now where a learned model sits in SAM, because it is usually not where people first expect. Most TinyML models on robots are classifiers: they turn a window of raw sensor data into a label such as “tap”, “shake” or “still”, or “red target”. That makes the model a stage of the Perceptor: a learned synthetic sensor, exactly like the turret's balance but fitted from examples instead of written by hand. The Decider stays hand-written and receives a cleaner, higher-level percept.

The usual place for TinyML in a robot. The model is the last stage of the Perceptor, turning 50 samples a second into a couple of labels a second. Everything downstream (the arbiter, the state machine, the network) receives a percept that is smaller, slower and more meaningful than the raw data, which is also why it is cheaper to send.

Keeping the learned part in the Perceptor has a practical benefit: the safety behaviours above it never depend on a model being right. If the classifier mislabels a shake as a tap, the robot reports the wrong thing; it does not drive into a wall. When you design your role below, put the model where its mistakes are cheap.

Part 7. Roles and Morphology

From this week on, each robot specialises. In Unit 3 a team of robots will carry out a mission that no single robot can: find a target, work out where it is, identify it and mark it, while telling a human what is happening. Each role needs a different body (morphology: what it can sense and what it can move), and the body decides which architecture makes sense. Different roles, different hard parts.

Warm Up

Exercise 1: Name the Architecture

(a) A state machine with two states (heating, not heating): the hysteresis band means the same temperature can give either answer, so it needs Memory. A version with a single threshold would be purely reactive. (b) Behaviour arbitration: “go to dock” outranks “bump and turn”, which outranks “drive on”. This is the design of the first commercial robot vacuums. (c) Layered: a slow deliberative layer on the hub over fast reactive control on each robot. (d) Learned, and specifically a learned Perceptor stage: it produces a label, not an action.

Exercise 2: Trace the Arbiter

(a) Track: Safe and Obey decline, Track wants control. (b) Obey: 1.2 s is fresher than the 2 s limit. (c) Search: the command is stale, the light is too dim, and Search always accepts. (d) Safe: the bumper outranks everything, including a brand-new command. That last case is the point of putting safety first: an operator cannot command the robot into a collision.

Intermediate

Exercise 3: Stop the Dithering

Near the edge of the beam the brightness percept wobbles across 1.25 from noise alone. Each crossing flips Track.wants, so control flips, and the two behaviours command different pan angles, which moves the eyes and changes the brightness again. Two different thresholds fix it, and the information needed is whether Track currently has control, which is already in Memory as m.active.

track_hysteresis.py MicroPython
class Track(Behaviour): name = "track" TAKE, KEEP = 1.25, 1.10 def wants(self, p, m): limit = self.KEEP if m.active == self.name else self.TAKE return p["bright"] >= limit
test_hysteresis.py Python
class M: active = None t, m = Track(), M() for b in [1.20, 1.26, 1.18, 1.12, 1.09, 1.20]: w = t.wants({"bright": b}, m) m.active = "track" if w else "search" print(b, w) # 1.2 False 1.26 True 1.18 True 1.12 True 1.09 False 1.2 False

Advanced

Exercise 4: A Role's Architecture

One reasonable list, highest priority first:

  1. Safe: p["fault"] or p["bumper"]. Freeze the servo, stop pinging. (Reactive.)
  2. Quiet: m.quiet_until > now, set when a “stop pinging” message arrives. Hold position without pinging so the other Scout has the air. (Executive, obeying the hub.)
  3. Track: p["range_cm"] < m.track_max with hysteresis as in Exercise 3. Keep the target centred with a small PID on its bearing. (Reactive control inside an executive behaviour.)
  4. Scan: always. Sweep between m.scan_lo and m.scan_hi. (Executive.)

The hub goal “scan only between 40° and 120°” does not become a behaviour. It changes m.scan_lo and m.scan_hi in Memory, and the Scan behaviour uses them. That is the layered pattern: the deliberative layer (on the hub) sets goals by changing the parameters of the executive layer, never by driving the servo itself. If the hub goes silent, the Scout keeps scanning the last sector it was given.

Paper Practice: Answers

Recall

P1. Five Architectures

Reactive rules (percept to action, no Memory); state machine (Memory holds a mode); behaviour arbitration (competing behaviours, priority wins); layered or hybrid (fast reflexes under slower planning); learned (behaviour or perception fitted from data).

P2. Braitenberg

Crossed: each sensor drives the wheel on the opposite side, so the vehicle turns toward the light. Straight: each sensor drives its own side's wheel, so the vehicle turns away from the light.

P3. Arbiter Rule

It walks the behaviours in priority order and gives control to the first one whose wants returns true.

P4. Where Learning Sits

As the last stage of the Perceptor (a learned synthetic sensor producing a label). The safety behaviours in the Decider never depend on the model being right; a misclassification produces a wrong report, not a dangerous action.

Apply

P5. Trace the Arbiter

(a) Safe. (b) Track. (c) Search. (d) Obey.

P6. Count the Arrows

From each of 5 states to each of 2 interrupt states and back: 5 × 2 × 2 = 20 arrows. An arbiter needs 2 new behaviours inserted at the right priority.

P7. Hysteresis in wants

No, yes, yes, yes, no, no. (The last 1.20 is below the take threshold because Track lost control at 1.09.)

P8. Layer Periods

Reactive: about 1 to 20 ms, on the Pico. Executive: about 100 ms, on the Pico. Deliberative: seconds, on the hub.

Analyze and Design

P9. Why Reactive Fails

With the light gone both eyes read alike, so the balance is zero, the same percept as perfect aim. A memoryless Decider gives the same action for the same percept, so it stops. Searching needs Memory that the light was lost (and which side it was last seen on).

P10. Dithering

Each behaviour's action changes the percept that the other's wants depends on (for example, Track's motion pushes brightness below the threshold, Search's sweep finds it again), so control flips. Fixes: hysteresis (different take and keep thresholds), a minimum time in control, or filtering the percept.

P11. Hub Goals

No. The goal changes parameters in the robot's Memory (scan limits) used by its Scan behaviour; the robot's own layers do the moving. If the hub goes silent, the robot keeps scanning the last sector it was given.

P12. Design a Role

1 Safe: bumper or fault. 2 Obey: a command younger than 2 s. 3 Aim: the world-model target is fresh (pan to pan_to(pose, x, y), beam on). 4 Idle: always (hold position, beam off). Any equivalent list with safety first and an always-true default last is correct.
