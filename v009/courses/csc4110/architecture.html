A smart light, a fan that starts when the room warms, a small robot that follows a wall: they all look different but are built from the same few parts. Before we wire anything, this lesson gives you the picture to hang the rest of the course on: what a node is, what a hub is, where each job belongs, and what a small processor has to work with.

Part 1. Sense, Think, Act

Strip any robot or IoT device down and it is the same loop. Sensors turn something physical (light, distance, tilt, a pressed button) into a number. A processor with memory runs your program and decides what to do with the numbers. Actuators turn a decision back into something physical (an LED, a servo, a fan, a pump, a motor). The actions change the world, the sensors see the change, and the loop closes.

Every node in this course, and every robot, runs the same loop: sense the world, think about what was sensed, act on the world, and sense again. The network adds a second way out of the thinking step: sending what was sensed or decided to other devices, and receiving what they send.

The only thing the Internet of Things adds to this loop is a network connection around the thinking step. A node can now report what it senses, and take instructions from somewhere else. A robot is the same kind of node with actuators that move: a robot is an IoT thing, and a group of robots is a group of IoT things that talk to each other.

Part 2. Nodes, Hubs and the Edge

Real systems divide the work. A node is a small, cheap, low-power device placed where the physical thing is. A hub (also called a gateway) is one more capable computer that the nodes connect to. In this course the nodes are Raspberry Pi Pico W boards and the hub is a Raspberry Pi running an MQTT broker.

A small IoT system. Edge nodes (each a Pico) sense and act. They talk over WiFi to a hub, which relays messages, remembers data and serves anything that wants to look in: a dashboard, a laptop, or another student’s agent.

The word edge means the devices at the boundary between the network and the physical world: the ones with sensors and actuators. Nodes talk to the hub, and not directly to each other, because that keeps each node simple: it only needs to know where the hub is. The hub can then pass messages along, store them, and let other programs join in. Later in the course your own programs become extra agents on the same network.

Part 3. What Goes Where

A good rule: a node should be able to do its safety-critical job with the network cut. If commands to a motor go quiet, the motor must stop, and only the node can guarantee that. Storage, history and decisions that need several nodes belong on the hub, because the node does not have the memory or the view.

Edge versus hub. Put anything that touches hardware, or must keep working without the network, on the node. Put anything that needs memory, storage or a view across many nodes on the hub. You will keep revisiting where each job belongs.

Part 4. What a Node Has to Work With

The budget of one node. None of this is a problem for a single sensor, but every limit shows up once you sample fast, send many values, or run several jobs at once. The course keeps returning to these numbers.

These limits are the reason for one of the course outcomes: aligning what the hardware can process with how much sensor data arrives. A quick way to reason about it is a data rate, the number of bytes per second a sensor produces.

rates.py MicroPython
def bytes_per_second(channels, bytes_each, hz): return channels * bytes_each * hz print(bytes_per_second(1, 2, 100)) # one light sensor at 100 Hz: 200 B/s print(bytes_per_second(6, 2, 100)) # accelerometer + gyro (6 values), 100 Hz: 1200 B/s print(bytes_per_second(1, 2, 20)) # ultrasonic distance at 20 Hz: 40 B/s

Those are small next to what a WiFi link can carry. The real limits are usually your program loop and the message overhead: a text message such as {"v":1,"seq":7,"ax":0.02} is dozens of bytes even when the value inside is two. You will measure this in Lab 3.

Part 5. The Smallest Possible Node

Your Pico already has a sensor and an actuator on board: an internal temperature sensor (analog channel 4) and an LED. That is enough for a complete sense, think, act program with nothing wired:

first_node.py MicroPython
from machine import ADC, Pin from time import sleep_ms adc = ADC(4) # channel 4 = the chip's internal temperature sensor led = Pin("LED", Pin.OUT) # the Pico W's on-board LED def read_temp_c(): volts = adc.read_u16() * 3.3 / 65535 return 27 - (volts - 0.706) / 0.001721 # formula from the RP2040 datasheet THRESHOLD = 30.0 # degrees C while True: temp = read_temp_c() # SENSE hot = temp > THRESHOLD # THINK led.value(hot) # ACT print(round(temp, 1), hot) sleep_ms(500)

The chip reads the temperature of its own silicon, so it runs a few degrees above the room. Warm the board with a finger and watch the number climb; when it crosses the threshold the LED lights. The code is only a few lines, but each one maps to a box in the loop diagram, and that mapping is what to look for in every program this term.

Part 6. Where the Course Goes

The shape of the term. First you build one complete node (sensing, filtering, driving outputs, and a first report to the network). Then you connect many nodes through a hub. Finally the nodes become agents that coordinate with each other without anyone in charge.

Three lab practicals mark the way. In Lab Practical 1 your robot unit senses, acts and transmits to the class broker. In Lab Practical 2 your agent exchanges messages with the instructor’s robot. Lab Practical 3 is a multi-agent mission. Everything in the weekly lessons builds toward one of them.

It could report battery level, speed, or how often it lost the line. The loop is sense, decide, steer, repeat.

Intermediate

Exercise 3: A Data Rate

Raw: 6 × 2 × 200 = 2400 B/s. As 90-byte text messages at 200 per second: 90 × 200 = 18 000 B/s, 7.5 times more. Text is convenient but costly, so later you will batch or filter before sending.

rates.py MicroPython
print(bytes_per_second(6, 2, 200)) # 2400 print(90 * 200) # 18000

Advanced

Exercise 4: Warm-up Alarm

The start-up value is the reference. Two thresholds make a hysteresis band: on above +2.0, off below +1.5, and unchanged in between.

alarm.py MicroPython
def decide(temp, ref, was_on): if temp > ref + 2.0: return True if temp < ref + 1.5: return False return was_on # inside the band: keep the old decision ref = read_temp_c() # measured once at start-up on = False while True: on = decide(read_temp_c(), ref, on) led.value(on) sleep_ms(500)
test_alarm.py MicroPython
print(decide(27.2, 25.0, False)) # True (more than 2.0 above) print(decide(26.7, 25.0, True)) # True (inside the band: stays on) print(decide(26.7, 25.0, False)) # False (inside the band: stays off) print(decide(26.4, 25.0, True)) # False (below +1.5: switches off)

Testing the same input with two different histories (the second and third lines) is the point of hysteresis: the answer depends on what happened before.
