A smart light, a fan that starts when the room warms, a small robot that follows a wall: they look different, but each one is the same kind of thing. It is an agent, situated in a physical world, that perceives, remembers, decides and acts. This lesson gives you the vocabulary for that, the Situated Agent Model (SAM), and then uses it to explain what an IoT system is: what a node is, what a hub is, where each job belongs, and what a small processor has to work with. Every lesson and lab this term will point back to the diagrams on this page.

Part 1. Agent and Environment

SAM starts from one split. There is an Agent, and there is an Environment the agent is situated in. The agent never has the environment's true state. It knows only what it can observe through its sensors, and it can change the world only through the actions its actuators can take. Everything an agent does happens in a loop: observe, decide, act, and observe again, because the action changed what there is to observe.

The Situated Agent Model. The Environment produces observables that the Perceptor detects; the Decider combines what is perceived now with what Memory holds; the Actuator carries the chosen action back out into the Environment. The loop closes through the world: the agent sees the results of its own actions. The four colours (blue Perceptor, gold Memory, orange Decider, green Actuator) are used for the same units in every diagram this term.

Inside the agent, the loop breaks into four units, each with one job:

  • Perceptor: detects observables and turns them into information the rest of the agent can use. On a robot that means a sensor, the circuit around it, the conversion to a number, and the filtering that makes the number trustworthy. Its output is a percept: a value with units, such as “42 cm” or “tilted 8° left”.
  • Memory: holds information over time. A percept is a snapshot of now; Memory is what lets the robot know the current state of its state machine, the last place it saw a target, a running average, or how many times it has restarted.
  • Decider: takes the current percepts together with Memory and chooses what to do. This is where the “intelligence” lives, and most of the course is about building better Deciders: a threshold, a state machine, a PID controller, an arbiter of behaviours, a trained classifier, a coordinator of other robots.
  • Actuator: carries out the chosen action. It is the only unit allowed to change anything outside the agent: drive an LED, move a servo, switch a motor, or (from Unit 2 on) send a message.

Memory sits apart from the Perceptor because the two answer different questions. The Perceptor answers “what is true right now?”; Memory answers “what has been true?”. A distance sensor that reads 200 cm cannot tell you whether an obstacle just moved away or was never there. Only Memory can.

Part 2. SAM on a Microcontroller

On a robot the four units are not abstract; each one is a specific chain of hardware and code. Follow one observable all the way through a Pico W and back out:

One pass through a Pico W, coloured by SAM unit. Steps 1 to 4 are the Perceptor and fill most of Unit 1: the electronics of a sensor (Week 1), conversion and sampling (Week 2), digital buses and pulses (Week 3). Step 6 is Memory, which the Decider reads and updates. Steps 7 to 9 are the Actuator: PWM, servos and switching loads (Week 4). The Decider sits in the middle and gets smarter all term.

The same split works for code. When you write a program for a robot, every line belongs to exactly one unit:

  • adc.read_u16(), imu.accel(), an averaging filter, a conversion to centimetres: Perceptor.
  • self.state = 'ARMED', a stored baseline, a ring buffer of the last 50 readings, a file in flash: Memory.
  • if dist < 20:, a state table lookup, pid.update(error), model.predict(features): Decider.
  • led.on(), servo.angle(90), pwm.duty_u16(d), and later client.publish(...): Actuator.

Keeping the units in separate functions or classes pays off quickly. You can test a Decider on your laptop by feeding it made-up percepts, you can swap a light sensor for a distance sensor without touching the decision logic, and when something goes wrong you can ask “which unit is lying?” instead of reading one long tangled loop.

Part 3. The Network Is One More Way to Sense and Act

The only thing the Internet of Things adds to a robot is a network connection, and SAM already has a place for it. A message that arrives from the network is an observable: the agent's Perceptor receives it, checks it and turns it into a percept, exactly as it does for a sensor reading. A message the agent sends is an action: it goes out through the Actuator and changes the world (it changes what other agents will observe). Nothing about the four units changes; the environment simply gets bigger.

The network in SAM terms. A subscribed message enters through the Perceptor (it must be checked and interpreted like any sensor value, and it can be late, missing or wrong). A published message leaves through the Actuator. From one robot's point of view the broker and the other robots are just part of its environment: things it can observe and influence, but never control directly. This idea carries Units 2 and 3.

This framing is more than tidy vocabulary; it predicts real engineering problems. Sensors are noisy, slow and sometimes fail, so you filter them and check them. Messages are also noisy, slow and sometimes fail (they arrive late, twice, out of order, or not at all), so the same habits apply. And because the network is part of the environment rather than part of the agent, a robot must keep doing its safety job when the network goes away, the same way it must cope when a sensor is unplugged.

Part 4. Nodes, Hubs and What Goes Where

Real systems divide the work between two kinds of device. A node (an edge device) is a small, cheap, low-power board placed where the physical thing is. A hub (also called a gateway) is one more capable computer that the nodes connect to. In this course the nodes are Raspberry Pi Pico W boards, one per student, and the hub is the class Raspberry Pi running an MQTT broker. (When you test at home, your laptop can stand in as the hub.)

In SAM terms both are agents, with very different bodies. A node has real sensors and actuators but a tiny Memory and a modest Decider. The hub has almost no sensors or actuators of its own, but a huge Memory (gigabytes of storage) and a Decider that can see every node at once. That difference decides where each job belongs. The rule to remember: a node must be able to do its safety-critical job with the network cut. If commands to a motor go quiet, the motor must stop, and only the node can guarantee that.

Edge versus hub. Put anything that touches hardware, or must keep working without the network, on the node. Put anything that needs a large Memory (history, storage) or a view across many nodes on the hub. You will keep revisiting where each job belongs, and in Unit 2 you will measure it.
The node and the hub drawn as SAM agents. The node is strong where the world is (sensing and acting) and weak in Memory; the hub is the opposite. A good IoT design gives each job to the agent whose body suits it.

Part 5. What a Node Has to Work With

The budget of one node. None of this is a problem for a single sensor, but every limit shows up once you sample fast, send many values, run a classifier, or run several jobs at once. The course keeps returning to these numbers.

These limits are the reason for one of the course outcomes: aligning what the hardware can process with how much sensor data arrives. Two quantities make the reasoning concrete. The first is a data rate, the number of bytes per second the Perceptor produces:

rates.py MicroPython
def bytes_per_second(channels, bytes_each, hz): return channels * bytes_each * hz print(bytes_per_second(1, 2, 100)) # one light sensor at 100 Hz: 200 B/s print(bytes_per_second(6, 2, 100)) # accelerometer + gyro (6 values), 100 Hz: 1200 B/s print(bytes_per_second(1, 2, 20)) # ultrasonic distance at 20 Hz: 40 B/s

The second is a loop budget. A SAM agent runs its four units over and over; one pass is a tick. If the robot must react within 20 ms, then perceive + decide + act must fit inside 20 ms, every time, with room to spare for the network.

A loop budget drawn to scale (the numbers are typical, not fixed). This picture comes back in Week 2 (how fast can the Perceptor sample?), in Unit 2 (what does a network call or a TinyML model cost?) and in Unit 3 (how stale can a message from another agent be?).

Part 6. The Smallest Possible SAM Node

Your Pico already has a sensor and an actuator on board: an internal temperature sensor (analog channel 4) and an LED. That is enough for a complete agent with nothing wired. Read this program by unit: each class is one box from Part 1, and the loop at the bottom is the arrows.

sam_node.py MicroPython
from machine import ADC, Pin from time import ticks_ms, ticks_diff, sleep_ms class Perceptor: """Turns the world into percepts (values with units).""" def __init__(self): self.adc = ADC(4) # channel 4 = the chip's own temperature sensor def sense(self): volts = self.adc.read_u16() * 3.3 / 65535 temp_c = 27 - (volts - 0.706) / 0.001721 # formula from the RP2040 datasheet return {"temp_c": temp_c} class Memory: """Holds what the agent knows over time.""" def __init__(self): self.hot = False # the decision made last tick self.ticks = 0 class Decider: """Chooses an action from the percepts and Memory.""" THRESHOLD = 30.0 def decide(self, percept, memory): memory.hot = percept["temp_c"] > self.THRESHOLD memory.ticks += 1 return {"led": memory.hot} class Actuator: """The only unit that changes the world.""" def __init__(self): self.led = Pin("LED", Pin.OUT) # the Pico W's on-board LED def act(self, action): self.led.value(action["led"]) perceptor, memory, decider, actuator = Perceptor(), Memory(), Decider(), Actuator() PERIOD_MS = 500 while True: start = ticks_ms() percept = perceptor.sense() # observe action = decider.decide(percept, memory) # decide (using Memory) actuator.act(action) # act print(memory.ticks, round(percept["temp_c"], 1), action) sleep_ms(max(0, PERIOD_MS - ticks_diff(ticks_ms(), start)))

The chip reads the temperature of its own silicon, so it runs a few degrees above the room. Warm the board with a finger and watch the number climb; when it crosses the threshold the LED lights. Notice two things. First, the percept is a dictionary with units in its key name (temp_c), not a raw ADC number; the rest of the program never sees the hardware. Second, the Decider can be tested without a Pico at all:

test_decider.py Python
class FakeMemory: # stands in for Memory on a laptop hot, ticks = False, 0 d, m = Decider(), FakeMemory() print(d.decide({"temp_c": 25.0}, m)) # {'led': False} print(d.decide({"temp_c": 31.2}, m)) # {'led': True} print(m.ticks) # 2

Ten lines would have done the same job as one undivided loop, and for this tiny program that would be fine. The structure is for what comes next: in Lab 1 the Perceptor reads buttons and the Decider is a state machine; in Lab 4 the Decider is a PID controller steering a servo; in Unit 2 it becomes a trained classifier; in Unit 3 its percepts include the beliefs of other robots. The four boxes stay the same.

Part 7. Where the Course Goes

The shape of the term in SAM terms. Unit 1 builds one agent, unit by unit, on a breadboard robot base that you keep all semester. Unit 2 connects the agents through the hub, gives each one a specialised body and role, and replaces hand-written Deciders with learned ones. Unit 3 makes the agents depend on each other: each robot's environment now includes the others, and the team must coordinate to finish a mission none of them could do alone.

Your robot's body follows the same arc. Everyone builds the same Stage 1 robot in Unit 1; in Unit 2 each robot is refitted for its role (Stage 2); by Unit 3 each is a finished specialist (Stage 3). Here is where Stage 1 ends up, and two of the specialists it becomes:

Stage 1, the common robot of Unit 1: a breadboard base with a Pico WH, buttons, LEDs, light and temperature dividers, an IMU, an ultrasonic sensor, a display, and a servo turret with twin light-sensor eyes. Every part sits in the zone of its SAM unit.
Two of the six Stage 3 specialists: a Scout (the ultrasonic sensor becomes a scan head on the servo) and a Pointer (a beam between the eyes). The other four are in the architectures and mission lessons.

Three lab practicals mark the way. In Lab Practical 1 your robot perceives, decides and acts on its own, and reports to the class broker. In Lab Practical 2 your specialist robot classifies something live and takes part in the class message contract. Lab Practical 3 is a multi-agent mission run on the class hub, with faults injected while it runs. Everything in the weekly lessons builds toward one of them.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Name the Units

Perceptor: two or three reflectance sensors under the robot, read and turned into “line is left / centred / right” (or a number from −1 to 1). Memory: which side the line was last seen on, so the robot knows which way to turn when it loses the line entirely. Decider: how hard to steer (a PID on the line position is the classic choice). Actuator: the two drive motors. It could publish its battery level or a “line lost” event, and receive a start, stop or new speed command (which arrives through its Perceptor).

Exercise 2: Edge or Hub

(a) Edge: it reads a sensor and drives an output, and should work without the network. (b) Hub: a month of data needs the hub's large Memory. (c) Edge: only the node can act when the network is gone. (d) Hub or laptop: it needs a screen and a view over many nodes, which a Pico cannot serve well.

Intermediate

Exercise 3: Which Unit?

(a) Perceptor: it turns a raw echo time into a percept with units. (b) Memory. (c) Actuator. (d) Decider: it combines a percept (cm) with Memory (state). (e) Actuator: publishing changes what other agents observe. (f) Perceptor: a received message is an observable, and validating it is the message equivalent of filtering a noisy sensor.

Exercise 4: A Data Rate and a Budget

(a) 6 × 2 × 200 = 2400 B/s. (b) 90 × 200 = 18 000 B/s, 7.5 times more. (c) At 200 Hz a tick is 5 ms. Reading plus sending is 0.6 + 3 = 3.6 ms, which fits, but only with 1.4 ms of slack for deciding and acting, and any network hiccup longer than that makes the loop miss deadlines. The usual fix, which you will build in Unit 2, is to keep sampling at 200 Hz but send a summary (or a classifier's answer) a few times a second.

Advanced

Exercise 5: A Decider That Needs Memory

Memory needs two things: the baseline (measured once at start-up) and whether the LED is currently on. The second is what makes this hysteresis: the same temperature gives a different answer depending on the past.

hysteresis.py MicroPython
class Memory: def __init__(self, baseline): self.baseline = baseline self.on = False class Decider: ON_ABOVE, OFF_BELOW = 2.0, 1.5 def decide(self, percept, memory): rise = percept["temp_c"] - memory.baseline if memory.on and rise < self.OFF_BELOW: memory.on = False elif not memory.on and rise > self.ON_ABOVE: memory.on = True return {"led": memory.on} # in sam_node.py: memory = Memory(perceptor.sense()["temp_c"])
test_hysteresis.py Python
d = Decider() m = Memory(25.0) for t in [26.0, 27.2, 26.7, 26.4, 26.7]: print(t, d.decide({"temp_c": t}, m)) # 26.0 {'led': False} # 27.2 {'led': True} more than 2.0 above # 26.7 {'led': True} inside the band: stays on # 26.4 {'led': False} below +1.5: switches off # 26.7 {'led': False} inside the band: stays off

The two 26.7 readings give different answers. That is the whole point of Memory: the Perceptor reported the same thing both times, and only the history tells them apart.

Paper Practice: Answers

Recall

P1. The Four Units

Perceptor: an LDR and its divider read with adc.read_u16() and scaled to a value with units. Memory: self.state = 'ARMED' or a stored baseline. Decider: a state table lookup, if dist < 20: or pid.update(...). Actuator: led.on(), servo.duty_ns(...), or client.publish(...). Any equivalent examples are correct.

P2. True or False: Commands

False. A received message is an observable: it enters through the Perceptor, which must check it like any sensor reading. The Decider then chooses an action, and only the Actuator carries it out.

P3. Memory or Perceptor?

The Perceptor only says what is true now: 200 cm. It cannot say whether an obstacle just moved away or was never there. Only Memory (for example, the last reading, or the time the obstacle was last seen) distinguishes the two cases.

P4. Edge Rule

A node must be able to do its safety-critical job with the network cut. Example: stopping a motor when commands go quiet (a deadman timer) must run on the node, because only the node can act when the network is gone.

Apply

P5. Data Rate

(a) 6 × 2 × 100 = 1200 B/s. (b) 80 × 100 = 8000 B/s. (c) 8000 / 1200 ≈ 6.7 times.

P6. Loop Budget

(a) Total worst case 8.8 ms; a 100 Hz loop allows 10 ms, so it fits with 1.2 ms (12 %) of slack. (b) 125 Hz allows 8.0 ms; 8.8 ms does not fit, so the loop overruns whenever the network step is at its worst.

P7. Label the Lines

(a) Perceptor (conversion to units). (b) Memory. (c) Actuator. (d) Decider (it combines a percept with Memory). (e) Actuator (publishing is an action). (f) Perceptor (validating an incoming observable).

P8. Hysteresis Trace

OFF, OFF, ON (above 30), ON, ON (still at or above 28), OFF (below 28), OFF (29 is inside the band, and the state was OFF). The two readings of 29 give different answers because of Memory.

Analyze and Design

P9. Draw It

Environment (room air, broker) → observables: temperature (and any received setpoint command) → Perceptor (sensor, divider, ADC, filter) → Decider (threshold with hysteresis) with Memory (fan on/off, last publish time, setpoint) → Actuator: switches the fan (physical action) and publishes tele/temp (network action) → the room cools and the broker's subscribers see the reading. Any clear drawing with these elements is correct.

P10. Node or Hub?

(a) Node: it closes a fast loop on hardware and must survive an outage. (b) Hub: it needs a large Memory and data from many nodes. (c) Node: it is part of reading the pin, at millisecond timescales. (d) Hub (or a coordinator): it needs a view of all three robots at once.

P11. Critique a Decider

It reads the hardware itself (that is the Perceptor's job) and reads the clock itself (so it cannot be tested at a chosen time). A testable signature passes both in: def decide(self, percept, memory, now): where percept holds a value with units (for example a light level) and now is a time in milliseconds.

P12. Event and Report

Publish an event (for example evt/alarm) immediately when the threshold is crossed, with hysteresis so it does not repeat while hovering; publish telemetry (tele/temp) on a slow schedule such as every 10 s. Events are rare, so the average stays far below one per second, and the time-critical news is never left waiting for the next periodic report.
