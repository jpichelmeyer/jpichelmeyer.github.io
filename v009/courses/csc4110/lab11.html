This lab builds a shared resource out of a lease, a queue and a contract. You write a manager that is the single judge of who may move the servo, and clients that ask, wait, use and give back, and then check by drills that crashes, restarts and impatient clients do not break it, and that the system recovers in a time you can state.

SAM lens. the manager's Memory (owner, lease, queue) is the only judge of who may move the servo. Clients perceive that Memory through retained state and act only through requests, so a crashed client costs at most one lease.

What You Will Build

One servo, several users, no collisions. One student’s Pico runs the manager: it owns a pan servo and decides, one at a time, who may move it. The other students run clients that ask for the servo, wait their turn in a queue, use it, and give it back. Everything in this lab is a combination of earlier lessons: the lease and queue of Week 13, the agent cycle, the contract, the failure habits of Week 8. The new work is making the pieces behave together, and then breaking the system the ways real systems break: a client that crashes while holding the servo, a manager that restarts, and a client that asks far too often.

The Lab 11 system. Each user writes only in their own subtree, so each command carries to: manager. The manager answers in its own subtree, and clients listen to it.

The Contract

The Lab 11 contract. The lease length (10 s) is a parameter of the manager; the clients assume it for their renewal and read the real owner from stat/owner.

Step 1. The Manager

The student who owns the servo builds it on GP14 (power it from its own pack with a common ground, as always) and runs this. It needs hub.py, agent.py, contract.py, and lease.py from the resource management lesson. The file servo.py is the one from Lab 10.

manager.py MicroPython
# manager.py -- owns the servo; many users may ask, one at a time may move it from time import ticks_ms, ticks_diff import hub from agent import Agent from lease import Lease from contract import check KINDS = { # the contract for what clients send, in THEIR cmd topics "claim": {"to": (str, None, None, True), "id": (int, 0, 2**31, True)}, "release": {"to": (str, None, None, True), "id": (int, 0, 2**31, True)}, "pan": {"to": (str, None, None, True), "id": (int, 0, 2**31, True), "deg": (float, -90.0, 90.0, True)}, } class Manager(Agent): PAN_GAP_MS = 200 # at most 5 pans per second def __init__(self, h, servo, lease_ms=10000): super().__init__("manager", h, period_ms=50) self.me = h.root.split("/")[1] self.servo, self.lease = servo, Lease(lease_ms=lease_ms, max_queue=4) self.last_pan = ticks_ms() self.shown = "?" # not equal to any real state: the first pass publishes it self.t_pub = ticks_ms() self.had_owner = True # so the servo is centred once at start self.refused = 0 h.on("lab/+/cmd/#", self.on_cmd) # everyone's commands: we pick out ours def on_cmd(self, topic, payload): parts = topic.split("/") user, kind = parts[1], parts[3] if len(parts) > 3 else "" schema = KINDS.get(kind) d = hub.decode(payload) if schema is None or d is None or d.get("to") != self.me: return # not for us: ignore, silently ok, why = check(schema, d) if not ok: self.refused += 1 self.hub.publish("evt/ack", {"cmd_id": d.get("id"), "user": user, "ok": False, "why": why}) return now = ticks_ms() if kind == "claim": state, pos = self.lease.claim(user, now) self.hub.publish("evt/ack", {"cmd_id": d["id"], "user": user, "ok": state != "full", "why": state, "pos": pos}) elif kind == "release": self.lease.release(user, now) self.hub.publish("evt/ack", {"cmd_id": d["id"], "user": user, "ok": True, "why": ""}) elif kind == "pan": if not self.lease.holds(user, now): self.hub.publish("evt/ack", {"cmd_id": d["id"], "user": user, "ok": False, "why": "not owner"}) elif ticks_diff(now, self.last_pan) < self.PAN_GAP_MS: self.hub.publish("evt/ack", {"cmd_id": d["id"], "user": user, "ok": False, "why": "too fast"}) else: self.last_pan = now self.servo.angle(d["deg"]) self.lease.claim(user, now) # a command from the owner renews the lease self.hub.publish("evt/ack", {"cmd_id": d["id"], "user": user, "ok": True, "why": ""}) def decide(self, obs): self.lease.tick(ticks_ms()) return self.lease.owner def act(self, owner): if owner is None and self.had_owner: self.servo.angle(0) # nobody owns it: go to centre, once self.had_owner = owner is not None def tell(self, obs, owner): state = (owner, tuple(self.lease.queue)) if state != self.shown or ticks_diff(ticks_ms(), self.t_pub) >= 3000: # on change, and every 3 s anyway self.shown = state self.t_pub = ticks_ms() self.hub.publish("stat/owner", {"owner": owner, "queue": list(self.lease.queue)}, retain=True)

Look for the decisions. The manager subscribes to lab/+/cmd/#, everyone’s commands, and ignores any not addressed to it. It checks each command against a schema before acting. A pan is accepted only if lease.holds(user, now), and it renews the lease, so an owner that is working keeps its servo without sending separate renewals. Ownership and queue changes are published retained, and the same message is repeated every 3 s even when nothing has changed (see the box below). And self.shown starts as "?" rather than None: an earlier version started it as None, and then after a manager restart it did not publish owner: none, so the stale retained message went on saying that a client owned the servo, and the clients believed it.

Step 2. The Clients

The other students run the client, with a list of pan angles to perform. Change MANAGER to the manager’s user name. A client is a small state machine (the agents and state machines lesson): IDLE, WAIT for the queue, OWN while it works.

client.py MicroPython
# client.py -- ask for the resource, use it, give it back from time import ticks_ms, ticks_diff import hub from agent import Agent class Client(Agent): def __init__(self, h, manager, jobs, lease_ms=10000): super().__init__("client", h, period_ms=100) self.me = h.root.split("/")[1] self.manager, self.jobs = manager, list(jobs) # jobs: a list of pan angles to perform self.state = "IDLE" self.n = 0 self.t_sent = ticks_ms() self.t_renew = ticks_ms() self.lease_ms = lease_ms self.owner = None self.done = [] h.on("lab/%s/stat/owner" % manager, self.on_owner) def on_owner(self, topic, payload): d = hub.decode(payload) if d: self.owner = d.get("owner") def send(self, kind, **f): self.n += 1 f["to"], f["id"] = self.manager, self.n self.hub.publish("cmd/" + kind, f) self.t_sent = ticks_ms() def step(self): now = ticks_ms() if self.state == "IDLE" and self.jobs: self.state = "WAIT" self.send("claim") elif self.state == "WAIT": if self.owner == self.me: self.state, self.t_renew = "OWN", now elif ticks_diff(now, self.t_sent) >= 1000: self.send("claim") # asking again keeps our place in the queue elif self.state == "OWN": if self.owner != self.me: self.state = "IDLE" # we lost it (lease expired): start over elif self.jobs and ticks_diff(now, self.t_sent) >= 300: self.send("pan", deg=float(self.jobs.pop(0))) self.done.append(now) elif not self.jobs: self.send("release") self.state = "IDLE" elif ticks_diff(now, self.t_renew) >= self.lease_ms // 3: self.send("claim") # renew well inside the lease self.t_renew = now
main.py (client) MicroPython
import hub from client import Client from agent import run MANAGER = "bob" # the name of the student who owns the servo h = hub.Hub() h.presence() run(h, [Client(h, MANAGER, [10, 20, 30, 40, 50])])

Notice what the client does not assume. It does not assume its claim was granted: it waits until stat/owner names it. It does not assume it still owns the servo: if stat/owner changes to someone else (the lease ran out), it goes back to IDLE and asks again. And it repeats its claim every second while waiting, which costs one message a second and keeps its place in the queue (the answer says where it stands).

Step 3. Run the System

On the test fixture (one manager, three clients, 5 pans each, a fake broker and clock), the three clients were served in the order they asked: the first was owner at 0.11 s, the second at 1.71 s and the third at 3.21 s, and all 15 pans completed by 4.7 s, when the servo returned to centre. There were 25 acknowledgements, none refused, and no pan was ever accepted from a user who was not the owner at that moment. Run yours and record the same things: the order, the time each client waited, and the total.

Why repeat a message that has not changed? The first version of this manager published stat/owner only when the owner changed. With a perfect link that is enough. In a fault-injection test (the next week’s lesson, simulated, 20 runs per setting), a link that lost 10 % of the messages it sent left 6 of 20 runs deadlocked, and at 30 % loss 14 of 20: the one message that said “amy owns the servo” was lost, so every client sat in WAIT listening for a state that was never repeated, while the manager thought amy owned it, and amy’s repeated claim renewed her lease for ever. The fix is the three-second repeat: a lost update is now corrected within about 3 s. Afterwards all 20 runs finished at every setting tried. State that others depend on should be said again, not just said once.

Step 4. Break It

The failure drills. For each, record what happened and what you expected, and for any that surprises you, find the line of code responsible.

Two of these were run in simulation, so you can compare. In drill 1 (client A unplugged 0.8 s after getting the servo, after two pans) the second client became owner at 10.75 s, about 10 s after A’s last command, and the other two finished by 13.7 s; A did two of its five pans. In drill 2 (manager restarted at 2.5 s), the servo went to centre, stat/owner was republished as none at 2.55 s, the client that had been waiting re-claimed and was owner again at 2.71 s, and all three clients completed 5 pans each.

  • Drill 3 and the lease length (drill 7) are the heart of the lab: a shorter lease recovers faster from a crash and costs more renewals; a longer one is cheaper and slower. Say which you would choose for a servo that a person is watching, and which for one that carries a load.
  • Drill 6: what should a client do when it is told “full”? Write what you chose in the report, and implement it: back off for a random time, and try again.
  • Drill 2 depends on shown = "?". Change it back to None, repeat the drill, and describe what the clients do. This is a real bug that survived into the first version of this lab.

Solutions

Warm Up

Exercise 1: Why the Retained Owner?

A retained message is delivered to a subscriber immediately on subscribing, so a client that starts while someone else holds the servo learns the owner and queue at once, without waiting for a change. The same message is what makes the first-ever state visible. The danger is the flip side: a retained message can be stale (the manager restarted and did not republish), which is why the manager publishes the real state at start, repeats it every few seconds, and why a client treats ownership as something it must confirm.

Intermediate

Exercise 2: Two Owners?

Client A owns the servo, loses WiFi for 12 s, and is silent; the lease (10 s) expires and the manager grants it to B and publishes owner: B. A’s link returns; for a moment before A’s next incoming stat/owner arrives, A still believes it owns the servo and may send a pan. The manager checks lease.holds(user, now) and refuses it (“not owner”), so the servo is never moved by both: the manager is the single judge, and the clients’ beliefs are only hints. The refusal also tells A it lost, and A returns to IDLE.

Advanced

Exercise 3: Handle “full”
full.py MicroPython
import random class PatientClient(Client): """A Client that backs off for 2 to 6 seconds when the manager says the queue is full.""" def __init__(self, h, manager, jobs, lease_ms=10000): super().__init__(h, manager, jobs, lease_ms) self.hold_off_until = None h.on("lab/%s/evt/ack" % manager, self.on_ack) def on_ack(self, topic, payload): d = hub.decode(payload) if d and d.get("user") == self.me and d.get("why") == "full": self.hold_off_until = ticks_add(ticks_ms(), random.randint(2000, 6000)) def step(self): now = ticks_ms() waiting = self.state == "WAIT" and self.owner != self.me if waiting and self.hold_off_until is not None: if ticks_diff(now, self.hold_off_until) < 0: return # still backing off: say nothing self.hold_off_until = None super().step() # everything else is unchanged

The random delay is jitter (from the Staying safe offline lesson of Week 7): without it, every client refused at the same moment would try again at the same moment. Note that on takes the filter and the function; a real version would keep a single handler for evt/ack and branch inside it.
