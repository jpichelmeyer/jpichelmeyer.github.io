This lesson covers latency and starvation as the two ways a message system is slow. You describe latency by percentiles rather than averages, divide a path into stages, see what loop speed does and does not change, watch a queue turn a small overload into a long wait, prevent starvation with aging, and write a latency budget with a percentile attached.

A message system has two ways of being slow, and they need different cures. Latency is how long one message takes to get from the sender’s decision to the receiver’s action. Starvation is a message that is never handled, or handled so late it is useless, because other messages keep getting served ahead of it. Both are invisible when the system is quiet and both appear exactly when it matters: when several students, several agents and a robot share one broker and one slow loop. This lesson shows how to measure latency honestly, where the time goes, why a queue turns a small overload into a large delay, and how to be fair without losing urgency.

All the numbers in this lesson come from a model whose assumptions are stated, run on a computer, not from a measurement of the lab network. The shapes are real; the values are yours to replace with the round-trip times you measured in Lab 5.

Part 1. Latency Is a Distribution

“The latency is 50 ms” is not a statement about a network; it is a statement about one message. Messages differ, so describe them with percentiles: the p50 (median) is the value half of the messages beat, the p95 is beaten by 95 in 100, the p99 by 99 in 100. A control system that acts on every message must survive the slow ones, so it is the high percentiles that set the design, not the average.

Model one command, from a decision on one Pico to an action on another. It waits for the sender’s loop to come round (up to 50 ms), crosses WiFi and the broker (median 12 ms, with the occasional long delay: 2 % of packets take an extra 80 to 250 ms, the retries and power-save wake-ups of the Week 6 lessons), waits for the receiver’s check_msg (up to 20 ms) and is handled (5 ms). Over 100,000 simulated messages:

The fraction of messages slower than each time (log scale), for the modelled command path. The median is 54 ms, but one message in a hundred takes 220 ms or more, four times longer, and the worst of 100,000 took 337 ms.
Where the time goes. The percentiles of the parts do not add up to the percentile of the whole (the p99s add to 256 ms, the whole is 220 ms) because the slow cases rarely coincide. But the pattern is the point: the two loops dominate the median, and the network alone makes the tail.

Measuring it on a real system. Two Picos do not share a clock, so you cannot subtract a send time from a receive time. Measure the round trip instead: send a message that the other side echoes, and subtract on the same clock, as you did in Lab 5. Half the round trip is a fair estimate of the one-way time on a symmetric path. The class below keeps the last 64 results and reports the percentiles, because a printed average hides exactly what you are looking for.

lat.py MicroPython
# lat.py -- measure latency the way you will judge it: by percentiles, not the average class Lat: def __init__(self, n=64): self.buf = [0] * n # the last n latencies, in ms (a ring) self.i = 0 self.count = 0 # how many were ever recorded self.n = n def add(self, ms): self.buf[self.i] = ms self.i = (self.i + 1) % self.n self.count += 1 def report(self): k = min(self.count, self.n) if k == 0: return None s = sorted(self.buf[:k]) # fine for 64 values; do not do this for 64,000 return {"n": self.count, "p50": s[k // 2], "p95": s[min(k - 1, (k * 95) // 100)], "max": s[-1]}

A sample of 64 gives only a rough p95 and no p99 at all (the p99 of 64 values is the largest one). Collect a few hundred before you quote a high percentile, and always quote the number of samples with it.

Part 2. What Making the Loops Faster Does and Does Not Do

The first instinct on seeing a slow system is to speed up the loops. The model shows what that buys. The same path, with the sender and receiver loops made shorter:

Faster loops halve the median (54 to 25 ms) but barely move the p99 (220 to 194 ms), because the tail comes from the network and no loop speed changes that.

This has a design consequence worth stating plainly. You cannot make the worst case small by tuning your own code; you can only make it survivable. A robot that must stop within 100 ms of a command cannot rely on a command arriving in 100 ms. That is why the lab robot has a deadman (it stops by itself two seconds after the last command), why leases expire, and why the guard in the collision lesson needs a latency figure that includes the slow messages. Where safety matters, the safe action must not depend on a message arriving; messages should improve behaviour, not permit it.

Speeding up the loops is still worthwhile for the median, and costs little, but it has a price on this hardware: every wake-up of the network code uses time and power, and a loop that polls every 5 ms leaves less time for the work. Choose the loop period from what the action needs: a servo moved every 20 ms gains nothing from a command handled in 2 ms.

Part 3. Queues: Why a Little Overload Becomes a Lot of Delay

A loop that handles one message per pass is a server, and messages waiting for it are a queue. If the server handles 100 messages a second and 50 arrive, the queue is mostly empty. If 95 arrive, the queue is almost always occupied, and because arrivals are random (bunched, then sparse), the wait is long even though the server is “nearly idle”. Take a server needing 10 ms per message, with messages arriving at random:

Time a message waits before it is handled, against load (server 10 ms per message, random arrivals, ms). At 50 % the mean wait is 5 ms. At 90 % it is 51 ms, and at 95 % the p95 is 322 ms, with the server still “idle” 5 % of the time.

Above 100 % the queue does not settle at all. With arrivals at 105 % of capacity, the 2,106th message (after 20 s) waited 1215 ms, and the wait keeps growing for as long as the overload lasts, because every message adds to the line. Three rules follow:

  • Keep the load well under capacity. About 70 % is a comfortable ceiling for anything with a deadline: the mean wait there is about 11 ms (about the service time itself) and the p95 about 37 ms.
  • Bound every queue. An unbounded queue turns overload into unbounded latency, and eventually into a crash for lack of memory. A bounded queue turns it into dropped messages, which you can count and which you can design for.
  • When full, drop the oldest, not the newest, for anything that describes the present (positions, readings, commands to “go to X”). The old message is already out of date; the new one is the truth. The inbox of the message-handling lesson does this.

The class limits from Week 6 (at most ten messages a second per student, payloads under about 200 bytes) exist partly for this reason: one broker and one 100-per-second loop is a shared server, and a single client that publishes 100 messages a second uses all of it.

Part 4. Starvation

Priority is the cure for slow commands: serve the urgent messages first, and the stop command never waits behind a hundred telemetry messages. But strict priority has a failure mode of its own. If urgent messages arrive continuously, the routine ones are never reached. Nothing is wrong with any single decision (each time, the urgent message really was more important), and yet the status report, the heartbeat or the configuration update is never handled. The agent looks alive to itself and dead to everyone else.

The model: a server of 100 messages a second, 15 routine messages a second (status and telemetry) and a rising rate of urgent ones. Strict priority against the same priority with aging, where a routine message that has waited 500 ms is served next regardless:

Starvation (60 simulated seconds, queues bounded at 40 and dropping the oldest). With strict priority the routine messages wait 1.3 s at 80 urgent per second, are 74 % starved at 95, and are almost entirely starved at 105. Aging serves nearly all of them, at the price of a later urgent answer (p95 70 ms to 185 ms at 80 per second).

This is a real trade-off and the table shows its price honestly: aging makes the urgent messages wait longer, because some routine messages go first. It is the right trade when the routine messages carry something the system needs (the heartbeat that proves you are alive, the status that your partner’s state machine waits for). It is the wrong trade for a loop whose urgent messages have a hard deadline that even one extra message would miss; there, give the urgent class a small, separate path, and make the rest wait. Decide, per class, what late costs and what never costs.

fairq.py MicroPython
# fairq.py -- urgent first, but nobody waits forever from time import ticks_ms, ticks_diff class FairInbox: """Two classes: urgent (control) and routine (everything else). Urgent is served first, EXCEPT that a routine message that has waited longer than max_wait_ms jumps the queue. Each class is bounded: when full, the OLDEST is dropped.""" def __init__(self, urgent_max=8, routine_max=16, max_wait_ms=500): self.urgent = [] # entries are (arrival_ms, topic, payload) self.routine = [] self.umax, self.rmax, self.max_wait = urgent_max, routine_max, max_wait_ms self.dropped = 0 self.promoted = 0 def put(self, topic, payload, urgent=False): q, cap = (self.urgent, self.umax) if urgent else (self.routine, self.rmax) if len(q) >= cap: q.pop(0) self.dropped += 1 q.append((ticks_ms(), topic, payload)) def get(self): now = ticks_ms() if self.routine and ticks_diff(now, self.routine[0][0]) >= self.max_wait: self.promoted += 1 q = self.routine # starving: serve it now elif self.urgent: q = self.urgent elif self.routine: q = self.routine else: return None _, topic, payload = q.pop(0) return topic, payload

Run on the same load with the real class, one message handled per 10 ms: at 95 urgent per second, 920 of 925 routine messages were served (against 236 without aging), with 899 promotions, and no routine message waited more than 527 ms. Both classes drop when full, 650 messages here, because 95 + 15 messages a second exceed what a 100-per-second loop can do: aging decides who is dropped, not whether anything is.

Starvation also happens at the sender. A control loop that publishes in a fixed order (“first the command, then the pose, then the status”) and skips the later ones when it is late will never send the status. The same cure applies: let the age of what has not been sent decide, and keep a count of messages that were skipped.

Part 5. A Latency Budget

A requirement such as “the robot stops within a quarter of a second of the stop command” is a budget to be divided among the stages, with a percentile attached (“in 99 % of cases”). The method:

  • Write the requirement with a percentile. “Within 250 ms” without “in 99 % of cases” is unverifiable.
  • List the stages (as in Part 1) and give each the figure you measured, not the figure you hope for.
  • Add the percentiles you must cover and compare with the requirement, keeping the caveat that p99s do not add exactly.
  • If it does not fit, change the design, not the requirement: a local reaction (the sensor acts directly on the actuator, with the network only informing), a shorter loop where the median is the problem, a deadman where the tail is, a lower rate where the load is.

The model’s path has a p99 of 220 ms, and the actuator needs about 30 ms to move, so a 250 ms requirement is just met, with nothing to spare for a second hop. A coordinator that relays the command (sensor to coordinator, coordinator to actuator) pays the network and the loop waits twice, and the budget is gone. That is the arithmetic behind the advice of the multi-agent lessons: fewer hops, and let the data go where it is needed.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Median or Worst?

Sorted already; k = 20. p50 is index 10, which is the 11th value: 16 ms. p95 is index (20 × 95) // 100 = 19, the last value: 250 ms, the same as the max. With 20 samples the “p95” is the worst case: a single bad round trip decides it. Quote high percentiles only from enough samples (a few hundred), and quote the count.

Exercise 2: Faster Loops

The median improves a great deal, from 54 ms to 25 ms in the model, because the waiting for the loops to come round is the largest part of the median. The p99 hardly moves (220 to 194 ms) because it is dominated by WiFi retries. To improve the worst case, reduce the number of hops, send less (less chance of a retry), keep the radio awake, or make the safe behaviour independent of the message: a deadman, a lease, or a local reaction.

Intermediate

Exercise 3: How Much Load?

Two students: 80 messages a second against a capacity of 100, utilization 0.8; the model gives a mean wait of about 19 ms and a p95 of 63 ms, acceptable. Five students: 200 messages a second against 100, utilization 2.0, a permanent overload: half the messages cannot be handled, whatever the queue policy. A bounded queue would drop roughly half of them and an unbounded one would grow without limit. The only cure is less traffic, which is why the class limit is ten messages a second per student.

Exercise 4: Aging on a Loaded Loop

For: a stop command that waits 449 ms at its p95 (rather than 226 ms) may be too late, so for commands with a hard deadline the extra delay is a real cost. Against: without aging, the routine messages were 74 % starved, so the heartbeat and status never arrived and the other agents would declare this one dead. Resolution: the two classes are not equally urgent to the deadline. Keep the stop command on its own tiny path with a very small queue, apply aging to the rest, and above all reduce the load: this table is for a loop at 110 % of capacity, which is a design error, not a scheduling problem.

ages.py MicroPython
class FairInbox2(FairInbox): def ages(self): now = ticks_ms() u = ticks_diff(now, self.urgent[0][0]) if self.urgent else None r = ticks_diff(now, self.routine[0][0]) if self.routine else None return u, r

Each queue is in arrival order, so the oldest message is the first one. Publishing {"age_u": ..., "age_r": ..., "drop": ...} in stat/q every few seconds lets you (and your partners) see overload as it builds, rather than discovering it as a missing message. A rising routine age with a flat urgent age is the signature of starvation beginning.
