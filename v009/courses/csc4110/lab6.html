Lab 6 builds the robot node from the week’s lessons and attacks it. You run the command logic with ownership, acknowledgements, rate limits and a deadman on real hardware, command it from your laptop, and then take away its network and its power while recording how long each safeguard takes.

SAM lens. commands arrive through the Perceptor, the Robot class is the Decider (validation, ownership, repeats, the deadman) and the actuators carry out only what it allows. The drills show that the safety logic needs no network to work.

What You Will Build

A robot node that obeys commands from the broker and stays safe when things go wrong. It has a pan servo and a drive output, the logic from the Topics and commands lesson (ownership, validation, acknowledgements, a deadman timer), a last will, and a retained state topic. It lives in your own subtree, so you can command it from your laptop with mosquitto_pub, and you can pull its network away and watch each safeguard work.

The Lab 6 setup. The robot logic and the broker are the same as in the lesson; only the actuators are yours.

Step 1. Build and Power

Lab 6 wiring, using the servo power rules of the PWM lesson. With the LED as the drive output, brightness stands in for motor speed, and you lose nothing: the safeguards act on the command, not on the motor.

Copy to the Pico: net.py, config.py, hub.py, robot.py, controller.py, actuators.py (below), and motor.py if you use the driver. The first four are in the lessons of this week.

actuators.py MicroPython
# actuators.py -- the hardware behind the Robot logic from machine import Pin, PWM class Actuators: """A pan servo on GP14, and a 'drive' output: the TA6586 motor driver on GP10/GP11 (motor=True), or an LED on GP16 whose brightness stands in for speed (motor=False).""" def __init__(self, motor=False): self.servo = PWM(Pin(14), freq=50) self.pan(0) if motor: from motor import Motor # from the Switching Loads lesson self.motor, self.led = Motor(10, 11), None else: self.motor, self.led = None, PWM(Pin(16), freq=1000, duty_u16=0) def pan(self, deg): deg = max(-90, min(90, deg)) self.servo.duty_ns(1_000_000 + int((deg + 90) / 180 * 1_000_000)) # 1.0 to 2.0 ms def drive(self, pct): if self.motor: self.motor.speed(pct) else: self.led.duty_u16(int(abs(pct) / 100 * 65535)) def stop(self): self.drive(0)
main.py MicroPython
# main.py for Lab 6: a robot node in your own subtree, with a loopback self-test import hub from robot import Robot from controller import Controller from actuators import Actuators from time import ticks_ms, ticks_diff h = hub.Hub() h.presence() robot = Robot(Actuators(), allow_spin=True) # Lab 6 only: the spin command exercises the deadman def on_cmd(topic, payload): kind = topic.rsplit("/", 1)[-1] h.publish("evt/ack", robot.command(kind, hub.decode(payload), ticks_ms())) h.on(h.mine("cmd/#"), on_cmd) # The loopback test: this same board also plays the controller, through the real broker. ctl = Controller(h, h.root, "me") # h.root is "lab/<you>/" script = [(2000, "claim", {}), (3000, "pan", {"deg": 30}), (3600, "pan", {"deg": -30}), (4400, "drive", {"pct": 60, "ms": 800}), (6000, "spin", {"pct": 40}), (9000, "stop", {})] t0, nxt, shown, reported = ticks_ms(), 0, None, set() while True: h.poll() now = ticks_ms() for why in robot.tick(now): h.publish("evt/stopped", {"why": why}) print("stopped:", why) st = robot.state() if st != shown: h.publish("stat/state", {"state": st[0], "owner": st[1]}, retain=True) shown = st print("state:", st) if nxt < len(script) and ticks_diff(now, t0) >= script[nxt][0]: kind, fields = script[nxt][1], script[nxt][2] print("send", kind, fields, "id", ctl.send(kind, now, **fields)) nxt += 1 ctl.tick(now) for cid in list(ctl.done): if cid not in reported: reported.add(cid) print("ack", cid, ctl.done[cid])

Step 4. Failure Drills

Now the part that matters. For each drill, write down the time each event happened (the -F "%I" option on mosquitto_sub gives timestamps) and compute the delays.

  • Drill A, network lost during a spin. Start spin 50 repeated from the laptop for a few seconds, then turn the WiFi access point (or your hotspot) off. Does the motor stop? When? Where did the decision to stop get made: on the Pico, or at the broker? What does the broker’s stat/online show, and when?
  • Drill B, power pulled. Unplug the Pico. How long until stat/online says false? Compare with the 30 to 45 s window for keepalive 30.
  • Drill C, recovery. Restore power or WiFi. How long until the node is online again? What retained messages were republished, and in what order? (The hello message is put first in the queue by Hub.connect.)
  • Drill D, retained command. Publish cmd/pan with -r and a valid payload. Reboot the Pico, claim the robot, and see what it does when the broker redelivers the old command. Then delete the stored message with an empty retained publish (-n -r) and repeat.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Read the Script

The spin is sent at 6,000 ms. The deadman allows 2,000 ms from the last command, so it fires just after 8,000 ms (at the first tick past that moment). At 8,500 ms the robot has stopped but still has an owner whose lease (30 s) has not expired, so the state is READY with the owner. The stop at 9,000 ms is then only a formality.

Exercise 2: Why Rejected?

Add "user":"jsmith": {"v":1,"seq":4,"t":0,"id":4,"user":"jsmith","deg":30}. The robot needs it to apply the ownership rule, because MQTT 3.1.1 does not tell a subscriber who published a message. The field is a claim, not proof; the proof is the access list, which decides who can publish on the topic at all.

Intermediate

Exercise 3: Owner “me”

The robot checks only that the user field of each command equals the owner stored by the claim. The name is arbitrary. A second controller that also called itself “me” would be treated as the same owner: it could command the robot, and renew its lease, with no protection. That is acceptable in your own subtree where only you can publish, and exactly why the real protection against an impostor is the broker’s access list. For the practical, the instructor grants write access to one user at a time.

Advanced

Exercise 4: Same Id Twice
dup_test.py MicroPython
class Counting: """A stand-in actuator that only counts what it is told.""" def __init__(self): self.pans = 0 def pan(self, deg): self.pans += 1 def drive(self, pct): pass def stop(self): pass act = Counting() robot = Robot(act) robot.command("claim", {"id": 1, "user": "me"}, 1000) fields = {"id": 77, "user": "me", "deg": 45} a1 = robot.command("pan", fields, 2000) a2 = robot.command("pan", fields, 2050) # the same command again: a retry print(a1 == a2, act.pans) # True 1: answered twice, done once fields2 = {"id": 78, "user": "me", "deg": 45} a3 = robot.command("pan", fields2, 2100) # a NEW id only 100 ms later print(a3) # refused: too fast

The first line prints True 1: the two acks are identical (the second came from the table of recent ids) and the actuator was told to pan once. The second print shows that a different id 100 ms later gets “too fast”. These two rules are independent: ids protect against retransmission, the rate rule against a different command arriving too soon. A real controller that retries correctly never trips the second.
