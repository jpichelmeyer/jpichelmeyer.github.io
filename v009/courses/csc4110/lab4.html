Lab 4 closes the loop. You build a controller that holds a light level against disturbances, tune it with a measured routine, and then analyze its behavior from the outside using the data it publishes. On the way you apply almost everything from the first four weeks: ADC and scaling, filtering, PWM, the cooperative loop, the network on-ramp and sampling theory.

What You Will Build

A closed loop that holds a light level steady. An LED shines on a light sensor; the Pico measures the light, compares it with a target set by a knob, and adjusts the LED’s brightness with PWM so that the measured level stays at the target, even when you shine a flashlight at the sensor. At the same time the loop reports what it is doing to the class broker, so you can plot its behavior from outside. This is the whole sense, decide, act, report cycle of a robot in the smallest possible package, and Lab Practical 1 asks for a loop of this kind.

The Lab 4 loop. The measured value (pv) is compared with the setpoint (sp) inside the PID, which produces the LED drive (u). Reporting is a side branch: it watches the loop and never changes it.

Wiring

The Lab 4 wire list. Build it in two stages: first confirm that avg(ldr) rises when the LED goes from off to full, and only then connect the knob.

Note the divider direction: with the LDR on the 3V3 side, more light gives a higher reading, which is what the PID expects (more LED, higher measurement). If you swap the LDR and the resistor, the reading goes down with more light, and the loop will be unstable because the sign is wrong. A wrong sign is the commonest cause of a controller that runs the LED to full brightness and stays there.

Step 1. The Program

Read it all before running it. calibrate() measures the sensor with the LED off and fully on, so that pv is scaled to 0 (dark) to 1 (full LED) whatever the room, the LDR and the resistor happen to be. The target comes from the knob, scaled to 0.15 to 0.85 so that it is always reachable. The control loop runs at 20 Hz, reports at 5 Hz, and publishes an event when the loop locks (within 0.03 of the target for a second) or loses lock.

main.py MicroPython
# main.py for Lab 4: hold a light level with PID, and report on the loop import net from machine import Pin, PWM, ADC from time import ticks_ms, ticks_diff, sleep_ms from pid import PID # from the PID lesson from every import Every # from the Pulses lesson from filters import EMA # from the Filtering lesson led = PWM(Pin(16), freq=1000, duty_u16=0) # the actuator: an LED through 220 ohms ldr = ADC(26) # the sensor: LDR + 10 k divider pot = ADC(27) # the setpoint knob def avg(adc, n=16): return sum(adc.read_u16() for _ in range(n)) / n / 65535 def calibrate(): """Read the sensor with the LED off and fully on.""" led.duty_u16(0); sleep_ms(500); lo = avg(ldr) led.duty_u16(65535); sleep_ms(500); hi = avg(ldr) led.duty_u16(0); sleep_ms(300) # let the LED and the sensor settle if hi - lo < 0.05: raise ValueError("the LDR does not see the LED: shield it and aim it") return lo, hi lo, hi = calibrate() pid = PID(1.5, 4.0, 0.0) # starting gains: tune them in Step 3 pv_f, sp_f = EMA(0.5), EMA(0.1) control, report = Every(50), Every(200) # a 20 Hz loop, a 5 Hz report sp = pv = u = 0.0 good_ms, locked = 0, False last = ticks_ms() def step(): global sp, pv, u, good_ms, locked, last if control.due(): now = ticks_ms() dt = ticks_diff(now, last) / 1000 last = now pv = pv_f.update((avg(ldr, 4) - lo) / (hi - lo)) sp = sp_f.update(0.15 + 0.7 * avg(pot, 4)) # keep the target reachable u = pid.update(sp, pv, dt) led.duty_u16(int(u * 65535)) # "locked" = within 0.03 of the target for one second if abs(sp - pv) < 0.03: good_ms += int(dt * 1000) else: good_ms = 0 if good_ms >= 1000 and not locked: locked = True net.publish("evt/lock", {"locked": True, "sp": round(sp, 2)}) elif good_ms == 0 and locked: locked = False net.publish("evt/lock", {"locked": False, "pv": round(pv, 2)}) if report.due(): net.publish("tele/loop", {"sp": round(sp, 3), "pv": round(pv, 3), "u": round(u, 3)}) try: while True: step() finally: led.duty_u16(0) # whatever happens, leave the actuator off

The try/finally at the end is the same habit as the motor bench test: if the program stops for any reason, the LED, the actuator, is turned off. And notice what is not in the loop: no sleep, no waiting for the network. net.publish queues the message and returns, as in Lab 3, so a network failure cannot stall the controller.

Step 2. Measure the Plant

Before closing the loop, measure what you are controlling. With the loop not running, set the LED to 0, 20, 40, 60, 80 and 100 % in turn, wait a second at each, and write down the filtered pv. Plot pv against LED percent. The curve is not a straight line: LDRs respond logarithmically, so equal steps of LED give unequal steps of pv. A PID with fixed gains copes with that, but you will see it as a loop that is quick at one end and sluggish at the other. Also time the sensor: switch the LED from off to full and see how long pv takes to reach 90 % of its final value. An LDR is far slower than a photodiode, often tens or even hundreds of milliseconds, and that delay sets how hard you can push the gains.

Step 3. Tune the Loop

The tuning routine. Change one gain at a time, wait for the loop to settle, and write each result in your table. The starting gains are in main.py; the numbers worth recording are the steady-state gap, the overshoot and the recovery time after the flashlight.

Step 5 is the windup test from the PID lesson on real hardware: while the LDR is covered, the loop cannot reach its target, the controller output saturates at full, and a controller without the clamp would build up a huge integral and overshoot for a long time after you uncover the sensor. Ours does not, because the PID class stops integrating when it is saturated. Confirm that by watching the recovery.

Step 4. What to Expect

A simulated run of the loop (a first-order plant with a 0.15 s time constant; a real LDR will be slower and less tidy, so expect your curves to differ in detail). P alone leaves a permanent gap. Adding the integral closes it, and the flashlight pushes pv up for a moment before the controller dims the LED to compensate.

Numbers from the simulation, for comparison with yours: with P and I together the loop first stays within 0.03 of the target about 1.2 seconds after starting, the flashlight pushes the reading about 0.16 above the target at its worst, and the loop is back inside the band about 0.7 seconds later with the LED drive down from 0.48 to 0.23 (it has absorbed the flashlight’s light). With much higher gains (kp = 6, ki = 12) the simulation recovers faster, and a real LDR will flicker or oscillate at those values.

Step 5. Look from the Outside

On the laptop that runs your broker session, capture the loop’s telemetry while you run the tuning routine, and then measure the run with a script instead of by eye.

analyze.py MicroPython
# analyze.py: run on your laptop. mosquitto_sub -v -t "lab/+/tele/loop" > loop.txt import json def load(path): """Read mosquitto_sub -v lines: '<topic> <json>'. Returns (seconds, sp, pv, u) rows.""" rows = [] for line in open(path): topic, _, payload = line.partition(" ") if topic.endswith("tele/loop"): d = json.loads(payload) rows.append((d["t"] / 1000, d["sp"], d["pv"], d["u"])) return rows def settle_time(rows, t0, t1, band=0.03): """Seconds after t0 until pv stays within `band` of sp up to t1 (None if it never does).""" seg = [r for r in rows if t0 <= r[0] < t1] for i, r in enumerate(seg): if all(abs(q[2] - q[1]) < band for q in seg[i:]): return round(r[0] - t0, 2) return None def peak_error(rows, t0, t1): """The largest distance from the setpoint in the window.""" return round(max(abs(r[2] - r[1]) for r in rows if t0 <= r[0] < t1), 3)

The script works on what the broker received, which is five samples per second. The control loop sees twenty. That difference matters: in the simulation the flashlight pushes the real reading 0.16 above the target at its worst, but the telemetry at 5 Hz shows a worst case of only about 0.11, because the peak falls between two reports. And with the higher gains the telemetry hides the disturbance completely: every reported sample is inside the band, although the loop did leave it. This is the sampling lesson again, applied to your own measurement. It is also why the evt/lock event exists: an event is sent at the moment something happens, instead of being left for a fixed-rate sample to catch.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: The Cost of Telemetry

One message is 20 + 69 + 5 = 94 bytes, so 5 per second is 470 B/s. The control loop runs at 20 Hz and reports at 5 Hz, so there are 4 control updates for every message, and only the most recent is reported. Messages: 5 + 2 = 7 per second, under the limit of 10, with a margin of 3.

Exercise 2: Scale the Reading

pv = (raw − lo) / (hi − lo) with a span of 0.48: for 0.54, pv = 0.24 / 0.48 = 0.5. For 0.78, pv = 1.0. For 0.25, pv = −0.05 / 0.48 = −0.10: below zero, because the ambient light changed after calibration. The PID simply sees an error that is larger than the target and drives the LED harder; it does not know the scaling is off. Re-calibrating when conditions change, or filtering out of-range values like the next exercise, is the engineering answer.

Intermediate

Exercise 3: Why P Alone Falls Short

At steady state u = 0.30, so the error must be e = u / kp = 0.30 / 1.5 = 0.20, which matches the simulation’s 0.196 gap. Doubling kp to 3.0 halves it to 0.10. It never reaches zero for any finite kp, because a P controller needs an error to produce any output at all. A huge kp amplifies sensor noise into LED flicker, and combined with the sensor’s delay it makes the loop oscillate. The integral term solves the problem differently: it keeps growing until the error is zero, at which point it supplies the whole 0.30 by itself.

Advanced

Exercise 4: Guard the Sensor
guard.py MicroPython
class Guard: """Declares a sensor fault after `limit` bad readings in a row, and clears it after `limit` good ones. check() returns "fault", "clear" or None.""" def __init__(self, lo=-0.3, hi=1.3, limit=5): self.lo, self.hi, self.limit = lo, hi, limit self.bad = self.good = 0 self.fault = False def check(self, pv): if self.lo <= pv <= self.hi: self.good += 1 self.bad = 0 if self.fault and self.good >= self.limit: self.fault = False return "clear" else: self.bad += 1 self.good = 0 if not self.fault and self.bad >= self.limit: self.fault = True return "fault" return None
test_guard.py MicroPython
g = Guard() seq = [0.5] * 3 + [-1] * 5 + [0.5] * 5 print([(i, r) for i, x in enumerate(seq) for r in [g.check(x)] if r]) # [(7, 'fault'), (12, 'clear')] fault on the 5th bad reading, clear on the 5th good one g = Guard() seq = [0.5, -1, -1, -1, -1, 0.5, -1, -1, -1, -1, -1] print([(i, r) for i, x in enumerate(seq) for r in [g.check(x)] if r]) # [(10, 'fault')] four bad then a good one resets the count, so no fault until the later run

In step() you would call guard.check(pv) on each control update. On "fault": set u to 0, turn the LED off, reset the PID (pid.i = 0), and publish evt/fault. While guard.fault is true, skip the PID. On "clear": resume and publish evt/fault with false. Requiring five in a row on both sides, instead of reacting to one reading, stops a single glitch from toggling the loop on and off, the same idea as the debounce of Lab 1.
