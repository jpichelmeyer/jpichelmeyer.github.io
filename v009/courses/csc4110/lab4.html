This is Unit 1's capstone lab: a complete, continuously running telemetry node, your Pico, your sensor, reporting real readings to the Pi 3B+ broker, with nothing left to fake or simulate. Everything you need was built somewhere in the last four weeks; today is entirely about assembly, testing, and handling the ways a multi-stage system actually fails in practice.

The full system, start to finish. Today's new ground isn't any individual piece, it's keeping all of them running correctly, together, continuously, which is a genuinely different kind of challenge than any single-lesson exercise so far.

Materials

  • 1 × Raspberry Pi Pico WH with the full stack installed: MicroPython firmware, umqtt.simple
  • 1 × photoresistor + 10kΩ resistor (from Lab 2), or any other analog sensor from your kit you'd rather use instead
  • Access to the classroom's Pi 3B+ broker and its IP address
The LDR voltage divider on a breadboard. The LDR and the 10 kΩ resistor meet in the orange column, which goes to GP26.

Requirements

Your main.py must, running continuously with no computer attached once started (recall: save it as main.py, per Lesson 1):

  1. Connect to WiFi and then to the broker on startup, with a unique CLIENT_ID (your assigned Pico number).
  2. Sample your chosen sensor and apply a moving-average filter with a window size you choose and can justify.
  3. Publish a JSON telemetry packet (value, unit, t_ms) to lab/<your-id>/<sensor-kind> on a publish interval you choose and can justify.
  4. Subscribe to lab/<your-id>/cmd and respond to at least one simple command published to it, toggling the onboard LED on receiving b"led_on" / b"led_off" is sufficient.
  5. Use a single non-blocking while True loop for all of the above, publishing and checking for commands have to coexist in the same loop, not two separate scripts.
The whole Lab 4 system as topics. Readings flow out of the Pico on one topic; commands flow back on another. Anyone subscribed to the right topic can take part.

Handling the Real World: Reconnection

Every script so far has assumed the WiFi and broker connections, once established, just stay up. In practice, over a long enough run, they don't always, a brief WiFi hiccup, the broker restarting. A capstone-quality telemetry node should at least detect a dead connection rather than silently stop publishing forever:

main.py (excerpt) MicroPython
def publish_reading(): global client packet = make_packet(filtered_read(), "raw_adc") try: client.publish(TOPIC, packet) except OSError as e: print("publish failed, reconnecting:", e) try: client.connect() # try to re-establish the existing MQTTClient except OSError: pass # next interval will just try again

This isn't a complete, bulletproof solution, real production IoT systems handle this with considerably more care, but it demonstrates the core idea worth internalizing: a networked device that assumes the network never fails is making an assumption that will eventually be wrong, and "eventually wrong" in a device meant to run unattended is a real design problem, not an edge case to ignore.

A telemetry node as a state machine. Detecting the failure, retrying with a growing delay, and returning to normal are three separate jobs.

Procedure

  1. Build up the four requirements incrementally, confirm WiFi connects, then confirm a single publish lands correctly (check with mosquitto_sub), then add the filter, then add the subscribe/command handling, then add the reconnection attempt last.
  2. Run the complete script for at least five continuous minutes while watching mosquitto_sub -h localhost -t "lab/<your-id>/#" -v on the Pi.
  3. While it's running, publish an LED command to your cmd topic from the Pi and confirm the Pico reacts within one loop iteration, without interrupting the ongoing telemetry stream.
  4. Disconnect your Pico's WiFi briefly (walk out of range, or disable the AP if you control it) during the run, then restore it, and observe whether your reconnection handling recovers the stream or whether it needs a manual restart.

Lab Report

  1. State your chosen sensor, window size, and publish interval, and justify each in one or two sentences, tying back to the relevant lesson (noise filtering for window size, sampling-rate reasoning for interval).
  2. Describe what happened during the disconnect/reconnect test in step 4, did your node recover automatically, or require a manual restart? If it didn't recover, describe what you believe would need to change for it to.
  3. Describe one thing about running a system continuously for five-plus minutes that didn't show up at all in any single-lesson exercise this unit.

Intermediate

Exercise 3: A Runtime Command
main.py MicroPython
def on_message(topic, msg): global INTERVAL_MS if msg == b"led_on": led.value(1) elif msg == b"led_off": led.value(0) elif msg.startswith(b"rate="): try: INTERVAL_MS = int(msg[5:].decode()) except ValueError: pass # "rate=banana": ignore it

Test it with mosquitto_pub -t lab/pico01/cmd -m rate=2000 and watch the stream slow down.

Advanced

Exercise 4: Backoff Reconnect
main.py MicroPython
def reconnect(): delay = 1 while True: try: client.connect() return # success: caller carries on except OSError: sleep(delay) delay = min(delay * 2, 30)

The doubling stops a whole classroom of Picos from hammering a restarting broker every second. The cap stops the wait from growing absurdly long.
