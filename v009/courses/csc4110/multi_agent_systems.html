This lesson introduces agents and the state machines that coordinate them. You model every node as a sense, decide, act and tell cycle, write a complete small agent against a base class, compare centralised, hierarchical and peer organisations, and use the broker, with its access list, as a shared bus. Then you let state machines on different boards follow each other: publishing state retained, remembering when each peer was last heard, and agreeing over a lossy link with safe defaults that need no help from the other side.

SAM lens. The lesson's four-step cycle is SAM by another name: sense is the Perceptor, decide is the Decider with its Memory, act and tell are the Actuator's physical and network outputs. In a team, each agent's environment includes the others. A state machine is a Decider whose Memory is the current state; across boards it can only perceive the other machines through messages, so it keeps a belief about each peer, with an age.

Until now one board did one job and everything else was infrastructure. This unit changes the question from “what can one Pico do?” to “what can several do together, with nobody in charge of all of them?” A system built from independent, communicating decision-makers is a multi-agent system, and it behaves differently from any single program, however clever. The robot you built in Units 1 and 2 (senses, acts, reports, obeys commands, survives outages) already is an agent. The new part is that other agents listen to it and decide what to do because of what it says.

Part 1. What Makes Something an Agent

An agent is a program with its own sensors, its own outputs and its own decision-making, which acts on its own view of the world and tells others what it saw and did. It runs one cycle, forever: sense, decide, act, tell. A collection of agents becomes a system when what each one tells shapes what the others decide.

The agent cycle. Each agent repeats these steps at its own pace, with no knowledge of how many others exist.
agent.py MicroPython
# agent.py -- the four-step cycle, and a loop that runs several agents from time import ticks_ms, ticks_diff class Agent: def __init__(self, name, hub, period_ms=100): self.name, self.hub, self.period = name, hub, period_ms self.last = ticks_ms() self.steps = 0 def sense(self): return None # read sensors, or look at what arrived def decide(self, obs): return None # apply local rules (and remembered state) def act(self, decision): pass # drive outputs def tell(self, obs, dec): pass # publish what we saw and did def step(self): obs = self.sense() dec = self.decide(obs) self.act(dec) self.tell(obs, dec) self.steps += 1 def tick(self, now): if ticks_diff(now, self.last) >= self.period: self.last = now self.step() def run(hub, agents, wdt=None): """The whole program: poll the network, then give every agent its turn.""" while True: hub.poll() now = ticks_ms() for a in agents: a.tick(now) if wdt: wdt.feed()

A concrete agent overrides the four methods and nothing else. The loop around them never changes, which is what makes agents easy to combine on one board: run polls the hub (with the bounded inbox of Unit 2) and then gives every agent its turn. Here is a complete small one, a sentry with an HC-SR04 and an LED:

sentry.py MicroPython
# sentry.py -- one concrete agent: reports distance, lights an LED when something is near from agent import Agent class Sentry(Agent): NEAR, FAR = 20.0, 30.0 # centimetres: a band, so it does not flicker def __init__(self, hub, read_cm, led): super().__init__("sentry", hub, period_ms=100) self.read_cm, self.led = read_cm, led self.near = False self.last_sent = None def sense(self): return self.read_cm() # None if the echo timed out def decide(self, cm): if cm is None: return self.near # no reading: keep the last decision if cm < self.NEAR: self.near = True elif cm > self.FAR: self.near = False return self.near def act(self, near): self.led.value(1 if near else 0) def tell(self, cm, near): if near != self.last_sent: # tell only when the decision changes self.hub.publish("stat/sentry", {"near": near, "cm": cm}, retain=True) self.last_sent = near

Note what each method does not do. sense does not decide; decide does not touch hardware; tell publishes a decision, not a stream of readings, and only when the decision changes. The sentry was run on the test fixture with the distance script 50, 25, 15, 25, 35 and then sensor failure, a second apart. The LED came on at 15 cm, stayed on at 25 cm (inside the 20 to 30 band), went off at 35 cm, and ignored the timeout. The broker saw exactly three retained messages: near: false at start, near: true at 3 s and near: false at 5 s, while step() ran 80 times in eight seconds. Eighty cycles, three messages.

Part 2. Why Several Agents

  • Distribution. Sensors and actuators are in different places, and each needs a processor nearby. A scan head on one side of a table cannot share a wire with one on the other.
  • Specialisation. A Pico has 264 kB of RAM. One job per board keeps each program small enough to understand and to test.
  • Robustness. One agent failing need not stop the rest, if the others notice and respond (the watchdog, will and lease of Unit 2 are how they notice).
  • Scale. More capacity means one more agent, not a rewrite.

The price is coordination. Agents share no memory, only messages that take time, can be lost, and can arrive twice. Every agent therefore works from an incomplete and slightly out-of-date picture of the others. Most of the rest of this unit is about living with that honestly.

Part 3. How to Organise Them

Three ways to organise the same agents. In this course the lines are never real wires: every agent talks only to the broker, and the organisation is a matter of who listens to whom.

In a centralised design one coordinator collects reports and issues instructions. It is the easiest to build, and when the coordinator stops, everything stops (Lab 9 deliberately tests that). A hierarchy limits the damage to a branch. A peer design has no single point of failure, but nobody sees the whole picture, so agreement has to be built in (Lab 11 builds a small piece of it). You will meet all three in Labs 9 to 12.

The honest comparison. Decentralising removes the single point of failure, and moves its cost into the rules for agreeing.

Part 4. The Broker as the Shared Bus

Agents never talk to each other directly. Each publishes into its own part of the topic tree (lab/<user>/{tele,evt,cmd,stat}/<name>, from Unit 2) and subscribes to the parts it needs. The broker is a shared bus, sometimes called a blackboard: agents write what they know where others can read it. The access list that you have had since Lab 5 already does the job: everyone may read lab/#, and everyone may write only their own lab/<user>/#. So a misbehaving agent can only damage its own corner.

Who writes where in a three-agent system. A command is a message in the sender’s subtree, addressed by a field; the receiver listens to its sender.

This has a consequence that surprises people: “sending a command to the actuator” and “the actuator receiving a command” are two separate acts joined only by a subscription. If the actuator subscribes to the wrong coordinator, nothing is received and nothing is reported as wrong. Good agents therefore say what they are listening to (in their retained stat/online or a stat/subs message), and good tests check it.

Part 5. State Machines Across Boards

In Unit 1 you wrote a state machine to answer “what is this board doing now?”. With several boards, each machine must also answer “and what is the other one doing?”, and it cannot look; it can only listen to messages that are late, lost, repeated or stale. Two habits make that manageable. First, write the machine as a table of (state, event) to (next state, action) instead of nested if statements: every combination is then either in the table or visibly missing, and a timeout is just another event (“after 500 ms in this state, fire timeout”), so there is no hidden sleep. An event a state does not expect is ignored but counted: among agents, late and duplicate messages are normal, so crashing on them is a bug, but staying silent about them is a worse one.

The requester as a diagram of its table. The retry count is part of the state (ASK1, ASK2, ASK3), so the machine needs no counter variable and every path can be listed.

Second, make every state change a message. Publish the state retained, so that an agent that joins late learns it at once. On the listening side, remember not only the last state of each peer but when you heard it, because a retained message is as old as the last change and says nothing about whether the peer is still alive:

peers.py MicroPython
# peers.py -- what I last heard about the others, and how old that is from time import ticks_ms, ticks_diff class Peers: def __init__(self, stale_ms=10000): self.stale_ms = stale_ms self.seen = {} # name -> (state, time I heard it) def heard(self, name, state): self.seen[name] = (state, ticks_ms()) def state(self, name): """The last known state, or "UNKNOWN" if never heard or too old.""" s = self.seen.get(name) if s is None or ticks_diff(ticks_ms(), s[1]) > self.stale_ms: return "UNKNOWN" return s[0] def age_ms(self, name): s = self.seen.get(name) return None if s is None else ticks_diff(ticks_ms(), s[1])

Peers.state returns "UNKNOWN" for a peer never heard, or not heard for longer than stale_ms. That third answer is the important one: a machine that plans on a stale “the door is closed” is as wrong as one that has never heard from the door, and it is safer to treat both as unknown and act on that. (With the presence will from Unit 2, stat/online says when a peer has gone, and the stale rule covers a peer that is online but silent.)

Part 6. Agreeing Over a Lossy Link

Suppose a requester asks a door to open. Neither can see the other. The requester sends open; the door opens and sends ack; if either message is lost, one side knows something the other does not. Here is one exchange with a lost acknowledgement:

A lost acknowledgement. The requester cannot tell a lost open from a lost ack, so it repeats; the door must therefore treat a repeated open as harmless (OPEN plus open answers again and does nothing else). It is the id-and-idempotence rule from Unit 2, now between two machines.

Retries make success likely but never certain. If every retry’s acknowledgement is lost, the requester gives up and goes to FAULT while the door is in fact OPEN: the two machines disagree. What keeps that from becoming a failure is the door’s own timeout: OPEN falls back to CLOSED after 5 seconds without a renewal, whatever the requester believes.

  • Each side needs a safe default that does not depend on the other: the door closes by itself; the robot’s motor stops by itself (the deadman of Unit 2).
  • Disagreement is bounded, not eliminated. The honest design question is “for how long can the two views differ, and what is the worst thing that can happen in that time?”.
  • Report the failure. FAULT is a state with a name, published like any other, so that a person or another agent can see it and reset it.

Warm Up

Exercise 1: Is It an Agent?

(a) Barely: it senses and tells, but decides nothing and acts on nothing. (b) Yes: it runs the whole cycle. (c) No: it only displays; it has no decision or output of its own. (d) Yes, and a richer one than (b): it senses (range, pan), decides (validates and arbitrates commands), acts (servo, motor), and tells (pose, state, acks).

Exercise 2: Pick an Organisation

(a) Centralised: small and simple, and one coordinator is easy to test. (b) Hierarchy: a controller per floor or per wing, so one failure affects a branch, and the top level sees summaries. (c) Peers: no single point of failure, with explicit agreement rules; the price is that the design must tolerate stale information about the others.

Intermediate

Exercise 3: Wrong Subscription

The sensor publishes tele; the coordinator sees it and publishes cmd/led in its own subtree; the actuator, listening elsewhere, receives nothing and its LED never changes. The broker shows no error, and the coordinator sees no acknowledgement. Find it by looking at the traffic (mosquitto_sub -v -t "lab/#" shows the command was published), then at the actuator’s subscriptions. The defence is the pattern of Unit 2: the actuator publishes the filters it listens to, and the coordinator retries and reports “no answer” after a timeout.

Advanced

Exercise 4: Write a Light Agent
lightagent.py MicroPython
from agent import Agent class LightAgent(Agent): def __init__(self, hub, read_light, led): super().__init__("light", hub, period_ms=100) self.read_light, self.led = read_light, led self.state = "ok" self.sent = None def sense(self): return self.read_light() def decide(self, level): if level < 15000: self.state = "dark" elif level > 17000: self.state = "ok" return self.state def act(self, state): self.led.value(1 if state == "dark" else 0) def tell(self, level, state): if state != self.sent: self.hub.publish("stat/light", {"state": state, "level": level}, retain=True) self.sent = state

The band between 15,000 and 17,000 is the same device as Sentry: remembered state turns a threshold into a band, so a reading that wobbles around one value cannot make the output flicker.

Paper Practice: Answers

Recall

P1. What Is an Agent

A program with its own sensors, outputs and decision-making, which acts on its own view of the world and tells others what it saw and did. Sense, decide, act, tell (in SAM terms: Perceptor, Decider with Memory, Actuator, and the Actuator's network voice).

P2. Three Organisations

Centralised: the coordinator is a single point of failure. Hierarchical: a failure takes down a branch; still has bosses. Peer: no single point of failure, but nobody sees the whole picture, so agreement must be built in.

P3. Shared Bus

It writes only to its own subtree lab/<user>/# and may read all of lab/#. A misbehaving agent can damage only its own corner.

P4. Three Answers

The last known state, or UNKNOWN if never heard, or UNKNOWN if not heard for longer than stale_ms. Planning on a stale "closed" is as wrong as never having heard; treating both as unknown is safer.

P5. Retained State

So a late joiner learns the current state at once. It does not say whether the publisher is still alive: it is as old as the last change.

P6. Bounded Disagreement

"For how long can the two views differ, and what is the worst thing that can happen in that time?" Disagreement is bounded, not eliminated.

Apply

P7. Count the Messages

Three: near false at start, near true at 15 cm, near false at 35 cm (25 is inside the band, so no change).

P8. Who Listens

Carl's publish succeeds and reports nothing wrong. Dana never receives the command, and nothing reports an error either. Sending and receiving are separate acts joined only by a subscription.

P9. Trace a Table

request: ASK1. timeout: ASK2. timeout: ASK3. ack: OPEN.

Analyze and Design

P10. Incomplete Picture

Agents share no memory, only messages that take time, can be lost and can arrive twice. Habits: keep the age of everything you know about a peer (and treat stale as unknown); give each agent a safe default that does not depend on hearing from the others.

P11. Safe Defaults

Door: close by itself after a time without renewal. Requester: after giving up, treat the door as unknown (or closed), send close, report FAULT, and not proceed as if it were open.

P12. Design the Timeout

Slow but successful exchanges are retried unnecessarily, adding duplicate traffic (and, without idempotence, duplicate actions). Choose the timeout from the measured high percentile of the round trip (say the p99 plus margin, around 300 to 500 ms).
