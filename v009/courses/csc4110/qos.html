TCP already delivers bytes reliably while a connection is up. QoS, "quality of service", is about something different: what MQTT promises about a message when the connection might drop at the wrong moment. It is a small dial with three settings, and picking the right one is a matter of asking what a lost or repeated message would cost.

Part 1. Three Levels

  • QoS 0, at most once. Send it and forget it. If the connection fails at that instant, the message is lost.
  • QoS 1, at least once. The receiver acknowledges with PUBACK. The sender keeps the message until it is acknowledged and resends it if not, so it arrives, but possibly more than once.
  • QoS 2, exactly once. A four-step handshake guarantees a single delivery. It costs the most packets, and umqtt.simple does not implement it.
The three delivery levels as message exchanges. Each step up adds acknowledgements: QoS 1 adds one packet, QoS 2 adds three. umqtt.simple can publish at QoS 0 and 1.
main.py MicroPython
client.publish(b"lab/pico01/stat/led", b"on", retain=True, qos=1) # waits for the broker's PUBACK client.subscribe(b"lab/pico01/cmd/#", qos=1)

Note that a QoS 1 publish() in this library blocks until the acknowledgement arrives. That is a hidden pause in your loop, and it can last a long time if the network is failing.

Part 2. What Happens When Something Is Lost

The difference between the levels only shows when a packet is lost. At QoS 0 the sender never finds out. At QoS 1 the missing acknowledgement tells the sender to try again, marked as a duplicate:

When something is lost. At QoS 0 a lost PUBLISH is gone for good. At QoS 1 the sender keeps the message until it is acknowledged and sends it again, which can deliver it twice.

This is the price of "at least once". If the PUBLISH did arrive and only the acknowledgement was lost, the receiver now gets the same message twice. Anything that responds to QoS 1 messages must therefore be safe to run twice: set the fan to "on", do not toggle it; record a reading by sequence number rather than adding it again.

Part 3. Two Levels in One Delivery

The publisher and each subscriber choose a level independently, and the broker delivers at the lower of the two. A QoS 1 publish reaching a subscriber that asked for QoS 0 arrives at QoS 0. To get a QoS 1 guarantee end to end, both sides must ask for it.

The level a subscriber actually receives is the lower of the publisher's level and its own subscription level. A QoS 1 publish delivered to a QoS 0 subscriber arrives at QoS 0.

Part 4. Choosing

What reliability costs. Each step up adds packets and waiting. For a reading that is replaced a second later, QoS 0 is usually the right choice.
A starting point for choosing. Match the level to what a lost or repeated message would cost.

A good default for this course: telemetry at QoS 0, commands and state at QoS 1 with idempotent handlers. Raising everything to QoS 1 "to be safe" makes each publish wait for the broker, which slows a small device and amplifies every network problem.

Exercises

Practice problems in three tiers. Do each on paper or on your own board first, and only then open its solution below. Many problems have more than one correct answer; if yours behaves the same way, it is right even if it looks different.

Warm Up

Exercise 1: Delivered QoS. A message is published at QoS 1 to a topic where subscriber A asked for QoS 0, subscriber B for QoS 1, and subscriber C for QoS 2. At what QoS does each receive it?

Exercise 2: Count the Packets. A sensor publishes once a second for an hour. How many packets does the Pico send plus receive for the publish exchange alone at QoS 0, and at QoS 1?

Intermediate

Exercise 3: Make a Command Safe to Repeat. This handler toggles an LED on each toggle command. Explain the problem at QoS 1 and rewrite it so a repeated command has no extra effect.

Advanced

Exercise 4: Drop Duplicates by Id. Some actions cannot be made idempotent (for example, dispensing one dose). Give each command an id in the payload, and write a handler that ignores an id it has recently seen, remembering only the last 16 so memory stays bounded.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Delivered QoS

Delivered QoS is the minimum of the two: A gets 0, B gets 1, C gets 1 (the publisher only used QoS 1, so a QoS 2 subscription cannot raise it).

Exercise 2: Count the Packets

At QoS 0: 1 packet per message, 3600 per hour. At QoS 1: PUBLISH plus PUBACK is 2 per message, 7200 per hour. The extra packets also keep the radio busy longer, which matters on battery.

Intermediate

Exercise 3: Make a Command Safe to Repeat
main.py MicroPython
# Unsafe: a duplicate delivery flips it back def on_message(topic, msg): led.toggle() # Safe: the command carries the wanted state, so repeating it changes nothing def on_message(topic, msg): if msg == b"on": led.value(1) elif msg == b"off": led.value(0)

At QoS 1 a duplicate is normal. A command that means "make it so" is idempotent; a command that means "change it" is not.

Advanced

Exercise 4: Drop Duplicates by Id
main.py MicroPython
import json seen = [] def is_new(cmd_id): if cmd_id in seen: return False seen.append(cmd_id) if len(seen) > 16: seen.pop(0) # forget the oldest return True def on_message(topic, msg): cmd = json.loads(msg) # {"id": 41, "do": "dose"} if is_new(cmd["id"]): dispense()

The list is capped because RAM is small. Choose its length to be longer than any plausible resend window, but not unbounded.
