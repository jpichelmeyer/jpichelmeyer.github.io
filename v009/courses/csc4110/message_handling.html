This lesson covers what happens to a message between the network and the motor. You keep the callback minimal, bound the queue and the work per pass, give commands priority over telemetry and keep only the latest of each telemetry topic, and use uasyncio for jobs that wait.

Messages arrive when the network chooses, not when your loop is ready. If the node handles each one the instant it arrives, a burst can starve the control loop; if it handles them too slowly, the queue grows until memory runs out; if it drops the wrong ones, a stop command disappears behind a hundred pieces of telemetry. This lesson is about the discipline between the socket and the actuator: do almost nothing in the callback, put arrivals in a small bounded queue, handle a limited number per pass, decide which messages matter most, and, when one loop gets crowded, let uasyncio run several loops side by side.

Part 1. Catch, Do Not Think

umqtt calls your callback from inside check_msg(), in the middle of the library’s own receive code. Everything slow you do there (parsing JSON, printing, publishing, driving a motor) delays the next receive and can break the connection. The rule is to catch the message and return.

callback.py MicroPython
# The rule for a callback: catch, do not think. inbox = [] def on_message(topic, payload): # called from inside check_msg() if len(inbox) < 20: # a bound: memory is small inbox.append((topic, payload)) # no parsing, no printing, no publishing here def pump(handle, budget=5): n = 0 while inbox and n < budget: # a bound: the loop must come round topic, payload = inbox.pop(0) handle(topic, payload) n += 1 return n

Both bounds in that code matter. The queue limit protects memory: the Pico has roughly 200 kB of it, and an unbounded list fed by a fast publisher will crash the node. The budget protects the control loop: the node handles at most five messages per pass and then goes back to its real job. (Hub from the topics lesson is built this way: its callback only appends to inbox, and poll(budget) runs the handlers.)

Between the network and the actuator: the callback is quick, the queue is bounded, the pump limits the work per pass, and only the handler does real work.

Part 2. A Stop Behind a Hundred Readings

A bounded first-in-first-out queue has a problem: when it is full, something has to go. Dropping the newest message (as on_message above does) means that a burst of telemetry fills the queue, and the stop command, which arrives last, is thrown away. Not dropping anything is no better, because the stop waits behind everything that came before it. Measured on the test fixture, where a burst of 200 telemetry messages on four topics was followed by cmd/stop, handling five messages per 20 ms pass at 5 ms each:

Three ways to queue the same burst. Only the policy that knows what the messages mean handles the stop in time.

The fix is to give messages different treatment by kind. Commands go into their own small queue and are handled first; they are rare, and each one matters. Telemetry from others is only worth its newest value, so keep one slot per topic and overwrite: an old reading has no value once a newer one has arrived.

inbox.py MicroPython
# inbox.py -- commands first, newest telemetry only class Inbox: def __init__(self, cmd_max=8, other_max=16): self.cmds = [] # (topic, payload): never dropped silently, small self.latest = {} # topic -> payload: only the newest of each topic is kept self.order = [] # arrival order of the topics in `latest` self.cmd_max = cmd_max self.other_max = other_max self.dropped = 0 def put(self, topic, payload): if b"/cmd/" in topic: if len(self.cmds) >= self.cmd_max: self.cmds.pop(0) self.dropped += 1 self.cmds.append((topic, payload)) return if topic not in self.latest: if len(self.order) >= self.other_max: old = self.order.pop(0) del self.latest[old] self.dropped += 1 self.order.append(topic) elif len(self.order) and topic in self.latest: self.dropped += 1 # an older message of this topic was replaced self.latest[topic] = payload def get(self): if self.cmds: return self.cmds.pop(0) if self.order: topic = self.order.pop(0) return topic, self.latest.pop(topic) return None

With this queue the burst of 200 telemetry messages collapses to four slots (196 replaced, counted in dropped), and the stop is the first thing handled, 5 ms after arrival. A flood of commands does overflow: twelve cmd/pan messages into a queue of eight keep the newest eight (the oldest four are dropped and counted), which is right for a pan command that says where to point now.

  • Count every drop. dropped is a number you can publish. Silent loss cannot be diagnosed; a counter that climbs says that a node is being overrun.
  • Decide per kind. Commands: small queue, newest wins, handled first. State and telemetry: latest per topic. A log that must be complete should not use this queue at all (see the data logging lesson).
  • Do not coalesce what is a sequence. If every message matters in order (a program of waypoints, say), it needs a bigger, ordered queue and a flow-control scheme, not this one.

Part 3. Several Loops at Once

So far one while True loop does everything in turn: poll the network, run the control step, send a report. That works until a job needs to wait (sleep 200 ms between reports, wait for a servo to settle) without freezing the rest. MicroPython includes uasyncio, a small cooperative scheduler: each job is an async def function that runs until it awaits, at which point the others get a turn.

tasks.py MicroPython
# tasks.py -- three jobs that each look like a loop of their own import uasyncio as asyncio import time async def control(robot): while True: robot.tick(time.ticks_ms()) await asyncio.sleep_ms(20) # 50 Hz; hands the CPU to the others async def network(hub, inbox): while True: hub.poll(budget=5) await asyncio.sleep_ms(10) async def report(hub, read): while True: hub.send("tele/pose", read()) await asyncio.sleep_ms(200) # 5 Hz async def main(robot, hub, inbox, read): asyncio.create_task(control(robot)) asyncio.create_task(network(hub, inbox)) asyncio.create_task(report(hub, read)) while True: await asyncio.sleep(1) # the main task has nothing else to do # asyncio.run(main(robot, hub, inbox, read))
Three tasks sharing one CPU. Each runs briefly, then waits; no task has to know about the others, but none may block.

Run on a desktop interpreter with the same code, the three tasks over two seconds produced 98 control ticks, 195 polls and 10 reports: close to the 50, 100 and 5 per second asked for, with only a few percent of timing slack. The approach has one rule that cannot be bent: a task must never block. A time.sleep(1) inside a task stops all of them for a second. Use await asyncio.sleep_ms(...) instead, and keep any blocking call (a WiFi connect, a long flash write) out of the tasks, or short enough for the watchdog.

  • Use asyncio when jobs wait, such as periodic reports, timeouts, and a state machine with delays. Do not use it to hide a design problem: if a handler is slow, it is slow in any scheduler.
  • Share state carefully. Tasks switch only at an await, so a block of code without an await is never interrupted by another task. That makes plain variables safe to share, much safer than interrupt handlers.
  • Keep the safety path simple. The deadman timer (motor off after 2 s without a command) belongs in the control task, which runs whether the network works or not.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Why Not Print?

The callback runs inside check_msg(), so every print (slow over USB) delays the library from reading the socket and from sending its keepalive ping. Under load the delay exceeds the keepalive allowance and the broker drops the client. Move the print to the handler, after the queue, and count messages rather than printing every one.

Exercise 2: Pick the Policy

(a) small queue, newest wins, handled first. (b) latest per topic: an old position has no value. (c) ordered and complete, with a bigger queue, sequence numbers and acknowledgements. Dropping or reordering a waypoint changes the route.

Intermediate

Exercise 3: The Loop Count

A full pass is 5 × 5 + 15 = 40 ms, so 25 passes a second, and 5 × 25 = 125 messages per second at most. If 300 arrive each second, the queue fills and drops 175 per second; with the policy of Part 2 the drops fall on old telemetry, not on commands. The designer must also notice that the control loop now runs at 25 Hz, not 50 Hz: handling work eats control time, which is why the budget exists.

Advanced

Exercise 4: Starve It
test_inbox.py MicroPython
ib = Inbox() for i in range(12): ib.put(b"x/cmd/pan", str(i).encode()) for i in range(3): ib.put(b"x/tele/a", str(i).encode()) ib.put(b"x/tele/b", str(i).encode()) out = [] while True: m = ib.get() if m is None: break out.append(m) print(len(out), ib.dropped)

Eight commands come out first (pans 4 through 11; the four oldest were dropped), then one message each for a and b (the value 2, the newest). That is 10 messages out. dropped is 4 (commands) + 4 (older telemetry replaced: two per topic) = 8.
