Every sensor and actuator in the course ends at a pin on the Pico. You now have two skills: building and measuring circuits (Electronics Basics) and running MicroPython on the board (Thonny and MicroPython). This lesson joins them. It covers what is on the board and what a pin can and cannot do, how to wire an LED and a button to a pin safely, how to read the pin map, and how to turn a noisy mechanical button into a clean event in code.

SAM lens. Pins are where the agent meets the world. An input pin with a button is the simplest Perceptor (and debouncing is its first filter); an output pin with an LED is the simplest Actuator. Everything later in Unit 1 widens one of these two.

Part 1. What Is on the Board

The Pico W is a microcontroller board: one chip that holds a processor, memory, and a set of built-in hardware blocks for talking to the outside world, all on a board a few centimetres long. Unlike a laptop it has no operating system to speak of; it starts running your program the moment power arrives. Its chip is the RP2040, and a second small chip, the CYW43439, supplies WiFi.

What is on the Pico W. The RP2040 chip holds the processor, the RAM and the hardware blocks that talk to the world. Program storage (flash), the WiFi chip and the USB connector sit beside it on the board.

Your program lives in flash and runs from there; the RAM only holds what changes while it runs, and it is wiped each time power is lost. Three of those hardware blocks (the ADC, PWM and I2C) are the subject of the next four weeks. Each is a small circuit inside the chip that does one job for you, so your code only has to say what you want. The block you meet first is the one labelled GPIO: the pins you can wire to.

Part 2. A Pin Is a Switchable Voltage

A pin on the Pico is a switch for voltage: when you set it high it sits at 3.3 V, and when you set it low it sits at 0 V (ground). Current flows when there is a complete loop from a high point, through something, back to ground. That is the loop you built from the battery pack in the Electronics lesson, with the pin standing in for the + side of the pack and your program deciding when the loop is live. Ohm's law works exactly as before: V = I × R, and a resistor limits the current.

The Pico's pins can supply only a few milliamps, so they are for signals, not for power. An LED is the simplest case. It drops about 2 V across itself when lit (red; other colours drop a little more) and has almost no resistance of its own, so it must always have a resistor in series or it will draw as much as the pin can give and be damaged, along with the pin.

The standard LED circuit: pin, resistor, LED, ground. The resistor takes the voltage the LED does not, and Ohm’s law gives the current. 220 Ω to 330 Ω gives a clearly visible LED at a few milliamps, safe for the pin.

The order of resistor and LED does not matter electrically; only that they are in the same loop. The LED does care about direction: its longer leg (the anode) goes toward the positive side. If an LED will not light, turn it around.

Compare this with the pack. From 4.8 V the red LED with 330 Ω carried 8.5 mA; from a 3.3 V pin with 220 Ω it carries 5.9 mA, so it is a little dimmer, and a blue or white LED (about 3 V) hardly lights at all. Two rules keep the pack and the Pico from hurting each other. Never connect the pack to a GPIO pin: the pins are 3.3 V logic, and anything much above that can damage them. And whenever the pack and the Pico are both in a circuit (the servo in Lab 4, for example), join the pack's − to a Pico GND pin. Voltages only mean something relative to a shared 0 V, so two supplies with no common ground cannot agree on what a signal is.

Part 3. The Pico on the Breadboard

The Pico plugs across the centre channel of the breadboard, one row of pins on each side, so that no two of its pins share a strip. Each pin then has free holes in its own column, and a part or jumper placed in that column is connected to that pin. This is the same strip rule you used for the LED circuit, applied to the pins of a module. Lab 1 shows the exact layout used for the robot. The breadboard's power rails carry 3V3 and GND from the Pico's own pins, and the habit from the Electronics lesson still applies: ground first.

Part 4. Which Pin Is Which

The course pin map on a Pico W (top view, USB at the top). Blue are GPIO pins and green are the three analog inputs. The labels beside them are the pins this course uses by default, chosen so that nothing collides: the I2C pair, the analog sensors and the individual signals, with a few pins left spare. GP23, GP24, GP25 and GP29 are used internally by the WiFi chip and are not on the header.

Using the same pins every week saves wiring time and makes your code easy to compare with a classmate’s. Nothing forces these choices (most GPIO can do most jobs), but a few are fixed: only GP26, GP27 and GP28 can read analog voltages, and I2C has a few allowed pin pairs.

Part 5. Digital Output: an LED on a Pin

Wire a red LED to GP8 (physical pin 11 on the map above): GP8, then a 220 Ω resistor, then the LED's long leg, then the LED's short leg to any GND pin. This is the circuit of the diagram in Part 2, built on the board. Then drive it from the REPL, one line at a time:

REPL session MicroPython
>>> from machine import Pin >>> led = Pin(8, Pin.OUT) >>> led.on() # GP8 goes to 3.3 V: the LED lights >>> led.off() # GP8 goes to 0 V >>> led.value(1) # the same as led.on() >>> led.toggle() # flip it

The number in Pin(8) is the GP number, the label on the map, and not the physical pin number. GP8 is physical pin 11. This catches everyone once. Compare it with Pin("LED") from the last lesson: the name refers to the LED on the board, and the number refers to a pin on the header, but the code that follows is identical.

Now use the multimeter, which is the quickest way to learn whether a fault is in the wiring or in the code. With the black lead on a GND pin, touch the red lead to GP8: it should read about 3.3 V when led.on() is in effect and about 0 V after led.off(). Then measure across the resistor while the LED is lit; with 220 Ω you expect about 1.3 V (5.9 mA × 220 Ω). If the pin reads right but the LED is dark, the fault is in the wiring. If the pin does not change, it is in the code.

Part 6. Reading a Button

A button connects two points when pressed. Wired between a pin and ground, it needs one more thing: when the button is not pressed the pin is connected to nothing, which is a floating input and reads random noise. A pull-up resistor fixes that by connecting the pin to 3.3 V through a high resistance, so it reads 1 by default; the button, when pressed, connects the pin to ground and wins. The Pico has these resistors built in, switched on with a single argument.

A button read with the internal pull-up. The logic is inverted: pressed reads 0 and released reads 1. Engineers call this active low. Wire the button between the pin and GND, and ask for Pin.PULL_UP in the code.
gpio.py MicroPython
from machine import Pin from time import sleep_ms led = Pin(8, Pin.OUT) # output: we set it button = Pin(6, Pin.IN, Pin.PULL_UP) # input: we read it, with the pull-up on while True: pressed = button.value() == 0 # active low: 0 means pressed led.value(pressed) # LED follows the button sleep_ms(10)

Part 7. Bounce

A mechanical button does not close cleanly: for a few milliseconds the contacts chatter, so one press can read as several. If you captured a button press on the oscilloscope in the Electronics lesson, this is the trace you saw. If your program counts presses it will count too many. The fix is to ignore a change until the reading has been steady for a short time (20 to 50 ms) before believing it:

One press as the Pico sees it. The contacts bounce for a few milliseconds before settling, so the program waits until the value has stayed the same for a short debounce time before accepting it as a real press.
button.py MicroPython
from machine import Pin from time import ticks_ms, ticks_diff class Button: """Debounced, active-low button. pressed() is True once per press.""" def __init__(self, pin, debounce_ms=30): self.pin = Pin(pin, Pin.IN, Pin.PULL_UP) self.debounce_ms = debounce_ms self.raw = self.stable = self.pin.value() self.changed_at = ticks_ms() def pressed(self): raw = self.pin.value() now = ticks_ms() if raw != self.raw: # it moved: restart the timer self.raw = raw self.changed_at = now elif raw != self.stable and ticks_diff(now, self.changed_at) >= self.debounce_ms: self.stable = raw # steady long enough: believe it return raw == 0 # report only the press, not the release return False a = Button(6) count = 0 while True: if a.pressed(): count += 1 print("presses:", count)

This is deliberately non-blocking: pressed() returns at once, and the main loop stays free to do other work such as sampling a sensor. A version that called sleep_ms(30) inside would freeze the whole program for each press. Keeping loops moving is a habit that matters more and more through the term.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Pick a Resistor

330 Ω: (3.3 − 2.1) / 330 = 1.2 / 330 ≈ 3.6 mA. 100 Ω: 1.2 / 100 = 12 mA, more than a pin should give. Use 330 Ω (or anything above about 220 Ω). The LED is dimmer at 3.6 mA but still plainly visible.

Exercise 2: What Does It Read?

Released: 1. Pressed: 0. The expression button.value() == 0 (or not button.value()) is True while it is held.

Exercise 3: GP or Pin?

The GP number: Pin(8). Physical pin 11 is GP8. Pin(11) would talk to GP11, which on the course map is the ultrasonic sensor's echo input, so the LED would stay dark and the sensor wire would be disturbed.

Intermediate

Exercise 4: A Voltage Divider

A divider gives V_out = V_in × R2 / (R1 + R2) = 5 × 2000 / 3000 = 3.33 V. A 3.3 V pin should not see 5 V, so this brings a 5 V signal down to a level the Pico can accept. You will use exactly this on the ultrasonic sensor’s echo wire.

divider.py MicroPython
def divider(vin, r1, r2): return vin * r2 / (r1 + r2) print(round(divider(5, 1000, 2000), 2)) # 3.33 print(round(divider(3.3, 10000, 10000), 2)) # 1.65

Advanced

Exercise 5: Count Presses

Replace the pin and clock with stand-ins you control, then feed in a bounce pattern: released, then 1 and 0 flickering for 8 ms, then 0 for 100 ms, then released.

test_button.py MicroPython
class FakePin: def __init__(self): self.v = 1 def value(self): return self.v clock = [0] fake = FakePin() b = Button.__new__(Button) # skip __init__ so no real pin is used b.pin, b.debounce_ms = fake, 30 b.raw = b.stable = 1 b.changed_at = 0 ticks_ms = lambda: clock[0] # replace the clock the class looks up presses = 0 timeline = [(0, 1), (10, 0), (12, 1), (14, 0), (16, 1), (18, 0)] + [(t, 0) for t in range(20, 140, 5)] + [(140, 1), (200, 1)] for t, v in timeline: clock[0], fake.v = t, v if b.pressed(): presses += 1 print(presses) # 1

Eight milliseconds of chatter and a long steady press give exactly one count. Try shortening the steady part to under 30 ms and you get none, which is the debounce time doing its job.

Paper Practice: Answers

Recall

P1. Two Chips

The RP2040 is the microcontroller: processor, RAM and hardware blocks (ADC, PWM, I2C, SPI). The CYW43439 is the separate WiFi chip.

P2. Floating Input

An input connected to nothing, which reads random noise. The pull-up connects the pin to 3.3 V through a high resistance, so it reads 1 until the button connects it to ground.

P3. Analog Pins

GP26, GP27 and GP3. GP23, GP24, GP25 and GP29 are used by the WiFi chip.

P4. Pack and Pin

Voltages are only meaningful relative to a shared reference, so the pack and the Pico need a common 0 V for a signal from one to mean anything to the other. The pack's + is about 4.8 V, well above the 3.3 V logic of a GPIO pin, and a higher voltage than the pin is rated for can damage it.

Apply

P5. LED Current

(3.3 − 2.0) / 220 = 5.9 mA; (3.3 − 2.0) / 330 = 3.9 mA.

P6. Choose a Resistor

R = (3.3 − 2.2) / 0.003 = 367 Ω. 330 Ω gives 3.3 mA and 390 Ω gives 2.8 mA; either is fine, 390 Ω is the conservative choice.

P7. Debounce Trace

t=0: raw changes, timer restarts at 0. t=10: changes back, timer restarts at 10. t=20: changes again, timer restarts at 20. t=30 and t=40: steady but only 10 and 20 ms. t=50: steady for 30 ms and different from stable, so it returns True, exactly once, at t=50.

P8. Counting Bounces

(a) Falling changes at samples 3, 5 and 8: three presses. (b) One: the reading is only steady at 0 for three or more samples from the eighth sample onward.

Analyze and Design

P9. Inverted Logic Bug

The input is active low: released reads 1, pressed reads 0. The condition is true when released. Use if button.value() == 0: (or if not button.value():).

P10. Wrong Pull

It reads 1 in both cases: the pull-up and the button both connect it to 3.3 V. Fix: wire the button to GND instead, or keep it to 3.3 V and use Pin.PULL_DOWN (then pressed reads 1).

P11. Dead LED Checklist

(1) Polarity: turn the LED around. (2) The circuit loop: resistor and LED share a strip, and the LED returns to a ground that is connected to the Pico's GND. (3) The right pin: the GP number in code matches the physical pin (check the pin map). (4) The pin is an output and set high: test Pin(n, Pin.OUT).on() in the REPL. Also: a resistor accidentally placed with both legs in one strip (shorted out) or a much too large value.

P12. Safe Mode
listing MicroPython
from machine import Pin import sys if Pin(6, Pin.IN, Pin.PULL_UP).value() == 0: # held at boot print('safe mode: robot not started') sys.exit() # back to the REPL # ... the robot program follows ...

Any version that checks the button before the robot starts and then stops cleanly is correct.
