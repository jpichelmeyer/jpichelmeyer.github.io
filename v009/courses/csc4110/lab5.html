Step 4. The Node

Copy formats.py from the Serialization lesson (reproduced below) and the files from earlier labs (mpu6050.py, every.py, net.py) to the Pico, and run main.py. It uses the helper net only to join WiFi and connect, then publishes on the raw client, because net.publish can send only JSON.

formats.py MicroPython
import json import struct # One sample: the envelope (version, sequence number, time) and three accelerations in g. def to_json(seq, t, ax, ay, az): return json.dumps({"v": 1, "seq": seq, "t": t, "ax": round(ax, 2), "ay": round(ay, 2), "az": round(az, 2)}).encode() def to_csv(seq, t, ax, ay, az): return ("1,%d,%d,%.2f,%.2f,%.2f" % (seq, t, ax, ay, az)).encode() # Binary: acceleration as whole milli-g in a signed 16-bit integer (resolution 0.001 g). REC = "<BHIhhh" # version, seq, t, ax, ay, az; little-endian, no padding def to_bin(seq, t, ax, ay, az): return struct.pack(REC, 1, seq & 0xFFFF, t & 0xFFFFFFFF, round(ax * 1000), round(ay * 1000), round(az * 1000)) def from_bin(buf): if len(buf) != struct.calcsize(REC): raise ValueError("wrong length") v, seq, t, ax, ay, az = struct.unpack(REC, buf) if v != 1: raise ValueError("unknown version") return {"seq": seq, "t": t, "ax": ax / 1000, "ay": ay / 1000, "az": az / 1000}
main.py MicroPython
# main.py for Lab 5: one sensor, three encodings, published to your own broker import net from machine import I2C, Pin from time import ticks_ms from mpu6050 import MPU6050 # from the I2C lesson from every import Every # from the Pulses lesson from formats import to_json, to_csv, to_bin # from the Serialization lesson i2c = I2C(0, sda=Pin(4), scl=Pin(5), freq=400_000) imu = MPU6050(i2c) imu.calibrate() # keep the board still for this second link = net.link() link.keepalive = 30 # set before the first connect: the broker now watches this client link.connect() # config.py must name YOUR broker's address for this lab sample = Every(200) # 5 samples per second seq = 0 def send(name, payload): """Publish raw bytes under lab/<you>/tele/<name>. Returns True if it left the board.""" if link.client is None: link.connect() if link.client is None: return False try: link.client.publish((link.root + "tele/" + name).encode(), payload) return True except OSError: link._drop() # forget the dead connection; the next call reconnects return False while True: if sample.due(): (ax, ay, az), _, _ = imu.read() seq += 1 t = ticks_ms() send("imu_json", to_json(seq, t, ax, ay, az)) send("imu_csv", to_csv(seq, t, ax, ay, az)) send("imu_bin", to_bin(seq, t, ax, ay, az))

Look at the line link.keepalive = 30. It changes the helper’s setting before the first connect, so the client now makes the keepalive promise. Because the node publishes five times a second the promise is kept automatically. And notice what send does when the network fails: it reports False and drops the dead connection; the next call reconnects. The node never raises an error and never blocks for long. You will meet the proper version of this idea, with back-off and a queue, in Week 8.

# size_report.py: run on the laptop. # mosquitto_sub -h localhost -u USER -P PASS -t "lab/+/tele/imu_#" -F "%t %x" | python3 size_report.py import sys, struct from collections import defaultdict REC = "<BHIhhh" count = defaultdict(int) nbytes = defaultdict(int) def handle(line): topic, _, hexpayload = line.strip().partition(" ") payload = bytes.fromhex(hexpayload) name = topic.rsplit("/", 1)[-1] count[name] += 1 nbytes[name] += len(payload) if name == "imu_bin" and len(payload) == struct.calcsize(REC): v, seq, t, ax, ay, az = struct.unpack(REC, payload) return (seq, t, ax / 1000, ay / 1000, az / 1000) def report(): for name in sorted(count): print("%-9s %5d messages %6.1f bytes each" % (name, count[name], nbytes[name] / count[name])) if __name__ == "__main__": for i, line in enumerate(sys.stdin): handle(line) if (i + 1) % 30 == 0: report()

Step 5. The Round Trip

Finally, measure what a message really costs in time. This program subscribes to a topic and publishes to the same topic, so each message comes back to the sender, and one clock measures the whole journey, with no need to synchronize two boards. Run it at your desk and again at the far corner.

rtt.py MicroPython
# rtt.py: how long does a message take to go to the broker and come back? import net from time import ticks_ms, ticks_diff, sleep_ms link = net.link() link.keepalive = 30 link.connect() topic = (link.root + "echo").encode() times = [] def on_msg(t, m): times.append(ticks_diff(ticks_ms(), int(m))) # now minus the time we put in the message link.client.set_callback(on_msg) link.client.subscribe(topic) # we hear our own messages: one clock, no sync needed for i in range(20): link.client.publish(topic, str(ticks_ms()).encode()) t0 = ticks_ms() while len(times) <= i and ticks_diff(ticks_ms(), t0) < 1000: link.client.check_msg() sleep_ms(100) times.sort() if times: print("n", len(times), " min", times[0], " median", times[len(times) // 2], " max", times[-1], "ms") else: print("no echoes: check the ACL and the topic")

The minimum shows the best the link can do; the maximum usually includes a lost packet that TCP had to resend (a retransmission timeout is far longer than a normal trip). The median is the number to quote. Keep these results: Lab 6’s command latency and Week 14’s latency budget start from them.

Warm Up

Exercise 1: Predict the Bandwidth

Per cycle: payload 68 + 26 + 13 = 107; headers 3 × 4 = 12; topics 24 + 23 + 23 = 70; total 189 bytes. At 5 cycles per second: 945 B/s, and 3 × 5 = 15 messages per second. That is fine for your own broker and 50 % over the class limit of 10 messages per second, which is why this node must not be run on the class hub as it stands.

Exercise 2: Reading the Table

Budget with a high percentile or the maximum you can tolerate, not the median: a command that is late once in twenty is still a command that was late. The median of 14 ms says the link is healthy most of the time; the 240 ms maximum, seventeen times the median, is a retransmission or a radio retry. A control loop must be designed to survive such outliers: it cannot assume every message takes 14 ms. Week 14 builds this into a latency budget.

Intermediate

Exercise 3: Silent Failure

The access list allows you to write only under lab/you/. The broker discards the publish without telling the publisher: for the client, publish() returned normally. Confirm by publishing to lab/you/x instead (it arrives), by running the broker with -v (it logs a denied publish at some verbosity levels, and your connection stays open), or by temporarily adding a write rule and watching the behavior change. A Pico program doing the same thing would see no exception, so a program that needs to know a message arrived has to ask the receiver for an acknowledgement, the pattern of Week 7.

Exercise 4: Do They Agree?
agree.py MicroPython
import json, struct def agree(json_line, csv_line, bin_bytes, tol=0.006): """Do the three encodings of one sample describe the same numbers?""" j = json.loads(json_line) c = csv_line.decode().split(",") v, seq, t, ax, ay, az = struct.unpack("<BHIhhh", bin_bytes) same_meta = (j["seq"], j["t"]) == (int(c[1]), int(c[2])) == (seq, t) a = (j["ax"], j["ay"], j["az"]) b = tuple(float(x) for x in c[3:6]) d = (ax / 1000, ay / 1000, az / 1000) close = all(abs(p - q) < tol and abs(p - r) < tol for p, q, r in zip(a, b, d)) return same_meta and close
test_agree.py MicroPython
j = to_json(17, 34120, 0.0198, -0.0101, 0.9801) c = to_csv(17, 34120, 0.0198, -0.0101, 0.9801) b = to_bin(17, 34120, 0.0198, -0.0101, 0.9801) print(agree(j, c, b)) # True print(agree(j, c, to_bin(17, 34120, 0.05, -0.0101, 0.9801))) # False: ax differs by 0.03 g

The tolerance is about one rounding step: JSON and CSV round to 0.01 g, so they can differ from the original by 0.005, and the binary is 0.001 resolution. Choosing the tolerance from the resolution of the encodings is the right way to compare floating values from different sources; testing for exact equality would fail every time.
