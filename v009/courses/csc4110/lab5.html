Step 3. The Node

Copy the files from earlier labs (mpu6050.py, every.py, net.py, and your two-broker config.py) to the Pico, and run this main.py. It publishes through net.publish, which adds the envelope, queues messages while the broker is unreachable, and never blocks for long.

main.py MicroPython
# main.py for Lab 5: IMU samples, five a second, as JSON to your own broker import net from machine import I2C, Pin from mpu6050 import MPU6050 # from the I2C lesson from every import Every # from the Pulses lesson i2c = I2C(0, sda=Pin(4), scl=Pin(5), freq=400_000) imu = MPU6050(i2c) imu.calibrate() # keep the board still for this second link = net.link() link.keepalive = 30 # set before the first connect: the broker now watches this client sample = Every(200) # 5 samples per second while True: if sample.due(): (ax, ay, az), _, _ = imu.read() net.publish("tele/imu", {"ax": round(ax, 2), "ay": round(ay, 2), "az": round(az, 2)})

Look at the line link.keepalive = 30. It changes the helper’s setting before the first connect, so the client now makes the keepalive promise. Because the node publishes five times a second, the promise is kept automatically.

On the laptop, pipe the messages into a small program that uses each message’s seq to count what arrived, what went missing and what came twice, exactly as in the Messages and JSON lesson:

seq_check.py Python
# seq_check.py: run on the laptop. # mosquitto_sub -h localhost -u you -P PASSWORD -v -t "lab/+/tele/imu" | python3 seq_check.py import sys, json prev = None n = lost = dup = restarts = nbytes = 0 for line in sys.stdin: topic, _, payload = line.strip().partition(" ") try: seq = json.loads(payload)["seq"] except (ValueError, KeyError, TypeError): continue # not a class message: skip it n += 1 nbytes += len(payload) if prev is not None: if seq > prev + 1: lost += seq - prev - 1 elif seq == prev: dup += 1 elif seq < prev: restarts += 1 # the Pico rebooted and started counting again prev = seq if n % 25 == 0: # a report every 5 s at 5 messages a second print("%d messages, %.0f bytes each, lost %d, duplicates %d, restarts %d" % (n, nbytes / n, lost, dup, restarts), flush=True)

Let it run for two minutes. Then stop the broker (Ctrl-C in its terminal) for about ten seconds and start it again, and watch the lost count. Finally press the Pico’s reset button and watch the restart count. Before each of these, write down your prediction.

Step 4. The Round Trip

Finally, measure what a message really costs in time. This program subscribes to a topic and publishes to the same topic, so each message comes back to the sender, and one clock measures the whole journey, with no need to synchronize two boards. Run it at your desk and again across the room.

rtt.py MicroPython
# rtt.py: how long does a message take to go to the broker and come back? import net from time import ticks_ms, ticks_diff, sleep_ms link = net.link() link.keepalive = 30 link.connect() topic = (link.root + "echo").encode() times = [] def on_msg(t, m): times.append(ticks_diff(ticks_ms(), int(m))) # now minus the time we put in the message link.client.set_callback(on_msg) link.client.subscribe(topic) # we hear our own messages: one clock, no sync needed for i in range(20): link.client.publish(topic, str(ticks_ms()).encode()) t0 = ticks_ms() while len(times) <= i and ticks_diff(ticks_ms(), t0) < 1000: link.client.check_msg() sleep_ms(100) times.sort() if times: print("n", len(times), " min", times[0], " median", times[len(times) // 2], " max", times[-1], "ms") else: print("no echoes: check the ACL and the topic")

The minimum shows the best the link can do; the maximum usually includes a lost packet that TCP had to resend (a retransmission timeout is far longer than a normal trip). The median is the number to quote. Keep these results: Lab 6’s command latency and Week 14’s latency budget start from them.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Predict the Bandwidth

Per message: 68 + 19 + 4 = 91 bytes. At 5 messages per second: 455 B/s and 5 messages per second, half the class limit. The real payload varies by a byte or two as the readings change sign or gain a digit.

Exercise 2: Reading the Table

Budget with a high percentile or the maximum you can tolerate, not the median: a command that is late once in twenty is still a command that was late. The median of 14 ms says the link is healthy most of the time; the 240 ms maximum, seventeen times the median, is a retransmission or a radio retry. A control loop must be designed to survive such outliers: it cannot assume every message takes 14 ms. Week 14 builds this into a latency budget.

Intermediate

Exercise 3: Silent Failure

The access list allows you to write only under lab/you/. The broker discards the publish without telling the publisher: for the client, publish() returned normally. Confirm by publishing to lab/you/x instead (it arrives), by running the broker with -v (it logs a denied publish at some verbosity levels, and your connection stays open), or by temporarily adding a write rule and watching the behavior change. A Pico program doing the same thing would see no exception, so a program that needs to know a message arrived has to ask the receiver for an acknowledgement, the pattern of Week 7.

Advanced

Exercise 4: Predict the Outage

When the broker stops, the next publish fails and the node tries to reconnect at once; that fails, so it waits 15 s before trying again, even though the broker came back after 10 s. In those 15 s the node queues 5 × 15 = 75 messages, but the queue keeps only the newest 40, so about 35 are lost (the oldest ones). When it reconnects it sends up to 5 queued messages per call while adding one new one, so the backlog clears in about two seconds. The retry wait, not the outage, sets the loss: that trade-off between reconnecting quickly and not hammering a dead broker is the subject of Week 7.
