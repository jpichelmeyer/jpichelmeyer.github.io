Part 1. What a Telemetry Packet Should Contain

A bare value, 41230, sent over and over, loses something important the moment anyone looks at it later: when was this reading taken, and what does the number even mean without context? A well-formed telemetry packet typically carries at least:

  • the value itself (ideally, already filtered, per Week 2)
  • a unit or label, so 41230 doesn't get misread as, say, a temperature in Celsius
  • a timestamp or sequence number, so readings can be ordered and gaps noticed later
main.py MicroPython
import json from time import ticks_ms def make_packet(value, unit): return json.dumps({ "value": value, "unit": unit, "t_ms": ticks_ms(), # milliseconds since this Pico booted }).encode()

Note ticks_ms() gives milliseconds since the Pico last booted, not wall-clock time, the Pico has no battery-backed clock and doesn't know what time it actually is unless told, which is outside this unit's scope. For comparing readings against each other from the same device, boot-relative time is enough; it's worth knowing that limitation exists rather than assuming t_ms means something it doesn't.

Part 3. Streaming: Putting It in a Loop

"Streaming" just means repeating the whole pipeline on an interval, using last week's non-blocking pattern so the loop stays responsive rather than freezing on each publish:

main.py MicroPython
from machine import ADC, Pin from time import ticks_ms, ticks_diff import json sensor = ADC(Pin(26)) WINDOW_SIZE = 5 window = [] def filtered_read(): raw = sensor.read_u16() window.append(raw) if len(window) > WINDOW_SIZE: window.pop(0) return sum(window) / len(window) INTERVAL_MS = 500 last_publish = ticks_ms() while True: now = ticks_ms() if ticks_diff(now, last_publish) >= INTERVAL_MS: value = filtered_read() packet = json.dumps({"value": value, "unit": "raw_adc", "t_ms": now}).encode() client.publish(b"lab/pico01/light", packet) last_publish = now client.check_msg() # stay responsive to any incoming commands, every loop pass

Notice filtered_read() is still called on every publish, not every loop iteration, the filter's window keeps accumulating samples only when there's actually a new ADC read, every INTERVAL_MS. A separate, faster timer could sample the ADC more often than it publishes, feeding the window more data without publishing every single one, worth considering as a refinement, not required for this unit.

Traffic grows in direct proportion to the sampling rate. Each tenfold increase multiplies bytes sent, power used and broker load by ten.

Part 4. Choosing INTERVAL_MS

This is Week 2's sampling-rate question again, now at the level of what gets published rather than what gets sampled. A slow-changing light level doesn't need updates every 50ms, a one-reading-per-second or even slower interval is often completely sufficient and keeps network and broker load low; publishing far faster than a signal actually changes wastes bandwidth without adding real information. Pick an interval by asking the same question Week 2 asked of sampling: how fast does this specific signal actually change?

Warm Up

Exercise 1: Choose an Interval

Every 10 to 60 seconds captures the change with room to spare. At 100 ms you would send 100× to 600× more data that says the same thing, wasting battery, bandwidth and broker time without adding information.

Exercise 2: Design a Packet

For example: {"seq": 17, "t_ms": 123456, "temp_c": 22.4, "light": 41230}. One packet for both readings keeps them tied to the same moment; the sequence number reveals lost messages.

Intermediate

Exercise 3: Add a Sequence Number
main.py MicroPython
import json from time import ticks_ms seq = 0 def make_packet(value, unit): global seq seq += 1 return json.dumps({"seq": seq, "t_ms": ticks_ms(), "value": value, "unit": unit}).encode()

The global keyword lets the function modify the module-level counter. Gaps in seq at the receiver mean lost messages.

Advanced

Exercise 4: Summarize in Batches
main.py MicroPython
batch = [] def add_reading(x): batch.append(x) if len(batch) == 10: summary = {"mean": sum(batch) / 10, "min": min(batch), "max": max(batch)} client.publish(b"lab/pico01/summary", json.dumps(summary).encode()) batch.clear()

One message per second instead of ten, with the trade-off that a brief spike is now seen only as a changed max, not as its own message.
