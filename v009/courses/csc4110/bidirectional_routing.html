Telemetry flows one way: from devices to whoever is listening. Real systems also need to send instructions back. MQTT has no built-in request and reply, but with a good topic layout you get two-way communication through the same broker, with the same simplicity.

Part 1. Two Lanes

Give each direction its own topic. A command lane carries instructions down to the device; a state lane carries what the device reports back. Keeping them separate means a device never mistakes its own report for an instruction, and permissions can differ: a dashboard may publish to cmd but never to stat.

Two lanes between a dashboard and a Pico. Commands travel down on a cmd topic; the device reports what it actually did on a stat topic.

Part 2. Command and Confirmation

The golden rule: a command is a request, not a fact. Publishing "on" does not mean the LED is on; it means someone asked. The device acts, then publishes the state it actually has, and the dashboard displays that.

A complete command and confirmation. The dashboard asks, the device acts, and only then does the stat topic change, so the dashboard shows what is true rather than what was requested.
main.py MicroPython
led = Pin(15, Pin.OUT) def on_message(topic, msg): if topic == b"lab/pico01/cmd/led": led.value(1 if msg == b"on" else 0) state = b"on" if led.value() else b"off" client.publish(b"lab/pico01/stat/led", state, retain=True) client.set_callback(on_message) client.subscribe(b"lab/pico01/cmd/#")

The state is read back from the pin, not copied from the command, so if something went wrong the report shows the truth. It is published retain=True so a dashboard that starts later learns the current state immediately (retained messages are covered properly in the next lesson).

Part 3. Echo Loops

Because everything flows through one broker, a device can accidentally hear itself. If it subscribes to a filter that includes the topics it publishes to, and its handler publishes in response, each message triggers another, and the broker is flooded in seconds.

A feedback loop. A device that subscribes to a filter broad enough to include its own output receives its own message, and if it replies to that message the broker is soon flooded. Subscribe narrowly.

Part 4. Addressing Groups

Often one instruction should reach several devices. Rather than publishing the same command many times, devices also subscribe to a shared group topic:

Addressing one device or all of them. Each Pico subscribes to its own cmd subtree and to a shared "all" subtree, so one publish reaches everyone.

The handler should treat both subscriptions the same way, since a device can receive a command either individually or as part of the group. A device reports state on its own stat topic, never on the shared one, so the dashboard still sees every device separately.

Intermediate

Exercise 3: A Switch That Reports
main.py MicroPython
fan = Pin(16, Pin.OUT) def on_message(topic, msg): if topic != b"lab/pico01/cmd/fan" or msg not in (b"on", b"off"): return # ignore anything unexpected fan.value(1 if msg == b"on" else 0) client.publish(b"lab/pico01/stat/fan", b"on" if fan.value() else b"off", retain=True)

Ignoring unknown topics and payloads first means a typo cannot switch anything. The reply reads fan.value() rather than echoing msg.

Advanced

Exercise 4: Individual and Group
main.py MicroPython
DEV = b"pico01" CMD_TOPICS = (b"lab/" + DEV + b"/cmd/fan", b"lab/all/cmd/fan") client.subscribe(b"lab/" + DEV + b"/cmd/#") client.subscribe(b"lab/all/cmd/#") def on_message(topic, msg): if topic not in CMD_TOPICS or msg not in (b"on", b"off"): return fan.value(1 if msg == b"on" else 0) client.publish(b"lab/" + DEV + b"/stat/fan", b"on" if fan.value() else b"off", retain=True)

Both command topics go through identical handling, and the report always goes to the device’s own stat topic so the dashboard sees each device separately.
