Until now the broker was something running on the Pi that your Pico connected to. In this lesson you set it up yourself: install it, let your Picos reach it, give each user a password and a limited set of topics, and learn where to look when something goes wrong.

Part 1. Install and Check

Mosquitto is a small program and the Pi 3B+ runs it comfortably. Install the broker together with its command-line tools, and confirm that it is running:

Pi terminal Shell
sudo apt update sudo apt install -y mosquitto mosquitto-clients sudo systemctl enable --now mosquitto systemctl status mosquitto # should say "active (running)"

Give the Pi a fixed address (a DHCP reservation on the router is simplest). Your Picos connect by IP address, and MicroPython cannot look up a name like raspberrypi.local on its own, so if the address changes every Pico must be edited.

Where Mosquitto keeps things on the Pi. Everything you configure lives under /etc/mosquitto; the broker's remembered state and its log live elsewhere.

Part 2. Letting the Picos In

Since Mosquitto 2.0 a default installation only listens on the Pi itself, so a Pico cannot connect even though the broker is running. Your settings go in a file of your own under /etc/mosquitto/conf.d/, which survives package upgrades, rather than in the main file:

Since Mosquitto 2.0 a fresh install only listens on the Pi itself. Your Picos are blocked until you add a listener and decide how clients prove who they are.
/etc/mosquitto/conf.d/lab.conf Config
listener 1883 allow_anonymous true # first test only: replaced in Part 3 persistence true persistence_location /var/lib/mosquitto/
Pi terminal Shell
sudo systemctl restart mosquitto ss -ltn | grep 1883 # shows the broker listening on all interfaces

persistence true makes the broker save retained messages and persistent sessions to disk, so they survive a restart (later lessons depend on this).

Part 3. Passwords and Permissions

An open broker lets anyone on the network publish to anything, including commands. Add a password file, then an access control list (ACL) that says who may read or write which topics:

Two separate checks. Authentication asks who you are (username and password); the access control list asks what that user may do on each topic.
Pi terminal Shell
sudo mosquitto_passwd -c /etc/mosquitto/passwd instructor # -c creates the file sudo mosquitto_passwd /etc/mosquitto/passwd pico01 # adds a user sudo mosquitto_passwd /etc/mosquitto/passwd dashboard
/etc/mosquitto/conf.d/lab.conf Config
listener 1883 allow_anonymous false password_file /etc/mosquitto/passwd acl_file /etc/mosquitto/acl persistence true persistence_location /var/lib/mosquitto/
/etc/mosquitto/acl Config
# every user may read and write only inside their own subtree pattern readwrite lab/%u/# user dashboard topic read lab/# user instructor topic readwrite lab/#

%u stands for the logged-in username, so a single pattern line gives pico01 its own subtree and nothing else. A Pico passes its credentials when it creates the client:

main.py MicroPython
client = MQTTClient("pico01", BROKER_IP, user="pico01", password="s3cret", keepalive=30) client.connect()

Part 4. Watching the Broker

The broker reports on itself through topics beginning with $SYS, and writes a log. Between them you can see who is connected and why a connection was refused or a message vanished:

The broker reports on itself through $SYS topics. Subscribe to them from the Pi to see who is connected and how busy it is.
Pi terminal Shell
mosquitto_sub -h localhost -u dashboard -P pw -v -t '$SYS/broker/clients/connected' journalctl -u mosquitto -f # live log: logins, refusals, denied topics

Quote $SYS in single quotes, otherwise the shell tries to expand it as a variable. A message denied by the ACL is dropped without any error on the Pico, so the broker log is where to look when one does not arrive.

Exercises

Practice problems in three tiers. Do each on paper or on your own board first, and only then open its solution below. Many problems have more than one correct answer; if yours behaves the same way, it is right even if it looks different.

Warm Up

Exercise 1: Which File?. Name the file for each job: (a) turn on remote connections, (b) store a hashed password, (c) say which topics a user may write, (d) see why a login was refused.

Exercise 2: It Works on the Pi, Not on the Pico. mosquitto_pub -h localhost on the Pi works, but a Pico gets a connection error. Give two likely causes, in the order you would check them.

Intermediate

Exercise 3: Write the Config. Write the config lines for a broker that listens on 1883, requires passwords from /etc/mosquitto/passwd, and keeps retained messages across restarts.

Advanced

Exercise 4: Design the Permissions. Three kinds of client use the broker: each Pico, a dashboard that watches everything, and an instructor tool that sends commands to any device. Write the ACL, and say which line is the most dangerous if mistyped.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Which File?

(a) /etc/mosquitto/conf.d/lab.conf (the listener line). (b) /etc/mosquitto/passwd, edited with mosquitto_passwd. (c) /etc/mosquitto/acl. (d) the broker log: journalctl -u mosquitto or /var/log/mosquitto/mosquitto.log.

Exercise 2: It Works on the Pi, Not on the Pico

1. The broker is only listening on localhost (no listener 1883 line, the Mosquitto 2.x default). Check with ss -ltn | grep 1883. 2. The Pico has the wrong IP address or is on another network. A password problem would give a refused connection rather than a timeout, so rule out the network layer first.

Intermediate

Exercise 3: Write the Config
lab.conf Config
listener 1883 allow_anonymous false password_file /etc/mosquitto/passwd persistence true persistence_location /var/lib/mosquitto/

Restart with sudo systemctl restart mosquitto after every change; a syntax error shows up in journalctl and the service will fail to start.

Advanced

Exercise 4: Design the Permissions
acl Config
pattern readwrite lab/%u/# # a Pico: only its own subtree user dashboard topic read lab/# # read-only: cannot send commands user instructor topic readwrite lab/#

The most dangerous is topic readwrite lab/# given to the wrong user, because it allows commands to every device. Keep the dashboard read-only and keep the instructor account out of student code.
