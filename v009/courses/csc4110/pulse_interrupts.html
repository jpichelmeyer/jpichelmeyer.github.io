A processor that can only do one thing at a time still has to notice many things that happen at their own pace: an echo returns, a magnet passes, someone walks by. This lesson covers how to time pulses, how interrupts let the hardware watch for them, and how to arrange a main loop so that nothing in it ever waits.

Part 1. When the Information Is in the Timing

Not every sensor reports a voltage or a number. Many just produce a pulse, and the information is in when it happens or how long it lasts. An ultrasonic rangefinder reports distance as the length of a pulse; a magnet passing a reed switch makes one pulse per turn; a motion detector raises a pin when someone moves; an infrared receiver encodes a button as a pattern of pulse lengths. Reading these needs a different tool from the ADC: a clock fast enough to time microseconds.

Part 2. The HC-SR04 Ultrasonic Rangefinder

The HC-SR04 measures distance by echo, as a bat does. You raise its TRIG pin for 10 µs; it sends a burst of 40 kHz sound from one transducer; the sound bounces off an object and returns to the other transducer; the ECHO pin is held high from the moment the burst is sent until the echo arrives. The pulse width is the round-trip time.

The HC-SR04 timing. A 10 µs pulse on TRIG starts a burst of eight 40 kHz pulses. ECHO goes high as the burst leaves and falls when the echo returns; its width is the sound’s round-trip time. Wait at least 60 ms between measurements so one echo cannot be mistaken for the next.

Sound travels at about 343 m/s in room-temperature air, which is 0.0343 cm per microsecond. The sound goes out and back, so the distance is half of speed × time, or t / 58.3 centimetres with t in microseconds. A 200 cm object returns an echo 11 660 µs wide. The speed of sound depends on temperature, about 331.3 + 0.606 × T m/s (T in °C), which is why a thermistor and a rangefinder make a better pair than either alone.

The module measures between about 2 cm and 4 m. Soft or angled surfaces (fabric, a surface tilted away) reflect little sound back and may read nothing or far too much, which is the first thing to try when a reading seems wrong.

The echo wire needs a voltage divider. The HC-SR04 is a 5 V module, so its ECHO output swings to 5 V, more than a Pico pin should see. Two kit resistors (1 kΩ in series, 2 kΩ to ground) bring it to 3.3 V. TRIG is driven by the Pico’s 3.3 V, which the module accepts.

Do not connect ECHO directly to the Pico. The RP2040 pins are not rated for 5 V inputs; it may work for a while and then fail. The divider costs two resistors and a minute of wiring. If your kit contains the 3.3 V version of the module (it may be labelled HC-SR04P or "3 V"), no divider is needed, but it does not hurt.

The simplest way to read the pulse is the built-in time_pulse_us, which waits for a pin to reach a level and times how long it stays there:

ranger_blocking.py MicroPython
from machine import Pin, time_pulse_us from time import sleep_us trig = Pin(10, Pin.OUT, value=0) echo = Pin(11, Pin.IN) def distance_cm(temp_c=20, timeout_us=30_000): """Blocking range measurement. Returns centimetres, or None if no echo came back.""" trig.value(0) sleep_us(2) trig.value(1) # a 10 microsecond pulse starts a measurement sleep_us(10) trig.value(0) t = time_pulse_us(echo, 1, timeout_us) # microseconds ECHO stays high; -1 or -2 on timeout if t < 0: return None speed = 331.3 + 0.606 * temp_c # speed of sound in m/s, corrected for temperature return t * speed / 20000 # round trip: halve it. (m/s * us / 20000 = cm)

It works, but notice what it does to your program: for up to 30 ms the processor can do nothing else, which is a long time if you are also sampling a sensor 100 times a second or reading a button. For a robot that has to keep its balance or respond to a stop command, that wait is not acceptable. The fix is to let the hardware tell you when the echo ends, which is what an interrupt does.

Part 3. Interrupts

There are two ways to notice that a pin changed. Polling means asking over and over: "has it changed yet?" It is simple, but if your loop is busy elsewhere when a short pulse arrives and ends, you miss it. An interrupt reverses the arrangement: you tell the chip which pin and which edge (rising, falling or both) to watch, and what function to run. The chip then does the watching in hardware. When the edge happens it pauses your main program, runs your handler immediately, and returns to exactly where it was.

Polling versus an interrupt. A loop that checks the pin only between other jobs can miss a pulse that rises and falls in between. An interrupt makes the chip watch the pin continuously and run a handler the moment the edge happens, whatever the main program was doing.

The cost is that a handler runs in the middle of your other code, so it has strict rules:

Rules for an interrupt handler. Anything slow, or anything that allocates memory (floats, strings and lists are all objects), can corrupt the program it interrupted. The standard pattern: the handler stores a number or sets a flag, and the main loop does the real work when it next looks.
ranger.py MicroPython
from machine import Pin from time import ticks_us, ticks_ms, ticks_diff, sleep_us class Ranger: """HC-SR04 measured with an interrupt, so the main loop never waits for the echo.""" def __init__(self, trig_pin=10, echo_pin=11): self.trig = Pin(trig_pin, Pin.OUT, value=0) self.echo = Pin(echo_pin, Pin.IN) self.t_rise = 0 self.width = None # echo width in microseconds, set by the interrupt self.busy = False self.started = 0 self.cm = None # the latest result (None = nothing came back) self.echo.irq(trigger=Pin.IRQ_RISING | Pin.IRQ_FALLING, handler=self._edge) def _edge(self, pin): # interrupt handler: tiny, no printing, no floats now = ticks_us() if pin.value(): self.t_rise = now else: self.width = ticks_diff(now, self.t_rise) def start(self): self.width = None self.started = ticks_ms() self.busy = True self.trig.value(1) sleep_us(10) self.trig.value(0) def update(self): """Call every loop. Returns True once when a new result is ready in self.cm.""" if not self.busy: return False if self.width is not None: self.cm = self.width / 58.3 # about 58.3 microseconds per cm at 20 C elif ticks_diff(ticks_ms(), self.started) > 40: self.cm = None # 40 ms with no echo: nothing in range else: return False self.busy = False return True

Read it from the bottom up. start() fires the trigger and notes the time, then returns immediately. The _edge handler stamps the clock when ECHO rises and subtracts when it falls, leaving the width in self.width. update() is called on every pass of the main loop: a cheap check that returns True once when a result (or a timeout) is ready. Nothing waits.

ranger_demo.py MicroPython
from machine import Pin from time import ticks_ms, ticks_diff r = Ranger() r.start() last = ticks_ms() while True: if r.update(): print("distance:", None if r.cm is None else round(r.cm, 1)) if not r.busy and ticks_diff(ticks_ms(), last) >= 60: # a new measurement every 60 ms last = ticks_ms() r.start() # ...everything else the node does goes here, and keeps running...

Part 4. Counting Events

A reed switch closes when a magnet passes it; one pulse per pass. Counting pulses over a time window gives a rate: rotations per second, or any "number of times per interval". (A wheel encoder, if you add one later, is counted exactly the same way.) Because the reed switch is mechanical, it bounces like a button, so the handler ignores any edge that comes too soon after the last good one:

pulsecounter.py MicroPython
from machine import Pin, disable_irq, enable_irq from time import ticks_us, ticks_diff class PulseCounter: """Count falling edges on a pin (reed switch, encoder, flow sensor) and ignore bounce.""" def __init__(self, pin, min_gap_us=5000): self.pin = Pin(pin, Pin.IN, Pin.PULL_UP) self.min_gap = min_gap_us self.n = 0 self.last = ticks_us() self.pin.irq(trigger=Pin.IRQ_FALLING, handler=self._edge) def _edge(self, pin): now = ticks_us() if ticks_diff(now, self.last) > self.min_gap: # too soon after the last one = bounce self.n += 1 self.last = now def count(self): state = disable_irq() # read it with interrupts off so it cannot change mid-read n = self.n enable_irq(state) return n

count() turns interrupts off for an instant while it reads the number. Without that, a pulse arriving halfway through the read could leave the program with an inconsistent value. Wire the reed switch between GP12 and ground, like a button, and the same class counts passes. To get a rate, compare the count now with the count a fixed time ago and divide:

rate.py MicroPython
counter = PulseCounter(12) prev, prev_t = 0, ticks_ms() def pulses_per_second(): global prev, prev_t now_t, n = ticks_ms(), counter.count() dt = ticks_diff(now_t, prev_t) rate = (n - prev) * 1000 / dt prev, prev_t = n, now_t return rate

Two more pulse sensors in your kit work the same way. The PIR motion sensor raises its output while it sees movement, so attach an interrupt on the rising edge and record the time of the last event (it needs about a minute to settle after power-up, and it holds the output high for a few seconds after each trigger). The infrared receiver idles high and goes low during the 38 kHz bursts a remote control sends; the first low pulse of a Sony-style or NEC-style remote button press is distinctive and long, so you can check that it works by timing it:

ir_leader.py MicroPython
ir = Pin(12, Pin.IN, Pin.PULL_UP) # receiver output: high when idle, low during a burst def ir_leader_us(timeout_us=100_000): """Width of the first LOW pulse after a button press on a remote, in microseconds.""" return time_pulse_us(ir, 0, timeout_us) # a NEC remote starts with about 9000 us

Part 5. A Loop That Never Waits

Put these ideas together and a node has several jobs running at different rates: range every 60 ms, a status LED every 500 ms, a report once a second. The trick is that none of them ever sleeps. Each asks "is it my turn?" and, if not, the loop moves straight on. A tiny timer class does the asking:

every.py MicroPython
from time import ticks_ms, ticks_diff, ticks_add class Every: """A timer you ask, not wait for: if every.due(): ...""" def __init__(self, ms): self.ms = ms self.last = ticks_ms() def due(self): now = ticks_ms() if ticks_diff(now, self.last) < self.ms: return False self.last = ticks_add(self.last, self.ms) # keep a steady rhythm ... if ticks_diff(now, self.last) >= self.ms: # ... but if we fell far behind, self.last = now # skip the missed ones, do not burst return True
A cooperative loop. Every job is a quick yes-or-no check followed by a small amount of work if it is due. Because no job waits, the loop keeps coming around, and each timer fires at its own rate. If you add a sensor, you add one more box.

There is no multitasking magic: the jobs take turns, so each must be short. If one of them takes 30 ms, every other job is late by up to 30 ms. That is why time_pulse_us had to go, and why the reading, filtering and sending of Lab 3 are written as small pieces.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Echo to Distance

At 20 °C: 5830 / 58.3 = 100 cm. At 0 °C sound travels at 331.3 m/s instead of 343.4 m/s, so the same echo corresponds to 5830 × 331.3 / 20000 = 96.6 cm. Using 20 °C when the air is at 0 °C would read 3.5 % too far. Temperature correction matters only if you need better than a few percent.

Exercise 2: The Divider

V = 5 × 1 / (2 + 1) = 1.67 V. That is below the Pico’s high threshold (about 2 V), so the pin may read the echo as low all the time and the rangefinder never seems to answer. Safe for the pin, wrong for the circuit. The 1 kΩ must be the one in series (nearest the ECHO wire) and the 2 kΩ the one to ground.

Intermediate

Exercise 3: Bounce Filter

It starts with last = 0. The edge at 10 000 is 10 000 µs after, so it is counted. The edges at 11 000 (1 ms later) and 12 500 (2.5 ms after the counted one) are rejected as bounce. 40 000 is counted. 41 200 is rejected. 90 000 is counted. The total is 3.

test_counter.py MicroPython
us = [0] ticks_us = lambda: us[0] # a clock we control (replaces the one the class looks up) c = PulseCounter(12) # needs a real or stand-in Pin us[0] = 0 c.last = 0 for t in (10_000, 11_000, 12_500, 40_000, 41_200, 90_000): us[0] = t c._edge(c.pin) # call the handler directly, as the interrupt would print(c.count()) # 3

Advanced

Exercise 4: Three Jobs, One Loop
test_every.py MicroPython
us = [0] ticks_ms = lambda: us[0] timers = {60: Every(60), 500: Every(500), 1000: Every(1000)} for e in timers.values(): e.last = 0 fired = {n: 0 for n in timers} for ms in range(0, 3001): us[0] = ms for n, e in timers.items(): if e.due(): fired[n] += 1 print(fired) # {60: 50, 500: 6, 1000: 3}

Three seconds is 50 periods of 60 ms, 6 of 500 ms and 3 of 1000 ms, and the counts agree. Because each timer advances its last by exactly one period rather than resetting to "now", a loop that is a little late on one pass does not stretch the rhythm: the next one is still on schedule.
