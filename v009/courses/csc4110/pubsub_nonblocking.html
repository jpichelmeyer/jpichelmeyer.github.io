TCP gets two machines reliably exchanging bytes, but says nothing about who talks to whom, and when. This lesson covers the communication pattern MQTT is actually built around, publish-subscribe, and a coding habit, non-blocking loops, that becomes essential the moment a device needs to both send data and stay responsive at the same time.

Part 1. Request-Response, the Pattern You Already Know

Most web traffic works like this: a client sends a request ("give me this webpage"), and the server sends back exactly one response. The client always initiates; the server never speaks unless spoken to. This works fine when one device wants something specific from one other device, but it's an awkward fit for this unit's actual goal: many sensor nodes continuously reporting data to whoever wants to hear it, without any of them needing to know in advance who that is.

Request-response needs the asker to know who to ask and to ask every time. Publish-subscribe lets a sender announce data once and lets any number of listeners receive it.

Part 2. Publish-Subscribe

Publish-subscribe (pub-sub) decouples senders from receivers entirely through a middleman. A publisher sends a message labeled with a topic, without knowing or caring who, if anyone, is listening. A broker receives that message and forwards it to every currently connected subscriber that asked for that topic. Publishers and subscribers never talk to each other directly, only to the broker.

The publisher's entire job is handing one message to the broker; fanning it out to however many subscribers actually want it is the broker's problem, not the publisher's. Add a fourth subscriber tomorrow and Pico #1's code doesn't change at all.

This is exactly the shape of this course's telemetry setup: every Pico publishes its own sensor readings without needing to know what, if anything, is watching that data, a dashboard, a logging script, another Pico, none of it changes what the sensor node itself has to do.

Part 3. Why Blocking Code Becomes a Problem

Every script so far has used plain sleep() to pace a loop, which blocks: the whole program, every single line, stops dead for that duration. That's been fine when sleeping was the only thing happening. It stops being fine the moment a device also needs to, say, immediately react to an incoming message from the broker, a sleep(1) mid-loop means up to a full second of total unresponsiveness, every single loop.

blocking.py (the pattern to move away from) MicroPython
while True: publish_reading() sleep(1) # completely unresponsive for a full second, every loop
A blocking delay stops the whole program for its duration; a non-blocking loop keeps spinning and only acts when its interval has elapsed.

Part 4. Non-Blocking Loops with ticks_ms()

The standard MicroPython pattern replaces sleep() with checking elapsed time against a stored timestamp, so the loop can keep spinning (and doing other work) and only act once enough real time has actually passed:

non_blocking.py MicroPython
from time import ticks_ms, ticks_diff INTERVAL_MS = 1000 last_publish = ticks_ms() while True: now = ticks_ms() if ticks_diff(now, last_publish) >= INTERVAL_MS: publish_reading() last_publish = now check_for_incoming_messages() # runs every loop, never delayed

Two details worth noticing: ticks_ms() is used instead of a plain subtraction of two timestamps, because the underlying counter wraps around (resets to zero) after enough time passes, and ticks_diff() correctly handles that wraparound where naive subtraction wouldn't. And check_for_incoming_messages() now runs on every pass through the loop, not once a second, since nothing is blocking it anymore.

Warm Up

Exercise 1: Which Pattern?

(a) Pub-sub: many senders, unknown listeners. (b) Request-response: one specific answer to one specific question. (c) Either works; pub-sub keeps them decoupled (the heater just subscribes to a command topic), request-response gives a direct acknowledgement.

Exercise 2: How Many Passes?

1000 ms / 5 ms ≈ 200 times per second, versus once per second with sleep(1). The non-blocking loop notices a message within about 5 ms instead of up to a second.

Intermediate

Exercise 3: Un-Block a Blink
main.py MicroPython
from machine import Pin from time import ticks_ms, ticks_diff led = Pin("LED", Pin.OUT) last = ticks_ms() while True: now = ticks_ms() if ticks_diff(now, last) >= 250: led.toggle() last = now # other work can go here and runs on every pass

Same visible behaviour, but the loop is now free to do other work between toggles.

Advanced

Exercise 4: A Reusable Timer
main.py MicroPython
from machine import Pin from time import ticks_ms, ticks_diff class Every: def __init__(self, ms): self.ms = ms self.last = ticks_ms() def ready(self): now = ticks_ms() if ticks_diff(now, self.last) >= self.ms: self.last = now return True return False led = Pin("LED", Pin.OUT) blink = Every(250) report = Every(1000) while True: if blink.ready(): led.toggle() if report.ready(): print("alive")

Each Every remembers its own last time, so any number of independent jobs can share one loop.
