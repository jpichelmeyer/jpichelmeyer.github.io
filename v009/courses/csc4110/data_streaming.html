A telemetry stream is more than a loop that publishes. Once data flows continuously you start to care about how much, how steadily, what gets lost, and what happens when the link breaks. This lesson gives you the vocabulary and the standard techniques for each.

Part 1. Rate, Throughput, Latency

  • Rate: how many messages per second you publish.
  • Throughput: how many bytes per second that adds up to (rate × message size).
  • Latency: how long one message takes to get from the sensor to the subscriber.
  • Jitter: how much that latency varies from message to message.

Throughput is the one you control most directly. Every tenfold increase in rate multiplies the traffic, the radio's power use and the load on the broker by ten:

Traffic grows in direct proportion to the sampling rate. Each tenfold increase multiplies bytes sent, power used and broker load by ten.

Part 2. Knowing What You Did Not Receive

MQTT by default does not guarantee that every message arrives (the default level, QoS 0, is "send it once and hope"). Unit 2 covers stronger guarantees, but even then a subscriber benefits from being able to see loss. A sequence number that rises by one per message does exactly that:

A sequence number is a cheap way to know what you did not receive. Any jump larger than one marks lost readings.
main.py MicroPython
last_seq = None def on_message(topic, msg): global last_seq seq = json.loads(msg)["seq"] if last_seq is not None and seq != last_seq + 1: print("lost", seq - last_seq - 1, "messages") last_seq = seq

Part 3. Sending Less

Most signals are quiet most of the time, so a fixed rate wastes most of its messages. Two common remedies:

  • Report by exception (a deadband): publish only when the value has changed by more than a threshold, plus a slow heartbeat so that silence means "unchanged", never "dead".
  • Summarize: sample fast but publish the mean, minimum and maximum of each batch. You keep the information that matters (and any spike shows in the maximum) at a fraction of the traffic.
Sending only when the value has moved enough (orange dots) carries nearly the same information as sending everything, at a fraction of the traffic.

Part 4. When the Link Drops

A device that publishes during a WiFi outage has three choices: drop the readings, stop and wait, or queue them. Queuing is only safe if it is bounded, because RAM is small:

While the link is down, readings queue up in RAM. A fixed upper limit and a rule for what to discard keep an outage from becoming a crash.
main.py MicroPython
class Buffer: def __init__(self, maxlen): self.maxlen = maxlen self.items = [] def add(self, item): if len(self.items) >= self.maxlen: self.items.pop(0) # drop the oldest to make room self.items.append(item) def drain(self, send): while self.items: send(self.items[0]) self.items.pop(0) # removed only after a successful send

Deciding what to throw away is a design decision, not a detail: for a thermometer the newest readings matter most, but for a log you might prefer to keep the oldest.

Part 5. Putting It Together

A well-behaved telemetry node publishes at a rate chosen for its signal, labels every message with a sequence number and timestamp, reduces traffic where it can, and degrades gracefully when the network disappears. None of this changes the sensor code; it is all in how the stream is handled.

Missing: 103, 104, 107, 108, 109, so 5 readings lost. Each gap is (next − previous − 1): 105 − 102 − 1 = 2, and 110 − 106 − 1 = 3.

THRESH = 500 HEARTBEAT_MS = 60000 last_sent = None last_time = ticks_ms() def maybe_publish(value): global last_sent, last_time now = ticks_ms() changed = last_sent is None or abs(value - last_sent) >= THRESH quiet_too_long = ticks_diff(now, last_time) >= HEARTBEAT_MS if changed or quiet_too_long: publish(value) last_sent = value last_time = now

The heartbeat matters: without it, "no messages" would be ambiguous between "nothing changed" and "the device died".

Exercise 4: A Bounded Backlog
main.py MicroPython
class Buffer: def __init__(self, maxlen): self.maxlen = maxlen self.items = [] def add(self, item): if len(self.items) >= self.maxlen: self.items.pop(0) # forget the oldest self.items.append(item) def drain(self, send): while self.items: send(self.items[0]) # may raise if the link is down self.items.pop(0) # only removed once sent backlog = Buffer(50)

The size cap protects the Pico's small RAM. Removing an item only after send succeeds means a failed send leaves it queued for the next attempt.
