This lab joins the features, the log and the budgets into one working pipeline. You turn a 50 Hz IMU stream into 2 Hz features on the node, keep a bounded log in flash and a full log in SQLite at the hub, train a threshold from your own recordings and deploy it as a small file, and check your design against measured budgets and an outage.

What You Will Build

A node that understands its own motion and a hub that remembers it. On the Pico, the MPU6050 is sampled at 50 Hz; a window turns the samples into features (mean, spread, range); a one-number model decides moving or still; a z-score flags unusual readings; and a ring log in flash keeps the node’s own events. At the hub, a logger writes everything into SQLite, you ask it questions, train a better threshold from your own recording, and send it back to the node as model.json. Only the features cross the network: about 2 messages a second instead of 50.

The Lab 8 loop. Data goes up as features, the model comes down as a file. Between runs, the log is the only thing that links what happened to what you changed.

Step 1. The Node

Copy to the Pico: net.py, config.py, hub.py, backoff.py, resilient.py (Lab 7), mpu6050.py (from the I²C lesson), and the four new modules of this week: window.py and anomaly.py (features lesson), ringlog.py (data logging lesson) and profile.py (budgets lesson). Wire the MPU6050 as in Lab 3 (SDA GP0, SCL GP1). Then run this main.py:

main.py MicroPython
# main.py for Lab 8: features at the edge, a log at the hub import math, json from time import ticks_ms, ticks_diff from machine import I2C, Pin import resilient from mpu6050 import MPU6050 from window import Window from anomaly import Anomaly from ringlog import RingLog from profile import Cost i2c = I2C(0, sda=Pin(0), scl=Pin(1), freq=400000) imu = MPU6050(i2c) win = Window(10) # 10 samples at 50 Hz = 0.2 s odd = Anomaly(alpha=0.05, k=4.0) log = RingLog("log", seg_bytes=4096, segs=4) h = resilient.ResilientHub(keepalive=30, wifi_timeout_s=5) h.presence() try: threshold = json.load(open("model.json"))["threshold"] except (OSError, ValueError): threshold = 0.05 # a starting guess until the hub sends a trained value moving = 0 c_read, c_feat = Cost(), Cost() t_sample, t_report, t_cost = ticks_ms(), ticks_ms(), ticks_ms() def note(*vals): log.add(",".join(str(v) for v in (ticks_ms(),) + vals)) note("boot") while True: h.poll() now = ticks_ms() if ticks_diff(now, t_sample) >= 20: # 50 Hz t_sample = now a, _, _ = c_read.run(imu.read) mag = math.sqrt(a[0] * a[0] + a[1] * a[1] + a[2] * a[2]) win.add(mag) f = c_feat.run(win.features) if f: if moving == 0 and f["std"] > threshold * 1.1: moving = 1 note("moving", 1) elif moving == 1 and f["std"] < threshold * 0.9: moving = 0 note("moving", 0) if odd.update(mag): h.publish("evt/anomaly", {"mag": round(mag, 3)}) note("anomaly", round(mag, 3)) if ticks_diff(now, t_report) >= 500 and win.count == win.n: # 2 Hz of features t_report = now f = win.features() h.publish("tele/imu", {"mean": round(f["mean"], 3), "std": round(f["std"], 4), "min": round(f["min"], 3), "max": round(f["max"], 3), "moving": moving}) if ticks_diff(now, t_cost) >= 10000: # a cost report every 10 s t_cost = now c_read.report("imu read", 20) c_feat.report("features", 20)

The program was run on the test fixture for 20 simulated seconds with a quiet signal, a noisier one from 6 s to 12 s, and a fake clock. It published 39 tele/imu messages (about 2 per second, instead of 1,000 raw samples), reported moving: 1 from 6 s to 12 s, wrote moving,1 at 6,040 ms and moving,0 at 12,120 ms to the ring log, and raised two evt/anomaly messages at the start of the movement, when the signal suddenly became livelier than the recent past. The timing report printed zeros there because the fake clock does not run during a call; on the real board you will see real numbers.

Check: shake the board and watch tele/imu from the laptop (mosquitto_sub -v -t "lab/YOURNAME/tele/imu"). Let it lie still on the bench. The std should differ by a factor of several; if it does not, calibrate() and the I²C wiring are the first suspects.

Report the threshold and its accuracy on the training sessions, then test it on session (c) and on a fresh walking session and report the accuracy there. If the test accuracy is much worse than the training accuracy, explain why, and what you would collect next.

Step 4. Budgets

Read the cost report the node prints every ten seconds. Fill in a table: the time to read the IMU, the time to compute the features, and each as a percentage of the 20 ms loop (average and worst). Then calculate your link budget: messages per second and bytes per second of tele/imu (the logger gives you the payload length, LENGTH(payload)), and compare with the class limits. Finally, compute what it would have cost to send every sample as its own JSON message.

Step 5. Pull the Plug

Switch off the WiFi for 30 seconds while the node is moving, then switch it on. Using the log on the node (for l in log.lines(): print(l) in the Thonny shell) and the log at the hub, find: when the node noticed the link was down, which messages the hub is missing, and whether the node kept computing. State clearly which log you used to answer each part and why the other could not.

Exercises

Practice problems in three tiers. Do each on paper or on your own board first, and only then open its solution below. Many problems have more than one correct answer; if yours behaves the same way, it is right even if it looks different.

Warm Up

Exercise 1: Count the Messages. The node publishes tele/imu at 2 Hz, each message about 120 bytes. For a 5-minute session, how many messages and bytes should the logger hold? If the database has 540 rows for the session, what happened?

Intermediate

Exercise 2: Still, But Flagged. The anomaly detector flags the start of every walking session even though a walking robot is not faulty. Explain why, and say whether this is a bug and what you would change so that “start of motion” is an expected event and not an anomaly.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Count the Messages

5 × 60 × 2 = 600 messages, about 72,000 bytes of payload. 540 rows means 60 messages (10 %) are missing. Look for gaps in seq (a query comparing each seq with the previous one, using LAG) and in t: gaps grouped together mean an outage, scattered gaps mean loss on the link (QoS 0).

Intermediate

Exercise 2: Still, But Flagged

The z-score compares the current reading with the recent past. When motion starts, the readings become suddenly more variable than the mean and variance learnt during stillness, so a few readings are many deviations out: they are unusual relative to the past, which is what the detector measures, so it is not a bug. To avoid treating start of motion as a fault, feed the detector the residual after the motion state is known (a separate detector per moving state), or ignore anomalies for a second after a moving change, or apply the detector to a feature that does not depend on the activity (such as a saturated sensor value).
