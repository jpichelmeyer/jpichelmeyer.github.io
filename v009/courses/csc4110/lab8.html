The Detector

The Lab 8 detector in one picture. Smooth with an EMA, track the spread, score each reading, require a few anomalies in a row, then publish.

Use the LDR circuit from Lab 2. Your program reads the sensor (filtered by an EMA), feeds each reading to a z-score detector with warm-up and a floor on the spread, counts consecutive anomalies, and then publishes. It publishes two things: a features packet every few seconds on lab/<id>/tele/features, and an alert, retained, on lab/<id>/stat/alert when the persistence rule fires and again when it clears.

main.py (outline) MicroPython
det = ZScore(alpha=0.05, warmup=30, floor=2.0) smooth = EMA(0.3) PERSIST = 3 streak = 0 alert = False win = Window(50) while True: x = smooth.update(sensor.read_u16() >> 4) z = det.update(x) streak = streak + 1 if abs(z) > 3 else 0 now = streak >= PERSIST if now != alert: alert = now client.publish(ALERT, b"1" if alert else b"0", retain=True, qos=1) if win.add(int(x)): client.publish(FEATURES, json.dumps(win.features()).encode()) win.reset() client.check_msg() sleep_ms(100)

Tune It

The detector's three dials and what each one trades. There is no setting that is fast, sensitive and never wrong; tuning is choosing which mistakes you can live with.

There is no best setting, only a trade between catching real events quickly and raising false alarms. Decide which mistake is worse for this application, then tune toward it, and measure rather than guess: record at least five minutes of undisturbed signal and count how many alerts it raises on its own, then cover the sensor ten times and count how many it catches and how long each takes.

Solutions

Warm Up

Exercise 1: Trace the Alert

Earliest: three samples, so about 0.3 s after the first anomalous reading. If the first anomalous sample is the second after the change, the alert comes at the fourth sample, about 0.4 s. Persistence always adds (k − 1) sample periods to the detection delay.

Exercise 2: Why the Floor?

The variance decays to 0, so std = 0 and the division is by zero (or, with floats, tiny and huge z-scores). A single count of 121 would give an enormous z and trigger an alert for a trivial change. A floor on the standard deviation (here 2.0 counts, say) means a change must be genuinely larger than the sensor’s resolution to count.

Exercise 3: Measure False Alerts per Hour
main.py (additions) MicroPython
alerts = 0 started = ticks_ms() # when alert goes from False to True: alerts += 1 # on a button press, or after N minutes: hours = ticks_diff(ticks_ms(), started) / 3_600_000 print(alerts, "alerts in", round(hours, 2), "h =", round(alerts / hours, 1), "per hour")

Measure over a long enough run that the number means something: with a rate near one per hour, five minutes of data tells you almost nothing. Report the length of the run with the rate.

Advanced

Exercise 4: Compare Two Settings

Hold the sensor, the room, the threshold and persistence fixed, and run each alpha through the same two tests: an undisturbed run of at least ten minutes (count false alerts per hour) and ten identical cover-and-release events (record detection delay and whether each was caught). Judge on both numbers together: the larger alpha adapts faster to slow drift and so produces fewer false alerts on a drifting signal, but may follow a slow real fault and miss it, while the smaller alpha is steadier but slower to forgive a legitimate change in baseline. The right choice depends on which of those failures matters more.
