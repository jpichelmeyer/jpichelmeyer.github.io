This lab connects everything from the week: a MOSFET switch you build, a program that obeys remote commands safely, and a test plan that proves it fails safe. Treat it like a real system: nothing in it should ever turn on unexpectedly.

The Circuit

Use a small load from your kit: a 5 V fan or buzzer if you have one, otherwise an LED with a 330 Ω resistor in series stands in for it. If the load is a coil or motor, add the flyback diode. Build with the Pico unplugged, check the ground connections, then power up.

The standard low-side switch. The Pico drives the gate through a small resistor; a pull-down keeps the load off while the Pico is booting; the load sits between the supply and the drain; a diode protects against inductive spikes.

The Topics

The topic map for Lab 7. A command goes in on cmd, the device reports the real output on stat, and a retained availability topic marks whether the device is there at all.

The Program

Build on your Lab 6 program (last will, state file, backoff). The output must: start OFF; obey on, off and on N on cmd/out with the validation from the message-handling lesson; switch itself off after the timer ends, after 30 seconds without contact, and after a maximum run time; and report the real pin state, retained, on stat/out. Use the asyncio structure if you wish, but make each of the three safety rules testable on its own.

main.py (outline) MicroPython
HANDLERS = {"out": handle_out} # dispatch table from the message-handling lesson def handle_out(msg): if not allowed(): # rate limit return apply(msg) # validated, timed, reported # main loop (or tasks) while True: try: client.check_msg() supervise() # timers + silence timeout keepalive.tick() maybe_save() except OSError: out.value(0) # fail safe FIRST, then recover connect_broker()

Lab Report

  1. Draw your schematic and say what the gate resistor, the pull-down and the diode (if used) do in your circuit.
  2. For each row of the test plan, record what happened. For the "stop the broker" test, how long after the last contact did the load switch off?
  3. Show the line of code that guarantees the output is OFF at start-up, and the hardware part that guarantees it before the program starts.
  4. Describe one way someone could still switch your output on when you would not want them to, and what you would add to prevent it.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Read the Schematic

Gate to GP15 through the 330 Ω resistor (and to ground through the 10 kΩ pull-down). Drain to the load’s negative side. Source to ground, joined to the Pico’s ground. The load’s positive side goes to the supply.

Exercise 2: Predict the Test

The Pico stops hearing from the broker, and after 30 seconds of silence the supervise rule switches the load off, so the load goes off at about the 30-second mark, before the broker returns. When the broker comes back, the Pico reconnects and reports off; it does not switch back on by itself.

Intermediate

Exercise 3: Fail Safe in the Exception Path

connect_broker() can block for a long time with backoff. If the output were switched off only after it returned, a load that was on when the link died would stay on for the whole outage. Doing the safe thing first means the device is already safe while it works on recovering.

Advanced

Exercise 4: Prove the Boot State

Power the circuit with the load connected, then unplug and replug USB while watching the load, and also press Stop and restart in Thonny. The load must never flicker on. That is guaranteed by the 10 kΩ pull-down holding the gate at ground whenever the pin is not driving it, with Pin(15, Pin.OUT, value=0) as the software side once the program runs.
