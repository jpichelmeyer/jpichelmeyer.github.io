This lab joins the four layers of the week into one node and then attacks it. You assemble a robot that backs off, remembers its restarts, feeds a watchdog only when healthy and keeps control independent of the network, and you measure how it behaves in eight failure drills.

What You Will Build

The Lab 6 robot, made to survive. You take the node that obeys commands and add the four layers of this week: backoff (it reconnects politely), persistence (it remembers its resets and outages across restarts), the watchdog (it recovers from a hang), and the bounded handling of the message lesson. Then you break it on purpose, with drills, and write down what happened. The aim is not a node that never fails; it is a node whose failures are short, safe and visible.

The layers of the Lab 7 node. The order matters: safety (control) first, then the network, then memory, with the watchdog watching all of it.

Step 1. Assemble the Node

Copy these files to the Pico: net.py, config.py, hub.py, robot.py, actuators.py (Lab 6), and the new ones from this week: backoff.py and resilient.py (network resilience lesson), dedupe.py (same lesson), store.py and state.py (state persistence lesson). Then replace main.py with the program below. Read it before you run it: every block of it is a decision from a lesson.

main.py MicroPython
# main.py for Lab 7: the Lab 6 robot, made to survive from machine import WDT, reset_cause, WDT_RESET from time import ticks_ms, ticks_diff import hub, resilient, state from robot import Robot from actuators import Actuators from dedupe import Dedupe st = state.State("state.json", {"resets": 0, "wdt": 0, "outages": 0}, min_gap_ms=30000) st.set("resets", st.data["resets"] + 1) if reset_cause() == WDT_RESET: st.set("wdt", st.data["wdt"] + 1) st.tick(force=True) h = resilient.ResilientHub(keepalive=30, wifi_timeout_s=5) h.presence() robot = Robot(Actuators(), allow_spin=True) # starts IDLE, outputs off, always seen = Dedupe() def on_cmd(topic, payload): kind = topic.rsplit("/", 1)[-1] d = hub.decode(payload) h.publish("evt/ack", robot.command(kind, d, ticks_ms())) # the robot's id table makes this idempotent h.on(h.mine("cmd/#"), on_cmd) wdt = WDT(timeout=8000) shown, was_online, last_pass, t_report = None, False, ticks_ms(), ticks_ms() while True: now = ticks_ms() last_pass = now h.poll() # the link may be down: this must not block for why in robot.tick(now): # the control step runs whatever the network does h.publish("evt/stopped", {"why": why}) online = h.status == "ONLINE" if was_online and not online: st.set("outages", st.data["outages"] + 1) shown = None # a restarted broker may have lost the retained state was_online = online s = robot.state() if s != shown and online: h.publish("stat/state", {"state": s[0], "owner": s[1], "resets": st.data["resets"], "wdt": st.data["wdt"]}, retain=True) shown = s if online and ticks_diff(now, t_report) >= 1000: t_report = now h.publish("tele/health", {"attempts": h.attempts, "outages": st.data["outages"], "dropped": h.rx_dropped}) st.tick() if ticks_diff(ticks_ms(), last_pass) < 2000: # healthy: the loop came round wdt.feed()

Five things to notice. (1) wifi_timeout_s=5 keeps every blocking call inside the watchdog’s 8 seconds. (2) The robot is built idle each time, never from saved state. (3) h.poll() returns at once when the link is down, so robot.tick keeps running and the deadman keeps working. (4) State is published only when online, because a publish on a dead link only adds to the confusion. (5) The watchdog is fed at the end of a pass, and only if the pass was healthy.

Before the lab, the program was run on the test fixture (a fake broker and clock) through a scripted outage: claim at 4 s, a spin command at 5 s, the network cut at 7 s and restored at 67 s, then a simulated watchdog restart. The motor ran from 6 s (about a second after the command) and was off by 8 s with the network still down, because the deadman needs no network. After the link returned, the node was back online 6 to 33 seconds later (six runs with different jitter, average 22 s), because its backoff was already at the 30-second ceiling. The counters after the simulated watchdog reset was {resets: 2, wdt: 1, outages: 1}. Your numbers will differ; the shapes should match.

Step 2. The Drills

Run each drill from the laptop with the cmd() and watch() helpers of Lab 6, and keep a table: what you did, what the node did, the time of each event, and the delay in seconds. For drills that need a lost network, switch off your phone hotspot or unplug the access point; do not unplug the broker laptop’s network, which is also yours.

The eight drills. Each one tests a different layer; if a drill surprises you, the explanation is the learning.
  • Expected for drill D: the lease (30 s) expires while the link is down, so the robot releases ownership and your pan is refused with “not owner”. Ownership is time-limited by design, and a long outage means you must claim again.
  • Drill F needs a temporary edit: put time.sleep(10) in the loop. The board resets about 8 seconds later, and reset_cause() is WDT_RESET. Remove the edit afterwards. If your Thonny session loses the board, do not worry: that is the test passing.
  • Drill G is a measurement, not a fault: look at dropped in tele/health, and at how long the first command after the flood takes to be acknowledged.

Step 3. Improve One Thing

Choose one weakness the drills exposed and fix it. Examples: make the first retry faster for a short glitch, publish a stat/link message with the outage duration after each reconnect, add a check that the sensor was read recently to healthy(), or replace the loop with the uasyncio version from the message-handling lesson. Describe the weakness, the change, and a measurement that shows the change helped.

Warm Up

Exercise 1: Read the Backoff

At the ceiling the next attempt is up to 30 × 1.25 = 37.5 s after the last failed one, and, because the link returns at a random point in that wait, the average is about half the wait: 15 to 19 s. The ceiling is a good idea because without it the waits would keep doubling (1, 2, 4 ... 64, 128 s), and a node would sit out minutes after a long outage; with a ceiling it tries every half minute at a trivial cost.

Intermediate

Exercise 2: Stuck Online

(1) Subscription lost: it reconnected but did not resubscribe; check that connect resubscribes (the Hub does) and that cmd/# is in the filter list. (2) Publishing to a topic the ACL denies: a denied publish is silent; check the broker log or publish from a known-good client to the same topic. (3) Stale shown state: the node thinks the state was already published but a restarted broker lost the retained copy, so it never republishes; the listing resets shown to None when the link drops. Take that line out, restart the broker without persistence, and see the retained state go missing.
