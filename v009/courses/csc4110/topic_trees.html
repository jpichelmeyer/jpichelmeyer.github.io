Unit 1 used topics as labels. From here on they are the address system for everything you build, so it is worth designing them on purpose. A good topic tree makes wildcards, permissions and dashboards easy; a careless one makes each of them painful, and is hard to change once devices are deployed.

Part 1. A Topic Is an Address

An MQTT topic is a UTF-8 string made of levels separated by /. The broker does not know what any level means; it only matches strings. The structure exists for people, and for wildcards, which work level by level. Topics are case-sensitive, and nothing needs to be created in advance: the first publish to a topic brings it into existence.

A topic tree for the lab. Each level narrows the address, from the whole site down to one measurement. Keeping the device at the same depth everywhere is what makes wildcards (next lesson) work.

Read a topic from left to right as an address that narrows: site, then device, then the kind of message, then the specific thing. Everything under lab/pico01 belongs to one device, which is exactly what a permission rule or a subscription will later want to say.

Part 2. Rules That Save You Later

Topics that cause trouble later (left) next to the versions that scale (right). Most bad topics break one of three rules: keep a consistent shape, keep values out of the topic, and use simple characters.
  • Keep the same shape everywhere. If the device id is always the second level, lab/+/tele/light means "every device's light" and nothing else.
  • Never put a value in a topic. The value belongs in the payload; a topic per reading would create thousands of topics the broker must track.
  • Use lowercase letters, digits and short words. Spaces and capitals invite typos that fail silently, because a misspelled topic is simply a different topic.
  • No leading slash. /lab/x has an empty first level and does not match lab/x.
  • Keep it short. The full topic travels with every single message, so a long one costs bytes, power and RAM on every publish.

Part 3. One Template for the Whole Course

From now on this course uses site/device/direction/name. The direction level separates three kinds of traffic, which have different rules about who may publish and how they are handled: tele for telemetry going out, cmd for instructions coming in, and stat for the state a device reports about itself.

One template for every topic: site / device / direction / name. Direction separates telemetry (data going out), commands (instructions coming in) and state (what the device reports it is doing).

Unit 1’s lab/pico01/light becomes lab/pico01/tele/light. A small helper keeps every topic in your code consistent and catches mistakes at the moment they are made rather than after a message has silently gone nowhere:

topics.py MicroPython
SITE = "lab" DIRECTIONS = ("tele", "cmd", "stat") def topic(device, direction, name): if direction not in DIRECTIONS: raise ValueError("bad direction: " + direction) for part in (device, name): if not part or "/" in part or " " in part or part != part.lower(): raise ValueError("bad topic part: " + part) return "/".join((SITE, device, direction, name)) print(topic("pico01", "tele", "light")) # lab/pico01/tele/light

Intermediate

Exercise 3: A Topic Builder That Checks
topics.py MicroPython
def topic(device, direction, name): if direction not in ("tele", "cmd", "stat"): raise ValueError("bad direction") for part in (device, name): if not part or "/" in part or " " in part or part != part.lower(): raise ValueError("bad part") if "+" in part or "#" in part: raise ValueError("wildcard in a publish topic") return "lab/%s/%s/%s" % (device, direction, name) try: topic("pico01", "tele", "li+ght") except ValueError as e: print("rejected:", e)

Wildcards are only legal in subscriptions, and a publish to a topic containing one is an error. Catching it here gives a clear message instead of a silent failure on the broker.

Advanced

Exercise 4: Parse and Route
topics.py MicroPython
def parse(t): parts = t.split("/") if len(parts) != 4 or parts[0] != "lab" or parts[2] not in ("tele", "cmd", "stat"): return None return parts[1], parts[2], parts[3] print(parse("lab/pico01/cmd/led")) # ('pico01', 'cmd', 'led') print(parse("lab/pico01/led")) # None: too few levels print(parse("home/pico01/cmd/led")) # None: wrong site

Returning None for anything unexpected lets the caller ignore stray messages with one if, which is the first step of safe message handling later this unit.
