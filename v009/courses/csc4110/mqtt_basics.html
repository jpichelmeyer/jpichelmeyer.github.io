This lesson introduces publish and subscribe, the broker’s role and the few packets a node uses. You write a subscriber with a callback and a publisher without net.py, and learn why umqtt.simple needs you to ping. Then you open the broker itself: the three files that decide who may connect and what each user may touch, and how to run your own copy on your laptop so you can test at home.

SAM lens. Subscribing is a new Perceptor input and publishing a new Actuator output. A callback is the network's interrupt handler: catch the message, hand it to the Perceptor's queue, and return. The broker is part of every robot's environment, and its access list decides which parts of that environment each agent may change.

MQTT is the language your node has been speaking since Lab 3. It was designed in the late 1990s for tiny devices on poor links, which is a fair description of a Pico on WiFi, and it remains the most common way for IoT devices to exchange small messages. This lesson covers the idea behind it (publish and subscribe), the few packet types it uses, and the first programs that publish and subscribe on their own, without net.py.

Part 1. Three Ways to Talk

Three communication patterns. Publish and subscribe puts a broker in the middle, and the middle is what lets you add a logger, a dashboard or a second robot without touching the sensor’s code.

That freedom has a price: the broker is a single point of failure, a message can have zero listeners and nobody finds out, and there is no built-in “reply to this request”. Later weeks build a request-and-answer convention out of two topics, a command and an acknowledgement, precisely because the protocol does not give you one.

Part 2. The Pieces

  • Broker. The server that receives every message and forwards it to the clients that asked. Yours is Mosquitto on the class Raspberry Pi.
  • Client. Your Pico, your laptop script, the instructor’s robot. Each has a client id that must be unique: if two clients connect with the same id the broker disconnects the first, which can cause a baffling cycle of reconnects.
  • Topic. A text path such as lab/jsmith/tele/imu, with / between levels. Topics are not created or declared; they exist the moment someone publishes to them.
  • Payload. The bytes of the message, up to the broker’s limit. MQTT does not care what is in them. We use JSON.
  • Subscription. A filter that is matched against topics of published messages. A filter may contain wildcards (next lesson).
The packets you will meet. There are fourteen in the full protocol, but a sensor node uses these six. The sizes are small on purpose: MQTT’s fixed header is only two bytes.

Part 3. A First Subscriber and a First Publisher

net.py only publishes. To receive, a client subscribes to a filter and sets a callback, a function the library calls when a matching message arrives. umqtt.simple calls the callback from inside check_msg(), which looks at the network socket and returns immediately if nothing has arrived. That makes it safe to call every pass of a cooperative loop. Here is a subscriber for the instructor’s robot telemetry, complete with the keepalive ping explained below:

sub.py MicroPython
from umqtt.simple import MQTTClient from time import ticks_ms, ticks_diff, sleep_ms import config inbox = [] def on_msg(topic, payload): inbox.append((topic, payload)) # the callback only remembers: it must be quick c = MQTTClient(b"pico-" + config.MQTT_USER.encode(), config.BROKER, config.BROKER_PORT, config.MQTT_USER, config.MQTT_PASSWORD, keepalive=30) c.set_callback(on_msg) c.connect() c.subscribe(b"robot/tele/#") # the filter, with a wildcard last_ping = ticks_ms() while True: c.check_msg() # returns at once if nothing is waiting if ticks_diff(ticks_ms(), last_ping) > 15000: c.ping() # keepalive 30 s: speak at least every 15 s last_ping = ticks_ms() while inbox: topic, payload = inbox.pop(0) print(topic.decode(), payload.decode()) sleep_ms(10)

Two habits in that program matter more than the rest. The callback does not do any work: it appends to a list and returns, and the main loop handles the message when it is ready. A callback runs in the middle of check_msg(), so slow work there delays every other job just as a long sleep would. And the topic and the payload arrive as bytes, so decode them before comparing with strings (topic.decode()).

pub.py MicroPython
import json from umqtt.simple import MQTTClient import config c = MQTTClient(b"pico-" + config.MQTT_USER.encode(), config.BROKER, config.BROKER_PORT, config.MQTT_USER, config.MQTT_PASSWORD, keepalive=30) c.connect() topic = "lab/%s/evt/hello" % config.MQTT_USER # you may only write under lab/<you>/ c.publish(topic.encode(), json.dumps({"msg": "hi"}).encode()) c.disconnect() # a clean goodbye: the broker does not fire the last will

The disconnect() at the end is a clean goodbye. If the program had simply stopped, the broker would eventually decide the client had died, and fire its last will (a message the client registers in advance for exactly that case; Week 7). Which of the two happened is information the rest of the system can use.

Part 4. Keepalive

A TCP connection can be dead without either side knowing: the Pico loses power, or the router reboots, and nothing tells the broker. MQTT’s answer is the keepalive: the client promises to send something at least once every keepalive seconds, and if it has not, the broker closes the connection after 1.5 times that interval (and fires the last will). When the node has no data to send it sends a PINGREQ, and the broker answers PINGRESP.

Keepalive with a 30-second setting. The node pings every 15 s. Power is lost at 40 s; the last packet the broker heard was the ping at 30 s, and 45 s after that, at 75 s, it closes the connection and publishes the last will. The failure is detected 35 s after it happened.

One trap: umqtt.simple does not send pings for you. If you pass keepalive=30 and never call ping() (or publish something), the broker will disconnect you after 45 seconds of quiet. Node programs that publish at least every few seconds never notice; a node that mostly listens is the one that vanishes. And keepalive=0, the default, switches the whole mechanism off, which net.py did in Unit 1 on purpose: a node that only publishes has no need for a last will.

Part 5. The Broker and Its Three Files

The class hub. Every client talks only to the broker. Three files decide its behavior: the configuration, the list of users and passwords, and the access list. Change any of them and restart (or reload) the service.

The class broker is Mosquitto, a small, open-source MQTT broker running on the instructor’s Raspberry Pi. It reads its configuration once at start-up and from then on does nothing but accept connections and move messages. It stores nothing except retained messages (Week 7). Three files decide its behavior. The configuration says how to run:

broker.conf Config
listener 1883 # without this, Mosquitto 2.x accepts connections from this machine only allow_anonymous false # everyone must log in password_file passwd # who you are acl_file acl # what you may touch

Two lines deserve attention. Since version 2.0 Mosquitto will not accept connections from other machines unless you declare a listener, a deliberate default meant to stop accidental exposure. And allow_anonymous false forces a login: without it, anybody who can reach the port can publish to anything. The password file holds each user name with a salted hash of the password, never the password itself, and is managed with the mosquitto_passwd tool.

Part 6. The Access List

The third file says what each logged-in user may do. Lines starting with pattern apply to every user, with %u replaced by the user’s name; lines under a user heading apply to that user alone. This is the class access list:

acl Config
# /etc/mosquitto/acl # The instructor can do anything. user instructor topic readwrite # # Everyone else (patterns apply to every logged-in user; %u is the user name): pattern write lab/%u/# # write only inside your own subtree pattern read lab/# # read everyone's data pattern read robot/# # read the instructor's robot
What the access list above allows for the user jsmith. The most important property is the second row: a publish that the ACL denies is not an error the client sees. The message simply never arrives.

That last point causes more lost afternoons than any other. With MQTT 3.1.1, the version umqtt speaks, the broker has no way to say “not authorised” to a publisher, so it quietly discards the message (it may even acknowledge it at QoS 1). The same applies to a subscription to a forbidden topic: you are subscribed, and you will hear nothing. The only evidence is a message that never shows up at a subscriber. When a publish does not arrive, check the topic’s spelling against the access list before you debug your code.

Part 7. A Broker on Your Own Laptop

The class broker is only there in class. To test at home, run the same program on your own laptop. Your laptop becomes your private sandbox broker; the Pi stays the class hub. Nothing on the Pico changes except the address it connects to. Installing takes one command (Lab 5 walks through the rest):

install Shell
# macOS (Homebrew) brew install mosquitto # Windows: run the installer from mosquitto.org, then work in a terminal opened # in the Mosquitto folder (usually C:\Program Files\mosquitto) # Linux (Debian or Ubuntu) sudo apt install mosquitto mosquitto-clients

To move between the two brokers without editing several lines each time, give config.py both sets of settings and a single switch. The names at the bottom are the same ones net.py already reads, so nothing else changes:

config.py MicroPython
# config.py -- your own settings. Never share this file or put it online. WHERE = "class" # "class" or "home": the only line you change WIFI = { "class": ("class-network-name", "wifi-password"), "home": ("my-home-wifi", "my-home-password"), } BROKERS = { # address, user name, password "class": ("192.168.1.50", "jsmith", "your-broker-password"), # the class Raspberry Pi "home": ("192.168.0.23", "jsmith", "your-laptop-password"), # your laptop running Mosquitto } WIFI_SSID, WIFI_PASSWORD = WIFI[WHERE] BROKER, MQTT_USER, MQTT_PASSWORD = BROKERS[WHERE] BROKER_PORT = 1883

When the Pico cannot reach your laptop broker, it is almost always one of four things:

  1. No listener 1883 line. Mosquitto then answers only programs on the laptop itself, so mosquitto_sub on the laptop works while the Pico gets NO BROKER.
  2. The firewall. Your laptop’s firewall may block port 1883. Allow Mosquitto on private networks (never on public ones).
  3. A changed address. Your laptop’s address can change when it rejoins the WiFi. Check it (ipconfig on Windows, ipconfig getifaddr en0 on a Mac, ip addr on Linux) and update the home line.
  4. The network keeps devices apart. Many campus and guest networks stop devices from talking directly to each other. A laptop broker works on your home WiFi or a phone hotspot; in class, use the class Pi.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Ping Interval

The promise is one packet every 20 s. The broker waits 1.5 × 20 = 30 s of silence before it drops the connection. Ping at half the keepalive, every 10 s, so that one lost or late ping does not trigger a false death.

Exercise 2: Read the ACL

(a) yes: it is inside lab/bob/. (b) no, silently dropped: only lab/bob/ is writable. (c) yes: everything under lab/ is readable. (d) The subscription is accepted, but he only receives messages on topics he may read: lab/ and robot/. (e) no: robot/ is read-only for students.

Intermediate

Exercise 3: Missed It

A receives only the t = 12 s message: a subscription only sees messages published after it exists, and the broker keeps no history. If the t = 5 s message had been retained, the broker would store it and deliver it to A the moment A subscribed at t = 10 s, so A would receive both. That is how a late arrival learns the current state, covered in the QoS lesson.

Exercise 4: Why Hash?

It protects against someone who reads the file (a stolen SD card, a backup) learning the passwords. It does not protect passwords on the wire: with listener 1883 and no TLS, the CONNECT packet carries the user name and password as plain text, so anyone who can capture traffic on the network sees them. That is acceptable on a private classroom network and is why config.py must never hold a password that you also use anywhere else.

Advanced

Exercise 5: Diagnose

First, the user name in the topic: the node’s MQTT user may be jsmith2 while the topic says jsmith, so the ACL silently drops every message. Second, the topic itself: a typo, a leading slash (/lab/... is a different topic), or capitals. Third, a subscriber problem specific to this student’s node: the callback never runs because check_msg() is not called, or the client id collides with another and the first is being kicked off (the log will say “already connected”). The broker log and mosquitto_sub -d separate these quickly.

Paper Practice: Answers

Recall

P1. Publish and Subscribe

Senders and receivers do not know about each other, so a logger, dashboard or second robot can be added without touching the sender. Costs: the broker is a single point of failure; a message can have no listeners and nobody finds out; there is no built-in reply.

P2. Client Id

The broker disconnects the first one. If both keep reconnecting they knock each other off in a cycle.

P3. Clean Goodbye

A clean disconnect tells the broker the client left on purpose, so its last will is not published. A power cut leaves the connection silent; after 1.5 keepalives (or a broken TCP connection) the broker decides the client died and publishes its will.

P4. Callbacks

From inside check_msg(), when a matching message has arrived. It runs in the middle of the library's receive code; slow work there delays every other job and can break the connection. Store the message and return.

P5. Three Files

The configuration file (listeners, login rules, persistence, limits, logging), the password file (users and their hashed passwords) and the access-list file (which topics each user may read and write).

P6. Listener Line

It accepts connections only from the same machine (localhost), so no Pico or laptop on the network can connect.

P7. Silent Denial

Nothing: no error. The broker discards the message (and may even acknowledge it at QoS 1). The only evidence is a subscriber that never receives it (and, on a broker you run yourself with -v, the broker's own output).

Apply

P8. Detection Delay

1.5 × 20 = 30 s after the last packet: at t = 50 s, 23 s after the failure.

P9. Read the ACL

(a) Yes. (b) No (not her subtree). (c) Yes (everyone may read lab/#). (d) No, unless a separate line grants her write access to robot/r1/cmd/#.

Analyze and Design

P10. The Silent Listener

umqtt.simple does not send pings by itself. With nothing published, the broker hears nothing for 1.5 × 30 s and closes the connection. Call ping() every keepalive/2 (or publish something) inside the loop.

P11. Bytes Versus Strings

The topic arrives as bytes (b'lab/amy/cmd/stop'), which never equals a string. Decode it (topic.decode()) or compare with a bytes literal.

P12. Never Arrives

A topic typo (wrong case, a leading slash, a different user name in the path); the access list denying the publish (writing outside your own subtree); publishing to a topic your subscription does not match; the program not actually reaching the publish line. Check spelling against the ACL first.
