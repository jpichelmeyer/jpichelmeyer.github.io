This lesson covers surviving the network. You catalogue what fails, replace a fixed retry with exponential backoff and jitter after seeing why synchronised retries are a stampede, deal with late, missing and duplicate messages after an outage, and use the hardware watchdog to restart a node that has hung without trapping it in a reboot loop.

A node on WiFi will lose its network. Not rarely, and not only in tests: access points restart, a microwave oven runs, someone carries the robot into a lift, the broker is updated at lunchtime. A prototype that works only while everything is fine is a demonstration; a node that notices, recovers and does not make things worse is a product. This lesson is about the second kind: what fails, how a node decides to try again, how not to flatten the broker when two dozen nodes try at once, how to deal with the messages that arrive late or twice afterwards, and how a watchdog rescues a node that has hung.

Part 1. What Fails

A catalogue of network and node failures. The first rule of recovery is that the control loop does not stop while the network is down: the robot keeps doing its job locally, and the network layer works in the background.

Part 2. Trying Again, Politely

net.py retries a failed connection every retry_s seconds, 15 by default. That is simple, and it has two weaknesses: it is slow to recover from a short glitch (up to a 15-second wait for a link that returned after one second), and it is synchronised when many nodes fail together. The usual fix is exponential backoff with jitter: wait a short time after the first failure, double the wait after each further failure up to a ceiling, and add a random spread so that nodes do not retry in step.

backoff.py MicroPython
import random class Backoff: """Waits that double after every failure, with a ceiling and a random jitter.""" def __init__(self, first_ms=1000, cap_ms=30000, jitter=0.25): self.first, self.cap, self.jitter = first_ms, cap_ms, jitter self.fails = 0 def next_ms(self): self.fails += 1 wait = min(self.cap, self.first * (2 ** (self.fails - 1))) return int(wait * (1 + self.jitter * (2 * random.random() - 1))) # +/- 25 % def reset(self): self.fails = 0
resilient.py MicroPython
# resilient.py -- a Hub that backs off instead of hammering a dead broker import hub from backoff import Backoff class ResilientHub(hub.Hub): def __init__(self, **kw): super().__init__(**kw) self.backoff = Backoff() self.retry_ms = 0 # the first attempt is immediate self.attempts = 0 def connect(self): self.attempts += 1 ok = super().connect() if ok: self.backoff.reset() self.retry_ms = self.backoff.first # after a drop, wait a moment before the next try else: self.retry_ms = self.backoff.next_ms() return ok
The backoff schedule used by ResilientHub: 1, 2, 4, 8, 16 then 30 seconds, each randomized by plus or minus a quarter.

What does each choice buy? Two experiments, both simulated, answer it. First, one node and a broker that disappears for a while (12 random outages for each length, measured on the test broker):

One node, one broker. A short fixed delay recovers fastest and spends the most attempts, which costs battery and log lines; backoff spends the fewest and recovers slowest. For one robot on a bench the fast fixed retry is fine. The trade changes when many nodes share a broker.

Second, the herd. Twenty-four nodes lose the broker at the same instant (a restart) and all use the same retry timer. The broker can accept one new connection every 250 ms. Because their timers are in step, every round of retries arrives at the same moment and only one is accepted; the rest fail and retry together again. Randomising the delay breaks the pattern. The simulation below is deliberately harsh, a worst case of perfect synchrony, but the effect is real:

herd.py Python
# herd.py: 24 clients lose the broker together. It accepts one new connection per 250 ms (4 a second). import random, heapq def wait(policy, fails): if policy == "fixed": return 2000 if policy == "jitter": return int(2000 * (1 + 0.25 * (2 * random.random() - 1))) # the same, but randomized base = min(30000, 1000 * 2 ** fails) # backoff: 1, 2, 4, 8 ... capped at 30 s return int(base * (1 + 0.25 * (2 * random.random() - 1))) # with +/- 25 % jitter def run(policy, clients=24, service_ms=250, seed=1): random.seed(seed) events = [(wait(policy, 0), c, 0) for c in range(clients)] # (time, client, failures so far) heapq.heapify(events) last_accept, done, attempts = -service_ms, 0, [] while done < clients: t, c, fails = heapq.heappop(events) attempts.append(t) if t - last_accept >= service_ms: last_accept, done, finished = t, done + 1, t else: heapq.heappush(events, (t + wait(policy, fails + 1), c, fails + 1)) busiest = max(sum(1 for a in attempts if t0 <= a < t0 + 1000) for t0 in attempts) return finished / 1000, len(attempts), busiest for policy in ("fixed", "jitter", "backoff"): rs = [run(policy, seed=s) for s in range(50)] print("%-8s all back after %5.1f s | %5.1f attempts in total | %4.1f in the busiest second" % ( policy, sum(r[0] for r in rs) / 50, sum(r[1] for r in rs) / 50, sum(r[2] for r in rs) / 50))
The herd simulation, averaged over 50 runs. Jitter is what rescues the stampede: the same timer with a random spread recovers in a quarter of the time and with a quarter of the attempts. Backoff adds a ceiling on attempts for long outages, at the price of slower recovery from short ones.

Put together: use a short first wait, a modest ceiling (10 to 30 s), and always jitter. A robot that must recover quickly can lower the ceiling; a battery sensor that sleeps most of the time can raise it.

Part 3. What Arrives Afterwards

While the link was down, net.py queued the node’s messages (40 of them at most; Lab 3 measured how long that lasts). When the link returns they leave the board oldest first, five per call, so they arrive at the receiver late and in a burst, each carrying its original time t. The receiver sees three new effects, and should deal with each deliberately.

  • Gaps. If the queue overflowed, the oldest messages were dropped. The seq numbers show exactly how many (the find_gaps function of Lab 3). Never infer loss from silence alone; read seq.
  • Lateness. A message that arrives now but was made ten seconds ago is history, not the current state. Anything that acts (a control loop, a collision check) must look at t or the age, not just at the arrival.
  • Duplicates. After a reconnect, a retry can deliver a message the receiver already has (an ack was lost). The receiver can recognise a repeat by the pair of seq and t, and ignore it.
dedupe.py MicroPython
class Dedupe: """Drops a message already seen. Messages are identified by (topic, seq, t), so a node that reboots and starts counting again from 1 is not mistaken for a repeat.""" def __init__(self, keep=16): self.keep = keep self.recent = [] def seen(self, topic, d): key = (topic, d["seq"], d["t"]) if key in self.recent: return True self.recent.append(key) if len(self.recent) > self.keep: self.recent.pop(0) return False

The key is (topic, seq, t) and not seq alone. A node that reboots restarts its sequence at 1, and a check that only looks at seq would discard its first messages after every reset as “old”. Keying on time as well keeps a rebooted node distinct from a repeated message.

Part 4. The Watchdog

A program can fail by stopping, in a way no exception reports: a blocking call that never returns, a loop that spins, a library state that locks up. Software cannot always rescue itself from that, so the RP2040 has a hardware watchdog timer: a counter that counts down and resets the chip when it reaches zero, unless the program keeps feeding it. A healthy program feeds it every pass of the loop; a hung one does not, and is restarted.

watchdog.py MicroPython
from machine import WDT, reset_cause, WDT_RESET from time import ticks_ms, ticks_diff if reset_cause() == WDT_RESET: print("last reset was the watchdog: something hung") wdt = WDT(timeout=8000) # the longest the Pico allows is about 8.3 s; it cannot be stopped last_pass = ticks_ms() def healthy(now, limit_ms=2000): """The loop is healthy if it came round recently. Add checks of your own here.""" return ticks_diff(now, last_pass) < limit_ms while True: now = ticks_ms() last_pass = now # ... poll the hub, run the control loop, read sensors ... if healthy(now): wdt.feed() # only a healthy loop earns more time
How a watchdog saves a hung node. The restart is rough (RAM is lost), which is why state persistence is the next lesson, but a robot that restarts is better than one that sits there with its motor on. (With a motor, the restart also clears the driver inputs.)
  • It cannot be stopped. Once started, a WDT runs until the chip is reset. While developing, start it only in the final main.py; if you start it from Thonny the board will reset eight seconds after you stop the program.
  • The maximum is about 8.3 seconds. Every blocking call in your loop must be shorter than that, including net.py’s WiFi connect, whose default timeout is 8 s. Set it to 5 (Link(wifi_timeout_s=5)), or feed the watchdog inside any long wait.
  • Feed only when the loop is healthy. wdt.feed() placed carelessly (in a timer interrupt, say) keeps feeding a dead program. The healthy() check is where you decide what “healthy” means: the loop came round, the sensor was read recently, the control output is finite.
  • Find out why you restarted. reset_cause() returns WDT_RESET after a watchdog restart. Count them and publish the count: a node that restarts twice an hour is telling you something.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Backoff Schedule

1, 2, 4, 8, 16, 30 (the cap), 30 seconds. The third wait is 4 s ± 25 %, so between 3 and 5 seconds. The sample run of Backoff in the lesson’s test printed 817, 2347, 4527 and 7020 ms for the first four, each inside its range.

Exercise 2: How Many Tries?

Backoff: attempts at about 1, 3, 7, 15, 31 s, and then every 30 s: the first five take 31 s, and the remaining 269 s hold about 9 more, so about 14 to 16 attempts (the simulation averaged 15.8). Fixed 5 s: 300 / 5 = 60 (simulated 62). The backoff node spends a quarter of the effort.

Intermediate

Exercise 3: Will It Reset?

The reconnect attempt blocks for up to 8 s. The watchdog has 8 s, and the node also spent time in the rest of the loop, so the watchdog fires and the board resets every time the network is down: a reboot loop that is worse than the original failure. Fix one: shorten the blocking call (wifi_timeout_s=3) so every pass stays well inside the limit. Fix two: feed the watchdog from inside the wait (in _wifi_up’s loop, between the short sleeps), so a long wait is allowed while the program is plainly still running. The first is simpler and keeps the control loop responsive too.

test_dedupe.py MicroPython
d = Dedupe() msgs = [("lab/a/tele/imu", 1, 100), ("lab/a/tele/imu", 2, 200), ("lab/a/tele/imu", 2, 200), ("lab/a/tele/imu", 1, 90), ("lab/a/tele/imu", 3, 300), ("lab/b/tele/imu", 2, 200)] print([d.seen(t, {"seq": s, "t": ms}) for t, s, ms in msgs]) # [False, False, True, False, False, False]

Only the third is a repeat (the same topic, seq and t as the second). The fourth has seq 1 and a smaller time: it is not a repeat of anything seen, and a counter that starts over together with a clock that starts over means the node rebooted. The last is on a different topic, so its identical numbers mean nothing. The Dedupe window is only 16 entries, so it protects against retransmissions in the last few messages, not against a very old duplicate; a bigger window costs RAM.
