This lesson covers keeping a robot safe and useful when the network fails. You catalogue what fails, replace a fixed retry with exponential backoff and jitter, handle the burst of messages that arrives afterwards so that a stop is never stuck behind telemetry, use the hardware watchdog to restart a node that has hung, and decide what the node should remember across that restart and what it must forget.

SAM lens. The first rule here is SAM's: the network is part of the environment, not part of the agent, so the Perceptor, Decider and Actuator keep working when it disappears. The watchdog restarts an agent whose Decider has hung, and its Memory across the restart keeps what describes the agent and forgets anything that would make the Actuator move.

A node on WiFi will lose its network. Not rarely, and not only in tests: access points restart, a microwave oven runs, someone carries the robot into a lift, the broker is updated at lunchtime. A prototype that works only while everything is fine is a demonstration; a node that notices, recovers and does not make things worse is a product. This lesson is about the second kind: what fails, how a node decides to try again, how it tries again without flattening the broker, how it handles the burst of messages afterwards, how a watchdog rescues a node that has hung, and what it should remember when it restarts.

Part 1. What Fails

A catalogue of network and node failures. The first rule of recovery is that the control loop does not stop while the network is down: the robot keeps doing its job locally, and the network layer works in the background.

Part 2. Trying Again, Politely

net.py retries a failed connection every retry_s seconds, 15 by default. That is simple, and it has two weaknesses: it is slow to recover from a short glitch (up to a 15-second wait for a link that returned after one second), and it is synchronised when many nodes fail together. The usual fix is exponential backoff with jitter: wait a short time after the first failure, double the wait after each further failure up to a ceiling, and add a random spread so that nodes do not retry in step.

backoff.py MicroPython
import random class Backoff: """Waits that double after every failure, with a ceiling and a random jitter.""" def __init__(self, first_ms=1000, cap_ms=30000, jitter=0.25): self.first, self.cap, self.jitter = first_ms, cap_ms, jitter self.fails = 0 def next_ms(self): self.fails += 1 wait = min(self.cap, self.first * (2 ** (self.fails - 1))) return int(wait * (1 + self.jitter * (2 * random.random() - 1))) # +/- 25 % def reset(self): self.fails = 0
resilient.py MicroPython
# resilient.py -- a Hub that backs off instead of hammering a dead broker import hub from backoff import Backoff class ResilientHub(hub.Hub): def __init__(self, **kw): super().__init__(**kw) self.backoff = Backoff() self.retry_ms = 0 # the first attempt is immediate self.attempts = 0 def connect(self): self.attempts += 1 ok = super().connect() if ok: self.backoff.reset() self.retry_ms = self.backoff.first # after a drop, wait a moment before the next try else: self.retry_ms = self.backoff.next_ms() return ok
The backoff schedule used by ResilientHub: 1, 2, 4, 8, 16 then 30 seconds, each randomized by plus or minus a quarter.

Why the random spread? Picture the whole class losing the broker at the same instant, when the instructor restarts it. If every node retries on the same timer, every round of retries arrives at the same moment, the broker can accept only a few, and the rest fail together and retry together again: a stampede. A random spread of a quarter either way scatters the attempts, and everyone is back in a fraction of the time.

Put together: use a short first wait, a modest ceiling (10 to 30 s), and always jitter. A robot that must recover quickly can lower the ceiling; a battery sensor that sleeps most of the time can raise it.

Part 3. Commands First

When the link comes back, two bursts happen at once. Outgoing, net.py’s queue empties: the saved messages leave oldest first, a few per pass, each still carrying its original seq and t, so a receiver must judge them by age and sequence number, never by when they arrived. Incoming, the broker delivers whatever matched your subscriptions, including every retained message, all together. The node has to survive that without its control loop stalling and without losing the one message that matters most: a stop.

Hub is already built for the incoming side. Three habits make it work, and you need them in any program that receives:

  1. Catch, do not think. The callback runs inside check_msg(), in the middle of the library’s own receive code. It only appends the message to the inbox and returns. Anything slow there (parsing JSON, printing, publishing, moving a servo) delays the next receive and can break the connection.
  2. Two bounds. The inbox holds at most inbox_max messages, which protects memory (an unbounded list fed by a fast publisher will crash the node), and poll() handles at most five per pass, which protects the control loop. Every message the inbox has to throw away is counted in rx_dropped. Publish that number: silent loss cannot be diagnosed.
  3. Subscribe to little. A first-in, first-out inbox treats every message the same, so a stop that arrives behind 200 pieces of telemetry waits its turn: at five messages per 20 ms pass that is 0.8 s, long enough for a robot to hit something. The simplest cure is a robot node that subscribes only to its own commands, so nothing can queue in front of them. A node that must also hear other robots should keep only the newest message from each of their topics, because an old reading is worthless once a newer one has arrived.

Part 4. The Watchdog

A program can fail by stopping, in a way no exception reports: a blocking call that never returns, a loop that spins, a library state that locks up. Software cannot always rescue itself from that, so the RP2040 has a hardware watchdog timer: a counter that counts down and resets the chip when it reaches zero, unless the program keeps feeding it. A healthy program feeds it every pass of the loop; a hung one does not, and is restarted.

watchdog.py MicroPython
from machine import WDT, reset_cause, WDT_RESET from time import ticks_ms, ticks_diff if reset_cause() == WDT_RESET: print("last reset was the watchdog: something hung") wdt = WDT(timeout=8000) # the longest the Pico allows is about 8.3 s; it cannot be stopped last_pass = ticks_ms() def healthy(now, limit_ms=2000): """The loop is healthy if it came round recently. Add checks of your own here.""" return ticks_diff(now, last_pass) < limit_ms while True: now = ticks_ms() last_pass = now # ... poll the hub, run the control loop, read sensors ... if healthy(now): wdt.feed() # only a healthy loop earns more time
How a watchdog saves a hung node. The restart is rough (RAM is lost), which is why the next two parts are about what to keep, but a robot that restarts is better than one that sits there with its motor on. (With a motor, the restart also clears the driver inputs.)
  • It cannot be stopped. Once started, a WDT runs until the chip is reset. While developing, start it only in the final main.py; if you start it from Thonny the board will reset eight seconds after you stop the program.
  • The maximum is about 8.3 seconds. Every blocking call in your loop must be shorter than that, including net.py’s WiFi connect, whose default timeout is 8 s. Set it to 5 (Link(wifi_timeout_s=5)), or feed the watchdog inside any long wait.
  • Feed only when the loop is healthy. wdt.feed() placed carelessly (in a timer interrupt, say) keeps feeding a dead program. The healthy() check is where you decide what “healthy” means: the loop came round, the sensor was read recently, the control output is finite.
  • Find out why you restarted. reset_cause() returns WDT_RESET after a watchdog restart. Count them and publish the count: a node that restarts twice an hour is telling you something.

Part 5. What to Remember After a Restart

When a node restarts, RAM is gone: the mode, the calibration offsets, the count of resets, the position the servo was in. A restart is not an exotic event. The watchdog causes one on purpose, a brownout causes one by accident, and every power-up is one. So decide in advance what the node keeps, and just as important, what it deliberately forgets.

A decision table for state. The test for each item is “what is the cost of being wrong?” A stale calibration is a nuisance; a stale motor command moves a robot that nobody expects to move.

The rule that follows: restore what is descriptive (it describes the node), and re-derive what is active (it makes the node do something). After a watchdog reset especially, the node should wake up in a safe, quiet state, announce itself, and wait to be told what to do.

The Pico keeps files in flash memory. Flash survives power loss, but it has two properties that RAM does not. It wears out: each block can be erased and rewritten only a limited number of times (on the order of tens of thousands to a hundred thousand, and the file system spreads writes around, which helps but does not remove the limit). And a write takes real time, tens of milliseconds, during which your control loop is not running and the watchdog is counting. The consequence is a habit: write rarely, and only when something changed.

state.py MicroPython
# state.py -- remember a little, write rarely import time import store class State: def __init__(self, path, default, min_gap_ms=60000): self.path = path self.data = store.load(path, default) self.min_gap = min_gap_ms self.last = time.ticks_ms() self.dirty = False self.writes = 0 def set(self, key, value): if self.data.get(key) != value: self.data[key] = value self.dirty = True def tick(self, force=False): now = time.ticks_ms() if self.dirty and (force or time.ticks_diff(now, self.last) >= self.min_gap): store.save(self.path, self.data) self.last = now self.dirty = False self.writes += 1

State writes only when a value really changed (set compares) and not more often than min_gap_ms. A simulated hour in which one value changes every ten seconds (360 changes) produced 60 writes with a one-minute gap, instead of 360, and the last value was still saved by the next write. Writing a sensor reading to flash every second would be 86,400 writes a day.

Part 6. Saving Safely and Starting Quietly

Suppose power fails while state.json is being rewritten. The file is half old, half new, or empty, and the next boot finds invalid JSON. The standard defence is the atomic write: never modify the real file in place. Write the new content to a temporary file, make sure it is complete, then rename it over the old one. A rename is one small operation, so the file is always either the complete old version or the complete new version.

store.py MicroPython
# store.py -- save a small dict so that a reset can never leave half a file import json, os def save(path, data): tmp = path + ".tmp" with open(tmp, "w") as f: f.write(json.dumps(data)) f.flush() try: os.remove(path) except OSError: pass os.rename(tmp, path) def load(path, default): for p in (path, path + ".tmp"): try: with open(p) as f: return json.loads(f.read()) except (OSError, ValueError): pass return default
The four steps of an atomic save. The only dangerous gap is between steps 3 and 4, and load covers it by reading the temporary file as a fallback.

machine.reset_cause() tells the program why it started. Use it to choose the starting behaviour: after a power-on, restore the saved mode; after a watchdog reset, count it, and start idle with every output off.

main.py (start of) MicroPython
# boot.py part of main.py -- decide how to start from machine import reset_cause, PWRON_RESET, WDT_RESET import state st = state.State("state.json", {"resets": 0, "mode": "IDLE", "pan": 0}) cause = reset_cause() if cause == WDT_RESET: st.set("resets", st.data.get("resets", 0) + 1) st.set("mode", "IDLE") # never resume a motion after a hang st.set("pan", 0) st.tick(force=True) print("start:", st.data, "cause:", cause)

That script, run in the test environment with a saved state of mode BUSY, pan 40 and a watchdog cause, printed {'resets': 1, 'mode': 'IDLE', 'pan': 0}: the reset was counted, and the node did not resume the motion that was in progress when it hung.

Exercises

Practice problems in three tiers. Do each on paper or on your own board first, and only then open its solution below. Many problems have more than one correct answer; if yours behaves the same way, it is right even if it looks different.

Warm Up

Exercise 1: Backoff Schedule. With first wait 1 s, cap 30 s and no jitter, list the waits after failures 1 to 7. With ±25 % jitter, within what range is the third wait?

Exercise 2: Why Not Print? A student prints each received message inside the callback “to see what arrives”, and the node starts disconnecting from the broker whenever traffic rises. Give the likely reason, and say where the print belongs.

Intermediate

Exercise 3: Will It Reset? A node starts the watchdog at 8,000 ms. In its loop it calls net.publish, which may try to reconnect with the default 8-second WiFi timeout, then calls wdt.feed(). What goes wrong when the access point is off, and how do you fix it two different ways?

Exercise 4: Keep or Forget. For a robot with a servo, a motor, a filtered range reading, a calibration offset for the IMU, and a count of reboots, say for each whether it should be restored after a watchdog reset.

Advanced

Exercise 5: Where Is the Gap? The save function removes the old file and then renames the temporary file. Suppose the board loses power right after the os.remove. Walk through the next boot. Which file does load use, and is anything lost?

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Backoff Schedule

1, 2, 4, 8, 16, 30 (the cap), 30 seconds. The third wait is 4 s ± 25 %, so between 3 and 5 seconds. The sample run of Backoff in the lesson’s test printed 817, 2347, 4527 and 7020 ms for the first four, each inside its range.

Exercise 2: Why Not Print?

The callback runs inside check_msg(), so every print (slow over USB) delays the library from reading the socket and from sending its keepalive ping. Under load the delay exceeds the keepalive allowance and the broker drops the client. Move the print to the handler, after the queue, and count messages rather than printing every one.

Intermediate

Exercise 3: Will It Reset?

The reconnect attempt blocks for up to 8 s. The watchdog has 8 s, and the node also spent time in the rest of the loop, so the watchdog fires and the board resets every time the network is down: a reboot loop that is worse than the original failure. Fix one: shorten the blocking call (wifi_timeout_s=3) so every pass stays well inside the limit. Fix two: feed the watchdog from inside the wait (in _wifi_up’s loop, between the short sleeps), so a long wait is allowed while the program is plainly still running. The first is simpler and keeps the control loop responsive too.

Exercise 4: Keep or Forget

Restore: the IMU offset (descriptive, costly to remeasure) and the reboot count (a diagnosis). Forget: the motor and servo targets (restart with outputs off) and the filtered reading (a few seconds of data; the filter refills itself).

Advanced

Exercise 5: Where Is the Gap?

After the remove, state.json does not exist but state.json.tmp is complete (it was flushed in step 2). load first tries state.json, which raises OSError, then tries state.json.tmp and returns the new data. Nothing is lost. If power had failed during step 1, state.json would still be the complete old copy, and the half-written .tmp would be ignored. The next successful save overwrites the leftover .tmp.

Paper Practice: Answers

Recall

P1. First Rule

The control loop does not stop while the network is down: the robot keeps doing its job locally, and the network layer recovers in the background.

P2. Backoff with Jitter

Wait a short time after the first failure and double the wait after each further failure, up to a ceiling. Randomise each wait (for example by ±25 %) so that many nodes do not retry in step.

P3. Catch, Do Not Think

Store the message in a bounded queue and return. Never parse heavily, print, publish, drive hardware or block inside it.

P4. Watchdog Facts

Once started it cannot be stopped until the chip resets; its maximum timeout is about 8.3 s, so every blocking call must be shorter; it should be fed only when the loop is healthy; reset_cause() reports WDT_RESET afterwards. Any three.

P5. Descriptive or Active

Restore what is descriptive (it describes the node: calibration, counters); re-derive what is active (it makes the node do something: modes, motor commands) from fresh commands.

Apply

P6. Schedule

Waits before attempts 2 to 6: 1 + 2 + 4 + 8 + 16 = 31 s. Attempts 7 and 8 add 30 + 30: 91 s.

P7. Stop Behind Telemetry

After 200 / 5 = 40 passes: about 800 ms later (plus its own pass). If the node subscribes only to its own commands, nothing can queue in front of the stop and it is handled on the next pass.

P8. Write Count

360; 60; 12.

Analyze and Design

P9. Healthy Feeding

The interrupt keeps firing even when the main loop is hung, so the watchdog never resets a dead program. Feed at the end of a pass of the main loop, only when a healthy() check passes (loop came round, sensor read recently, outputs sane).

P10. Too Long a Wait

The connect can outlast the watchdog, so the board resets during a reconnect, possibly in a loop. Set wifi_timeout_s=5, or feed the watchdog inside the wait.

P11. What to Restore

Restore (a) and (b): they describe the node and are harmless if slightly stale. Do not restore (c) or (d): they make the node act, and after a hang the node should start idle and wait for fresh commands.

P12. Atomic Save

Write the new content to state.json.tmp, make sure it is complete (close/flush), then rename it over state.json. Until the rename the old file is intact; after it the new one is; a loader that falls back to the .tmp covers the instant between. The file is never half old, half new.

  2. Describe exponential backoff with jitter, and why the jitter matters when many nodes fail together.
  3. Keep a callback minimal, bound the inbox, count drops, and explain why a robot node subscribes only to what it needs.
  4. Use the watchdog safely: feed it only when the loop is healthy, and keep every blocking call shorter than its timeout.
  5. Decide what to restore after a restart, write state rarely and atomically, and start idle after a watchdog reset.
