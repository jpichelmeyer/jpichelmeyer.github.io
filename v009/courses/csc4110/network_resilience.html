In Unit 1 the network was assumed to work. In real deployments it fails constantly and briefly: the router restarts, someone walks past the antenna, the broker is updated. A resilient device is not one that never fails but one that recovers by itself, quickly, without making things worse.

Part 1. Where It Can Fail

Where a connection can fail, and how each failure shows up on the Pico. A robust program checks all four, because one fixed assumption ("WiFi is fine") hides the rest.

There are four places, and the Pico cannot tell which has failed by waiting. So the recovery code checks them in order from the bottom: is WiFi up? Can I reach the broker? Is the connection still alive? That also tells you what to report.

Part 2. Reconnect Politely

The naive loop retries instantly and forever. That drains power, and if the broker is restarting it can keep hitting it before it is ready. Wait a little longer after each failure (exponential backoff), up to a cap:

Waiting longer after each failed attempt (exponential backoff). Retrying every second forever wastes power and hammers a broker that is still starting; doubling the wait up to a cap is gentler.
main.py MicroPython
import random def backoff(attempt, base=1, cap=30): delay = min(cap, base * 2 ** attempt) return delay / 2 + random.random() * delay / 2 # half fixed, half random def connect_broker(): attempt = 0 while True: try: if not wlan.isconnected(): connect_wifi() client.connect() client.subscribe(b"lab/pico01/cmd/#") # sessions may be clean: re-subscribe client.publish(ONLINE, b"online", retain=True) return except OSError as e: print("connect failed:", e) time.sleep(backoff(attempt)) attempt += 1

The random part, jitter, matters when many devices lose the broker together. Without it they all retry at the same instants and hit the broker as a crowd:

Why add randomness. If thirty Picos lose the broker together and all retry on the same schedule, they hit it at the same instant every time. A little random jitter spreads them out.

Part 3. Detect, Then Recover

A dead connection often reveals itself only when you use it: publish() or check_msg() raises OSError. Catch it in the main loop, and send control to the reconnect function:

main.py MicroPython
while True: try: client.check_msg() if time_to_publish(): client.publish(TELE, payload) keepalive.tick() except OSError: connect_broker() # blocks, with backoff, until the link is back

The library umqtt.robust wraps this idea for you (install it with Thonny’s package manager or mip). Its client reconnects with a growing delay and retries the publish. It does not know what you were subscribed to or what state you had published, so those steps remain yours:

What umqtt.robust adds. A failed publish triggers a reconnect with a growing delay, then the publish is retried. You still need to re-subscribe and re-publish your state after a reconnect.

Part 4. The Last Resort

Sometimes the program itself hangs: a socket call that never returns, a bug in a loop. A watchdog timer restarts the board if the program stops proving it is alive. On the RP2040 the longest timeout is about eight seconds:

main.py MicroPython
from machine import WDT wdt = WDT(timeout=8000) # reboot if not fed within 8 s while True: ... # one pass of the loop wdt.feed() # "still alive"

Pair the watchdog with persisted state from the previous lesson: a watchdog reboot is only harmless if the device comes back up knowing what it was doing.

Warm Up

Exercise 1: Backoff Schedule

min(30, 2**attempt) gives 1, 2, 4, 8, 16, 30, 30 seconds. The cap stops the waits growing to minutes; the first few are short so a brief outage is recovered from quickly.

Exercise 2: Why Jitter?

Without jitter all thirty retry at identical times, so the broker receives thirty simultaneous connections after each wait, again and again. With jitter their retries are spread across the interval, so the broker sees a trickle and recovers smoothly.

Intermediate

Exercise 3: A Working Reconnect Loop
main.py MicroPython
def ensure_connected(): attempt = 0 while True: try: if not wlan.isconnected(): connect_wifi() client.ping() # raises OSError if the link is dead return except OSError: try: client.connect() client.subscribe(CMD_TOPIC) client.publish(ONLINE, b"online", retain=True) return except OSError: time.sleep(backoff(attempt)) attempt += 1

Pinging is a cheap way to test a connection you cannot otherwise see. The reconnect branch then redoes everything a fresh session needs: subscribe and re-announce.

Advanced

Exercise 4: Buffer While Away
main.py MicroPython
backlog = [] def publish_reading(payload): backlog.append(payload) if len(backlog) > 20: backlog.pop(0) # drop the oldest try: while backlog: client.publish(TELE, backlog[0]) backlog.pop(0) # only after a successful publish except OSError: connect_broker() # the backlog is sent on the next call

A reading is removed only after its publish succeeds, so a failure leaves it queued. The cap of 20 protects RAM during a long outage, at the cost of losing the oldest readings.
