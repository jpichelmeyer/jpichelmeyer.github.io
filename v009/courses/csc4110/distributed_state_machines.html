This lesson covers machines that run on several boards. You write a machine as a table with timeouts, publish its state retained and remember when you heard each peer, and make two machines agree over a lossy link with retries, repeats that are harmless, a named failure state and safe defaults that need no help from the other side.

In Unit 1 you wrote a state machine as the answer to “what is this board doing now?”. Here several machines run on different boards and each must also answer “and what is the other one doing?”. They cannot look; they can only listen to messages that are late, lost, repeated or stale. This lesson shows how to write a machine as a table that is easy to check, how to make the machine publish its own state so that others can follow it, and how two machines agree on something (a door is open, a lease is held) when the messages between them can be lost.

Part 1. Write the Machine as a Table

A machine written as nested if statements hides what it does not handle. The same machine written as a table of (state, event) to (next state, action) can be read, counted and tested: every combination is either in the table or visibly missing. Timeouts become events too (“after 500 ms in this state, fire timeout”), so the machine has no hidden sleep.

machine.py MicroPython
# machine.py -- a state machine as a table, with timeouts from time import ticks_ms, ticks_diff class Machine: def __init__(self, name, table, start, timeouts=None, actions=None, on_change=None): self.name = name self.table = table # {(state, event): (next_state, action_name or None)} self.state = start self.timeouts = timeouts or {} # {state: (ms, event)}: "after ms in this state, fire event" self.actions = actions or {} # {action_name: function(machine, data)} self.on_change = on_change self.entered = ticks_ms() self.ignored = 0 def fire(self, event, data=None, now=None): now = ticks_ms() if now is None else now step = self.table.get((self.state, event)) if step is None: self.ignored += 1 # an event this state does not expect: ignore, but count return False nxt, action = step if action: self.actions[action](self, data) if nxt != self.state: old, self.state, self.entered = self.state, nxt, now if self.on_change: self.on_change(old, nxt) else: self.entered = now # a self-loop restarts the timeout return True def tick(self, now=None): now = ticks_ms() if now is None else now t = self.timeouts.get(self.state) if t and ticks_diff(now, self.entered) >= t[0]: self.fire(t[1], None, now)

Two choices in fire matter. An event the state does not expect is ignored but counted (ignored): in a network of agents, late and duplicate messages are normal, and crashing on them is a bug, but silence about them is a worse one. And a self-loop (same state) restarts the timeout, which is how a repeated open renews the door’s fail-safe timer.

The requester as a diagram of its table. The retry count is part of the state (ASK1, ASK2, ASK3), so the machine needs no counter variable and every path can be listed.

REQUESTER = { ("IDLE", "want"): ("ASK1", "send_open"), ("ASK1", "ack"): ("HOLD", None), ("ASK1", "timeout"): ("ASK2", "send_open"), # same id: the door ignores a repeat ("ASK2", "ack"): ("HOLD", None), ("ASK2", "timeout"): ("ASK3", "send_open"), ("ASK3", "ack"): ("HOLD", None), ("ASK3", "timeout"): ("FAULT", "send_close"), # give up, and say so ("HOLD", "done"): ("IDLE", "send_close"), ("FAULT", "reset"): ("IDLE", None), } REQ_TIMEOUTS = {"ASK1": (500, "timeout"), "ASK2": (500, "timeout"), "ASK3": (500, "timeout")} DOOR = { ("CLOSED", "open"): ("OPEN", "ack"), ("OPEN", "open"): ("OPEN", "ack"), # a repeat: answer again, do nothing more ("OPEN", "close"): ("CLOSED", "ack"), ("CLOSED", "close"): ("CLOSED", "ack"), ("OPEN", "timeout"): ("CLOSED", None), # nobody renewed it: fail safe } DOOR_TIMEOUTS = {"OPEN": (5000, "timeout")}

Part 2. Telling and Listening

A machine whose state nobody can see is a private matter. Making a state change a message turns the machine into part of the system. Two rules from Unit 2 apply directly. Publish the state retained, so that an agent that joins late learns it at once. And on the listening side, remember not just the last state of each peer but when you heard it, because a retained message is as old as the last change and tells you nothing about whether the peer is still alive.

peers.py MicroPython
# peers.py -- what I last heard about the others, and how old that is from time import ticks_ms, ticks_diff class Peers: def __init__(self, stale_ms=10000): self.stale_ms = stale_ms self.seen = {} # name -> (state, time I heard it) def heard(self, name, state): self.seen[name] = (state, ticks_ms()) def state(self, name): """The last known state, or "UNKNOWN" if never heard or too old.""" s = self.seen.get(name) if s is None or ticks_diff(ticks_ms(), s[1]) > self.stale_ms: return "UNKNOWN" return s[0] def age_ms(self, name): s = self.seen.get(name) return None if s is None else ticks_diff(ticks_ms(), s[1])
glue.py MicroPython
# glue: publish every state change, retained; listen to the others import hub from machine import Machine from peers import Peers h = hub.Hub() h.presence() peers = Peers(stale_ms=10000) def changed(old, new): h.publish("stat/state", {"name": "door", "state": new, "was": old}, retain=True) door = Machine("door", DOOR, "CLOSED", DOOR_TIMEOUTS, {"ack": send_ack}, on_change=changed) def on_peer(topic, payload): d = hub.decode(payload) if d: peers.heard(topic.split("/")[1], d.get("state")) h.on("lab/+/stat/state", on_peer) # everyone's state, retained: late joiners get it at once

Peers.state returns "UNKNOWN" for a peer never heard, or not heard for longer than stale_ms. That third answer is the important one: a machine that plans on a stale “the door is closed” is as wrong as one that has never heard from the door, and it is safer to treat both as unknown and act on that. (With the presence will from Unit 2, stat/online says when a peer has gone, and the stale rule covers a peer that is online but silent.)

Part 3. Agreeing Over a Lossy Link

The door and the requester must agree that the door is open. Neither can see the other. The requester sends open; the door opens and sends ack; if either message is lost, one side knows something the other does not. Here is one exchange with a lost acknowledgement:

A lost acknowledgement. The requester cannot tell a lost open from a lost ack, so it repeats; the door must therefore treat a repeated open as harmless (OPEN plus open answers again and does nothing else). The pattern is the id-and-idempotence rule from Unit 2, now written as a table.

To measure how well this works, the two machines were run 3,000 times through a simulated link that loses each message with probability p, with a 40 ms delay, a 500 ms timeout and three tries. The success rate matches the formula 1 − (1 − (1 − p)²)³, which you can check by hand: each try needs both messages to arrive.

Three tries of a 500 ms timeout against a lossy link. Retries buy a great deal, and still leave a failure rate you must design for.

The interesting number is hidden in the “gave up” column. At 20 % loss the requester gave up 126 times, and in 108 of those (86 %) the door had in fact opened: the open arrived, only the ack did not. The requester is in FAULT and the door is OPEN. The machines disagree. Two things keep that from becoming a failure: the requester sends close as it gives up (itself lossy), and, decisive, the door’s own timeout: OPEN falls back to CLOSED after 5 seconds without a renewal. In every one of the simulated runs the door was closed by the end.

  • Each side needs a safe default that does not depend on the other: the door closes by itself; the robot’s motor stops by itself (the deadman of Unit 2).
  • Disagreement is bounded, not eliminated. The honest design question is “for how long can the two views differ, and what is the worst thing that can happen in that time?”.
  • Report the failure. FAULT is a state with a name, published like any other, so that a person or another agent can see it and reset it.

Warm Up

Exercise 1: Read the Table. Using the DOOR table, what happens in each case? (a) The door is CLOSED and receives close. (b) The door is OPEN and nothing arrives for 5 s. (c) The door is CLOSED and receives timeout.

Exercise 2: The Formula. Check the 20 % row of the table by hand: the probability that one try succeeds, and that three tries all fail.

Intermediate

Exercise 3: Longer Timeout or More Tries?. You may change the requester to use a 1,000 ms timeout and five tries, or 250 ms and six tries. At 20 % loss, which has the higher success rate, and what does each cost in the worst-case time to give up?

Advanced

Exercise 4: Add a State. The door should close after the requester says done, but a robot still in the doorway must not be hit. Add a state CLOSING to the DOOR table that waits for a sensor event clear before closing, and give up (go back to OPEN) if blocked arrives.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Read the Table

(a) ("CLOSED", "close") is in the table: it stays CLOSED and answers ack (a harmless repeat). (b) The OPEN timeout fires, ("OPEN", "timeout") goes to CLOSED, no action. (c) ("CLOSED", "timeout") is not in the table, so the event is ignored and ignored goes up by one; CLOSED has no timeout of its own, so this would only happen if something fired it by mistake, which is what the counter would show.

Exercise 2: The Formula

One try needs the open (0.8) and the ack (0.8): 0.8 × 0.8 = 0.64. A try fails with probability 0.36, and three tries all fail with 0.36³ = 0.0467, so success is 0.953, matching the measured 95.8 % within the noise of 3,000 trials (126 / 3,000 = 4.2 %).

Intermediate

Exercise 3: Longer Timeout or More Tries?

Success depends only on the number of tries (the timeout does not change whether a message is lost): five tries give 1 − 0.36⁵ = 99.4 %, six give 1 − 0.36⁶ = 99.8 %. The worst-case time to give up is 5 × 1,000 = 5 s against 6 × 250 = 1.5 s. The short timeout wins on both, until it becomes shorter than the round trip (delay plus the broker and the loop time), when a late but successful ack arrives after the timeout and causes needless repeats: keep the timeout about twice the measured round trip of Lab 5.

door2.py MicroPython
DOOR2 = { ("CLOSED", "open"): ("OPEN", "ack"), ("OPEN", "open"): ("OPEN", "ack"), ("OPEN", "close"): ("CLOSING", "ack"), # asked to close: check the doorway first ("CLOSING", "clear"): ("CLOSED", None), # the sensor sees nobody there ("CLOSING", "blocked"):("OPEN", None), # someone is in the way: stay open ("CLOSING", "open"): ("OPEN", "ack"), ("OPEN", "timeout"): ("CLOSING", None), # failsafe goes through the same check } DOOR2_TIMEOUTS = {"OPEN": (5000, "timeout")}

The timeout now goes through CLOSING too, so even the fail-safe closes only when the doorway is clear. Note that this creates a new question that the table makes visible: what if blocked never stops? CLOSING needs its own timeout (and a decision about what to do), and the missing row is easy to see in the table and hard to see in nested ifs.
