Last lab proved a raw TCP connection to the Pi 3B+ works. MQTT (Message Queuing Telemetry Transport) is the actual protocol spoken over that connection, publish-subscribe's rules written down precisely enough for a Pico and a broker, built by different people, to understand each other perfectly. This lesson gets a Pico actually speaking it.

Part 1. Why MQTT Specifically

MQTT was designed from the start for exactly this course's situation: small, often battery- or low-power devices, on networks that aren't always perfectly reliable, sending small, frequent messages. Its messages carry minimal overhead compared to heavier protocols like HTTP, and the protocol itself (connection handling, keeping track of who's subscribed to what) is handled entirely by the broker, a sensor node's job is reduced to connect, publish, and occasionally subscribe.

Part 2. Mosquitto: the Broker Software

The Pi 3B+ for this course runs Mosquitto, the most widely used open-source MQTT broker, listening on the standard port 1883 you already connected to in last week's lab. Mosquitto's entire job is what Part 2 of the pub-sub lesson described in the abstract: accept connections from clients, remember who's subscribed to which topics, and forward each incoming publish to every matching subscriber. Every Pico in the room is a client of this one broker.

Three publishing Picos and one subscriber, all connected independently to the same broker. Any of these Picos could just as easily subscribe too; client and server are roles a connection plays, not a property of the hardware.
A complete MQTT exchange. Both devices connect to the broker, one subscribes, and every PUBLISH from the first is forwarded by the broker to the second. The publisher and subscriber never speak to each other.

Part 3. umqtt.simple: MQTT in MicroPython

MQTT isn't built into MicroPython the way socket is. umqtt.simple is the standard, lightweight library that implements it; install it onto your Pico once via Thonny's Tools → Manage packages (search micropython-umqtt.simple), the same one-time-per-board idea as flashing firmware back in Lesson 1.

main.py MicroPython
from umqtt.simple import MQTTClient import network from time import sleep # ... WiFi connection from Lesson 1 goes here, unchanged ... CLIENT_ID = "pico-01" # must be unique per device on the broker BROKER_IP = "192.168.1.42" client = MQTTClient(CLIENT_ID, BROKER_IP) client.connect() print("connected to broker as", CLIENT_ID) client.publish(b"lab/pico01/status", b"online") client.disconnect()

Three things worth noticing immediately: CLIENT_ID has to be unique across every device talking to this broker, two Picos connecting with the same ID will conflict, which is exactly why every board in the room needs its own distinct ID (pico-01, pico-02, and so on, assigned by your instructor or chosen and recorded by you). Both the topic and the message to publish() are passed as bytes (the b"..." prefix), not plain strings, which umqtt.simple requires. And client.connect() is a completely separate step from the WiFi connection, WiFi gets you on the network at all; this is the MQTT-level handshake with the broker specifically, layered on top.

The pieces of a PUBLISH message. The header tells the broker how to handle it; the topic says where it goes; the payload is opaque bytes that the broker never reads.

Part 4. Subscribing and Receiving

Subscribing needs a callback function, called automatically whenever a message arrives on a topic you've subscribed to, plus a loop that actually gives the library a chance to check for incoming messages:

main.py MicroPython
def on_message(topic, msg): print("received on", topic, ":", msg) client = MQTTClient(CLIENT_ID, BROKER_IP) client.connect() client.set_callback(on_message) client.subscribe(b"lab/pico01/cmd") while True: client.check_msg() # non-blocking -- returns immediately if nothing's waiting sleep(0.1)

check_msg() is the MQTT-specific version of last week's non-blocking idea: it peeks for an incoming message and returns right away either way, rather than sitting and waiting for one, which is exactly why it fits naturally inside a ticks_ms()-based loop that's also doing other things, publishing sensor readings, blinking an LED, in the same pass.

Three places to watch an MQTT conversation at once: a terminal subscribed to everything under lab/, a terminal playing a dashboard that sends commands, and the Pico's own shell.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Duplicate Client IDs

A client ID must be unique. The broker treats the second connection as the same client coming back and disconnects the first. If both keep retrying, they take turns kicking each other off, giving flapping, intermittent data. Give every board its own ID.

Exercise 2: Bytes, Not Strings

MQTT messages are raw bytes on the wire, and umqtt.simple expects bytes for topics and payloads. Passing a str gives a type error or garbled output depending on the version. Convert with .encode() or write a b"..." literal.

Intermediate

Exercise 3: A Counter
main.py MicroPython
n = 0 while True: client.publish(b"lab/pico01/counter", str(n).encode()) n += 1 sleep(1)

str(n) makes the number text and .encode() turns the text into bytes. Watch it with mosquitto_sub -t "lab/pico01/counter".

Advanced

Exercise 4: Echo in Capitals
main.py MicroPython
def on_message(topic, msg): client.publish(b"lab/pico01/out", msg.upper()) client.set_callback(on_message) client.subscribe(b"lab/pico01/in") while True: client.check_msg()

Test it from the Pi: mosquitto_pub -t lab/pico01/in -m hello while mosquitto_sub -t lab/pico01/out is running. Publishing from inside the callback is perfectly fine.
