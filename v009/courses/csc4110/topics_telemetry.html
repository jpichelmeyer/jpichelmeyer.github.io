This lesson sets the class conventions for topics (tele, evt, cmd and stat) and explains wildcards and what a subscription costs. Then it adds the return path: hub.py, which lets a node subscribe and receive without ever blocking; the acknowledgement convention that turns publish and subscribe into a conversation; the command logic of the Lab 6 robot, with validation, ownership and repeated commands; and the fail-safes that keep a robot safe when its controller disappears.

SAM lens. Topic kinds map onto SAM: tele and evt are what an agent's Actuator says about its percepts and decisions, cmd is what other agents ask of it, and stat is its Memory made public. A command arrives through the Perceptor, is judged by the Decider (validation, ownership, repeats), and only then reaches the Actuator; the fail-safes keep the Actuator safe when the Perceptor stops hearing from its owner.

A topic is the only address a message has, so the way you name topics is the design of your system. A good scheme lets a logger collect everything with one subscription, lets one robot listen for commands addressed to it and nobody else, and lets the access list protect the right things. A bad one forces you to rename topics in six programs the day you add a second robot. This lesson sets the class conventions and shows how wildcards work, then adds the return path: commands that reach a node, the acknowledgements that answer them, and the fail-safes that keep a robot safe when the program commanding it disappears.

Part 1. A Tree With Four Branches

The class topic tree for one student: lab/<user>/<kind>/<name>. Four kinds cover almost everything a node does, and the kind tells every reader how to treat the message.
The four kinds. A late subscriber needs the current state (retained), but should not be handed an old event as if it had just happened, or a stale command, which could move a robot long after anyone wanted it to.
  • Put identity and kind in the topic, values in the payload. lab/jsmith/tele/imu with {"roll": 12.3}, not lab/jsmith/tele/roll12.3. The access list works on topics, and a subscriber can only filter on topics.
  • Lower case, no spaces, no leading or trailing slash. /lab/x and lab/x are two different topics; so are Lab and lab.
  • Never start a topic with $. Those belong to the broker.
  • Short, stable names. The topic is sent with every message, so a long one costs bytes at every rate, and renaming it later breaks every reader.
  • One meaning per topic. If two different payload shapes arrive on one topic, every subscriber needs a special case. Use two topics.

Part 2. Wildcards

A subscription filter can contain two wildcards. + stands for exactly one level; # stands for everything that remains and may only appear at the end. A publisher never uses wildcards, only a subscriber does.

Filters and the topics they match. The second row is a classic surprise: lab/+/tele/# receives the topic lab/jsmith/tele itself, because # matches zero or more levels.

Wildcards are powerful and expensive. Every message that matches is delivered to you, and a Pico cannot keep up with a firehose. If the class has 24 students each publishing 7 messages a second, lab/# brings 168 messages a second to your node. Subscribe to the narrowest filter that does the job, and subscribe to broad ones only on a laptop.

What different filters cost the subscriber. The Pico’s own WiFi stack and callback must process every delivered message whether or not the program wants it, so the filter is also a performance setting.

Part 3. Commands Need Answers

Publish and subscribe has no reply: when you publish a command, publish returning tells you only that the bytes left your board. Whether the broker accepted the topic, whether the robot was listening, whether it obeyed, whether it was allowed to: none of that is visible. The convention that fills the gap is simple and universal. Every command carries an id. The node answers on an ack topic with the same id and a verdict. It also publishes its state as a retained message, so that anyone can check what the robot is doing without asking.

A command conversation. The id ties each answer to its question, since many commands may be in flight and acks can arrive out of order. A refusal is an answer too: the controller learns why, instead of waiting in silence.

Part 4. hub.py: A Node That Listens

hub.py extends net.Link from the on-ramp lesson. Everything net.py did (queue, retry, never block) still works; the new methods subscribe, receive, keep the connection alive and announce the node. Read it through once: it is the working form of the callback, ping and keepalive ideas from the MQTT lesson.

hub.py MicroPython
# hub.py -- net.py with ears: it can subscribe, receive and announce itself. # import hub # h = hub.Hub() # h.on(h.mine("cmd/#"), handler) # handler(topic, payload) for every matching message # while True: # h.poll() # call once per pass of your main loop import json from time import ticks_ms, ticks_diff import net def match(filt, topic): """MQTT wildcards: + is exactly one level, # is everything that remains.""" f, t = filt.split("/"), topic.split("/") for i, part in enumerate(f): if part == "#": return True if i >= len(t) or (part != "+" and part != t[i]): return False return len(f) == len(t) def decode(payload): """bytes -> dict, or None if it is not a valid version-1 message. Never raises.""" try: d = json.loads(payload) except (ValueError, TypeError): return None if not isinstance(d, dict) or d.get("v") != 1: return None if not isinstance(d.get("seq"), int) or not isinstance(d.get("t"), int): return None return d class Hub(net.Link): def __init__(self, keepalive=30, inbox_max=20, **kw): super().__init__(**kw) self.keepalive = keepalive # seconds; the broker drops us after 1.5 x of silence self.handlers = [] # (filter, function) self.inbox = [] # messages the callback has caught, waiting for poll() self.inbox_max = inbox_max self.rx_dropped = 0 self.will = None # set by presence() self.hello = None self.last_ping = ticks_ms() def mine(self, topic): """A full topic inside your own subtree: mine("cmd/#") -> "lab/jsmith/cmd/#".""" return self.root + topic def on(self, filt, handler): self.handlers.append((filt, handler)) if self.client: try: self.client.subscribe(filt.encode()) except OSError: self._drop() def send(self, topic, data, retain=False): """Publish to a FULL topic outside your own subtree (the access list must allow it).""" mine, self.root = self.root, "" try: return self.publish(topic, data, retain) finally: self.root = mine def presence(self, topic="stat/online"): """Register a last will, and announce 'online' at every connect. Both are retained.""" t = self.root + topic self.will = (t, json.dumps({"v": 1, "seq": 0, "t": 0, "online": False})) self.hello = (t, json.dumps({"v": 1, "seq": 0, "t": 0, "online": True})) def close(self): """A planned shutdown: say so, then disconnect. (A clean disconnect suppresses the will.)""" if self.client and self.will: try: self.client.publish(self.will[0].encode(), self.will[1].encode(), retain=True) self.client.disconnect() except OSError: pass self.client = None def _make_client(self): c = super()._make_client() c.set_callback(self._on_msg) if self.will: c.set_last_will(self.will[0].encode(), self.will[1].encode(), retain=True) return c def _on_msg(self, topic, payload): # runs inside check_msg(): only remember, never work self.inbox.append((topic.decode(), payload)) if len(self.inbox) > self.inbox_max: self.inbox.pop(0) self.rx_dropped += 1 def connect(self): if not super().connect(): return False try: for filt in {f for f, _ in self.handlers}: self.client.subscribe(filt.encode()) except OSError: self._drop() return False if self.hello: self.log.insert(0, (self.hello[0], self.hello[1], True)) # first thing sent self.last_ping = ticks_ms() return True def poll(self, budget=5): """Receive, keep the connection alive, and run handlers for up to `budget` messages.""" if self.client is None: if self.last_try is None or ticks_diff(ticks_ms(), self.last_try) >= self.retry_ms: self.connect() return 0 try: for _ in range(budget): before = len(self.inbox) self.client.check_msg() if len(self.inbox) == before: break if self.log: self._flush(5) if ticks_diff(ticks_ms(), self.last_ping) >= self.keepalive * 500: self.client.ping() self.last_ping = ticks_ms() except OSError: self._drop() return 0 n = 0 while self.inbox and n < budget: topic, payload = self.inbox.pop(0) for filt, fn in self.handlers: if match(filt, topic): fn(topic, payload) n += 1 return n
What one pass of poll() does. Every step is short and bounded, so a node that polls inside its control loop stays responsive however much the network sends it.

Three methods are worth remembering. h.mine("cmd/#") builds a full topic in your own subtree. h.on(filter, handler) registers a handler for every message matching a filter. h.send(topic, data) publishes to a full topic outside your subtree, which the access list will allow only where you have been given write access. The plain h.publish("evt/ack", ...) still writes into lab/<you>/.

Part 5. The Robot’s Logic

The robot node you will build in Lab 6 accepts four commands. This table is its interface: what anyone commanding it may send, and what it will refuse.

The robot’s commands. Only the owner’s commands are obeyed; others get an ack with ok false and why “not owner”. Every command carries an integer id, which comes back in the ack, and the name of the user sending it (a claim, not proof: the access list is what really decides who may publish). A bad payload, an unknown command or an out-of-range value is rejected with an ack and changes nothing. If the motor is running and no valid command arrives for 2 s it stops; if the owner is silent for 30 s the robot releases ownership, stops and returns to IDLE. The robot answers on lab/<you>/evt/ack and keeps its state, retained, on stat/state.

The logic below implements that table. It contains no hardware: it takes an actuator object that provides pan(deg), drive(pct) and stop(), which is why the same code can be tested on a laptop with a stand-in that only records what it was told. The first function, validate, checks a command against the table and returns a reason, never an exception.

robot.py MicroPython
# robot.py -- the command logic of a robot node. No hardware in here: it calls an actuator object, # so the same logic can be tested on a PC with a stand-in. from time import ticks_ms, ticks_diff def validate(kind, d, allow_spin=False): """Check a command against the command table. Returns (True, "") or (False, why).""" if not isinstance(d, dict): return False, "bad payload" if not isinstance(d.get("id"), int): return False, "missing id" if not isinstance(d.get("user"), str) or not d["user"]: return False, "missing user" if kind == "pan": deg = d.get("deg") if not isinstance(deg, (int, float)): return False, "deg must be a number" if not -90 <= deg <= 90: return False, "deg out of range" elif kind == "drive": pct, ms = d.get("pct"), d.get("ms") if not isinstance(pct, (int, float)) or not isinstance(ms, int): return False, "pct and ms are required" if not -100 <= pct <= 100: return False, "pct out of range" if not 0 < ms <= 1500: return False, "ms out of range" elif kind == "spin" and allow_spin: pct = d.get("pct") if not isinstance(pct, (int, float)) or not -100 <= pct <= 100: return False, "pct out of range" elif kind not in ("stop", "claim"): return False, "unknown command" return True, "" class Robot: def __init__(self, act, lease_ms=30000, deadman_ms=2000, pan_gap_ms=200, allow_spin=False): self.act = act # needs pan(deg), drive(pct), stop() self.lease_ms, self.deadman_ms, self.pan_gap_ms = lease_ms, deadman_ms, pan_gap_ms self.allow_spin = allow_spin self.owner = None self.owner_seen = 0 # time of the owner's last valid command self.run_until = None # when a timed drive must end self.running = False self.last_cmd = 0 self.last_pan = None self.acks = {} # id -> ack, so a repeated command is answered, not repeated self.order = [] def _remember(self, cid, ack): self.acks[cid] = ack self.order.append(cid) if len(self.order) > 8: self.acks.pop(self.order.pop(0), None) def _stop(self): self.act.stop() self.running = False self.run_until = None def command(self, kind, d, now): """Handle one command. Always returns an ack dict; never raises.""" ok, why = validate(kind, d, self.allow_spin) if not ok: return {"cmd_id": d.get("id") if isinstance(d, dict) else None, "ok": False, "why": why} cid, user = d["id"], d["user"] if cid in self.acks: return self.acks[cid] # a repeat: same answer, no second action ack = {"cmd_id": cid, "ok": True, "why": ""} free = self.owner is None if kind == "claim": if free or self.owner == user: self.owner, self.owner_seen = user, now else: ack.update(ok=False, why="busy") elif self.owner != user: ack.update(ok=False, why="not owner") else: self.owner_seen = self.last_cmd = now if kind == "stop": self._stop() elif kind == "pan": if self.last_pan is not None and ticks_diff(now, self.last_pan) < self.pan_gap_ms: ack.update(ok=False, why="too fast") else: self.act.pan(d["deg"]) self.last_pan = now else: # drive or spin self.act.drive(d["pct"]) self.running = d["pct"] != 0 self.run_until = now + d["ms"] if kind == "drive" else None self._remember(cid, ack) return ack def tick(self, now): """Call every pass of the main loop. Returns a list of reasons for anything it stopped.""" out = [] if self.running and self.run_until is not None and ticks_diff(now, self.run_until) >= 0: self._stop(); out.append("time up") if self.running and ticks_diff(now, self.last_cmd) > self.deadman_ms: self._stop(); out.append("deadman") if self.owner and ticks_diff(now, self.owner_seen) > self.lease_ms: self._stop(); self.owner = None; out.append("lease expired") return out def state(self): if self.owner is None: return "IDLE", None return ("BUSY" if self.running else "READY"), self.owner

Walk through command in order, because the order is the design. Validate first, so that nothing malformed reaches any other logic. Then look for a repeat: if this id has been answered, return the stored answer and do nothing, which makes a retransmitted command harmless (idempotent). Then the owner check: a claim succeeds if the robot is free or already yours; anything else requires you to be the owner. Only then does it act, and the act itself is bounded: pan is rate-limited, and drive carries its own duration.

The glue between this logic and the broker is a dozen lines. The callback gets the kind from the last level of the topic, decodes the payload (None if invalid, which validate turns into “bad payload”), hands both to the robot, and publishes whatever comes back.

main.py MicroPython
# main.py: a robot node on the broker (in your own subtree for Lab 6) import hub from robot import Robot from actuators import Actuators # Lab 6: servo on GP14, motor driver or LED from time import ticks_ms h = hub.Hub() h.presence() # last will + retained "online" robot = Robot(Actuators()) def on_cmd(topic, payload): kind = topic.rsplit("/", 1)[-1] # ".../cmd/pan" -> "pan" ack = robot.command(kind, hub.decode(payload), ticks_ms()) h.publish("evt/ack", ack) h.on(h.mine("cmd/#"), on_cmd) shown = None while True: h.poll() now = ticks_ms() for why in robot.tick(now): h.publish("evt/stopped", {"why": why}) st = robot.state() if st != shown: # publish state only when it changes h.publish("stat/state", {"state": st[0], "owner": st[1]}, retain=True) shown = st

Notice how little this program decides. The rules are in Robot, the transport is in Hub, and main.py only connects them. When something goes wrong you can ask which of the three failed.

Part 6. Fail-Safes

A robot has to be safe when its controller fails, because a controller will fail: the laptop sleeps, the program crashes, the WiFi drops, a student closes the lid. The design rule is: the safe state must be the default state, and staying out of it must require continuous effort. Three mechanisms in Robot.tick implement it at three time scales.

Four independent safeguards. None depends on the network being up at the moment of failure, which is the point: a safeguard that needs a message to trigger is useless when messages stop arriving.

Two points about the table. First, the motor-protecting mechanisms live in the node, not in the controller: asking the controller to “remember to send stop” fails in exactly the situation it is meant for. Second, a command with a bounded duration is safer than an unbounded one plus a stop, because there is nothing to forget. Continuous control, the joystick style, exists too, and uses the deadman: the controller must keep repeating the command (say every 200 ms) or the motor stops after 2 s. In Lab 6 you will run the robot with allow_spin=True and watch the deadman work.

Part 7. Retrying Without Doing It Twice

The network can lose a command, or it can lose the ack. The controller cannot tell which: both look like silence. The only strategy that works is to send again, with the same id, and let the robot recognise the repeat. The Controller class below does exactly that: it remembers what is pending, resends after retry_ms, and after tries attempts reports a failure.

controller.py MicroPython
# controller.py -- sends commands, matches acknowledgements, retries with the SAME id. from time import ticks_diff from hub import decode class Controller: def __init__(self, hub, root, user, retry_ms=500, tries=3): self.hub, self.root, self.user = hub, root, user # root: "robot/r1/" self.retry_ms, self.tries = retry_ms, tries self.next_id = 1 self.pending = {} # id -> [kind, fields, time last sent, attempts] self.done = {} # id -> the ack, or a "no answer" failure hub.on(root + "evt/ack", self._on_ack) def send(self, kind, now, **fields): cid = self.next_id self.next_id += 1 fields["id"], fields["user"] = cid, self.user self.pending[cid] = [kind, fields, now, 1] self.hub.send(self.root + "cmd/" + kind, fields) return cid def _on_ack(self, topic, payload): d = decode(payload) if d and d.get("cmd_id") in self.pending: self.done[d["cmd_id"]] = d del self.pending[d["cmd_id"]] def tick(self, now): for cid, p in list(self.pending.items()): if ticks_diff(now, p[2]) < self.retry_ms: continue if p[3] >= self.tries: self.done[cid] = {"cmd_id": cid, "ok": False, "why": "no answer"} del self.pending[cid] else: p[2], p[3] = now, p[3] + 1 self.hub.send(self.root + "cmd/" + p[0], p[1]) # same id: the robot will not act twice
A lost ack, repaired by a retry. The robot panned once, when it first saw id 3, and answered the repeat from its table of recent ids. Without the id table every retry would pan the servo again; with a drive command it would drive again.

One question has no clean answer: after three attempts with no ack, did the robot act? It may have received every one of them and every ack may have been lost. The controller can only say “I do not know.” The safe response is to treat the state as unknown, command a stop, and read the robot’s retained stat/state before doing anything else. That is why stop is always honored, and why the state is retained: it is the one message a controller can fetch at any moment to find out the truth.

Warm Up

Exercise 1: Match or Not

(a) yes. (b) no: + covers exactly one level, so lab/+ matches only two-level topics. (c) yes: # also matches the parent, zero further levels. (d) no: +/tele/imu has three levels and the topic has four. (e) yes: an empty level is still a level, and + matches it (which is exactly why a stray double slash is so hard to find).

Exercise 2: Read the Ack

The claim is refused with ok false, why “busy”, because bob is not the owner and the robot is not free. The pan is refused with ok false, why “not owner”. The robot moves nothing, and jsmith’s lease is not refreshed by either, so bob’s traffic cannot keep jsmith’s claim alive nor interfere with it.

Intermediate

Exercise 3: What Does a Filter Cost?

(a) 12 × (3 + 0.1) = 37.2 per second plus the occasional state change. (b) 12 × 0.1 = 1.2 per second. (c) 12 per hour = 0.0033 per second, essentially none, but each is retained, so a new subscriber receives all 12 immediately on connecting. Subscribing narrowly cuts the load by a factor of thirty.

Exercise 4: Which Safeguard?

(a) The bounded command: the motor stops at its 1.5 s deadline, about 1.1 s after the crash. (b) The deadman: 2 s after the last command (spin does not time out by itself). (c) The lease: 30 s after the last valid command, the robot releases the owner and returns to IDLE. (d) Power failure removes the motor’s power as well as the logic’s, so the motor stops physically; the last will (after about 45 s) lets everyone know the robot is gone. If the motor had its own battery and the driver inputs floated, this is where a pull-down resistor on the inputs earns its place.

Advanced

Exercise 5: How Long to Give Up?

Attempts are sent at 0, 500 and 1,000 ms, and the controller gives up at about 1,500 ms, when the third attempt’s time is also up. The danger: the first attempt may actually have arrived and started the motor, only the acks were lost. The controller now says “no answer” while a motor is running for up to 1,500 ms from the first arrival. After a “no answer” it must send stop (repeating until acknowledged) and then read stat/state. It must never assume that no answer means no action.

Paper Practice: Answers

Recall

P1. Four Kinds

tele (telemetry): not retained; evt (events): not retained; cmd (commands): never retained; stat (state): retained.

P2. Wildcards

+ matches exactly one level; # matches all remaining levels (zero or more) and may only be the last level. Only subscribers use wildcards.

P3. Ack Convention

Every command carries an id; the robot answers on an ack topic with the same id and a verdict; the robot publishes its state retained so anyone can check it at any time.

P4. Idempotent

Receiving the same command twice has the same effect as receiving it once. The robot keeps a table of recent ids and their acks; a repeat gets the stored ack and no second action.

P5. Safe Default

The safe state must be the default state, and staying out of it must require continuous effort (fresh commands, a held lease).

Apply

P6. Match or Not

(a) Yes: # matches zero levels. (b) Yes. (c) No: the third level must be tele. (d) No: + matches only one level, so the third level is x.

P7. Firehose

168 messages per second, too many for a Pico. Stat changes: 24 per minute, 0.4 per second.

P8. Trace the Robot

id 1: ok (amy owns it). id 2: refused, "not owner". id 3: ok, servo pans to 30. id 3 again: the stored ack (ok) is returned and the servo does not move. It moved once.

P9. Deadman

When 2 s have passed with no command from the owner: at about t = 3000 ms (on the next tick after that).

Analyze and Design

P10. Bad Topic Design

The value is in the topic, so every reading is a new topic: subscribers cannot filter usefully, retained storage fills with junk, and the access list and logger see thousands of topics. Put the value in the payload: lab/amy/tele/imu with {"roll": 12.3}.

P11. Lost Ack or Lost Command

Both look like silence. Resend with the same id; the robot acts at most once and answers repeats from its table. After several attempts with no answer the outcome is unknown: command a stop and read the retained state before doing anything else.

P12. Where Fail-Safes Live

It fails in exactly the situations it is meant for: a crash, a sleeping laptop, a lost network. The protection must live in the node (deadman, bounded durations, leases), working without any message.
