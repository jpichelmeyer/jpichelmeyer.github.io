This lesson sets the class conventions for topics (tele, evt, cmd and stat), explains wildcards and what a subscription costs, shows how to decide when a sensor value deserves a message with a deadband and a heartbeat, and introduces the robot interface specification that Lab Practical 2 is built on.

A topic is the only address a message has, so the way you name topics is the design of your system. A good scheme lets a logger collect everything with one subscription, lets one robot listen for commands addressed to it and nobody else, and lets the access list protect the right things. A bad one forces you to rename topics in six programs the day you add a second robot. This lesson sets the class conventions, shows how wildcards work, designs the telemetry that flows over the topics, and ends with the first interface specification you will have to read and obey.

Part 1. A Tree With Four Branches

The class topic tree for one student: lab/<user>/<kind>/<name>. Four kinds cover almost everything a node does, and the kind tells every reader how to treat the message.
The four kinds. A late subscriber needs the current state (retained), but should not be handed an old event as if it had just happened, or a stale command, which could move a robot long after anyone wanted it to.
  • Put identity and kind in the topic, values in the payload. lab/jsmith/tele/imu with {"roll": 12.3}, not lab/jsmith/tele/roll12.3. The access list works on topics, and a subscriber can only filter on topics.
  • Lower case, no spaces, no leading or trailing slash. /lab/x and lab/x are two different topics; so are Lab and lab.
  • Never start a topic with $. Those belong to the broker.
  • Short, stable names. The topic is sent with every message, so a long one costs bytes at every rate, and renaming it later breaks every reader.
  • One meaning per topic. If two different payload shapes arrive on one topic, every subscriber needs a special case. Use two topics.

Part 2. Wildcards

A subscription filter can contain two wildcards. + stands for exactly one level; # stands for everything that remains and may only appear at the end. A publisher never uses wildcards, only a subscriber does.

Filters and the topics they match. The second row is a classic surprise: lab/+/tele/# receives the topic lab/jsmith/tele itself, because # matches zero or more levels.

Your own code needs the same rule when it dispatches a received message to the right handler, because the broker tells you only the topic of the message, not which of your subscriptions caused it:

match.py MicroPython
def match(filt, topic): """MQTT wildcards: + is exactly one level, # is everything that remains.""" f, t = filt.split("/"), topic.split("/") for i, part in enumerate(f): if part == "#": return True if i >= len(t) or (part != "+" and part != t[i]): return False return len(f) == len(t)

Wildcards are powerful and expensive. Every message that matches is delivered to you, and a Pico cannot keep up with a firehose. If the class has 24 students each publishing 7 messages a second, lab/# brings 168 messages a second to your node. Subscribe to the narrowest filter that does the job, and subscribe to broad ones only on a laptop.

What different filters cost the subscriber. The Pico’s own WiFi stack and callback must process every delivered message whether or not the program wants it, so the filter is also a performance setting.

Part 3. Designing Telemetry

Sending a reading every second is simple and wasteful: most of the time nothing has changed. There are three honest ways to decide when to send, and most nodes use a mixture:

  • Periodic. Send every T seconds. Easy for the receiver (a regular signal) and predictable for the network. Wasteful when the value is flat.
  • On change (report by exception). Send only when the value has moved by at least a deadband. Cheap for slow signals; the receiver must remember the last value and cannot tell “unchanged” from “node died”.
  • Heartbeat. Send at least every H seconds even if nothing changed, so that silence means trouble.
reporter.py MicroPython
from time import ticks_ms, ticks_diff class Reporter: """Decides when a slowly changing value is worth a message.""" def __init__(self, deadband, min_ms=200, max_ms=60000): self.deadband, self.min_ms, self.max_ms = deadband, min_ms, max_ms self.last_val = None self.last_t = None def check(self, value, now=None): """True if the value should be sent now.""" now = ticks_ms() if now is None else now if self.last_t is None: send = True # the first value always goes else: age = ticks_diff(now, self.last_t) if age < self.min_ms: send = False # never faster than min_ms elif age >= self.max_ms: send = True # heartbeat: "still here, same value" else: send = abs(value - self.last_val) >= self.deadband if send: self.last_val, self.last_t = value, now return send
One hour of a temperature signal (grey), and the points where a Reporter with a deadband of 0.2 °C chose to send (orange). The step at 2000 s is reported at once. Sixty-five messages carry the same information as 3,600, to within the deadband.
The deadband sets the trade between bandwidth and accuracy. The worst error is always just under the deadband, so you can choose it from what the receiver needs: no one needs a room temperature to 0.05 °C.

Part 4. A Robot Interface Specification

Lab Practical 2 asks your program to talk to a robot you did not build: the instructor’s. When that happens the only thing you have is a document, the interface specification: what topics exist, who may publish on each, what the payloads look like, how fast, and what the robot does when it is given nonsense or nothing at all. Reading one carefully is a skill worth practising now. Here is a draft of the robot’s specification. The final version, with any changes, is issued before the practical.

Draft robot interface, part 1: what the robot reports. state is one of IDLE, READY, BUSY or FAULT; owner is the user who currently holds the robot or null. range_cm is null when the rangefinder sees nothing.
Draft robot interface, part 2: what you may tell it. The access list will give one user at a time write access to robot/r1/cmd/#. The last paragraph of the spec is the part people skip, and it is the part that decides what happens when your code or the network fails.

Read it the way an engineer reads a contract: for each topic, who writes it, who reads it, how often, in what shape, and what happens at the edges. The validate function below is the robot’s side of the rules: it checks a command against the specification and returns a reason, never an exception. You will write the same kind of check for your own commands in the next lesson.

validate.py MicroPython
def validate(kind, d): """Check a command payload against the robot interface spec. Returns (True, "") or (False, "reason"). Never raises.""" if not isinstance(d, dict): return False, "bad payload" if not isinstance(d.get("id"), int): return False, "missing id" if not isinstance(d.get("user"), str) or not d["user"]: return False, "missing user" if kind == "pan": deg = d.get("deg") if not isinstance(deg, (int, float)): return False, "deg must be a number" if not -90 <= deg <= 90: return False, "deg out of range" elif kind == "drive": pct, ms = d.get("pct"), d.get("ms") if not isinstance(pct, (int, float)) or not isinstance(ms, int): return False, "pct and ms are required" if not -100 <= pct <= 100: return False, "pct out of range" if not 0 < ms <= 1500: return False, "ms out of range" elif kind not in ("stop", "claim"): return False, "unknown command" return True, ""

Exercises

Exercise 2: What Does a Filter Cost?. Twelve students each publish 3 tele messages and 0.1 evt messages per second, and one stat/online change per hour. How many messages per second reach a node subscribed to (a) lab/#, (b) lab/+/evt/#, (c) lab/+/stat/online?

Intermediate

Exercise 3: Choose the Deadband. A rangefinder reports distance to a wall in cm, with noise of about ±0.5 cm after filtering. A robot that must stop 20 cm from the wall reads it. What deadband would you give the Reporter, what minimum interval, and what heartbeat? Say what goes wrong with 0.1 cm.

Advanced

Exercise 4: Reject It. Using validate, list the result for each of these commands, and say what the robot should do in each case: (a) pan with id 1, user jsmith and deg 45; (b) pan with deg 120; (c) pan with no id; (d) drive with id 2, pct 60 and ms 5000; (e) a stop with id 3; (f) a command named “fly”; (g) the payload "hello".

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Match or Not

(a) yes. (b) no: + covers exactly one level, so lab/+ matches only two-level topics. (c) yes: # also matches the parent, zero further levels. (d) no: +/tele/imu has three levels and the topic has four. (e) yes: an empty level is still a level, and + matches it (which is exactly why a stray double slash is so hard to find).

Exercise 2: What Does a Filter Cost?

(a) 12 × (3 + 0.1) = 37.2 per second plus the occasional state change. (b) 12 × 0.1 = 1.2 per second. (c) 12 per hour = 0.0033 per second, essentially none, but each is retained, so a new subscriber receives all 12 immediately on connecting. Subscribing narrowly cuts the load by a factor of thirty.

Intermediate

Exercise 3: Choose the Deadband

A deadband of 1 cm (twice the noise) reports real movement and ignores jitter; the stopping rule needs a precision of a centimetre or two, so 1 cm is no loss. A minimum interval of 100 ms matches the sensor’s rate, and a heartbeat of 2 to 5 s tells the robot the sensor is alive, because a wall that has not moved looks exactly like a dead sensor. With 0.1 cm, noise alone crosses the deadband constantly, so the Reporter degenerates into periodic sending at the maximum rate, the opposite of what you wanted.

Advanced

Exercise 4: Reject It
test_validate.py MicroPython
u = "jsmith" print(validate("pan", {"id": 1, "user": u, "deg": 45})) # (True, '') print(validate("pan", {"id": 1, "user": u, "deg": 120})) # (False, 'deg out of range') print(validate("pan", {"user": u, "deg": 1})) # (False, 'missing id') print(validate("drive", {"id": 2, "user": u, "pct": 60, "ms": 5000})) # (False, 'ms out of range') print(validate("stop", {"id": 3, "user": u})) # (True, '') print(validate("fly", {"id": 1, "user": u})) # (False, 'unknown command') print(validate("pan", "hello")) # (False, 'bad payload')

In every False case the robot publishes an ack with ok false and the reason, and does nothing else: no partial motion, no clamping to the nearest legal value. Clamping looks friendly but hides the sender’s bug, and a robot that does something slightly different from what it was asked is harder to debug than one that refuses. Note that the check on id comes first, so that every rejection can name the command it refers to.

Checkpoint

Before moving on, make sure you can:

  1. Name a topic correctly and say which of the four kinds it is.
  2. Say whether a filter matches a topic, including the parent case of #.
  3. Choose a subscription filter that is narrow enough for a microcontroller.
  4. Pick a deadband, a minimum interval and a heartbeat for a given signal and justify them.
  5. Read an interface specification and check a command against it, including what the robot does with bad input and with silence.
