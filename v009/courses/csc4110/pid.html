Until now, outputs were set by rules: if dark, switch on. But sometimes you want an output to hold a quantity at a target, such as a light level, a temperature or a speed, even as conditions change. Feedback control does that: measure, compare with the target, adjust, repeat. The most widely used recipe for the adjusting step is the PID controller.

Part 1. The Feedback Loop

The feedback loop. The controller compares what you want (the setpoint) with what the sensor reports, and turns the difference, the error, into an output that pushes the plant toward the setpoint.

The setpoint is what you want; the measurement is what the sensor says you have; their difference is the error. The controller turns the error into an output (a PWM duty cycle) that pushes the system toward the setpoint, and the sensor then reports the result, closing the loop. We will use an LED shining on an LDR: the PWM duty controls the LED, and the LDR reading is the thing to hold.

Part 2. Three Ideas in One Formula

  • P (proportional): act on the error now. Bigger error, bigger push. On its own it always settles short of the target, because a small error produces too small a push to remove itself.
  • I (integral): act on the error accumulated so far. A persistent small error builds up until it forces the output high enough to remove it. It removes the leftover error, but its memory makes the response overshoot.
  • D (derivative): act on how fast things are changing. It brakes the output as the measurement approaches the target, reducing overshoot, but it amplifies noise.
pid.py MicroPython
class PID: def __init__(self, kp, ki, kd, out_min=0.0, out_max=1.0): self.kp, self.ki, self.kd = kp, ki, kd self.out_min, self.out_max = out_min, out_max self.i = 0.0 self.prev = None def update(self, setpoint, measurement, dt): error = setpoint - measurement d = 0.0 if self.prev is None else -(measurement - self.prev) / dt # on the measurement self.prev = measurement i_new = self.i + self.ki * error * dt out = self.kp * error + i_new + self.kd * d if out > self.out_max: out = self.out_max # saturated: do not let the integral grow elif out < self.out_min: out = self.out_min else: self.i = i_new return out

Two details matter. The derivative is taken on the measurement, not the error, so a sudden change of setpoint does not produce a violent spike. And the integral is updated only when the output is not saturated; the reason is in Part 4.

The same step, three controllers (simulated on a two-lag plant). P alone settles short of the target; adding I removes that error but overshoots; adding D trims the overshoot and settles sooner.

P alone (Kp = 2) stops at 0.20 when the target is 0.30: one third short. PI (adding Ki = 4) reaches the target but overshoots by about 17 %. PID (adding Kd = 0.2) overshoots by about 13 % and settles a little sooner. The derivative term helps, but modestly here, which is typical: it is the first thing to leave out if your sensor is noisy.

Part 4. Integral Windup

The output of a real actuator is limited: a PWM duty cannot exceed 100 %. Suppose the target is unreachable for a while. The error stays large, so the integral keeps growing, far beyond what the output can use. When the target becomes reachable again, that huge stored value keeps the output pinned at its limit long after it should have backed off. This is windup:

Integral windup. While the output is saturated the integral keeps growing, and when the target finally becomes reachable that stored-up error drives the output the wrong way for a long time. Clamping the integral while saturated fixes it.

In the simulation, the PID that keeps integrating needed 3.6 s to come back within 2 % of the new target; the one that stops integrating while saturated needed 2.1 s. The fix is the one line in update: only accept the new integral when the output is inside its limits.

Part 5. Tuning on Real Hardware

A tuning procedure that works on real hardware. Change one thing at a time, always from a safe starting point, and test with a step change in the setpoint and with a disturbance (for example, covering the sensor).
simulate.py MicroPython
def simulate(gains, setpoint=0.3, seconds=8, dt=0.05, tau1=0.5, tau2=0.3): """A two-lag plant: output -> y1 -> y2 (what the sensor sees). Try gains here first.""" pid = PID(*gains) y1 = y2 = 0.0 ys = [] for _ in range(int(seconds / dt)): u = pid.update(setpoint, y2, dt) y1 += dt / tau1 * (u - y1) y2 += dt / tau2 * (y1 - y2) ys.append(y2) return ys print(round(simulate((2.0, 0.0, 0.0))[-1], 2)) # 0.2: P alone stops short print(round(simulate((2.0, 4.0, 0.2))[-1], 2)) # 0.3: PID reaches the target

Run the loop at a fixed period (use ticks_ms to keep it steady, and pass the real dt), filter the sensor with the EMA from the Noise Filtering lesson before it reaches the controller, and scale the measurement and setpoint to the same range (for example 0 to 1). Your plant is not the simulated one, so treat the simulation as a place to understand the behaviour, not as a source of final gains.

Warm Up

Exercise 1: One Update by Hand

error = 0.10. Integral: 0.10 + 4 × 0.10 × 0.05 = 0.12. Derivative (on the measurement): −(0.20 − 0.18) / 0.05 = −0.4, so the D term is 0.2 × (−0.4) = −0.08. Output = 2 × 0.10 + 0.12 − 0.08 = 0.24. The D term subtracts because the measurement is rising, which is exactly its braking effect.

Exercise 2: Which Gain?

(a) steady error: raise Ki (or Kp a little). (b) overshoot and ringing: lower Ki or Kp, or add a little Kd. (c) slow: raise Kp. Change one at a time and retest, because the gains interact.

Exercise 4: Demonstrate Windup
windup_test.py MicroPython
class NaivePID(PID): def update(self, setpoint, measurement, dt): error = setpoint - measurement d = 0.0 if self.prev is None else -(measurement - self.prev) / dt self.prev = measurement self.i += self.ki * error * dt # always integrate return max(self.out_min, min(self.out_max, self.kp * error + self.i + self.kd * d)) def settle_time(pid): y1 = y2 = 0.0 ys = [] for k in range(200): sp = 1.4 if k * 0.05 < 3 else 0.3 u = pid.update(sp, y2, 0.05) y1 += 0.05 / 0.5 * (u - y1) y2 += 0.05 / 0.3 * (y1 - y2) ys.append(y2) after = ys[60:] return next(i * 0.05 for i in range(len(after)) if all(abs(v - 0.3) <= 0.006 for v in after[i:])) print(settle_time(PID(2.0, 4.0, 0.2)), settle_time(NaivePID(2.0, 4.0, 0.2))) # about 2.1 and 3.6 seconds

Only one line differs between the two controllers, and it makes the recovery more than a second and a half slower. This is a good example of a defect that only appears when the output saturates, which is why you test saturation deliberately.
