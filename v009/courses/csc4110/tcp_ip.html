This lesson opens the layers under net.py: WiFi, IP, TCP and MQTT. You will learn what each one adds in bytes and in time, how addresses and masks decide who can reach whom, why a connection should be opened once and kept, why every network call needs a timeout, and how to find the broken layer when a message does not arrive.

Every message your node has sent so far travelled over WiFi, through IP, inside TCP, to a program on the Raspberry Pi. You were able to ignore all of that because net.py hid it. This week we open the box. You will not memorize protocols; you will learn what each layer does, what it costs in bytes and in time, and how to tell, when a message does not arrive, which layer failed.

Part 1. Layers

The layers a message passes through. Each layer wraps the one above in its own header. By the time the Lab 4 message of 94 bytes is an IP packet it is 134 bytes, 70 % of it your information; the radio adds more, and the receiver’s acknowledgements add further traffic.

The idea of layering is that each layer solves one problem and trusts the one below. WiFi moves frames between your board and the access point and deals with radio problems. IP gives every device an address and sends packets from one address to another across several networks. TCP (or its simpler sibling UDP) turns packet delivery into something an application can use: TCP delivers bytes in order, resends what is lost, and tells the program if the connection breaks. MQTT uses TCP to carry its small messages. Most network debugging is finding the lowest layer that is broken.

Part 2. Addresses

When the Pico joins the network, the access point’s DHCP service hands it four numbers. You can read them with wlan.ifconfig():

where.py MicroPython
import network wlan = network.WLAN(network.STA_IF) def where_am_i(): ip, mask, gw, dns = wlan.ifconfig() print("address", ip) print("mask ", mask) print("gateway", gw) print("dns ", dns) return ip, mask, gw NAMES = {0: "idle", 1: "connecting", 2: "wrong stage", 3: "got an address", -1: "connect failed", -2: "no access point found", -3: "wrong password"} def why(): """Say, in words, how the WiFi link is doing.""" return NAMES.get(wlan.status(), "unknown code %d" % wlan.status())
The four numbers DHCP gives your board. The mask divides an address into a network part and a device part; devices on the same network talk directly, and everything else goes through the gateway.

The test “are these two devices on the same network?” is a bitwise AND with the mask. It is worth writing yourself once, because it is the quickest way to see why a Pico on the guest WiFi cannot reach a Pi on the lab network: they are on different networks, and the gateway may be configured not to pass the traffic.

subnet.py MicroPython
def ip_to_int(ip): a, b, c, d = (int(x) for x in ip.split(".")) return (a << 24) | (b << 16) | (c << 8) | d def same_subnet(ip1, ip2, prefix): """True if two addresses are on the same network, given the prefix length (24 for /24).""" mask = (0xFFFFFFFF << (32 - prefix)) & 0xFFFFFFFF return (ip_to_int(ip1) & mask) == (ip_to_int(ip2) & mask) def prefix_of(mask): """255.255.255.0 -> 24""" return bin(ip_to_int(mask)).count("1")

The broker’s address should not change, or your config.py stops working; the instructor either reserves an address for the Pi in the router (a DHCP reservation) or sets a fixed one. Your board’s address can change every time it joins, which is why programs should connect to the broker and never expect the broker to find them.

Part 3. TCP: A Connection Is a Conversation

TCP starts with a three-message handshake before any data moves. The client sends a SYN, the server answers SYN-ACK, the client replies ACK. Only then is the connection open. MQTT adds its own handshake on top: a CONNECT message and a CONNACK reply. So before your node can send its first byte of data, two round trips have already happened.

Setting up an MQTT connection. Two round trips pass before the first byte of data. With a 20 ms round trip that is 40 ms, which is why a node should connect once and keep the connection open instead of connecting for every message.

You can feel this yourself with a few lines on the Pico and a few on your laptop. The laptop runs a tiny server that answers with your text in capitals; the Pico connects, sends, and times both stages.

echo_server.py Python
# echo_server.py: run on your laptop with python3 echo_server.py import socket srv = socket.socket() srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1) srv.bind(("0.0.0.0", 9000)) srv.listen(1) print("listening on port 9000") while True: conn, addr = srv.accept() print("connection from", addr) while True: data = conn.recv(256) if not data: break # the other side closed conn.send(data.upper()) # reply with the text in capitals conn.close()
echo_client.py MicroPython
import socket from time import ticks_ms, ticks_diff def ask(host, port, text, timeout_s=3): """Open a TCP connection, send text, return (reply, connect_ms, round_trip_ms).""" addr = socket.getaddrinfo(host, port)[0][-1] s = socket.socket() s.settimeout(timeout_s) # never wait forever try: t0 = ticks_ms() s.connect(addr) # the three-way handshake happens here t1 = ticks_ms() s.send(text.encode()) reply = s.recv(256) # blocks until data arrives or the timeout expires t2 = ticks_ms() return reply.decode(), ticks_diff(t1, t0), ticks_diff(t2, t1) finally: s.close() print(ask("192.168.1.20", 9000, "hello broker")) # your laptop's address here

settimeout is the important line. Without it, recv waits for as long as it takes, and a control loop that calls it freezes whenever the server is quiet. With it, the call raises OSError after the timeout, and your program can decide what to do. Everything that touches the network in a robot should have a timeout.

Part 4. TCP or UDP?

UDP is TCP with the guarantees removed: you send a datagram and hope. There is no handshake, no ordering, no retransmission and no notice if it is lost. That makes it cheap and fast, and good for data that is stale a moment later (a position update, an audio sample). TCP is right when every message matters, or when order matters, or when you want to know that the other side is gone. MQTT chose TCP, and the price is the handshake above and a retransmission delay when a packet is lost: the following messages wait behind the lost one.

udp.py MicroPython
import socket def send_udp(host, port, text): """Fire and forget: no connection, no acknowledgement, no retry.""" s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM) try: s.sendto(text.encode(), socket.getaddrinfo(host, port)[0][-1]) finally: s.close()
TCP and UDP side by side. We use TCP through MQTT. UDP returns later, in the multi-agent unit, where an occasional lost position update does not matter.

Part 5. Signal Strength

A radio link degrades gradually, then suddenly. The access point reports the received signal strength (RSSI) in dBm, a negative number: closer to zero is stronger. The scan below lists every network the board can hear, so you can find out whether a failure is simply a weak signal.

scan.py MicroPython
import network from time import sleep_ms wlan = network.WLAN(network.STA_IF) wlan.active(True) def scan(): """Print every 2.4 GHz network the Pico can hear, strongest first.""" nets = wlan.scan() # (ssid, bssid, channel, rssi, security, hidden) nets.sort(key=lambda n: -n[3]) for ssid, bssid, ch, rssi, sec, hid in nets: print("%-24s ch%-3d %4d dBm" % (ssid.decode(), ch, rssi)) scan()
A rough guide to RSSI. Below about −80 dBm packets are retried so often that throughput and battery life suffer, and connections drop. Walls, a metal enclosure around your robot, and your own body all change the number, so measure where the robot will actually operate.

Part 6. When It Does Not Work

Work from the bottom layer up and stop at the first failure. Each step has a tool.

The failure ladder. net.py reports levels 1 and 4 as NO WIFI and NO BROKER. A message that never appears at level 5 with everything else healthy is usually a topic typo or an access-list denial, and the broker will not tell you which.

Solutions

Give each exercise an honest try before opening its solution.

Warm Up

Exercise 1: Same Network?

With /24 the first three numbers must match: 192.168.1 matches the Pi, so yes. 192.168.2 does not match, so no: traffic would have to go through the gateway. If the mask were 255.255.254.0 (/23), the network part is the first 23 bits, which makes 192.168.0.0 to 192.168.1.255 one network, but .2.x is still outside it; you would need /22 (255.255.252.0), which covers .0 to .3, for the laptop to share a network with the Pico.

Exercise 2: Bytes on the Wire

94 / 134 = 70 %. At 5 messages per second the IP traffic is 134 × 5 = 670 B/s (the 470 B/s you computed in Lab 4 counted only the MQTT part). A 20-byte message becomes 60 bytes, so only 20 / 60 = 33 % is information. Small messages are mostly overhead, which is one reason to send fewer, slightly larger ones.

Intermediate

Exercise 3: Connect Every Time?

Each connection costs 2 × 20 = 40 ms before data moves, so option A spends 5 × 40 = 200 ms per second, a fifth of the time, waiting. If the code is blocking, the control loop is stalled for that time. Opening and closing also makes the broker log a connection and a disconnection per message, uses the radio far more (worse for batteries), and defeats the last will, which only means something for a connection that stays open. Option B pays the setup cost once.

Advanced

Exercise 4: Pick the Access Point
best_ap.py MicroPython
def best_ap(nets, ssid): """nets: tuples (ssid, bssid, channel, rssi, security, hidden) as bytes ssid. Strongest usable AP.""" want = ssid.encode() if isinstance(ssid, str) else ssid best = None for n in nets: if n[0] == want and n[3] >= -80: if best is None or n[3] > best[2]: best = (n[1], n[2], n[3]) return best
test_best_ap.py MicroPython
nets = [(b"class", b"aa:01", 1, -72, 3, 0), (b"class", b"aa:02", 6, -58, 3, 0), (b"class", b"aa:03", 11, -85, 3, 0), (b"other", b"bb:01", 6, -40, 3, 0)] print(best_ap(nets, "class")) # (b'aa:02', 6, -58) print(best_ap(nets, "missing")) # None

The loop keeps the strongest entry that passes the −80 dBm floor, so the −85 dBm access point is ignored even though it is on the right network, and the −40 dBm one is ignored because its name is different. On the Pico you can pass the chosen BSSID to wlan.connect(ssid, password, bssid=...) to pin the board to that access point.
