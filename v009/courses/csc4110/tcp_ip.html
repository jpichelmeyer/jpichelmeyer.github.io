Your Pico now has an IP address, which answers "where is this device on the network." That alone isn't enough to actually have two devices exchange data reliably, which is what this lesson covers: how an address gets a conversation started, and the protocol MQTT itself (next week) is quietly built on top of.

Part 1. Addresses and Ports

An IP address identifies a device on a network, the Pico's wlan.ifconfig()[0] from last lesson, or the Pi 3B+'s own address once it's set up as this unit's broker. That alone identifies a machine, not a specific program running on it; a single Pi could, in principle, run a broker and a web server and a dozen other things simultaneously, all reachable at the same IP address.

Ports disambiguate which program on that machine a connection is meant for, a number from 0 to 65,535 tacked onto the address. MQTT brokers conventionally listen on port 1883; your web browser talks to most ordinary websites on port 80 or 443. An address plus a port together, written like 192.168.1.42:1883, uniquely identifies one specific listening program on one specific machine.

One physical machine, one IP address, potentially several independent programs each listening on their own port. Connecting to the wrong port on the right machine typically just fails to connect at all, nothing is there to answer.
The four values in wlan.ifconfig(). The subnet mask decides which part of the address names the network and which part names the device.

Part 2. TCP: Reliable, Ordered Delivery

TCP (Transmission Control Protocol) is what most of the internet, and MQTT specifically, is built on. Two things make it the right foundation for sensor telemetry: it's reliable (data that's sent is confirmed received, and automatically resent if it's lost along the way) and ordered (bytes arrive in the same sequence they were sent, even if the underlying network delivers pieces out of order). Together, "IP" (the addressing scheme from Part 1) and "TCP" (the delivery guarantee) are almost always spoken of as one pair, TCP/IP, because essentially nothing uses one without the other.

That reliability isn't free, there's overhead in all that confirming and resending, which is part of why this matters for an embedded device with limited resources: TCP is doing real, nontrivial work on your Pico's behalf every time it talks to the broker.

Network software is built in layers, each wrapping the one above it. A problem at any layer breaks everything above it, so debugging works from the bottom up.

Part 3. Client and Server

A TCP connection has two distinct roles, not two equal peers. A server sits and listens on a known address and port, doing nothing until someone connects to it; mosquitto on the Pi 3B+ is a server in exactly this sense. A client is the one that initiates, reaching out to a known address and port to start a connection; every Pico in this course is a client of that one broker.

The server must already be running and listening before any client can connect to it, this is why bringing up mosquitto on the Pi happens before any Pico tries to reach it, not the other way around.
A TCP connection is set up with three messages, carries data in acknowledged pieces, and is closed politely. All of this happens inside the networking library; you only see connect() succeed or raise an error.

Solutions

Warm Up

Exercise 1: Same Network?

Network part 192.168.1, host part .57. 192.168.2.42 is on a different network (the third number differs). A /24 holds 254 usable addresses (0 and 255 are reserved).

Exercise 2: Client or Server?

(a) Pico = client, broker = server. (b) browser = client, website = server. (c) mosquitto_sub = client, mosquitto on the Pi = server. The client is whoever opens the connection; a device can be a client of one service and a server of another.

Intermediate

Exercise 3: Unpack the Tuple
main.py MicroPython
ip, mask, gateway, dns = wlan.ifconfig() print("address:", ip) print("subnet mask:", mask) print("gateway:", gateway) print("dns:", dns)

Tuple unpacking assigns all four in one line. The gateway is the router: anything not on your own network is sent there first.

Advanced

Exercise 4: Which Layer Failed?

(a) Link (WiFi): never joins the network. (b) Network (IP): nothing answers at that address, so a timeout. (c) Transport (TCP): the machine answers but refuses the port. (d) Application (MQTT): everything works; the message is simply delivered to nobody. Debug from the bottom up.
