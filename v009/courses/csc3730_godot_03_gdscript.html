Now that you know your way around the editor, it's time to make something move. GDScript is how you tell nodes what to do.

Part 1. What is GDScript?

GDScript is Godot's built-in scripting language. It reads a lot like Python (indentation-based blocks, no semicolons, # comments), but it's written specifically to work with Godot's nodes and scenes. A script is always attached to a node, and its whole job is to give that node behavior: react to input, move itself, talk to other nodes, respond when something happens.

You could use C# instead (Godot supports it natively), but GDScript is tightly integrated, loads faster, and is what most of the built-in documentation and community tutorials assume. That's what we'll use all semester.

Part 2. Attaching Your First Script

  1. Create a new scene (Scene → New Scene) and add a Node2D as the root, then add a child node under it: a Sprite2D or ColorRect works fine for now. Anything you can see on screen.
  2. Select the node you want to script in the Scene dock, then click the little scroll-with-a-plus icon next to it (or right-click the node → Attach Script).
  3. In the dialog: leave Language as GDScript, leave Template as Default, and confirm the path (e.g. res://player.gd). Click Create.
  4. Godot switches you to the Script tab (top-center, same row as the 2D/3D tabs from the tour) and opens your new file with some boilerplate already in it.

Part 3. Anatomy of a Script

The default template gives you this:

player.gd GDScript
extends Node2D func _ready(): pass func _process(delta): pass
  • extends Node2D: every script inherits from some node type. This one is attached to a Node2D, so it extends that class and gets access to everything a Node2D can do (position, rotation, etc).
  • _ready(): runs once, the moment this node enters the scene tree. Good for setup: grabbing references, setting initial values.
  • _process(delta): runs every single frame, automatically. delta is the time (in seconds) since the last frame, usually a small number like 0.016. You use it so movement and animation stay smooth and consistent no matter how fast or slow the game is running.

Try adding print("hello from " + name) inside _ready(), then press Play (top-right, from the tour). Check the Output tab in the bottom panel: that's where print() statements show up.

Part 4. Running & Checking Your Work

The tour mentioned two Play buttons in the top-right; here's what each one actually does and where to look once something's running.

  • Run Current Scene (the icon with a small clapperboard, or F6): runs whatever scene is currently open in the editor, regardless of anything else in the project. This is what you'll use constantly while building and testing one scene at a time.
  • Run Project (the big triangle, or F5): runs the project's designated Main Scene, the one that loads first when the whole game starts.

On a brand new project, there isn't a Main Scene set yet. The first time you press F5, Godot will ask you to pick one. Choose the scene you've been working on. You can change this pick later under Project → Project Settings → Application → Run → Main Scene.

Once something's running:

  • The Output tab (bottom panel, from the tour) is where every print() statement shows up, in order, as your script executes.
  • The Debugger tab, right next to Output, is where runtime errors show up in red, with a file name, a line number, and usually a plain-English description. Invalid get index ... on base 'null instance' is a common one; it almost always means a $NodeName or get_node(...) path doesn't match what's actually in the Scene dock (check for a typo or a node that got renamed).
  • To stop, click the square Stop button next to Play (or just close the game window).

If you press Play and nothing seems to happen, work through these in order: is the script actually attached to the node (check the Scene dock for the little script icon next to it)? Is that the node you meant to attach it to? And, before anything else, what does the Output/Debugger panel say? An error there is usually the fastest way to find out what's wrong.

Part 5. Variables and the Inspector

Declare variables with var. GDScript supports optional static typing: adding : float, : int, etc. isn't required, but it catches mistakes early and is good practice.

player.gd GDScript
var speed: float = 200.0 var health: int = 3

Add @export above a variable and it shows up as an editable field in the Inspector (the panel from the tour that displays a selected node's properties).

player.gd GDScript
@export var speed: float = 200.0

This is genuinely useful, not just a nice-to-have: it lets you (or a teammate) tweak numbers like speed, health, or spawn rate directly in the editor while testing, without touching the script.

Part 6. Talking to Other Nodes

The tour showed the Scene dock's node tree; your script lives on one of those nodes, and often needs to reach its neighbors: a child, a sibling, whatever. Two ways to do that:

player.gd GDScript
$Sprite2D.modulate = Color.RED get_node("Sprite2D").modulate = Color.RED

$NodeName is shorthand for get_node("NodeName"); both walk the scene tree to find a node relative to the one your script is on. Nested paths work too, e.g. $HUD/HealthBar. If a node in the Scene dock is renamed or moved, any $path pointing at it needs to be updated to match, so keep this in mind as your scenes grow.

Part 7. Building the Environment and Agent Scenes

Everything from here builds toward one small, autonomous, moving agent, the foundation the whole rest of this course sits on. Two scenes, kept separate on purpose:

  1. Environment. New scene, Node2D root, renamed Environment. Add a Camera2D child (its Enabled property defaults to on, so nothing extra is needed here unless you later add a second camera). Set Environment as the project's Main Scene: Project → Project Settings → Application → Run → Main Scene, the same setting from Part 4.
  2. Agent. A separate new scene, Node2D root, renamed Agent. Add a Sprite2D child and set its Texture to agent_sprite.svg (import it into the project first, e.g. under res://images/). Nudge the Sprite2D's Position up slightly, (0, -24) works well, so it rotates around a point nearer its base rather than dead center of its bounding box.
  3. Select the Agent root and attach a new script, scripts/agent.gd.
  4. Back in Environment, drag agent.tscn from the FileSystem dock into the scene to instance it as a child.

Part 8. Autonomous Movement: Rotation and Forward Speed

Rather than a free-floating velocity vector that can point anywhere, this agent moves the way most things actually do: face a direction, then move forward along it. Two separate ideas, built up one at a time.

Forward direction. Every Node2D carries a transform, and its y basis vector is one of the two directions baked into that transform, rotating right along with the node.

agent.gd GDScript
extends Node2D func _get_agent_forward() -> Vector2: return -transform.y

At rotation = 0, -transform.y points straight up, exactly the direction agent_sprite.svg is drawn facing (its point sits at the top of the image). As rotation changes, this vector rotates right along with it. (You'll also sometimes see this written as Vector2.UP.rotated(rotation), which gives the identical result; here we're just reading it directly off the node's own transform.)

Moving forward.

agent.gd GDScript
const RATE_MOVE: float = 100.0 func _move_forward(delta_passed: float, move_speed: float) -> void: global_position += delta_passed * move_speed * _get_agent_forward() func _process(delta: float) -> void: _move_forward(delta, RATE_MOVE)

Press Play: the agent slides off in a straight line, at 100 pixels per second, in whatever direction it happened to start facing.

Rotating.

agent.gd GDScript
const RATE_ROTATION: float = 0.5 * PI func _rotation_auto_simple(delta_passed: float, rotation_angle: float) -> void: rotation += delta_passed * rotation_angle func _process(delta: float) -> void: _rotation_auto_simple(delta, RATE_ROTATION) _move_forward(delta, RATE_MOVE)

rotation now increases by RATE_ROTATION radians every second (half of PI, or 90 degrees per second). Since _move_forward reads the agent's current facing fresh every single frame, turning and moving at the same time doesn't just spin the agent in place, it traces a wide, continuous loop, since the direction it's moving in is itself constantly rotating. Press Play and watch it circle.

This is exactly the state a Godot project can be handed off in for the next lesson: RATE_MOVE, RATE_ROTATION, _move_forward, _rotation_auto_simple, and _get_agent_forward, all in place.

Part 9. Wandering

A constant rotation rate produces an entirely predictable circle. Wander is the same shape of method, with the fixed rate swapped for a randomized one each frame:

agent.gd GDScript
const RATE_ROTATION_WANDER_MAX: float = 0.75 * PI func _rotation_wander(delta_passed: float, rotation_angle_max: float) -> void: rotation += delta_passed * randf_range(-rotation_angle_max, rotation_angle_max)

Notice it takes the exact same two arguments as _rotation_auto_simple, delta and a rate; only the formula inside differs. Swap which one _process calls to try it:

agent.gd GDScript
func _process(delta: float) -> void: _rotation_wander(delta, RATE_ROTATION_WANDER_MAX) _move_forward(delta, RATE_MOVE)

Instead of a perfect circle, the agent now meanders: a non-repeating, exploratory path built entirely out of the same two primitives (a rotation method and _move_forward) you already had. This is the classic Wander steering behavior, and next lesson introduces a way to let each agent choose which rotation method to run, rather than hardcoding a single call in _process.

Part 10. Signals, Briefly

Signals are how nodes notify each other that something happened, without needing a direct reference. A Button emits a pressed signal when clicked; an Area2D emits body_entered when something touches it.

Easiest way to connect one: select the node in the Scene dock, open the Node tab (next to Inspector), double-click the signal you want, and pick a node to receive it. Godot generates the function stub for you:

player.gd GDScript
func _on_button_pressed(): print("clicked!")

We'll use signals more once behavior gets event-driven (collisions, state changes). For now, just recognize the pattern; it'll come up constantly.

Checkpoint

Before moving on, make sure you can:

  1. Attach a script to a node and explain what _ready() vs _process(delta) is for.
  2. Explain the difference between Run Current Scene (F6) and Run Project (F5), and know where to look (Output / Debugger) when something goes wrong.
  3. Add an @export variable and see it appear in the Inspector.
  4. Explain why -transform.y is the agent's forward direction, and why that matches how agent_sprite.svg is drawn.
  5. Get an agent circling on its own using _rotation_auto_simple and _move_forward, and explain why constant rotation plus constant forward speed produces a loop rather than a straight line.
  6. Swap in _rotation_wander and describe how its motion differs from the constant-rate version.
  7. Reference a child node with $NodeName.

If all of this feels solid, you're ready for steering next: giving an agent a reason to turn, instead of turning on its own.
