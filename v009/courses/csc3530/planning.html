Means-ends analysis chooses one step at a time and gets trapped when goals interfere. Planning steps back: before acting, it reasons about whole sequences of actions, what each one needs and what each one changes, and orders them so that no step undoes the work of another. Planning is also where ARC program search gets smarter: the agent can reason about what a sequence of operations will do before running it.

Reading
  • Bennett, Ch. 13: Model-based reinforcement learning (AlphaZero) (PDF pp. 212–214 · 3 pages)
    Planning as simulating futures before acting, the search problem that comes with it, and why real brains switch strategies.

Part 1. States, Operators, and Goals

The classical representation comes from STRIPS (Fikes and Nilsson, 1971). A state is a set of conditions that are true. An operator has preconditions (what must be true to use it), an add list (what becomes true), and a delete list (what stops being true). A goal is a set of conditions to make true. Goel and Joyner's example: a robot has to paint both the ceiling and the ladder it stands on to reach the ceiling.

A STRIPS operator. Anything not mentioned in the add or delete list stays as it was.
Human cognition connection

Plans as hierarchies of goals entered psychology with George Miller, Eugene Galanter and Karl Pribram's Plans and the Structure of Behavior (1960). Their unit of behaviour was the TOTE loop (Test, Operate, Test, Exit), nested inside larger TOTEs. To hammer a nail: test whether the nail is flush; if not, operate (lift, strike) and test again. This week's Bennett reading adds an evolutionary angle: planning means simulating futures before acting, and the hard part is not the simulation but deciding which futures are worth simulating.

Part 2. A Planning Agent, and Goals That Clobber Each Other

ladder_agent.py: operators Python
# name: (preconditions, add list, delete list) OPS = { 'climb-ladder': ({'on-floor', 'ladder-dry'}, {'on-ladder'}, {'on-floor'}), 'descend': ({'on-ladder'}, {'on-floor'}, {'on-ladder'}), 'paint-ceiling': ({'on-ladder'}, {'ceiling-painted'}, set()), 'paint-ladder': ({'on-floor'}, {'ladder-painted'}, {'ladder-dry'}), } START = frozenset({'on-floor', 'ladder-dry'}) def apply(state, op): pre, add, delete = OPS[op] return frozenset((state - delete) | add) if pre <= state else None
ladder_agent.py: a forward state-space planner Python
def plan(state, goals): """Forward state-space planning: breadth-first over operator sequences until every goal condition holds.""" frontier, seen = deque([(state, [])]), {state} while frontier: s, steps = frontier.popleft() if goals <= s: return steps for op in OPS: nxt = apply(s, op) if nxt is not None and nxt not in seen: seen.add(nxt) frontier.append((nxt, steps + [op])) return None

A tempting shortcut is to achieve goals one at a time. Whether that works depends entirely on the order:

ladder_agent.py: one goal at a time Python
def one_goal_at_a_time(state, goals): """Achieve the goals in the order given, each with its own little plan.""" steps = [] for g in goals: sub = plan(state, {g}) if sub is None: print(f' cannot achieve {g} from {sorted(state)}') return None for op in sub: state = apply(state, op) steps += sub return steps print('goals in order [ladder, ceiling]:') print(' plan:', one_goal_at_a_time(START, ['ladder-painted', 'ceiling-painted'])) print('goals in order [ceiling, ladder]:') print(' plan:', one_goal_at_a_time(START, ['ceiling-painted', 'ladder-painted']))
Shell output Output
goals in order [ladder, ceiling]: cannot achieve ceiling-painted from ['ladder-painted', 'on-floor'] plan: None goals in order [ceiling, ladder]: plan: ['climb-ladder', 'paint-ceiling', 'descend', 'paint-ladder']

Painting the ladder first deletes ladder-dry, a precondition of climbing, so the ceiling becomes unreachable. In planning language, paint-ladder clobbers (or threatens) a precondition of climb-ladder. A partial-order planner builds the separate plans, finds threats like this one, and resolves each by adding an ordering constraint: the clobbering step must come after the step whose precondition it would destroy.

ladder_agent.py: detecting threats Python
def threats(plan_a, plan_b): """Steps of plan_a that delete a precondition of some step of plan_b. If there are any, plan_a must come after plan_b (or be repaired).""" found = [] for a in plan_a: for b in plan_b: clobbered = OPS[a][2] & OPS[b][0] if clobbered: found.append((a, b, clobbered)) return found p_ladder, p_ceiling = plan(START, {'ladder-painted'}), plan(START, {'ceiling-painted'}) print('separate plans:', p_ladder, p_ceiling) for a, b, what in threats(p_ladder, p_ceiling): print(f' threat: {a} deletes {sorted(what)}, which {b} needs, so {a} must come after {b}') print('joint plan by search:', plan(START, {'ladder-painted', 'ceiling-painted'}))
Shell output Output
separate plans: ['paint-ladder'] ['climb-ladder', 'paint-ceiling'] threat: paint-ladder deletes ['ladder-dry'], which climb-ladder needs, so paint-ladder must come after climb-ladder joint plan by search: ['climb-ladder', 'paint-ceiling', 'descend', 'paint-ladder']
A partial-order plan. Steps are ordered only where they must be. The threat (red dashed) is resolved by an ordering constraint (green): paint the ladder only after climbing it. Since painting the ladder also needs the robot on the floor, the ceiling gets painted in between.

Searching over complete sequences also finds the right plan here, because the problem is tiny. With twenty operators and a plan of ten steps, blind sequence search is hopeless, and reasoning about threats (which steps interact, and how) is what keeps planning tractable.

Part 3. A Taste of ARC: Plan in the Abstract, Then Refine

In week 3 the agent searched over concrete programs, running every candidate on every train pair. A planner can do better by reasoning in an abstract state space first. Here the abstract state is just the size of the grid and the size of its largest object, and each size-changing operator gets a model of its effect: double_w doubles the width, crop_largest makes the grid the size of the largest object, and so on.

arc_plan.py: operators with preconditions and effects Python
def largest(g): return crop_object(g, max(find_objects(g), key=lambda o: o['size'])) def desc(g): """The abstract state a planner reasons about: grid size and the size of the largest object. Cheap to compute, ignores colours entirely.""" objs = find_objects(g) big = max(objs, key=lambda o: o['size']) if objs else None return {'h': len(g), 'w': len(g[0]), 'oh': big['height'] if big else 0, 'ow': big['width'] if big else 0} # name: (precondition on desc, effect on desc, concrete function) SIZE_OPS = { 'crop_largest': (lambda d: d['oh'] > 0, lambda d: dict(d, h=d['oh'], w=d['ow']), largest), 'double_w': (lambda d: True, lambda d: dict(d, w=2 * d['w']), lambda g: hconcat(g, g)), 'double_h': (lambda d: True, lambda d: dict(d, h=2 * d['h']), lambda g: vconcat(g, g)), 'mirror_w': (lambda d: True, lambda d: dict(d, w=2 * d['w']), lambda g: hconcat(g, flip_h(g))), 'mirror_h': (lambda d: True, lambda d: dict(d, h=2 * d['h']), lambda g: vconcat(g, flip_v(g))), 'scale2': (lambda d: True, lambda d: dict(d, h=2 * d['h'], w=2 * d['w']), lambda g: scale(g, 2)), 'scale3': (lambda d: True, lambda d: dict(d, h=3 * d['h'], w=3 * d['w']), lambda g: scale(g, 3)), 'transpose': (lambda d: True, lambda d: dict(d, h=d['w'], w=d['h']), transpose), } NEUTRAL = {'none': lambda g: g, 'flip_h': flip_h, 'flip_v': flip_v, 'rot180': rotate180}

The planner looks for operator sequences whose predicted effect turns every train input's size into the matching output's size. That is cheap: no grids are built. Only the plans that survive are refined into concrete programs, by trying size-neutral operators (flips, half-turns) in each gap and checking the result on the real grids.

arc_plan.py: abstract planning Python
def abstract_plans(task, max_len=2): """Plan in the abstract space: every sequence of size-changing operators whose predicted effect turns each train input's size into its output's.""" starts = [desc(p['input']) for p in task['train']] goals = [(len(p['output']), len(p['output'][0])) for p in task['train']] for n in range(0, max_len + 1): for seq in itertools.product(SIZE_OPS, repeat=n): ok = True for d, goal in zip(starts, goals): for name in seq: pre, eff, _ = SIZE_OPS[name] if not pre(d): ok = False break d = eff(d) if not ok or (d['h'], d['w']) != goal: ok = False break if ok: yield seq
arc_plan.py: refinement Python
def refine(seq, task): """Turn an abstract plan into a concrete program by optionally inserting one size-neutral operator, and keep the first that fits every pair.""" for pos in range(len(seq) + 1): for nname, nf in NEUTRAL.items(): prog = list(seq[:pos]) + [nname] + list(seq[pos:]) def run(g, prog=prog): for step in prog: g = NEUTRAL[step](g) if step in NEUTRAL else SIZE_OPS[step][2](g) return g try: if all(run(p['input']) == p['output'] for p in task['train']): return [s for s in prog if s != 'none'], run except Exception: pass return None, None

Twenty-one tasks, found by refining about a thousand abstract plans across all 400 tasks. That is far fewer concrete checks than last week's program search needed (about 16,600) for a similar score. Week 3's search still solves a few tasks this planner misses, because its primitives include operations (like gravity) that this planner has no effect model for. That is the price of abstraction: you can only plan with operators whose effects you can predict.

SAM lens

A planner is a Decider that reasons about future states before the Actuator does anything. The operator models (preconditions and effects) are procedural knowledge in long-term Memory. Detecting threats between subplans is a job the Monitor can share: it watches for one part of the plan undoing another.
