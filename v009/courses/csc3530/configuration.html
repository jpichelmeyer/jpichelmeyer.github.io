Planning built a sequence of actions from scratch. Most design is not like that. When an engineer designs a chair, a circuit, or a timetable, the overall structure is usually known in advance; what remains is choosing values for its parts so that everything fits together. That is configuration: a routine kind of design in which a known plan skeleton is refined, one variable at a time, under constraints. It sits right on top of last week's constraint propagation and planning.

Reading
  • McShane, Nirenburg & English, Ch. 3, §3.2.4 and Ch. 8, §8.4: From script to plan; the next step in the current plan (pp. 65, 240 · PDF 76, 251 · 2 pages)

Part 1. Refining a Plan Skeleton

Configuration. The skeleton comes from memory; the work is assigning values in a sensible order and checking constraints on the partial design after every assignment, so bad choices are caught early.

Three features distinguish configuration from planning from scratch:

  • The components and their arrangement are known. A chair has legs, a seat, and a back. Only their properties are open.
  • Decisions are ordered, usually from the most constraining to the least. Deciding the number of legs first constrains everything after it.
  • Constraints are checked on partial designs, so a doomed choice is abandoned at once instead of after the whole design is finished.

This week's McShane reading makes the connection to scripts explicit: a plan is a script with one path chosen and its roles filled in. Configuration is the process of choosing them.

Human cognition connection

Configuration was one of expert systems' great successes. John McDermott's R1 (later called XCON, 1980s) configured orders for DEC's VAX computers, choosing and arranging hundreds of components, and was reported to save the company tens of millions of dollars a year. Studies of human designers find the same pattern: experts retrieve a known design skeleton and refine it, and they satisfice (Herbert Simon's word): they stop at the first design that meets every constraint rather than searching for the best possible one.

# The plan skeleton: a chair has legs, a seat, and a back. Each component # has variables with possible values; materials have mass and cost per unit. MATERIALS = {'pine': (0.6, 2), 'oak': (0.9, 5), 'steel': (1.5, 4), 'plastic': (0.4, 1)} SKELETON = [ # (component, variable, options), in the order decisions are made ('legs', 'count', [4, 3]), ('legs', 'material', ['steel', 'oak', 'pine', 'plastic']), ('seat', 'material', ['oak', 'pine', 'plastic']), ('back', 'material', ['oak', 'pine', 'plastic']), ] SIZE = {'legs': 1.0, 'seat': 2.0, 'back': 1.5} # units of material per part
chair_agent.py: constraints on partial designs Python
def check(design, spec): """Return the first violated constraint, or None. Partial designs are checked only on what has been decided so far.""" mass = cost = 0 for comp in ('legs', 'seat', 'back'): mat = design.get((comp, 'material')) if mat is None: continue n = design.get(('legs', 'count'), 1) if comp == 'legs' else 1 mass += MATERIALS[mat][0] * SIZE[comp] * n cost += MATERIALS[mat][1] * SIZE[comp] * n if mass > spec['max_mass']: return f'mass {mass:.1f} kg > {spec["max_mass"]}' if cost > spec['budget']: return f'cost ${cost:.0f} > ${spec["budget"]}' if spec.get('outdoor') and design.get(('seat', 'material')) == 'pine': return 'pine seat will rot outdoors' return None
chair_agent.py: refinement with backtracking Python
def configure(spec, design=None, depth=0): """Assign variables one at a time in skeleton order, checking constraints after each assignment and backing up when one is violated.""" design = design or {} if len(design) == len(SKELETON): return design comp, var, options = SKELETON[len(design)] for value in options: trial = {**design, (comp, var): value} problem = check(trial, spec) print(' ' * depth + f'{comp}.{var} = {value}' + (f' x {problem}' if problem else '')) if problem is None: done = configure(spec, trial, depth + 1) if done: return done return None spec = {'max_mass': 7.0, 'budget': 20, 'outdoor': True} print('spec:', spec) result = configure(spec) print('design:', {f'{c}.{v}': x for (c, v), x in result.items()})

Read the trace as a designer's notebook. Steel legs looked fine until the seat and back made the chair too heavy, so the agent backed up and tried oak legs, which ran over budget as soon as a seat was added. Pine legs with an oak seat and a plastic back satisfy every constraint, and the agent stops there: a satisficing design, not necessarily the best one. Notice that it never had to consider a three-legged chair, because the first branch it tried eventually worked.

Part 3. A Taste of ARC: Configuring a Tiled Output

Many ARC outputs are built from copies of the input, flipped or rotated and arranged in a block. That is a configuration problem. The skeleton is an a×b arrangement of tiles (the sizes come from comparing input and output sizes), the variables are which part fills each slot, and the constraint is that every train pair is reproduced.

Task 46442a0e.
arc_config.py: the parts Python
# The parts a tiled output can be built from: the input under one of the # eight symmetries of a square, or an empty (black) tile. PARTS = {'id': lambda g: [r[:] for r in g], 'flip_h': flip_h, 'flip_v': flip_v, 'rot90': rotate90, 'rot180': rotate180, 'rot270': rotate270, 'transpose': transpose, 'anti': lambda g: rotate180(transpose(g)), 'blank': lambda g: [[0] * len(g[0]) for _ in g]} def block(grid, i, j, h, w): return [row[j * w:(j + 1) * w] for row in grid[i * h:(i + 1) * h]]
arc_config.py: configure slot by slot Python
def configure(task): """Skeleton: the output is an a x b arrangement of tiles, each tile one of PARTS applied to the input. Variables: a, b, and the part in each slot. Constraint: every train pair must be reproduced exactly.""" p0 = task['train'][0] h, w = dims(p0['input']) H, W = dims(p0['output']) if H % h or W % w or (H, W) == (h, w): return None a, b = H // h, W // w design = {} for i in range(a): for j in range(b): # values for this slot that satisfy the constraint on EVERY pair ok = [name for name, f in PARTS.items() if all(dims(p['output']) == (a * len(p['input']), b * len(p['input'][0])) and f(p['input']) == block(p['output'], i, j, len(p['input']), len(p['input'][0])) for p in task['train'])] if not ok: return None design[(i, j)] = ok[0] return a, b, design def build(config, grid): a, b, design = config rows = [] for i in range(a): tiles = [PARTS[design[(i, j)]](grid) for j in range(b)] for r in range(len(grid)): rows.append([v for t in tiles for v in t[r]]) return rows

Twelve tasks. Several of them (46442a0e, 7fe24cdd, 8d5021e8) were missed by program search and planning, because their outputs need a different transform in each tile, which a short program of whole-grid operations cannot express. Configuration does not search over sequences at all; it fills each slot independently, and the constraint does the rest. Choosing the right representation of the solution (a design with slots instead of a program) changed what was easy.

SAM lens

The plan skeleton is procedural Memory (a script for a kind of design). Refinement is a Decider; checking constraints on partial designs is the Monitor; backing up when a constraint fails is the Monitor controlling the Decider. Your agent's TaskFrame invariants (output size!) are exactly the specification that a configuration step needs.

Discuss
  1. The chair agent satisficed. When should an ARC agent satisfice (take the first configuration that fits) and when should it look for alternatives?
  2. Is choosing the order of decisions (legs first, then seat) part of the knowledge or part of the algorithm? What happens if you reverse it?
  3. McShane says a plan is an instantiated script. Is a configured design a plan? What is the difference?
