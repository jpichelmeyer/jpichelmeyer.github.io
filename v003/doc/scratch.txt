How common would that exact structure (like the specific organization of keys you used, not their exact values, of course) of the CSS you presented there be in atomic design?
    
    The structure I used—separating Primitives (raw values) from Semantics (functional decisions)—is considered the industry standard for professional Atomic Design systems.
    While you might see different naming conventions (e.g., some people use base vs theme), the "layered" approach is how systems like Adobe’s Spectrum, Salesforce’s Lightning, and Shopify’s Polaris are built.
    Here is why that specific organization is so common:
    1. It Mirrors the "Atomic" Philosophy
    In Atomic Design, atoms are built from subatomic particles.

        Primitives are the "quarks" (the smallest possible values).
        Semantics are the "tokens" (the first level of meaning).
        By the time you get to an Atom (like a button), you aren't using a hex code; you are using a semantic decision.

    2. The "Semantic Middle Layer" is the Secret Sauce
    Beginners often skip the semantic layer and go straight from palette to component:

        Bad: .button { color: var(--blue-500); }
        Standard: .button { color: var(--action-primary); }

    The reason the standard structure uses that middle layer is theming. If you want to add a "Dark Mode," you don't change --blue-500. You simply tell the CSS that, in dark mode, --action-primary now points to --blue-200.
    3. Naming Conventions (The "Taxonomy")
    The "Category-Property-Rank" naming (e.g., color-neutral-900) is the most common way to organize keys. It makes variables searchable. If a developer starts typing --color-, their code editor will automatically list every color available, keeping the "system" easy to navigate.
    4. Common Variations
    While the logic is standard, the syntax varies slightly depending on the tech stack:

        Tailwind Users: Often put these in a tailwind.config.js rather than a CSS file.
        Design Tool Users: Figma's "Variables" feature now forces this exact structure (Library > Alias > Component) to stay in sync with code.

No, you should not always put a . (dot) in front of the first / in Python file paths. The . denotes the current working directory, while a leading / denotes the root directory. Use ./ only when specifically referencing a file relative to the script's current location, not for absolute or root-relative paths. 
Key Takeaways for Pathing:

    ./file.txt: Means "file.txt in the current directory."
    /file.txt: Means "file.txt in the root directory" (e.g., C:/file.txt or /file.txt on Linux).
    Best Practice: For cross-platform compatibility, avoid hardcoding forward or backward slashes altogether. Use pathlib or os.path.join() to handle path separators automatically.
    Windows Note: Python handles forward slashes (/) even on Windows, so C:/folder/file is valid, but raw strings (r'C:\path') are also common for handling backslashe

/*================================================================================

    Information dependency

================================================================================*/

We consider fileChild information dependent on fileParent if 
    CSS     fileChild references a class from fileParent
    JS      fileChild needs to call a function/variable from fileParent

We visualize this with

    fileChild <--- fileParent

There should be only one file that has no children:     v002/index.html
All other files should have EXACTLY one child.
Files may have multiple parents.


Formal syntax/structure for handling information dependency:
    
    ==================================================
    CSS
        ----------------------------------------------
        fileParent (.css)
        ----------------------------------------------
        :root{
        
        }
                
        .my-gen-use-class{
            ...: ....;
            ...: ....;
        }
        
        #my-unique-class{
            ...: ....;
            ...: ....;
        }
        
        ----------------------------------------------
        fileChild (.css)
        ----------------------------------------------
        @import 'rel/path/to/fileParent.css

    ==================================================
    JS
    
        ----------------------------------------------
        fileParent (.js)
        ----------------------------------------------
        const GLOBAL_PARAM = ...
        
        // This is usuable by fileChild
        export function myFunction(params){
            // body logic
        }
        
        // This is NOT usuable by fileChild
        function myOtherFunction(params){
            // body logic
        }
        
        
        ----------------------------------------------
        fileChild (.js)
        ----------------------------------------------
        import * as Boot from './fileParent.js';
        'use strict';
            
    ==================================================
